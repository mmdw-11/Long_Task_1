## 1. 动态拓扑与协作恢复

使用冻结的 `dynamic_topology_mechanism_suite_v1`。资源匹配、能力接力、故障替补和多待办协作各 10 个场景，每个场景按组重复两次。固定拓扑组采用预设稀疏协作关系，完整方法组启用动态成员选择、接力及故障替补，两组各 80 次。仅动态选择组关闭接力与替补，在接力与替补两类场景共运行 40 次。各组使用同一真实模型，仓库查询均通过 HTTP 工具读取同一份经 SHA-256 校验的 CPython 仓库元数据快照。

初跑中，完整组未通过的 16 次替补运行均遇到 GitHub API 限流。故障注入以原成员成功调用工具为前提，限流会干扰故障触发或替补验证。重跑修复了接力次数设为 0 时误用默认值的问题，并保留了全员失败前的模型、工具和事件轨迹。替补成功要求替补成员被选中，并成功完成指定仓库查询。

下表采用各组共用的工具完成标准。仓库查询须返回目标仓库的有效记录，计算器须返回题设算式的正确值；故障替补场景要求故障后有成功成员完成仓库查询。

| 场景 | 固定拓扑 | 完整方法 | 仅动态选择 | 固定拓扑 P50 | 完整方法 P50 |
|---|---:|---:|---:|---:|---:|
| 资源匹配 | 20/20 | 20/20 | — | 4.57 秒 | 2.91 秒 |
| 能力接力 | 20/20 | 20/20 | 0/20 | 4.82 秒 | 9.58 秒 |
| 故障替补 | 0/20 | 20/20 | 0/20 | 6.46 秒 | 9.65 秒 |
| 多待办协作 | 20/20 | 20/20 | — | 9.59 秒 | 14.49 秒 |

三组在故障替补场景中均成功触发 20/20 次注入故障。完整方法恢复 20 次，固定拓扑和仅动态选择组均为 0 次。资源匹配场景中，完整方法平均启用 1 个成员，固定拓扑平均启用 2 个成员，两组工具完成率相同。能力接力和多待办场景中，两组的工具完成率相同，固定拓扑的中位耗时更短。

按包含指定拓扑事件的机制验收口径，完整方法通过 80/80，固定拓扑通过 20/80，仅动态选择组通过 0/40。该口径衡量接力、替补和拓扑重配置等事件是否发生。共用工具标准用于比较各组完成任务所需调用的情况。
结论：支持受控故障下的恢复能力。接力和多 TODO 暂未显示完成率优势。

重跑的 200 条汇总见 `revision-20261112/results/topology-audit.json`。场景轨迹见 `revision-20261112/results/topology/cases/`，故障替补采用保留失败轨迹后的复测记录 `revision-20261112/results/topology-recovery/cases/`。

## 2. LoCoMo 长期记忆问答

### 初轮审计

使用 `data/processed/locomo_memory_eval20_bge_v1.jsonl`。四组回答同一批 20 道带参考答案和证据的 LoCoMo 问题，使用同一生成模型及 QA 裁判。引擎使用项目范围混合检索、5 个候选、BGE-M3 重排与归档证据展开，历史片段约 1,800 字符，关闭记忆写入裁判。

| 方法 | QA 正确数 | 精确匹配 | 答案 F1 | 平均上下文 token 估计 | 平均 QA 输入 token | 平均端到端耗时 |

| 全历史 | 8/20 | 15% | 0.342 | 19,744.80 | 18,686.65 | 1.82 秒 |

按初轮的候选证据口径，引擎 MRR 为 0.322，Hit@1／3／5 分别为 20%／40%／65%，平均金标证据召回率为 46.83%。这一口径可覆盖未送入答题模型的候选片段。引擎平均写入耗时 1.98 秒，检索 5.02 秒，模型问答 0.80 秒。原始记录见 `results/02-memory-audit/locomo/*/{rows.jsonl,summary.json}`。

### 22 题配对实验

## 3. TIDE-Anchor 长程上下文连续性

## 6. TIDE-Placement 约束调度

使用 `RouteCostBench-100.jsonl`，来源为 C-Eval 验证集选择题。抽取大学经济学 42 题、高中历史 20 题、高中物理 19 题、基础医学 19 题。每题配对运行全云和严格 AUTO，按最终选项精确匹配评分。云模型为 DeepSeek V4 Flash。重跑将端侧和边缘模型从 Qwen2.5 0.5B／3B Instruct 分别更换为 7B／14B Instruct，使用 Q4_K_M 量化权重，由同一服务器上的两个 llama.cpp CPU 端点提供推理。严格 AUTO 启用约束模式，使用 BGE-M3 路由和可行域筛选，在可行域内按现有规则排序。实验未加载训练后的策略权重。

| 指标 | 全云 | 严格 AUTO |
|---|---:|---:|
| 正确题数 | 92/100 | 78/100 |
| 模型请求成功 | 100/100 | 99/100 |
| 全流程延迟 P50 | 1,437.80 ms | 5,666.14 ms |

99 条发起推理的 AUTO 记录均按选定层级执行，另有 1 题因无可行放置被阻断。与全云相比，AUTO 的估算云 API 费用降低 81.21%，全流程 P50 约为全云的 3.94 倍。费用按输入 1.5 元／百万 token、输出 4.5 元／百万 token 计算，包含本轮记录到的全部云调用，不包含本地部署和推理成本。初轮 AUTO 缺少云调用 token 用量，费用对比采用本轮两组数据。耗时对应本次单服务器 CPU 分层配置。
