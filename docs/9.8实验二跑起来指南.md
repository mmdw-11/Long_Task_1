## 3. Pilot 结束后的强制检查

每个方法均应有：

```text
summary.json
rows.jsonl
report.md
```

必须检查：

| 检查项 | 合格结果 | 不合格意味着什么 |
|---|---|---|
| 样本数 | 全部为 22 | 断点续跑或数据加载有问题 |
| ID 集合 | 方法间完全一致 | 对照不公平 |
| Ours metadata | `embedding_model=BGEM3EmbeddingModel`、`candidate_retriever=hashing_hybrid`、`reranker=bge_m3` | BGE 未真实接入 |
| Ours 参数 | `candidate_k=20`、`top_k=5` | 误用了本地快速预实验设置 |
| Ours Full | `memory_judge_calls>0`、`parse_errors=0` | Judge 没跑或 JSON 失败 |
| Ours Full 动作 | 报告 ADD/UPDATE/DELETE/NOOP | 没有可观测更新机制证据 |
| Full Context 12k | `avg_context_tokens <= 12000` | 预算基线失效 |
| 所有 rows | 无 `qa_error`、无 `qa_judge_error` | 模型调用失败，结果无效 |

Pilot 可能出现的结果及处理：

- `Evidence Recall@5` 很低、`qa_failure_with_incomplete_evidence` 很高：检索或证据选择不够；不要启动 final100，应修候选召回、重排或片段大小。
- `gold_evidence_complete` 高，但 `qa_failure_with_complete_evidence` 仍高：检索已足够，问题在 QA 生成；修 QA 提示/证据组织后重新做新的 pilot。
- Ours Full 的 `UPDATE+DELETE=0`：并不表示代码没跑，只表示此集合没有产生有效更新。可报告 Full 无收益，但不能声称更新机制提高了 QA。
- Ours Full 明显慢于 no Judge：正常，应把写入、检索、QA、Judge、端到端耗时分开报告。
- Mem0 指标高但 QA 不高：可能是抽取事实损失了多跳、数值或时态细节，不是自动的代码错误。
- Ours no Judge / Full 低于 Full Context：可能发生，不能通过调低 Judge 标准“修分”；先看证据完整性诊断。

只有 Pilot 的运行完整、元数据正确、且没有再改代码/参数时，才能进入 100 条正式实验。
