# 2026-07-22 当前情况：LMSYS 数据、端边云三分类标注与 BGE-M3 路由训练

## 一、当前目标
明确为端、边、云三档资源选择：

- `0` = `device`，端侧本地小模型
- `1` = `edge`，边缘侧中等模型
- `2` = `cloud`，云端强模型

训练 BGE-M3 :

> 给定一个用户 prompt，判断这个请求最低需要走端、边、云哪一档资源。

---

## 二、LMSYS Chatbot Arena 数据的定位

当前使用的数据集是：

- `lmsys/chatbot_arena_conversations`
> 对应网站：https://huggingface.co/datasets/lmsys/chatbot_arena_conversations

该数据集本身的原始语义是：

- 同一个用户问题
- 两个 Arena 模型分别回答
- 用户投票选择更好的回答

但是在本项目中，**不直接使用 LMSYS 的 `winner` 作为路由标签**。

原因：

- LMSYS 的 `winner` 表示“两个已有模型回答谁更好”
- 本项目需要的是“这个用户请求应该分配到 device / edge / cloud 哪一档”

因此，本项目使用 LMSYS 数据的方式是：

- LMSYS 提供真实、多样、通用的用户 prompt
- 端、边、云三档模型重新回答这些 prompt
- 再由 judge【云端模型】 评估三档回答质量
- 根据最低可用成本原则生成本项目自己的三分类标签

## 三、当前端、边、云真实执行后端

### 1. device：端侧本地模型

当前端侧已经从原来的 echo 模拟器升级为真实本地模型调用。

当前配置为：

- 后端：Ollama OpenAI-compatible endpoint
- 模型：`qwen2.5:0.5b`
- endpoint：`http://127.0.0.1:11434/v1`

对应 `.env` 配置示例：

```env
DEVICE_BASE_URL=http://127.0.0.1:11434/v1
DEVICE_MODEL=qwen2.5:0.5b
DEVICE_API_KEY=ollama
```

对应执行器：

- `engine/modules/execution/executors.py`
- `LocalModelExecutor`

行为：

- 如果 `DEVICE_BASE_URL` 和 `DEVICE_MODEL` 配置齐全，则真实调用本地 OpenAI-compatible 模型服务
- 如果没有配置，则回退到 `LocalEchoExecutor`

### 2. edge：边缘侧模型

当前边侧使用一个本地 HTTP wrapper 模拟边缘服务。

当前配置为：

- edge endpoint：`http://127.0.0.1:8001/infer`
- 内部调用：Ollama OpenAI-compatible endpoint
- 模型：`qwen2.5:3b`

对应 `.env` 配置示例：

```env
EDGE_ENDPOINT=http://127.0.0.1:8001/infer
EDGE_MODEL=qwen2.5:3b
EDGE_OLLAMA_BASE_URL=http://127.0.0.1:11434/v1
```

对应执行器：

- `engine/modules/execution/executors.py`
- `EdgeHttpExecutor`

边缘服务脚本：

- `examples/edge_cloud_scheduler/edge_ollama_server.py`

启动命令：

```powershell
.\.venv\Scripts\python.exe examples\edge_cloud_scheduler\edge_ollama_server.py
```

边服务接口：

```text
POST http://127.0.0.1:8001/infer
```

请求格式：

```json
{
  "prompt": "...",
  "system_prompt": "...",
  "metadata": {}
}
```

返回格式：

```json
{
  "text": "...",
  "model": "qwen2.5:3b",
  "metadata": {
    "backend": "edge-ollama"
  }
}
```

注意：

- 只写 `EDGE_ENDPOINT` 不代表边已经可用
- 必须先启动 `edge_ollama_server.py`
- 如果 `127.0.0.1:8001/infer` 没有服务，`EdgeHttpExecutor` 会 fallback 到 `LocalEchoExecutor`

### 3. cloud：云端强模型

当前云端使用 OpenAI-compatible 接口调用 BigModel / 智谱：

- 模型：`glm-5.2`
- base url：`https://open.bigmodel.cn/api/paas/v4`

对应 `.env` 配置示例：

```env
OPENAI_MODEL=glm-5.2
OPENAI_BASE_URL=https://open.bigmodel.cn/api/paas/v4
OPENAI_API_KEY=你的真实 key
```

对应执行器：

- `engine/modules/execution/executors.py`
- `OpenAICompatibleCloudExecutor`

注意：文档中不要写入真实 API key。

## 五、judge 当前如何判断

当前 judge 不是单独训练的评分模型，而是使用云端 `glm-5.2` 根据提示词进行结构化评估。

发送给 judge 的核心内容包括：

- 原始 task
- 当前质量阈值 `quality_threshold`
- device / edge / cloud 三份回答
- 评分要求

当前 judge 提示词要求：

```text
Score each answer from 0 to 1 for correctness, completeness, and instruction following.
Choose the cheapest sufficient tier: device first, then edge, then cloud.
Return strict JSON with keys scores, selected_tier, reason.
scores must map device/edge/cloud to numbers.
```

系统提示词：

```text
You are a strict model-routing evaluator. Return JSON only.
```

当前默认质量阈值：

```text
quality_threshold = 0.72
```

理论 fallback 选择规则：

```text
如果 device_score >= 0.72，则选 device
否则如果 edge_score >= 0.72，则选 edge
否则选 cloud
```

但当前脚本的实际优先级是：

1. 如果 judge 明确返回合法的 `selected_tier`，则采用 judge 返回值
2. 如果 judge 没有返回合法 `selected_tier`，才使用 `scores + threshold` fallback

因此最终标签来源是：

```text
端/边/云三份实际回答 + GLM-5.2 judge 的质量评估
```

而不是 LMSYS 原始 winner。

## 七、为什么重新跑结果可能不同[今天相同的prompt测试结果会有不同]

重跑标注时，`selected_tier` 可能发生变化，这是正常现象。

原因包括：

+ 量化模型和不同推理后端可能存在轻微非确定性
+ 云端 judge 也是 LLM，可能对边界样本给出略有差异的分数
+ 如果 edge 分数接近阈值 `0.72`，一次可能选 edge，另一次可能选 cloud
+ 如果输出文件使用 append 模式，旧数据和新数据混在一起会造成误判

当前脚本是追加写入：

```python
with output.open("a", encoding="utf-8") as out_fh:
```

因此正式跑新实验前，应先删除旧文件，或后续增加 `--overwrite` 参数。

## 九、当前已知问题与后续优化

### 1. judge 稳定性

当前 judge 是 LLM judge，不是固定评分模型。

问题：

- 分数可能有轻微波动
- 接近阈值的样本可能重跑后 tier 改变

后续可优化：

- 每条样本 judge 多跑 3 次取多数票
- 或输出多维 rubric：
  - correctness
  - completeness
  - instruction_following
  - safety
  - final

### 2. 标注脚本当前默认 append

当前 `label_lmsys_tiers.py` 默认追加写入。

风险：

- 旧二分类数据和新三分类数据可能混在同一个文件中

后续可优化：

- 增加 `--overwrite`
- 启动时检查已有文件 schema
- 如果 schema 不一致则拒绝追加

### 3. device 类别可能偏少

LMSYS prompt 普遍比简单 FAQ 更复杂，`qwen2.5:0.5b` 可能很难达到阈值。

后续可优化：

- 增加简单 prompt 来源
- 降低部分任务阈值
- 按任务类型设置不同阈值
- 使用更强一点的端侧模型

### 4. 当前 edge 是本机 wrapper

当前 edge 虽然通过 HTTP 服务模拟，但实际仍在本机调用 Ollama。

后续如果有**真实边缘机器**，可以只替换：

```env
EDGE_ENDPOINT=http://真实边缘机器:端口/infer
EDGE_MODEL=真实边缘模型名
```

## 十、当前结论

截至 2026-07-22，项目已经完成以下闭环：

```text
LMSYS prompt
  -> device(qwen2.5:0.5b)
  -> edge(qwen2.5:3b)
  -> cloud(glm-5.2)
  -> GLM-5.2 judge
  -> 三分类 label: 0=device,1=edge,2=cloud
  -> BGE-M3 embedding + LogisticRegression 三分类训练
  -> 生产 gate 输出 route_tier
  -> 调度器按 route_tier 选择端/边/云
```

下一阶段的重点不是继续改模型结构，而是：

1. 扩大 LMSYS 标注数据量
2. 检查三类 label 分布
3. 训练 `lmsys_bge_m3_3class`
4. 评估三分类 accuracy / macro F1
5. 根据混淆矩阵调整阈值、prompt 采样和 judge rubric




其他说明：
关于edge：
>真实 edge 机器，本质上就是：另一台机器跑一个中等模型，并暴露一个 HTTP /infer 接口给你的主项目调用。

现在本机的 edge 是：
```
主项目 -> http://127.0.0.1:8001/infer -> 本机 Ollama qwen2.5:3b
```
真实 edge 会变成：
```
主项目电脑 -> http://边缘机器IP:8001/infer -> 边缘机器上的 Ollama/vLLM/LM Studio 模型
```
真实 edge 需要一台局域网内机器，例如：IP: 192.168.1.50
模型: qwen2.5:3b / qwen2.5:7b / 其他中等模型
服务端口: 8001


边缘机器上要：
+ 安装并启动模型服务，比如 Ollama
+ 下载边缘模型，比如 qwen2.5:3b
+ 启动 /infer wrapper 服务

边缘机器操作
+ 在边缘机器上安装 Ollama，然后运行：
然后把项目里的这个脚本也放到边缘机器上：
examples/edge_cloud_scheduler/edge_ollama_server.py
在边缘机器的 .env 里配置：
```
EDGE_MODEL=qwen2.5:3b
EDGE_OLLAMA_BASE_URL=http://127.0.0.1:11434/v1
EDGE_HOST=0.0.0.0
EDGE_PORT=8001
然后启动：
examples\edge_cloud_scheduler\edge_ollama_server.py
```

这里关键是：
```
EDGE_HOST=0.0.0.0
```
表示它不只监听本机 127.0.0.1，而是允许局域网其他机器访问。

---

主项目机器操作

假设边缘机器 IP 是：

192.168.1.50
那你主项目机器的 .env 改成：

EDGE_ENDPOINT=http://192.168.1.50:8001/infer
EDGE_MODEL=qwen2.5:3b
然后在主项目机器测试：
```
python -c "from engine import EdgeHttpExecutor, InferenceRequest; r=EdgeHttpExecutor().run(InferenceRequest(prompt='Explain what an API is in one short sentence.', allocation={'tier':'edge','endpoint':'edge://default'})); print(r.executor, r.model, r.endpoint, r.success); print(r.text[:300]); print(r.metadata)"
```
成功应该看到：
```
EdgeHttpExecutor qwen2.5:3b http://192.168.1.50:8001/infer True
```
网络注意事项

如果连不上，一般查这几个：

1. 边缘机器和主项目机器是否在同一局域网
2. 主项目机器能否 ping 通边缘机器 IP
3. 边缘机器防火墙是否放行 8001 端口
4. edge 服务是否监听 0.0.0.0，而不是 127.0.0.1
5. Ollama 是否在边缘机器本地 11434 正常运行
Windows 防火墙可能要允许 Python 监听端口，或者手动放行 8001。
