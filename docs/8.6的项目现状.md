你现在的理解里，有一半接近目标架构，但和“当前代码实际行为”有几个关键区别。

最重要的一句话是：

> 当前项目是“先定义 Agent/节点和连接关系，再把它编译成图，然后执行图”；不是“输入任务后，由一个父 Agent 自动拆任务、现场创建若干 Agent”。

而技能系统目前是：

> 执行前读取已有技能，执行中记录轨迹，执行结束后由显式调用的离线演化服务生成候选技能；不是每个 Agent 执行完就由 `retrieval.py` 自动写 Markdown。

## 一、用通俗比喻理解整个项目

可以把项目看成一家“按流程图运行的公司”。

- `Orchestrator`：组织架构设计人员
- `AgentSpec`：员工档案
- `Node`：流水线上的工位
- `StateGraph`：流水线设计图
- `CompiledGraph`：已经安装完成、可以开机的流水线
- `GraphState`：所有工位共享的工作台和任务档案
- `HookManager`：每个工位旁边的监督与后勤系统
- `Memory`：公司历史资料库
- `Context Ledger`：当前订单的工作日志
- `SkillRepo`：经过审批的标准操作手册库
- `SkillRetriever`：开工前为当前员工查找相关操作手册
- `SkillTraceStore`：记录员工本次具体怎么干的
- `SkillEvolutionService`：下班后复盘录像，生成新版操作手册草案
- `Evaluator`：质检员
- `RecoveryStrategy`：发生错误后的应急预案
- `Scheduler`：决定这项工作使用本地、边端还是云端资源
- `Router`：决定任务下一步流向哪里

所以系统有两条不同链路：

```text
在线执行链路：
任务 → 已编排的图 → 节点/Agent 执行 → 返回结果

离线技能演化链路：
执行轨迹 → 提取候选技能 → 验证 → 人工审批 → 发布 → 下次执行时检索使用
```

这两条链路不能混为一谈。

# 二、你描述的流程，哪些正确、哪些不正确

你描述的是：

```text
输入任务 Prompt
    ↓
父 Agent 理解任务
    ↓
拆成若干子任务
    ↓
根据子任务现场创建 Agent
    ↓
子 Agent 工作
    ↓
子 Agent 继续创建下级 Agent
```

这是一个“动态组织、自主分解”的理想架构，但当前项目还不是这样。

当前真实流程是：

```text
开发人员或前端
    ↓
提前创建 AgentSpec
    ↓
提前设置父子关系和连线
    ↓
Orchestrator.build_graph()
    ↓
把每个 AgentSpec 转成 Node
    ↓
StateGraph.compile()
    ↓
输入任务
    ↓
CompiledGraph 按既定节点和边执行
```

也就是说：

- Agent 是执行前创建好的。
- 子 Agent 关系是执行前配置好的。
- 图结构也是执行前编译好的。
- 运行中的父 Agent不会调用 `create_agent()`。
- 运行中的 Agent不会自动修改图结构。
- Agent不会自动递归创建自己的子 Agent。
- 输入 Prompt 本身不会触发组织架构重建。

项目提供了“创建父子 Agent”的 API，但调用这个 API 的是开发代码或前端，不是运行中的父 Agent。

例如：

```python
orch = Orchestrator()

parent = orch.create_agent("manager")
child = orch.add_sub_agent(parent, name="researcher")

orch.set_entry(parent)
graph = orch.build_graph()

result = await graph.ainvoke({"input": "调查某个问题"})
```

这里的 `researcher` 是执行前由 Python 代码创建的，不是 `manager` 读完任务后自己创建的。

# 三、项目究竟编排的是节点还是 Agent？

准确答案是：

> 底层编排的是 Node；Orchestrator 提供了一种把 Agent 转换成 Node 的上层用法。

## 3.1 最底层是 Node

[node.py](D:/PythonProject/long_task_1/long_task_1/engine/node.py) 定义了三种节点：

```python
class NodeType:
    FUNCTION = "function"
    AGENT = "agent"
    SUBGRAPH = "subgraph"
```

所以图里的一个节点可以是：

- 普通 Python 函数
- AgentScope Agent
- 另一张子图

例如普通函数节点：

```python
graph.add_node("calculate", calculate_function)
```

Agent 节点：

```python
graph.add_node_object(agent_node("writer", writer_agent))
```

子图也可以被包装成节点。

## 3.2 Orchestrator 把 AgentSpec 转成 Node

[orchestrator.py](D:/PythonProject/long_task_1/long_task_1/engine/orchestrator.py) 管理的是 `AgentSpec`：

```text
AgentSpec
├── id
├── name
├── sys_prompt
├── model
├── description
├── children
└── config
```

调用 `build_graph()` 时，它会：

```text
AgentSpec
    ↓ node_factory
Node
    ↓ add_node_object()
StateGraph
```

因此，从使用者视角看是“编排 Agent”；从引擎视角看，最终编排和执行的始终是 Node。

## 3.3 父子 Agent 不等于自主上下级管理

`add_sub_agent()` 当前主要做两件事：

1. 在父 Agent 的 `children` 中记录子 Agent ID。
2. 默认添加一条 `parent → child` 的图边。

另外，构图时会给子节点添加：

```text
parent_id
parent_name
is_sub_agent
requires_parent_validation
```

这些元数据用于父级校验和上下文隔离。

但是父 Agent 本身并没有一个“根据任务决定要创建什么子 Agent”的内置逻辑。

所以：

```text
当前父子关系 = 预定义的层级信息 + 图连接 + 校验边界
```

而不是：

```text
当前父子关系 ≠ 父 Agent 运行时自主招聘下属
```

# 四、一次完整任务到底怎么运行

下面以 REST 请求为入口说明。

## 4.1 第一步：提前配置编排

前端或开发代码通过 [server/app.py](D:/PythonProject/long_task_1/long_task_1/engine/server/app.py) 提供的 API 创建 Agent：

```http
POST /api/agents
```

创建子 Agent：

```http
POST /api/agents/{id}/sub-agents
```

连接 Agent：

```http
POST /api/connections
```

设置入口：

```http
POST /api/graph/entry
```

这时只是修改 `Orchestrator` 里的配置，还没有执行任务。

## 4.2 第二步：接收任务

调用：

```http
POST /api/run
```

请求示例：

```json
{
  "input": {
    "run_id": "task-001",
    "goal": "制定杭州三日旅行计划",
    "task_type": "travel",
    "input": "3 人，预算 6000 元"
  },
  "recursion_limit": 50
}
```

服务端执行：

```python
compiled = orch.build_graph()
state = await compiled.ainvoke(req.input)
```

注意：每次 `/api/run` 都会调用一次 `build_graph()`，但这是把已经配置好的 Agent 编译成图，不是让 LLM 根据当前任务创建 Agent。

## 4.3 第三步：Orchestrator 构图

`Orchestrator.build_graph()` 会：

```text
检查是否存在 Agent
    ↓
确定入口 Agent
    ↓
为每个 AgentSpec 创建 Node
    ↓
添加普通边
    ↓
添加条件边
    ↓
没有出边的节点自动连接 END
    ↓
StateGraph.compile()
    ↓
安装 HookManager
    ↓
返回 CompiledGraph
```

默认情况下使用 `echo_node_factory`。

这个默认工厂并不会调用大模型，只会回显输入：

```text
[planner] 收到: 用户输入
```

要真正调用 AgentScope/LLM，需要传入实际的 `node_factory`，或者直接使用 `agent_node()`。

因此，REST 服务默认创建出来的 Agent 更接近“可视化占位执行节点”，不天然是一个真正调用大模型的智能体。

# 五、graph.py 的职责是什么

[graph.py](D:/PythonProject/long_task_1/long_task_1/engine/graph.py) 不负责创建 Agent，也不负责理解 Prompt。

它负责两件事：

## 5.1 构建图

`StateGraph` 提供：

```text
add_node()
add_node_object()
add_edge()
add_conditional_edges()
add_loop()
set_entry_point()
set_finish_point()
compile()
```

它只关心：

- 有哪些节点
- 节点之间怎么连接
- 哪个节点先执行
- 条件满足时走哪条边
- 循环什么时候退出

## 5.2 执行图

`CompiledGraph.astream()` 是核心执行循环。

通俗地说：

```text
拿到当前应该执行的节点列表 frontier
    ↓
执行 on_step_start
    ↓
为每个节点执行 on_node_start
    ↓
根据 FlowController 判断执行/跳过/延迟
    ↓
并发执行当前批次节点
    ↓
节点成功：on_node_end
节点失败：on_node_error
    ↓
合并节点返回的状态
    ↓
根据边和 RoutingPolicy 找下一批节点
    ↓
重复，直到没有后继节点或达到递归上限
```

这里的 `frontier` 是“当前超步可以执行的节点集合”。

例如：

```text
          → researcher →
planner                  reviewer
          → writer     →
```

执行顺序可能是：

```text
第 1 个 superstep：planner
第 2 个 superstep：researcher、writer 并行
第 3 个 superstep：reviewer
```

这就是 `graph.py` 的主要工作。

# 六、GraphState 是什么

[state.py](D:/PythonProject/long_task_1/long_task_1/engine/state.py) 管理所有节点共享的状态。

可以把它理解成一张所有工位共享的任务表：

```python
{
    "run_id": "task-001",
    "goal": "制定旅行计划",
    "input": "3 人，预算 6000",
    "messages": [...],
    "plan": [...],
    "budget": {...},
    "__failures__": [...],
    "__context_ledger__": {...},
    "__skill_context__": [...]
}
```

每个节点不会直接返回完整状态，只返回本次产生的增量：

```python
return {
    "hotel_options": [...],
    "messages": [...]
}
```

然后 `GraphState` 根据 reducer 合并。

例如：

- 普通字段默认覆盖。
- `messages` 使用追加 reducer。
- `__failures__` 使用追加 reducer。

因此节点之间主要通过共享状态传递结果。

# 七、HookManager 在整个流程中的位置

文件名是 [hooks.py](D:/PythonProject/long_task_1/long_task_1/engine/hooks.py)，不是 `hook.py`。

它不是业务 Agent，而是图执行引擎和扩展模块之间的总接线板。

完整位置如下：

```text
CompiledGraph
    │
    ├── on_step_start()
    │     ├── 更新 Context Ledger
    │     ├── 检查上下文预算
    │     └── 记录 step_start 技能轨迹
    │
    ├── on_node_start()
    │     ├── 检索长期记忆
    │     ├── 注入当前 Context Ledger
    │     ├── 检索并注入已发布 Skill
    │     ├── 记录 node_start 轨迹
    │     └── FlowController 决定执行/跳过/延迟
    │
    ├── acquire_resource()
    │     ├── Scheduler 分配资源
    │     ├── 安全脱敏
    │     └── 生成审计信息
    │
    ├── Node.invoke()
    │
    ├── on_node_end()
    │     ├── Evaluator 质检
    │     ├── 更新 Context Ledger
    │     ├── 写长期记忆
    │     ├── 检测漂移
    │     └── 记录 node_end 技能轨迹
    │
    ├── handle_validation_failure()
    │     ├── 仅记录
    │     ├── 暂停
    │     └── 改道修复节点
    │
    └── on_node_error()
          ├── 写 FailureTrace
          ├── RecoveryStrategy 生成恢复方案
          ├── 更新 Context Ledger
          └── 记录 node_error 技能轨迹
```

Hook 的意义是：不需要把记忆、技能、调度、恢复、安全代码写进每一个 Agent。

# 十、Memory、Context 和 Skill 有什么区别

这三个系统看起来很像，但职责完全不同。

| 系统 | 通俗理解 | 内容 | 生命周期 |
|---|---|---|---|
| Context | 当前任务的工作台 | 目标、约束、当前计划、已完成步骤 | 单次 run |
| Memory | 历史资料库 | 过去的信息、经验和检索内容 | 跨 run |
| Skill | 经验证的操作手册 | 标准步骤、失败处理、核验方式 | 跨 run、版本化发布 |
| Trace | 工作录像 | 本次具体执行事件 | 演化证据 |

举例：

```text
Context：
当前用户预算 6000 元，正在寻找酒店。

Memory：
之前用户偏好靠近西湖的酒店。

Skill：
计算旅行总预算时，必须包含交通、住宿、餐饮和活动费用。

Trace：
planner 第一步做了什么，hotel 节点返回什么，Evaluator 是否通过。
```

# 十一、engine/modules 下各文件夹负责什么

## `context/`：当前任务的上下文治理

- `_types.py`：上下文数据结构。
- `ledger.py`：维护每次 run 的上下文账本。
- `renderer.py`：把账本渲染为 `MEMORY.md`。
- `compressor.py`：压缩长输出，保存 `raw_ref`。
- `injector.py`：把目标、约束、事实拼成节点输入。
- `budget.py`：控制上下文 Token 预算。
- `drift.py`：检测重复执行、目标偏离、反复操作文件等。
- `checkpoint.py`：保存和恢复上下文现场。
- `policy.py`：统一加载上下文配置。

这里生成的 `MEMORY.md` 是当前 run 的运行摘要，不是技能文件。

## `memory/`：跨任务长期记忆

- `base.py`：记忆接口。
- `store.py`：四级混合记忆实现。
- `_types.py`：MemoryItem、MemoryScope 等类型。
- `embedding.py`：向量化。
- `judge.py`：判断记忆是否应该保存、更新或合并。
- `_utils.py`：辅助函数。

四级范围是：

```text
WORKING → TASK → PROJECT → GLOBAL
```

## `skills/`：程序性技能

- `_types.py`：Skill、Manifest、状态和验证报告。
- `repository.py`：保存、读取、发布、退休、回滚。
- `retrieval.py`：检索并注入已发布技能。
- `trace.py`：记录脱敏执行轨迹。
- `evolution.py`：从轨迹生成候选、验证和发布。
- `__init__.py`：公共导出。

## `execution/`：真正调用推理后端

- `base.py`：Executor 接口。
- `executors.py`：本地、边端、云端执行器。
- `registry.py`：执行器注册表。
- `runner.py`：带降级能力的推理调用。
- `_types.py`：请求和结果类型。

这部分解决的是“模型到底在哪里运行”。

## `scheduling/`：决定使用哪个执行资源

- `scheduler.py`：资源分配主逻辑。
- `policy.py`：调度规则。
- `gate.py`：判断任务复杂度、敏感级别等。
- `monitor.py`：检查系统资源。
- `learning.py`：学习型路由。
- `advanced_training.py`：高级训练流程。
- `production.py`：生产路由加载与配置。
- `base.py`、`_types.py`：基础接口和类型。

例如决定：

```text
简单任务 → 本地小模型
敏感任务 → 本地或可信边端
复杂任务 → 云端强模型
边端失败 → 云端降级
```

## `security/`：安全和审计

- `redaction.py`：API Key、Token、手机号、邮箱等脱敏。
- `audit.py`：生成内容哈希和审计包。
- `_types.py`：安全数据类型。

技能轨迹在写盘前会使用这里的脱敏器。

## 其他单文件模块

- `evaluation.py`：节点输出质检。
- `flow.py`：决定节点执行、跳过还是延迟。
- `recovery.py`：错误后重试、改道或终止。
- `routing.py`：调整下一批节点。
- `bge_local.py`：本地优先查找 BGE-M3 模型。

# 十五、最终回答你的几个问题

## 1. 是否由父 Agent自动理解任务并创建子 Agent？

不是。

当前父子 Agent 由 Python 代码或 REST API 提前创建。父 Agent 运行时不会自动创建子 Agent。

## 2. 子 Agent 是否可以继续创建下级 Agent？

从数据结构上可以提前建立多层父子关系；但运行中的子 Agent 不会自己调用 `add_sub_agent()`。

## 3. 创建过程是否在 `graph.py`？

不是。

- Agent 创建和父子关系：`orchestrator.py`
- Agent 转换成 Node：`orchestrator.py` 和 `adapters.py`
- 图结构保存和执行：`graph.py`

## 4. 编排的是节点还是 Agent？

底层编排 Node。

Agent、普通函数、子图都可以包装成 Node。`Orchestrator` 让“编排 Agent”看起来更方便，但最终还是 Node 图。

## 5. Agent 是否通过 hooks 使用 retrieval.py 创建技能？

不是。

`HookManager` 在节点执行前调用 `retrieval.py`，但它只是查找已发布技能并注入。

## 6. 技能是否在每次执行后自动写 Markdown？

不是。

执行时自动写的是 `trace.jsonl`。必须显式调用 `SkillEvolutionService`，才会根据轨迹创建候选 `SKILL.md`。

## 7. 当前是否已经实现完全自主进化？

还没有。

现在已经有完整的基础闭环组件，但演化调度仍需外部显式触发。它属于“受控、离线、需审批的技能演化”，不是“Agent 每次执行后自主修改自己”。




---

先澄清一个关键点：

> 当前仓库只有后端编排接口，没有实际的前端页面代码。因此现在并不存在可以直接点击的“创建 Agent”“生成技能”“批准技能”按钮。

这些按钮是未来前端可以基于现有 REST API 做出来的交互形式。目前创建 Agent 可以通过调用 API 或写 Python 代码完成；技能生成、验证和发布目前只能通过 Python 调用完成，还没有 REST 接口和前端页面。

# 一、“前端创建 AgentSpec”具体是什么意思

`AgentSpec` 可以理解成一张“Agent 员工档案”。

它包含：


例如，未来前端可以有一个“创建 Agent”表单：

```text

deepseek-v4-flash

其他配置：
任务类型 travel

```

点击“创建”以后，前端调用：

```http

```

```json
{
  "name": "travel_planner",

  "model": "deepseek-v4-flash",
```

所以你的理解基本正确：

> 未来可以有“创建 Agent”按钮，点击后填写 Agent 的名称、身份、职责、模型和配置。

但当前仓库中还没有这个前端页面，只有支持它的后端 API。

# 二、“为每个 AgentSpec 创建 Node”是什么意思

`AgentSpec` 和 `Node` 是两个不同层次的东西。

## 1. AgentSpec 是档案

它描述这个 Agent 是谁：

```text
名字是什么
使用什么模型
系统提示词是什么
职责是什么
有哪些子 Agent
```

它本身不能被图引擎直接执行。

## 2. Node 是可执行工位

`Node` 除了名字和元数据，还必须包含一个真正可以调用的函数：

```python
async def node_function(state):
    # 做具体工作
    return {"result": "..."}
```

所以 `Orchestrator.build_graph()` 需要把：

```text
AgentSpec：这个 Agent 是谁
```

转换成：

```text
Node：这个 Agent 在图中如何被调用
```

可以类比为：

```text
AgentSpec = 员工档案
Node = 员工在流水线上的工作岗位
```

员工档案不能直接生产产品。必须先给员工分配一个工位，并规定这个工位如何接收材料、如何工作、如何输出结果。

转换过程大致是：

```text
AgentSpec
├── name
├── sys_prompt
├── model
└── config
        │
        ▼
Node
├── name
├── node_type = AGENT
├── metadata
└── func(state) → update
```

## 3. 当前这里还有一个重要限制

`Orchestrator` 默认使用 `echo_node_factory()`。

默认 Node 只会回显：

```text
[travel_planner] 收到：用户输入
```

不会真正调用大模型。

要让它变成真实 Agent，必须提供真实的 `node_factory`，或者通过 `adapters.py` 的 `agent_node()` 包装 AgentScope Agent。

因此未来完整流程不能只是“填写 AgentSpec”，还必须解决：

```text
AgentSpec
    ↓
根据 model、sys_prompt 创建真实 AgentScope Agent
    ↓
通过 adapters.py 包装为 Node
```

当前 REST `/api/run` 默认没有完成这一步。这是后续需要重点补齐的缺口。

# 四、什么叫“在线流程”和“离线流程”

这里的“在线”和“离线”不是指有没有互联网。

它们指的是：这段工作是否位于用户等待结果的主请求中。

## 1. 在线流程

在线流程就是：

> 用户正在等待结果的任务执行流程。

例如用户提交：

```text
帮我制定杭州三日旅行计划，三个人，预算 6000 元。
```

从用户点击提交，到页面显示最终答案，这段流程都是在线流程。

```text
用户提交任务
    ↓
系统检索已有技能
    ↓
执行 Agent 图
    ↓
调用工具和模型
    ↓
进行结果质检
    ↓
返回最终答案
```

在线流程的要求是：

- 速度要快。
- 不能长时间阻塞。
- 不能因为技能演化失败而影响用户任务。
- 不能为了学习额外调用十几次模型。
- 只能读取已经验证和发布的技能。
- 出错时要能降级到无技能模式。

## 2. 离线流程

离线流程就是：

> 用户任务已经完成，不需要让用户等待的后台复盘工作。

例如晚上系统扫描白天完成的 100 个任务：

```text
哪些任务失败了？
哪些任务重复重试？
哪些成功任务使用了更短步骤？
有没有值得总结的新经验？
旧技能是否已经过时？
```

然后生成候选技能并执行回放验证。

用户不需要停留在任务页面等待这个过程。

离线流程可以：

- 花几分钟甚至几小时。
- 批量处理多条轨迹。
- 调用更强、更贵的模型。
- 重复运行候选评测。
- 生成人工审核报告。
- 被暂停或重试，而不影响在线任务。

## 3. 两者的关系

```text
在线流程负责“把当前任务做好”
                ↓
            产生轨迹
                ↓
离线流程负责“从过去任务中学习”
                ↓
        生成并发布新技能
                ↓
下一个在线任务读取新技能
```

通俗地说：

```text
在线 = 白天接订单、干活
离线 = 晚上复盘、编写操作手册
```

# 六、后续完整落地计划

## 第一阶段：补齐“真实 Agent 执行链路”

这是最高优先级。否则前端虽然能创建 AgentSpec，默认节点仍然只会回显。

### 需要实现

1. 新增统一的 `AgentFactory`。

输入：

```text
AgentSpec
模型配置
工具配置
执行资源
```

输出：

```text
真实 AgentScope Agent 或可执行 Node
```

2. `Orchestrator.build_graph()` 默认根据 AgentSpec 创建真实 Agent Node。

3. 从 `sys_prompt`、`model` 和 `config` 创建 Agent。

4. 将技能、记忆、上下文注入真实模型输入。

5. 支持工具白名单。

6. 支持模型不可用时的明确错误或降级。

7. REST `/api/run` 不再默认使用 Echo Node。

### 验收标准

- 前端创建一个 Agent 后，提交任务能获得真实模型回答。
- `sys_prompt` 确实影响回答。
- `model` 字段确实决定模型。
- 技能和 Context Ledger 确实进入模型输入。

## 第十阶段：再考虑动态创建 Agent

你最开始描述的“父 Agent根据 Prompt 创建子 Agent”，应该放在整个系统稳定之后。

合理流程应是：

```text
用户任务
    ↓
Planner Agent 生成结构化任务计划
    ↓
判断现有节点是否足够
    ├── 足够：使用已有工作流
    └── 不足：生成临时子图提案
               ↓
          权限和资源检查
               ↓
          工具白名单检查
               ↓
          图结构校验
               ↓
          在当前 run 的临时沙箱中执行
```

不能让 LLM直接调用无限制的 `create_agent()`。

必须限制：

- 最大动态 Agent 数。
- 最大递归深度。
- 允许的模型。
- 允许的工具。
- Token 和费用预算。
- 禁止修改正式编排。
- 临时 Agent 默认不能发布为永久 Agent。
- 子 Agent输出必须由父级或 Evaluator 验证。
- 同一个 run 中动态图结构必须写入 checkpoint。

建议先实现“动态子图提案”，而不是“任意创建 Agent”。

# 七、推荐实施顺序

最合理的顺序是：

```text
1. 真实 AgentFactory
2. 编排持久化与版本
3. Run 管理与实时事件
4. 完整轨迹
5. 技能管理 API
6. 后台自动生成候选
7. 标准化验证系统
8. 前端技能治理
9. 灰度发布与自动回滚
10. 受控动态创建 Agent
```

不要先做动态创建 Agent。因为如果真实执行、运行记录、验证和回滚还没有完整，动态创建只会扩大不可控范围。

最终完整闭环应当是：

```text
前端设计并发布 Agent 工作流
    ↓
用户选择工作流并输入任务
    ↓
真实 Agent 图在线执行
    ↓
保存上下文、失败、工具和技能轨迹
    ↓
后台离线聚类和生成候选技能
    ↓
自动验证候选
    ↓
人工在前端审核批准
    ↓
灰度发布
    ↓
在线监控
    ├── 表现良好 → 正式发布
    └── 表现退化 → 自动回滚
    ↓
新任务检索并使用新技能
    ↓
继续产生新轨迹，进入下一轮演化
```

这才是完整、合理、可审计、可回滚的 Agent 自我进化闭环。
