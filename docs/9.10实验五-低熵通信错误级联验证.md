# 实验五：低熵通信的错误级联验证（1 天精简版）

## 1. 目的与可宣称边界

本实验只回答一个工程问题：**当一条相关但错误的信息被多个中间 Agent 重复转述时，MessageCapsule 的接收者条件化门控和去冗余机制，能否减少该错误到达汇聚节点及最终节点的重复次数？**

它不验证模型是否会识别事实错误，也不测量 Shannon 熵，更不能据此声称系统能阻止第一条新鲜错误信息进入下游。当前实现的 `CommunicationManager.evaluate()` 使用相关性、证据置信度、角色匹配、新鲜度、冗余和预算压力评分；它没有事实真伪判别器。因此，一条“首次出现、相关、看起来有证据”的错误 Capsule 仍可能被投递。实验应把结论写为“抑制错误的**重复放大/级联**”，而不是“消除错误”。

时间限制为 1 天时，不接真实网页或外部工具，但**五个节点均必须调用同一条已测试成功的真实 LLM 连接**。错误源和三个中继消息采用受控覆盖：节点先完成真实 LLM 调用并保留连接 ID、响应元数据和非模拟标记，再用冻结的、带 `error_id` 的文本替换中继 payload。这样既保证两组实际经过真实模型运行时，也不把模型随机改写误当作通信方法的效果。

## 2. 被测实现与实际作用点

| 环节 | 当前实现 | 实验中要观察的事件/字段 |
|---|---|---|
| 定向投递 | `HookManager.resolve_successors()` 把 Capsule 交给图后继 | `capsule_delivered.recipient` |

- `engine/hooks.py`：节点结束创建 Capsule（279–304 行）；按后继路由并投递（485–513 行）。

## 3. 最小实验图与受控错误

使用一个固定的“分叉—汇聚”五节点图，而不是线性链：

```text
source ──→ verifier_A ──┐
   │                    ├──→ aggregator ──→ writer
   └──→ verifier_B ──┘
```

每个 case 给出一个可判定事实及其正确答案，例如“项目发布日期是 2026-09-10”。`source` 故意输出相反的错误主张，例如“发布日期是 2026-09-09”，并带固定 `error_id`（如 `ERR-07`）。两个 verifier 都执行同一确定性转述规则：把其输入中的主张写成“待核验结论”，从而形成两条语义高度相似的错误转述。`aggregator` 汇总收到的内容；`writer` 输出最终结论及其所依据的候选结论。

这样设计的理由是：错误只被注入一次；A/B 的重复转述模拟多 Agent 协作中常见的“重复即可信”放大；汇聚点是冗余门控真正应发挥作用的位置。不要让 verifier 自行纠错，否则测到的是 verifier 的事实能力，不是通信机制。

## 4. 两组对照（仅做必要对照）

| 组别 | 配置 | 预期差异 |
|---|---|---|
| B0：全文广播基线 | 不设置 `CommunicationManager`；`AgentRuntimeFactory` 将原有 `messages` 作为共享上游历史放入真实 LLM prompt | A/B 两条错误转述都会进入聚合上下文，错误可能被计数两次或更多 |
| Ours：低熵通信 | `Orchestrator.set_communication_manager(CommunicationManager())`；`AgentRuntimeFactory` 只将收件人 Capsule 放入下游真实 LLM prompt；默认 `min_contribution=0.28`、`redundancy_threshold=0.82`、`max_capsule_tokens=512` | A/B 中先到达 aggregator 的错误 Capsule 可投递；相似的后到 Capsule 应产生 `capsule_pruned`，原因含 `redundant` |

保持图、输入、错误注入位置、节点逻辑、模型配置（若使用模型）完全一致。不得把 Ours 的错误 source 删除或修改为正确答案；否则比较的是输入质量而非级联抑制。

建议使用 `CommunicationPolicy` 的代码默认值；虽然仓库有 `configs/communication_policy.yaml`，当前未发现自动加载该 YAML 的代码路径，实验脚本应显式记录实际传给 `CommunicationManager` 的 policy。

## 5. 样本与运行规模

数据集固定为 **100 个 case**，每条 case 均包含唯一的 `case_id`、`error_id`、正确事实、错误事实、A/B 两条转述文本及其相似度类别。每个 case 在 B0 和 Ours 各运行一次，因此总计为 **100 × 2 = 200 次受控 run**。这不是 200 条不同任务，而是同一 100 条任务在两种通信方法下的一一配对比较。

建议将冻结数据集写为 `examples/experiments/sample_data/communication_error_cascade_100.jsonl`；运行前计算其 SHA-256，并在所有结果元数据中记录该 hash。

| 子集 | Case ID | 数量 | A/B 关系 | 用途 |
|---|---|---:|---|---|
| 高相似重复 | `HS-001`–`HS-070` | 70 | 相同错误事实与 `error_id`，A/B 使用完全相同的冻结 relay 文本 | 主分析集；在当前 token-Jaccard 门控下形成无歧义重复正样本 |
| 部分相似重复 | `PS-001`–`PS-020` | 20 | 相同错误事实与 `error_id`，但解释、证据描述明显改写 | 阈值边界分析；不能强求全部剪枝 |
| 非重复信息 | `NR-001`–`NR-010` | 10 | A/B 含不同事实和不同 `error_id` | 安全性对照；检查不会把不同信息误认为重复 |

事实主题可在“日期、数量、版本、地点、规则”五类中均匀分布，每类 20 条；所有正确/错误值均是离线预置文本，不调用网页或模型生成。受控节点与固定输入下不做多 seed 重复：重复运行不会增加通信机制的证据强度，只会挤占当天的实现与审计时间。

## 6. 指标、判定与原始证据

### 6.1 主指标

1. **错误放大量（Error Amplification Count, EAC）**：aggregator 输入中含同一 `error_id` 的消息数。主假设为 `EAC_ours < EAC_baseline`。
2. **错误级联率（Error Cascade Rate, ECR）**：最终 writer 输出仍包含该 `error_id` 或错误事实的 run 占比。该指标可能不下降；因为首条错误可合法投递，必须如实报告。
3. **冗余错误剪枝率（Redundant Error Pruning Rate, REPR）**：高相似 case 中，第二条错误转述被 `capsule_pruned` 的比例；其 `reasons` 可以是 `redundant`，也可以是冗余度降低贡献分后触发的 `low_contribution`。两种情况均记录 `decision.components.redundancy`，并以 `>=0.80` 认定为重复抑制。主成功判据：`REPR >= 63/70（90%）`。
4. **误剪枝率（False Prune Rate, FPR）**：非重复对照中，被错误标为 `redundant` 的消息比例。成功判据：`FPR <= 1/10`；若出现误剪枝，必须逐条报告两条消息的 Jaccard 冗余分数。

不要使用“token 更少”作为主要成功标准；它只能作辅助指标，因为本实验的核心是错误传播轨迹，不是压缩率。

### 6.2 每次 run 必须保存

- `case_id`、组别、错误事实、正确事实、`error_id`、图版本和实际 policy；
- 原始事件序列，特别是所有 `capsule_created`、`capsule_delivered`、`capsule_pruned`；
- 每条剪枝事件的 `recipient`、`digest`、`decision.score`、`decision.components.redundancy` 与 `decision.reasons`；
- aggregator 的实际输入和 writer 的最终输出；
- 每个 run 的 EAC、ECR 命中与 REPR/FPR 判定；以及 `real_llm_nodes`（必须恰好为 source、verifier_A、verifier_B、aggregator、writer）。

建议写到 `runs/experiments/communication_error_cascade/<baseline|ours>/<case_id>.json`，并汇总为一个 CSV/JSONL。不要只保留汇总表，否则无法证明剪枝发生在聚合前。

## 7. 已实现的执行计划

1. 生成并冻结 `examples/experiments/sample_data/communication_error_cascade_100.jsonl`，其 SHA-256 写入运行目录的 `manifest.json`。
2. 先执行 10 条 smoke（建议 7 HS、2 PS、1 NR）：`python examples/experiments/run_communication_error_cascade.py --bootstrap-from-env --limit 10`。
3. smoke 的每次 run 都必须为 `valid`，且 `real_llm_nodes` 恰有五个节点；若模型失败、连接 ID 不一致、LocalEcho/模拟标记出现，脚本保留审计结果并以 non-zero 退出，禁止降级继续统计。
4. smoke 合格后运行全量 100 case × 2 方法：`python examples/experiments/run_communication_error_cascade.py --bootstrap-from-env`。结果在 `rows.jsonl`，逐 case 完整事件在 `cases/`，汇总在 `summary.json`。
5. 仅以 `status=valid` 的 run 为分母计算指标；任何 `invalid` run 必须报告数量与原因，不能填补、重命名为成功或混入两组均值。

| 组别 | N | Aggregator 平均 EAC | Writer ECR | REPR（高相似） | FPR（非重复） | 结论 |
|---|---:|---:|---:|---:|---:|---|
| B0 全文广播 | 100 |  |  | 不适用 | 不适用 |  |
| Ours 低熵通信 | 100 |  |  |  |  |  |

可接受的正向结论：

> 在受控的分叉—汇聚协作图中，低熵通信在不误剪两条非重复信息的前提下，降低了同一错误主张到达汇聚节点的重复次数。它抑制的是错误的重复放大，而非判断首条错误主张的事实真伪。

若 EAC 降低而 ECR 不变，仍是符合当前实现边界的有效结果：说明系统减少了重复污染，但需要额外事实核验或冲突检测模块，才能阻止首条错误继续影响最终回答。
