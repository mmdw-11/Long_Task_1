# 8.2 上下文管理专项最终落地情况

本文用于交接 `docs\华为文档第一部分计划.md` 对应的最终实现结果。重点说明当前系统的上下文完整逻辑、代码落点、运行产物和测试断言，不描述中间迭代过程。

## 一、总体逻辑：上下文不再只靠聊天历史

当前项目已经把“长任务上下文管理”拆成一条独立运行链路：每次任务执行时，系统不再只依赖完整对话历史，而是把关键目标、约束、计划、已完成步骤、待完成步骤、验证事实、未验证假设、失败记录、预算状态和下一步动作写入结构化账本。

核心入口是 `engine/modules/context` 文件夹：

- `engine/modules/context/_types.py` 中的 `ContextLedger` 定义一次 run 的上下文账本结构。
- `engine/modules/context/ledger.py` 中的 `ContextLedgerStore` 负责按 `run_id` 创建、读取、更新和落盘账本。
- `engine/modules/context/renderer.py` 中的 `ContextLedgerRenderer` 把账本渲染成可读的 `MEMORY.md`。
- `engine/modules/context/budget.py` 中的 `ContextBudgetController` 负责上下文预算检查。
- `engine/modules/context/injector.py` 中的 `ContextInjector` 负责把账本重新组织成节点执行前可注入的上下文。
- `engine/modules/context/drift.py` 中的 `DriftDetector` 负责检测重复执行、长时间 pending、无进展等漂移风险。
- `engine/modules/context/policy.py` 中的 `ContextPolicy` 负责把预算、账本、注入、漂移检测等参数配置化。

这套逻辑和长期记忆不是一回事：`engine/modules/memory` 更偏跨任务长期知识，`engine/modules/context` 更偏单次长任务的运行状态，保证任务中断、超预算、验证失败、恢复执行时仍能知道“现在做到哪里、哪些内容可信、下一步该做什么”。

## 二、上下文账本与 MEMORY.md 已落地

`engine/modules/context/_types.py` 中的 `ContextLedger` 当前保存这些字段：

- `run_id`：本次任务 ID。
- `original_goal`：原始任务目标。
- `hard_constraints`：硬约束，例如不能泄漏密钥、坏输出不能合并等。
- `current_plan`：当前计划。
- `completed_steps`：已完成节点，格式类似 `1:collect_requirements`。
- `pending_steps`：待执行节点。
- `key_facts`：关键事实，使用 `ContextFact` 表示，并区分 `verified=True/False`。
- `tool_summaries`：工具或节点输出摘要，长文本会变成摘要加 `raw_ref`。
- `failure_summaries`：最近失败，包括验证失败和漂移记录。
- `budget`：预算使用情况。
- `next_action`：下一步动作。

`engine/modules/context/ledger.py` 中的 `ContextLedgerStore.on_step_start()` 会在每个 superstep 开始时写入 pending 和 next action；`ContextLedgerStore.on_node_end()` 会在节点结束后写入 completed、摘要和事实；`ContextLedgerStore.on_node_error()` 会写入失败摘要。

`engine/modules/context/renderer.py` 中的 `ContextLedgerRenderer.render_markdown()` 会把账本同步渲染为 `MEMORY.md`，固定包含这些章节：

- `Original Goal`
- `Hard Constraints`
- `Current Plan`
- `Completed`
- `Pending`
- `Verified Facts`
- `Unverified Assumptions`
- `Key Files And Resources`
- `Recent Failures`
- `Budget`
- `Next Action`

因此队友接手一个长任务时，不需要翻完整对话，只看对应 run 的 `MEMORY.md` 就能知道任务目标、已完成内容、可信事实、风险点和下一步。

## 三、HookManager 把上下文系统接入执行链路

上下文系统真正生效的位置在 `engine/hooks.py` 的 `HookManager`。

`engine/hooks.py` 中的 `HookManager.on_step_start()` 会先调用 `_update_context_on_step_start()`，把当前 step 和 frontier 写到账本，再调用 `_check_context_budget()` 判断是否超预算。

`engine/hooks.py` 中的 `HookManager.on_node_start()` 会调用 `_inject_memory_context()`，进一步调用 `_inject_context_ledger()`。这一步会把账本注入到状态字段：

- `__context_ledger__`
- `__context_injection__`
- `__context_injection_text__`

也就是说，每个节点执行前都能拿到重新整理后的任务目标、约束、计划、事实和风险，而不是只看越来越长的历史消息。

`engine/hooks.py` 中的 `HookManager.on_node_end()` 会调用后置验证器，并调用 `_update_context_on_node_end()` 写入账本。节点输出只有通过验证后，才会作为 verified fact 沉淀；没有通过验证的内容会作为 unverified assumption 或 failure 记录。

## 四、上下文预算已经能真正阻断执行

预算控制由 `engine/modules/context/budget.py` 中的 `ContextBudgetController` 实现。

它会根据当前 state 粗略估算上下文 token 使用量，并扣除 `reserved_output_tokens`。如果超出 `max_context_tokens - reserved_output_tokens`，就返回不允许执行的决策。

`engine/hooks.py` 中的 `HookManager._check_context_budget()` 会把预算结果写回账本。如果不允许执行，会向 state 写入：

- `__run_status__ = "budget_paused"`
- `__pause_reason__ = "context budget exceeded: ..."`

`engine/graph.py` 中的 `CompiledGraph.astream()` 会在 step 开始后检查 `RUN_STATUS_KEY`。一旦发现 `__run_status__`，就停止继续执行后续节点。因此预算不是只记录日志，而是真的会阻断节点执行。

测试断言位置：

- `tests/test_context_ledger.py` 中的 `test_context_budget_pauses_before_node_execution` 断言超预算时 `state[RUN_STATUS_KEY] == BUDGET_PAUSED`，并断言 `messages` 不存在，说明 worker 没有被假执行。
- `tests/test_server_context_policy.py` 断言 REST 默认 Orchestrator 启用 `ContextPolicy` 后同样能触发 `budget_paused`。
- `tests/test_context_end_to_end_demo.py` 断言 demo 中 `messages_executed is False`，证明预算暂停不是表面状态。

## 五、后置验证失败已经能暂停或改道

后置验证由 `engine/modules/evaluation.py` 中的 `RuleEvaluator` 实现。

当前支持的核心校验包括：

- `required_update_keys`：节点输出必须包含指定 key。
- `required_files`：节点执行后指定文件必须存在。
- `requires_parent_validation`：子 agent 输出必须带有父级确认标记。
- `validation_failure_action`：验证失败后的动作。
- `validation_failure_targets`：验证失败后改道目标。

`engine/modules/evaluation.py` 中的 `ValidationFailureAction` 定义了三种行为：

- `record`：只记录，不阻断。
- `pause`：暂停任务。
- `reroute`：改道到修复节点。

真正控制流生效的位置在 `engine/hooks.py` 的 `HookManager.handle_validation_failure()` 和 `engine/graph.py` 的 `CompiledGraph.astream()`。

机制是：

1. 节点先执行，得到 `update`。
2. `HookManager.on_node_end()` 调用 `RuleEvaluator.evaluate_node()`。
3. 如果验证失败，`HookManager.handle_validation_failure()` 根据 action 返回暂停或改道目标。
4. `engine/graph.py` 在合并 `update` 前检查验证结果。
5. 如果验证失败，坏的 `update` 不会合并进 `GraphState`。
6. 如果 action 是 `reroute`，Graph 会把修复节点加入下一轮 frontier。
7. 如果 action 是 `pause`，Graph 写入 `__run_status__ = "validation_failed"` 并停止。

这解决了“节点表面运行成功，但输出不合格仍进入状态”的假性问题。

测试断言位置：

- `tests/test_context_ledger.py` 中的 `test_post_execution_validation_marks_unverified_and_records_failure` 断言缺少 `final_answer` 时，`result` 不会进入 state，且 `__run_status__ == "validation_failed"`。
- `tests/test_context_ledger.py` 中的 `test_post_execution_validation_can_reroute_without_merging_bad_update` 断言 `bad_result` 不会进入 state，同时会改道执行 `repair` 并产生 `fixed=True`。
- `tests/test_context_end_to_end_demo.py` 断言 demo 中 `bad_result_merged is False`，并断言 `final_answer` 来自修复节点。

补充说明：`engine/hooks.py` 中的 `validation_control_enabled` 做了兼容保护。只有启用 `context_ledger` 或显式传入 evaluator 时，验证失败才会影响控制流。普通 Orchestrator 的基础 echo 子 agent 不会被默认验证规则误拦截。

## 八、漂移检测已接入账本

漂移检测由 `engine/modules/context/drift.py` 中的 `DriftDetector` 实现。

当前主要检测三类问题：

- 同一个节点重复执行超过 `repeat_node_limit`。
- pending 步骤过多，说明任务可能卡住。
- 多步无进展，说明状态可能没有推进。

`engine/hooks.py` 中的 `_update_context_on_node_end()` 会在每次节点结束后调用 `DriftDetector.detect()`。检测结果会写入 state 的 `__context_drift__`，如果发现漂移，还会写入 `ContextLedger.failure_summaries`。

测试断言位置：

- `tests/test_context_ledger.py` 中的 `test_drift_detector_records_repeated_node_pattern` 构造循环节点，断言 `state["__context_drift__"]["drifted"] is True`，并断言账本 failure 里出现 `ContextDrift`。

## 九、长输出压缩与 raw_ref 已落地

长输出压缩由 `engine/modules/context/compressor.py` 中的 `ContextCompressor` 实现。

机制是：节点输出较短时，直接进入摘要；节点输出超过 `long_text_threshold` 时，不把全文塞进 `MEMORY.md`，而是：

1. 生成短摘要。
2. 把原始长输出保存到 raw 文件。
3. 在 `ToolSummary.raw_ref` 中保存引用路径。
4. 在 `MEMORY.md` 的 `Key Files And Resources` 中展示 raw_ref。

这样可以避免长工具结果撑爆上下文，同时保留可追溯原文。

测试断言位置：

- `tests/test_context_ledger.py` 中有关 long output 的测试会断言长文本被压缩，并产生 `raw_ref`。
- end-to-end demo 的 `runs/context_demo/ledger/demo-validation-reroute/MEMORY.md` 中可以看到 `collect_requirements` 和 `repair_answer` 的 raw 文件引用。

## 十三、交接时最需要说明的结论

当前上下文系统不是只写了数据结构，而是已经进入执行主链路：

1. `engine/graph.py` 推进 superstep。
2. `engine/hooks.py` 的 `HookManager.on_step_start()` 写账本、查预算。
3. 超预算时写入 `__run_status__ = "budget_paused"`，Graph 停止执行。
4. 节点执行前，`HookManager.on_node_start()` 注入账本上下文。
5. 节点执行后，`HookManager.on_node_end()` 做后置验证、写入账本、生成 `MEMORY.md`。
6. 验证失败时，`HookManager.handle_validation_failure()` 返回 pause 或 reroute。
7. `engine/graph.py` 在合并 update 前处理验证结果，坏输出不会进入 `GraphState`。
8. 每个 superstep 前，`engine/graph.py` 可通过 `GraphCheckpointStore` 保存 `step/frontier/state`。
9. 恢复时，`CompiledGraph.ainvoke(..., resume_from=...)` 从 checkpoint 恢复 `GraphState`、`frontier` 和 `step`。
10. demo 和测试已经证明“预算阻断、坏输出不合并、验证改道、checkpoint resume、MEMORY.md 产出”都是真实生效，不是只记录日志。

需要谨慎表述的是路由模型：代码已经支持 MLP + 对比微调优先策略，但当前对比微调最终模型文件不完整，生产实际使用的是 MLP fallback。
