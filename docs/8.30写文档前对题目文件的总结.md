# XH-202631 题目文件总结

> 依据：荣耀终端股份有限公司《面向超长程复杂任务的动态异构群体智能架构与深度协同推理技术比赛方案》。
>
> 用途：作为撰写本项目技术说明、比赛材料和论文时的需求基线。下文按题目文件的原有顺序整理，并将“必须满足的要求”和“写作时应提供的证据”分开说明。

## 一、发榜单位

发榜单位为荣耀终端股份有限公司，企业类型为国有企业，地址位于深圳市福田区香蜜湖街道东海社区红荔西路 8089 号。

这一信息说明题目关注的是面向终端生态和真实产业环境的通用智能系统，而不是只在实验室中运行的单一模型 Demo。后续材料应突出终端、边缘和云端协同，以及可部署、可演示、可扩展的工程属性。

## 二、题目名称

题目名称为：

> 面向超长程复杂任务的动态异构群体智能架构与深度协同推理技术

题目名称包含四个不可拆分的关键词：

1. **超长程复杂任务**：任务必须跨越多轮决策、多个节点和较长时间跨度，不能只展示一次问答或三步链式调用。
2. **动态**：任务执行过程中，系统应能根据状态变化、需求变化、故障和资源变化调整计划与协作关系。
3. **异构群体智能**：群体由能力、角色、模型、部署位置或工具权限不同的 Agent 构成。
4. **深度协同推理**：Agent 之间不仅传递文本，还要共享结构化状态、证据、约束、计划和反馈，形成可解释的协同闭环。

## 三、题目介绍

### 3.1 题目背景

题目将大模型的发展描述为从偏向即时响应的“System-1”式能力，向具备慢思考、规划和自主行动能力的“System-2”式自主通用智能体演进。产业和科研中的需求，也从单一环节提效，转向由 AI 自主完成超长程复杂决策流，例如：

- 系统级软件工程的自动化构建；
- 跨域、多源、模态异构数据的深度投研；
- 全域终端的统筹操控；
- 其他需要连续规划、工具调用和多阶段交付的复杂任务。

这类任务具有节点多、状态空间大、模态异构、依赖关系复杂等特点，需要系统跨越数百次逻辑拓扑流转，保持深度耦合的任务状态和长效时序规划能力。

### 3.2 现有技术的底层瓶颈

题目明确指出了三类直接瓶颈和一个系统性缺口。

#### （1）单体智能体的记忆与上下文瓶颈

单体 Agent 在长任务中会遭遇上下文膨胀、注意力稀释和记忆坍缩。随着历史信息累积，模型可能遗忘全局目标、丢失中间决策，或把旧状态误当成新状态。因此，系统不能只依赖单一模型不断扩大上下文窗口，而必须设计分布式记忆、上下文压缩和按需唤醒机制。

#### （2）刚性多 Agent 网络的通信瓶颈

传统多 Agent 系统常使用固定流水线、静态组队或密集通信。长程任务中的密集交互会导致 Token 冗余爆炸、噪声级联放大和决策混乱。题目要求根据任务语义动态生成稀疏路由，并通过信息瓶颈或结构化消息协议降低通信熵。

#### （3）异构资源利用不足

终端、边缘与云端在时延、算力、成本和数据敏感性方面不同。现有系统缺少根据子任务实时性、复杂度和隐私等级进行推理位置选择与模型切分的能力，因而无法充分利用云端处理高复杂度任务，也无法在端侧保护敏感数据。

#### （4）缺少内生自治闭环

系统还需要解决图结构动态路由、分布式协同推理、节点失效、需求变更和异常注入等问题。仅有静态工作流、单次规划或人工介入的重试，不能满足题目要求的高鲁棒自治引擎。

### 3.3 题目目标

赛题目标是探索下一代通用群体智能的底层架构与协同推理微基座，要求参赛者：

1. 打破单体模型的能力边界；
2. 摒弃仅依赖静态流水线的多 Agent 编排；
3. 构建具备全局动态任务编排和自适应网络拓扑的 Agent 生态网络；
4. 重点解决超长周期上下文连续性、神经符号协同推理和低熵通信；
5. 最终实现从高维、模糊的自然语言意图，到复杂非确定性环境中的全域自动化、高可靠闭环交付。

这里的“动态”不仅指条件分支。论文和演示应说明通信边、活跃 Agent、任务分解、资源位置和恢复路径如何随运行事件变化。

### 3.4 选题意义

#### 技术意义

题目聚焦群体智能协作这一 AGI 前沿方向，试图解决智能系统从“单点交互”走向“系统化自主执行”时的关键底层问题。参赛作品应同时具备理论设计、核心算法、运行时机制和可验证的工程实现，为高鲁棒、高可信智能系统提供基础。

#### 经济与社会效益

题目期待形成可复用的“数字劳动力”协作平台，降低复杂业务中的智力成本，推动产业从数字化向智能化转型，并支持 AI 自动开发、智能决策辅助等应用。项目介绍不能只写模型指标，还应交代跨行业复用能力、用户体验、产业落地和社会价值。

## 四、参赛对象

学生赛道面向 2026 年 6 月 1 日以前正式注册的国内全日制普通高校在校专科生、本科生、硕士和博士研究生，以及全日制职业教育本科、高职高专在校学生，不含在职研究生。

参赛可以个人或团队形式进行，每队不超过 10 人，每件作品不超过 3 名指导教师；允许跨专业、跨学校、跨地域组队，但每件作品只能由 1 所高校作为参赛主体提交。

本部分属于报名资格要求，不直接决定技术论文结构，但材料中应保持队伍和申报主体信息一致。

## 五、答题要求

题目要求作品由“材料文档”和“可运行系统”两部分组成，且两者必须共同证明系统能够在无人工干预下完成多 Agent 长程协作闭环。要求分为能力维度、场景验证和交付物规范。

### 5.1 超长程上下文连续性与记忆保持

系统必须在跨越多轮决策流转的长程任务中：

- 克服注意力稀释和记忆坍缩；
- 保存关键任务信息；
- 保存中间决策结果；
- 保存全局目标和硬约束；
- 避免状态丢失和语义漂移；
- 不依赖单一模型的长窗口无损外推。

因此，设计中至少要出现分布式或分层记忆、上下文压缩、上下文唤醒、状态账本、漂移检测和检查点恢复。实验中应分别测量任务成功、目标保持、约束遵守、记忆使用准确率、漂移率、Token 消耗和恢复成功率。

### 5.2 动态异构拓扑与低熵通信

群体必须包含多种异构能力的 Agent 角色。通信拓扑不能预设成静态全连接，也不能只把一条固定流水线称为动态协作。系统应：

- 根据任务语义动态生成稀疏路由；
- 在任务状态、证据、失败或预算变化时重构协作边；
- 控制通信冗余和噪声级联；
- 通过信息瓶颈、结构化消息或等价机制降低信息熵；
- 保持高价值证据、约束和决策能够到达正确的接收者。

论文需给出拓扑决策算法、消息结构、边或消息的选择依据，以及边密度、Token、冗余率、消息有效率、信息熵和错误传播率等可量化指标。

### 5.3 端—边—云异构资源自适应调度

系统须适配终端、边缘和云端异构算力环境，并根据以下因素自动决定推理位置或模型切分：

- 子任务实时性；
- 数据敏感等级；
- 任务复杂度；
- 资源可用性；
- 网络时延和带宽；
- Token/API 成本；
- 节点健康状态。

系统应充分利用云端算力处理复杂子任务，同时在端侧或边缘侧完成敏感数据脱敏和最小必要信息提取。论文需要说明调度目标、约束、算法和真实或可复现的资源测量方式。

### 5.4 评测场景要求

参赛方案必须在典型产业场景中完成可运行系统验证。仅展示抽象图结构或离线伪造轨迹不够。至少应准备两个高完成度、跨领域的长程任务，展示中途事件注入、拓扑变化、消息流转、资源迁移、异常恢复和最终交付。

适合当前项目的两个场景是：

1. **跨应用办公与终端助理**：邮件、日历、浏览器和文档协同，中途注入权限拒绝、日程冲突或优先级改变。
2. **软件工程自治交付**：需求分析、代码检索、实现、测试、修复和报告生成，中途注入测试失败、依赖不可用或约束变化。

### 5.5 材料文档要求

材料文档必须系统阐述：

- 群体智能总体架构；
- 动态拓扑路由算法；
- 记忆保持与上下文连续性机制；
- 低熵通信和协同推理协议；
- 端—边—云协同调度方法；
- 异常、需求变更和节点失效下的自治恢复机制；
- 核心算法伪代码；
- 时间、空间、通信或调度复杂性分析；
- 实验场景、基线、指标和结果解释。

### 5.6 可运行系统要求

系统必须具备可部署环境，能够接受运行过程中的：

- 动态异常注入；
- 用户需求变更；
- Agent 节点失效；
- 资源状态变化；
- 权限或工具调用失败。

在无人工干预下，系统应从高层意图出发，完成规划、执行、反馈、修复和最终交付，并展示中间决策过程与推理轨迹。前端可视化、SSE 事件、运行记录、检查点和可回放轨迹都是证明这一要求的重要载体。

## 六、作品评选标准

初审和终审采用相同评分标准，初审和终审分数占比分别为 40% 和 60%。总分由完整性、应用创新性、技术创新性、系统性能与效率四部分构成。

### 6.1 作品完整性：40 分

#### 系统基础与闭环能力：15 分

重点评估系统是否独立研发并具备完整的“感知—规划—执行—反馈”闭环，并考察其在数千步复杂任务中能否自主完成任务，过程中不能出现明显的过程遗忘或规划幻觉。

写作证据应包括：任务状态图、事件注入过程、长程轨迹、最终判定器和多随机种子结果，而不应只给出一次成功截图。

#### 组织架构与协作机制：15 分

重点评估是否引入层级、分工和组织管理思想，是否摒弃静态组队和无序自由通信，以及分工协作流程是否清晰。当前项目的父子 Agent、角色能力、动态拓扑和消息接收者选择应在此部分形成主线。

#### 多任务场景演示：10 分

评分由任务数量、领域跨度、完成度和泛化/组合能力决定。最高档要求成功演示 2 个及以上高完成度跨领域长程任务，并体现较强泛化或组合能力。

### 6.2 应用创新性：25 分

#### 场景覆盖与业务契合度：10 分

应从脱离实际需求、局限单一领域，提升到能够支撑多行业数字劳动力的平台潜力。项目介绍需把软件工程、办公终端、旅行规划等示例组织成可迁移的能力，而不是孤立 Demo。

#### 社会价值与经济效益：10 分

应说明系统如何降低复杂任务中的人工智力成本、提升生产效率、缓解劳动力结构性短缺，并具备何种商业化和产业转化潜力。

#### 用户体验与易用性：5 分

应提供交互友好、逻辑清晰的可视化界面，降低用户编排和使用门槛，并能够让用户理解任务进度、当前决策和最终结果。当前项目的 AgentForge Console、工作流编辑器、运行中心和事件轨迹可作为直接支撑。

### 6.3 技术创新性：20 分

#### 架构与交互降噪创新：10 分

重点考核群体交互中是否有效抑制冗余信息，是否通过信息过滤、结构化协议和路由选择解决决策混乱的“巴别塔”问题。论文必须把“低熵”定义成可测量机制，而不是宣传性形容词。

#### 核心算法与底层突破：10 分

重点考察长上下文管理、注意力衰减缓解、高质量多 Agent 数据集或其他底层算法是否具有原创性。直接套用开源框架只能作为基础分，必须说明自研控制器、协议、记忆、验证和调度机制的差异。

### 6.4 系统性能与效率：15 分

#### 执行成功率与鲁棒性：5 分

要求量化长周期任务的稳定性、自主纠错能力和任务成功率。应报告故障类型、恢复路径、恢复成功率、失败传播率和最终交付判定。

#### 资源效率：5 分

考察 Token、时间及其他计算成本。应报告平均值、P95 或 P99、Token 消耗、消息数量、边密度、API/算力成本和任务成功率之间的权衡。

#### 系统兼容性与可扩展性：5 分

考察是否兼容多种基础大模型，是否能灵活增删 Agent 角色，以及是否支持端、边、云和不同工具连接。当前项目的模块化 Hook、Agent 工厂、REST API、工作流导入导出和前端控制台可支撑这一评分点。

## 写作时的硬约束清单

最后，将题目要求压缩为论文和演示必须同时回答的十个问题：

1. 系统如何从自然语言意图形成任务图和子任务？
2. Agent 角色如何异构化、分工和形成层级组织？
3. 通信边为什么建立、删除或保留？
4. 消息如何压缩、校验和避免冗余传播？
5. 长程任务中目标、约束、证据和中间决策如何保持？
6. 需求变化、节点失败、工具失败和资源变化如何触发恢复？
7. 为什么某个子任务在端、边或云执行？
8. 如何展示无人工干预的感知—规划—执行—反馈闭环？
9. 如何用跨领域场景和可机读判定器证明任务成功？
10. 如何用成功率、鲁棒性、Token、时间、消息熵、边密度和成本证明系统有效？

后续论文的章节、算法伪代码、实验表格和演示脚本均应能回溯到上述问题，避免只描述功能而没有题目要求对应关系。
