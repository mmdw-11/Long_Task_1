## 一、漂移检测的详细流程
系统现在会给每次任务记住：用户最开始的总目标是什么、当前计划有哪些步骤、现在正在做哪一个 todo、哪些步骤已经完成、刚才 Agent 做了什么、有没有失败或异常。

任务开始时，给了一个总目标和计划，比如：
```
目标：改进语义漂移检测并补充文档
计划：检查现状、修改逻辑、补文档、跑测试
```
系统会把这些计划变成结构化 todo：
```
当前正在做：检查现状
后面还有：修改逻辑、补文档、跑测试
```
然后每次 Agent 执行前，系统都会把这些信息提醒给它：总目标是什么、当前应该做哪一步、前后还有哪些步骤。如果它发现计划不合理，也可以建议修改 todo。

Agent 执行完一步后，系统会把它刚刚做的事情记到账本里。然后漂移检测开始工作。

**漂移检测分两层**：

第一层是规则检测，主要抓“卡死”或“原地打转”的情况。比如：

同一个节点反复执行
同一个工具反复调用
同一个文件反复修改
输出内容连续几次几乎一样
一直有 pending 但没有完成进展
这些情况不用大模型判断，规则就能发现。如果命中，就认为出现了结构性漂移或死循环。

第二层是语义检测，判断 Agent 有没有跑题。
现在改成了让 LLM 判断。LLM 看三样东西：

总目标
当前 todo 计划
Agent 刚刚做的事情
然后让它判断三种情况：

1. on_track
   当前动作服务于当前 todo 或整体任务，没跑偏。

2. todo_update_needed
   当前动作不是严格按原计划走，但它是在合理调整计划，比如发现需要补一个测试步骤。
   这种不算漂移。

3. drifted
   当前动作和任务主线无关，比如本来要改漂移检测，却去写旅行攻略。
   这种才算真正语义漂移。
   如果 LLM 判断是 on_track，系统什么也不拦。

如果判断是 todo_update_needed，就看当前模式：

suggest 模式：
只记录“建议修改 todo”，不真的改计划。

auto 模式：
在安全范围内自动改 todo，比如插入一步、取消一步、切换当前步骤、标记完成。
如果判断是 drifted，系统会把这次漂移记录下来，运行结果里会看到 drifted=true，账本里也会留下失败记录，方便后面排查。

---

所以最简单地说，现在的漂移检测就是：

先看 Agent 有没有原地打转；
再看 Agent 当前动作是不是服务当前 todo；
如果只是合理改计划，不算漂移；
如果完全跑去做无关事情，才算漂移。
它的核心变化是：
不再用“当前动作像不像总目标”来粗暴判断，而是用“当前动作是否服务当前待办步骤”来判断。

## 二、todo部分的详细流程

**核心关系**：

`plan` 是用户或系统给的原始计划列表，`todo` 是系统把 `plan` 结构化之后得到的可追踪待办项，`suggest` 是“AI 认为计划需要改，但只提建议不动手”，`auto` 是“AI 认为计划需要改，并在受限规则下自动修改 todo”。

对应到一个 AI 功能界面，理解：

`goal` 像页面顶部的“总目标”。
`plan/current_plan` 像初始任务清单。
`todo_items` 像任务列表，每项有状态。
`active_todo` 像当前正在执行的任务。
`todo_update_needed` 像 AI 弹出的“建议调整任务清单”。
`suggest` 像只显示建议，不自动改。
`auto` 像 AI 有权限自动插入、替换、取消或切换任务。
`todo_events` 像操作日志，记录 todo 怎么被改过。
`open_questions` 像通知/提醒区，放“建议你更新计划”的消息。

### 1. plan 从哪里来

运行一开始从输入 state 里取：

```python
goal = original_goal / goal / task / input / query
plan = current_plan / plan
```
即如果调用图时传入：

```python
{
  "goal": "ship the feature safely",
  "current_plan": ["inspect code", "implement change"]
}
```

系统会把 `goal` 存成 `ledger.original_goal`，把 `current_plan` 存成 `ledger.current_plan`。

### 2. plan 变成 todo
规则：
如果 `ledger.todo_items` 还没有，但 `ledger.current_plan` 有内容，就把每个 plan item 变成一个 `TodoItem`：

```python
todo-1: inspect code
todo-2: implement change
```

第一项会自动变成当前活动项：

```python
todo-1 [in_progress] inspect code
todo-2 [pending] implement change
```

状态字段合法状态有：

`pending`、`in_progress`、`completed`、`blocked`、`cancelled`

所以 `plan` 更像“原始清单”，`todo_items` 才是运行时真正拿来跟踪、展示、判断漂移的结构化任务列表。

### 3. todo 进入 AI 的上下文

每个节点执行前，系统会构建一段 `Context Injection`。
它会把这些内容塞进节点上下文：

`Original Goal` 
`Current Step Objective`  
`Active Todo`  
`Nearby Todos` 
`Completed Todos` 
`Todo Policy`

其中 `Todo Policy` 明确告诉 AI：

```text
Work on the active todo. If the plan is incomplete or stale,
suggest a todo update instead of silently changing direction.
```
AI 应该围绕 active todo 工作；如果发现计划不完整或过期，应该建议更新 todo，而不是自己偷偷换方向。

换成界面语言就是：执行器界面左侧有任务清单，中间高亮当前任务，AI 每一步都能看到“现在应该做哪一项”和“旁边还有哪些任务”。

### 4. LLM Judge 判断 todo / plan 是否需要更新

节点执行结束后，漂移检测器会运行。它会把三个东西交给 LLM judge：

`original_global_goal`：总目标  
`task_plan_list`：当前 todo/plan  
`current_step_content`：当前节点刚刚做了什么

如果有 `todo_items`，它会传这种格式：

```text
todo-1 [ACTIVE] inspect code
todo-2 [pending] implement change
```

如果还没有 todo，则退回传 `current_plan`。

LLM judge 不是只看“当前动作 vs 总目标”，它还看“当前动作是否服务 active todo、相邻 todo 或整个计划”。这就是为什么“补测试”这种低相似度子任务不会轻易被误判为漂移。

### 5. Judge 的三种 decision

LLM judge 返回的是 `TaskDriftJudgeResult`。

它支持三种 `decision`：

`on_track`：当前动作没跑偏，继续。 
`todo_update_needed`：没跑偏，但计划需要更新。 
`drifted`：当前动作真的偏离任务目标。

这三者的区别非常关键。

`on_track` 表示：“这一步虽然可能只是小步骤，但它服务当前任务。” 
例如目标是“修复漂移检测”，当前动作是“补一个测试”。这不是漂移。

`todo_update_needed` 表示：“这一步不是坏事，但现有计划漏了它，应该把它纳入 todo。” 
例如计划是 `inspect code -> implement change`，但 AI 发现中间必须先 `write tests`。这不算跑偏，只是计划需要维护。

`drifted` 表示：“这一步已经离开主线。” 
例如目标是“修复上下文漂移检测”，当前动作却变成“写周末旅行攻略”。

### 6. suggest 模式：只建议，不改 todo

`suggest` 是默认模式

系统不会真的插入 `write tests`。
如果不是 auto，就会写入：

```python
ledger.open_questions.append("TodoUpdateSuggested: ...")
```

也就是界面上的“待确认建议”。

测试也验证了这一点：[test_context_ledger.py]
测试里原计划是：

```python
["inspect code", "implement change"]
```

judge 建议插入：

```python
"write tests"
```

但因为是 suggest 模式，最后断言 todo 没变：

```python
["inspect code", "implement change"]
```

只是在 `open_questions` 里出现 `TodoUpdateSuggested`。

界面上可以理解为：AI 弹出“建议在 inspect code 后加入 write tests”，但需要用户或上层控制器确认。【目前只是数据层实现，之后改进交互点】

### 7. auto 模式：自动改 todo，但只能做受限动作

```python
todo_update_mode="auto"
```

当 judge 返回 `todo_update_needed`，`HookManager` 会走 `_apply_todo_updates()`。

它只允许这些动作：

`insert`：插入一个 todo 
`replace`：替换一个 todo 内容 
`cancel`：取消一个 todo  
`complete`：标记完成 
`select`：切换 active todo

这些动作最后都委托给todo.py的 `TodoManager`。
测试在test_context_ledger.py。原计划：

```python
["inspect code", "implement change"]
```

judge 建议：

```python
insert after todo-1: write tests
```

因为开启 auto，最后 todo 变成：

```python
["inspect code", "write tests", "implement change"]
```

并且 `todo_events` 最后一条是：

```python
action == "insert"
```

界面上理解为：AI 不只是弹建议，而是直接把任务清单改了，同时在操作日志里记一笔，方便审计。

### 8. todo 改动同步回 plan

这个设计里，`current_plan` 和 `todo_items` 不是两套完全独立的数据。每次 todo 改动后，`TodoManager._sync_current_plan()` 会把未取消的 todo 内容同步回 `ledger.current_plan`。

所以：

```python
todo_items = [
  todo-1 inspect code,
  todo-3 write tests,
  todo-2 implement change
]
```

会同步成：

```python
current_plan = [
  "inspect code",
  "write tests",
  "implement change"
]
```

这保证了旧系统看 `current_plan` 也能拿到最新计划，新系统看 `todo_items` 则能拿到更丰富的状态、id、revision 和审计记录。

### 9. active todo 流转

`active_todo_id` 表示当前该做哪一项。

初始化时第一项自动 `in_progress`。
当一个 active todo 被标记为 `completed`、`blocked` 或 `cancelled`，`TodoManager` 会自动选择下一个 pending todo 作为 active。

这就是界面里的“完成当前任务后，自动高亮下一项”。

### 10. 漂移和 todo_update_needed 的区别
`todo_update_needed` 不是漂移。

它的判断边界是：

“计划需要补一项” → 不是漂移，是 todo 更新建议。 
“当前动作不服务目标也不服务计划” → 是漂移。 
“当前动作服务 active todo 或相邻 todo” → 正常。

---
注：
+ 漂移后不会自动暂停或改道：当前是“检测和记录已完成”，但“漂移后自动控制执行流”还没形成闭环。
+ auto模式的安全权限还比较简单，可以设计更安全的细化策略。
+ 系统没有自动判断“当前节点完成了 active todo，所以标记 completed”
+ 根据执行结果自动完成 todo的智能推进还没有完整实现
+ suggest的这个用户交互确认的接口等还不完善：没有 suggestion id、状态、创建时间、来源 judge、待应用 patch 等结构化字段；
没有“接受/拒绝/编辑后接受”的后端 API；
没有把 suggest 建议重新应用到 TodoManager 的确认流程等。

## 三、父agent、子agent的validated规则，整个流程

当前项目总体流程：先由外部编排器/代码/前端把 agent 和图结构建好，再把用户 prompt 作为输入丢进这张已经编译好的图里运行。

### 1. 先有编排
> 编排的意思就是：把一堆 agent / 节点安排成一张工作流程图。

核心类是 Orchestrator，它负责做这些事：
```
create_agent()       创建一个 agent
add_sub_agent()      声明某个 agent 是另一个 agent 的子 agent
connect()            声明 agent 之间的执行顺序
connect_conditional() 声明条件分支
set_entry()          设置入口 agent
build_graph()        把声明好的结构编译成可运行图
```
也就是说，agent 结构一般是在运行前建好的。

比如：
```
planner
  ├─ researcher
  └─ writer

reviewer
```
这棵父子关系树不是 prompt 自动生成的，而是代码或前端提前调用 create_agent() / add_sub_agent() 建出来的。

---

这里的节点 node = 图里可执行的一个步骤，可以是：
```
一个 agent
一个普通 Python 函数
一个工具执行器
一个子图
一个检查/路由/修复节点
```
比如 agent 节点：
```
researcher 节点 = 调用 researcher agent 去做调研
writer 节点 = 调用 writer agent 去写内容
```
普通函数节点：
```
load_email 节点 = 读取一封邮件
classify_email 节点 = 调用本地函数分类
finalize_email 节点 = 汇总处理结果
```
### 2. 父子关系和执行关系

add_sub_agent(parent, child) 表示child 归属于 parent。

带来效果：
```
用于前端可视化层级
给 child 加 parent_id / parent_name
给 child 标记 is_sub_agent=True
给 child 标记 requires_parent_validation=True
默认可以自动加一条 parent -> child 的边
```
真正决定“谁先运行、谁后运行”的，是图里的边：
```
orch.connect(parent, child)
orch.connect(child, reviewer)
```
所以：
```
父子关系 = 组织归属 / 管理关系
执行边 = 实际运行顺序
```
一个 agent 可以是某个 parent 的子 agent，但如果没有正确连接执行边，它不一定会按你想象的方式执行。

### 3. 给 prompt 后，prompt 只是输入，不会自动改图

运行时一般是这样：
```
graph = orch.build_graph()
state = graph.invoke({"input": "请帮我写一篇 AI 教育报告"})
```
这里的 prompt："请帮我写一篇 AI 教育报告"只是进入图执行时的初始 state。它会被入口 agent 读取，然后沿着已经定义好的图结构传递。

**当前项目不会自动做这件事【改进点】**：
```
看到 prompt
  -> 自动判断需要 researcher、writer、reviewer
  -> 自动创建它们
  -> 自动决定父子关系
  -> 自动连接执行流
```
之后需要再加一个“上层 planner / runtime orchestrator”。

### 4. 当前执行流程

以 multi_agent_workflow 里的结构为例：[即编排出的执行图]
```
planner -> researcher
planner -> writer
researcher -> reviewer
writer -> reviewer
```
展开即：
```
        ┌─> researcher ─┐
planner ┤               ├─> reviewer
        └─> writer ─────┘
```
执行大概是：

1. 用户输入进入全局 state

这个全局state可以理解成：整张执行图共享的一张任务白板 / 工作台记录本。
每个节点执行时都会读它，执行完后再往里面写入自己的结果。

比如一开始用户给了 prompt：
```
{
  "input": "写一篇 AI 教育报告"
}
```
这就是初始全局 state。

然后 planner 执行完，返回：
```
{
  "plan": "先调研，再写作，再审稿",
  "messages": [{"agent": "planner", "text": "我会先拆成三个步骤..."}]
}
```
系统会把它合并进全局 state，变成：
```
{
  "input": "写一篇 AI 教育报告",
  "plan": "先调研，再写作，再审稿",
  "messages": [
    {"agent": "planner", "text": "我会先拆成三个步骤..."}
  ]
}
```
然后 researcher 执行时，它能看到这些内容：
```
input
plan
messages
```
它执行完可能返回：
```
{
  "research_notes": "AI 教育的关键点包括个性化学习、教师辅助、隐私风险...",
  "messages": [{"agent": "researcher", "text": "..."}]
}
```
全局 state 又变成：
```
{
  "input": "写一篇 AI 教育报告",
  "plan": "先调研，再写作，再审稿",
  "research_notes": "AI 教育的关键点包括...",
  "messages": [
    {"agent": "planner", "text": "我会先拆成三个步骤..."},
    {"agent": "researcher", "text": "..."}
  ]
}
```
所以它的作用是：
```
保存用户输入
保存每个节点的输出
保存中间结果
保存上下文
保存执行状态
保存验证结果
保存错误记录
保存父级授权记录
```

2. planner 执行，读取 input，输出规划
3. planner 的输出合并进全局 state
4. researcher 和 writer 读取已有 state，各自执行
5. researcher / writer 输出合并或等待验证
6. reviewer 读取前面结果，输出最终审稿
7. 图结束，返回最终 state
全局 state 可以理解为一张共享白板。

每个节点执行时都会看到当前白板内容，然后返回一小块 update。系统再把 update 合并回白板。

### 5. 子 agent 的结果为什么要父级验证

因为子 agent 可能只是做中间工作。

比如 researcher 输出了一段资料，但它可能不完整、偏题、未经确认、只是草稿、包含错误。如果直接把它合并进全局 state，后面的 writer / reviewer 可能把它当成可靠事实继续使用。

所以项目里设计了两个字段：
```
requires_parent_validation
__parent_validation__
```
它们分别表示两件事。

requires_parent_validation 是节点 metadata 里的规则开关：这个 agent 的输出是否必须经过父级放行？

子 agent 默认会被标记：`requires_parent_validation = True`

__parent_validation__ 是运行时全局 state 里的授权记录：
```
{
  "__parent_validation__": {
    "child": {"approved": true}
  }
}
```
它表示：这一次运行里，child 的输出已经被父级/编排器批准，可以进入全局 state。

所以判断逻辑是：如果节点不需要父级验证->正常合并输出;如果节点需要父级验证：
```
  检查 state.__parent_validation__
  有 approved=True：
    合并输出
  没有：
    拦截输出，不让它污染全局 state
```
### 6. 现在父 agent 是否真的检查了正确性【改进点】

目前没有完整做到。

当前系统做的是“门禁”：有没有父级授权？
但还没有真正实现：
```
父 agent 读取子 agent 结果
  -> 判断是否正确
  -> 判断是否完整
  -> 判断是否契合目标
  -> 再写入 __parent_validation__
```
也就是说，当前 __parent_validation__ 更像是一个“放行凭证”，不是自动质量审查结果。

如果要做完整闭环，设想了一个流程：
```
child 执行
  -> child 输出暂存
  -> parent/reviewer 读取 child 输出
  -> parent 判断正确性、完整性、目标契合度
  -> parent 写入 __parent_validation__
  -> 系统再决定是否合并 child 输出
```
当前项目只完成了后半部分的门禁机制，还没有完整的父级审查 agent 流程。

### 7. 当前项目真正支持的模式

当前支持的是这种：
```
运行前：
  开发者/前端/外部编排器创建 agent
  声明父子关系
  声明执行边
  编译成图
```
```
运行中：
  图按已定义结构执行
  每个 agent 读取 state
  每个 agent 返回 update
  系统做合并、路由、验证、上下文记录
```
不支持完整的这种：【改进点】
```
运行中：
  父 agent 自己分析任务
  自己创建子 agent
  子 agent 再创建孙 agent
  图结构动态扩展
  自动重编译继续执行
```
### 8. 设想方案

**第一阶段：规划 agent**

用户 prompt
  -> meta-planner agent 分析任务
  -> 输出结构化计划
比如输出：

{
  "agents": [
    {
      "name": "researcher",
      "role": "资料调研",
      "parent": "planner"
    },
    {
      "name": "writer",
      "role": "写作整合",
      "parent": "planner"
    },
    {
      "name": "reviewer",
      "role": "质量审查",
      "parent": null
    }
  ],
  "edges": [
    ["planner", "researcher"],
    ["planner", "writer"],
    ["researcher", "reviewer"],
    ["writer", "reviewer"]
  ]
}
**第二阶段：外部 Orchestrator 建图**

读取 JSON
  -> create_agent()
  -> add_sub_agent()
  -> connect()
  -> build_graph()

**第三阶段：执行图**

把用户原始 prompt 放入 state
  -> 运行 planner/researcher/writer/reviewer
  -> 父级或 reviewer 做质量检查
  -> 写入 __parent_validation__
  -> 合并通过验证的结果

---
总结：
当前项目的真实状态是：
有 agent 图执行框架
有静态创建 agent 的 Orchestrator
有父子归属关系
有子 agent 输出门禁
有上下文 ledger / drift / todo 等长任务辅助能力

但还没有：
prompt 自动生成 agent 结构
父 agent 运行时动态创建子 agent
递归创建孙 agent
父 agent 自动审查子 agent 结果质量
根据审查自动写入 __parent_validation__

## 四、命令
昨天测试命令的详细解释：
用真实 REST 服务跑一次“正常任务”和一次“跑偏任务”，验证 DeepSeek 这个 `TASK_DRIFT_*` 模型是否真的参与了语义漂移判断。

**第一段：创建一个 Agent**
```powershell
$agent = Invoke-RestMethod `
  -Method Post `
  -Uri "http://127.0.0.1:8000/api/agents" `
  -ContentType "application/json; charset=utf-8" `
  -Body (@{
    name = "worker_ds"
    description = "处理真实业务任务"
  } | ConvertTo-Json -Compress)

$agent
```
向本地服务 `http://127.0.0.1:8000` 发一个 POST 请求，创建一个叫 `worker_ds` 的 agent。

**第二段：设置图入口**
```powershell
Invoke-RestMethod `
  -Method Post `
  -Uri "http://127.0.0.1:8000/api/graph/entry" `
  -ContentType "application/json; charset=utf-8" `
  -Body (@{
    agent_id = $agent.id
  } | ConvertTo-Json -Compress)
```
告诉系统，这个 agent 是执行图的入口节点。

也就是说后面 `/api/run` 执行任务时，会从这个 `worker_ds` 开始跑。

**第三段：跑一个正常任务 on-task**
```powershell
$onTask = Invoke-RestMethod `
  -Method Post `
  -Uri "http://127.0.0.1:8000/api/run" `
  -ContentType "application/json; charset=utf-8" `
  -Body (@{
    input = @{
      run_id = "ds-on-task"
      goal = "改进语义漂移检测并补充文档"
      current_plan = @("检查配置", "补充文档")
      input = "检查 configs/context_policy.yaml 是否打开 semantic_drift_mode"
    }
  } | ConvertTo-Json -Depth 10 -Compress)

$onTask.state.__context_drift__ | ConvertTo-Json -Depth 20
```

这段是在执行一个真实业务任务。
传给系统的信息是：

```text
run_id: ds-on-task
总目标: 改进语义漂移检测并补充文档
计划: 检查配置、补充文档
当前输入: 检查 configs/context_policy.yaml 是否打开 semantic_drift_mode
```

这个当前输入明显服务于总目标，因为检查配置就是改进漂移检测的一部分。

所以返回：

```json
"drifted": false,
"severity": "none"
```

意思是：没有检测到漂移。

里面还有：

```json
"semantic_drift_mode": "llm"
```

说明语义漂移检测当前是 LLM 模式。

```json
"task_drift_judge": "OpenAITaskDriftJudge"
```

说明用了 OpenAI-compatible 的真实模型 judge，也就是我们配置的 DS 接口。

```json
"task_drift_judge_result": {
  "is_task_drift": false,
  "reason": "..."
}
```

说明模型判断结果是：不是任务漂移。

**第四段：跑一个跑偏任务 off-task**
```powershell
$offTask = Invoke-RestMethod `
  -Method Post `
  -Uri "http://127.0.0.1:8000/api/run" `
  -ContentType "application/json; charset=utf-8" `
  -Body (@{
    input = @{
      run_id = "ds-off-task"
      goal = "改进语义漂移检测并补充文档"
      current_plan = @("检查配置", "补充文档")
      input = "写一份周末旅行攻略，推荐酒店和餐厅"
    }
  } | ConvertTo-Json -Depth 10 -Compress)

$offTask.state.__context_drift__ | ConvertTo-Json -Depth 20
```

这段是在故意测试跑偏。

你传给系统的信息是：

```text
总目标: 改进语义漂移检测并补充文档
计划: 检查配置、补充文档
当前输入: 写一份周末旅行攻略，推荐酒店和餐厅
```

“写旅行攻略”跟“改进语义漂移检测”完全无关。

所以返回：

```json
"drifted": true,
"severity": "medium"
```

意思是：检测到了漂移，严重程度 medium。

`reasons` 里有：

```text
semantic drift from task goal: ...
```

意思是：这是任务目标语义漂移，不是重复节点、重复工具那种结构性漂移。


```json
"task_drift_judge_result": {
  "is_task_drift": true,
  "reason": "..."
}
```

说明真实模型判断：这是任务漂移。

**字段意思解释**

```json
"drifted": false
```

是否发生漂移。`false` 表示没漂移，`true` 表示漂移。

```json
"reasons": []
```

漂移原因列表。没漂移就是空列表。

```json
"severity": "none"
```

漂移严重程度。常见是：

```text
none    没漂移
medium  一条漂移原因
high    多条漂移原因
```

```json
"metadata": {...}
```

调试信息，里面会告诉你这次是怎么判断的。

```json
"semantic_drift_mode": "llm"
```

说明当前用 LLM 做语义漂移判断。

```json
"task_drift_judge": "OpenAITaskDriftJudge"
```

说明用了真实的 OpenAI-compatible 接口。你现在虽然不是官方 OpenAI，但 DeepSeek/GLM 这种兼容接口也走这个类。

```json
"current_step_content": "..."
```

系统拿给 LLM 判断的“当前动作内容”。这里乱码是因为中文编码显示问题。

```json
"task_drift_judge_result": {
  "is_task_drift": true,
  "reason": "..."
}
```

这是模型返回的核心判断。
