## 上下文管理专项实施计划：对应原文档第一部分

原文档第一部分虽然标题是“24 小时持续运行 Agent Harness 环境的容错与恢复机制”，但落到当前项目里，核心确实首先是上下文管理问题。更准确地说，它包含四层：

1. 上下文不丢：避免原始目标、关键变量、历史结论被长对话冲掉。
2. 上下文不漂：避免指令稀释、注意力漂移和模型逐步偏离目标。
3. 上下文不污染：避免一次工具故障、低质量中间结果被后续 agent 当成事实。
4. 上下文可恢复：进程中断、预算耗尽、人工审核后能从压缩状态继续执行。

所以这里建议新增一个专门的 `context` 子系统，不把所有事情都塞进现有 memory 模块。`memory` 更偏长期检索与经验积累；`context` 更偏单次 run 的运行态控制、压缩、预算、注入和一致性维护。

### 1. 建立 Context Ledger：运行期上下文账本

优先级：最高。

#### 目标

为每个 `run_id` 建立一个结构化上下文账本，替代“把所有历史消息继续堆进 prompt”的粗暴方式。

它要记录：

- 原始任务目标。
- 用户硬约束。
- 当前计划。
- 已完成步骤。
- 未完成步骤。
- 关键变量和值。
- 关键文件路径。
- 工具调用摘要。
- 已确认事实。
- 待验证假设。
- 最近失败。
- 当前预算。
- 下一步执行意图。

#### 建议数据结构

新增：

```text
engine/modules/context/
  __init__.py
  _types.py
  ledger.py
  compressor.py
  injector.py
  drift.py
  budget.py
```

核心类型：

```python
@dataclass
class ContextLedger:
    run_id: str
    original_goal: str
    hard_constraints: list[str]
    current_plan: list[str]
    completed_steps: list[str]
    pending_steps: list[str]
    key_facts: list[ContextFact]
    open_questions: list[str]
    tool_summaries: list[ToolSummary]
    failure_summaries: list[FailureSummary]
    budget: ContextBudget
    updated_at: float
```

其中 `ContextFact` 必须区分事实来源和可信度：

```python
@dataclass
class ContextFact:
    text: str
    source: str
    confidence: float
    verified: bool = False
    node: str = ""
    step: int = 0
```

#### 为什么要这样做

原文档提到“上下文溢出与退化”的根因是早期任务指令和关键中间变量被截断。`ContextLedger` 的作用是把关键语义从聊天历史中抽出来，形成可控、可审计、可压缩的运行骨架。

这和当前 `HybridTieredMemoryStore` 不冲突：

- `ContextLedger`：单次 run 的强一致运行态。
- `MemoryStore`：跨 run 的长期记忆、项目知识、技能经验。

#### 代码落点

- 在 `HookManager.on_step_start()` 中读取或初始化 ledger。
- 在 `HookManager.on_node_end()` 中用节点输出更新 ledger。
- 在 `HookManager.on_node_error()` 中写入 failure summary。
- 在 `CompiledGraph.ainvoke()` 初始化时写入 `__context_ledger__` 引用。

#### 验收标准

- 一个长任务运行 20 个节点后，不看完整原始对话，只看 ledger 就能知道任务目标、进度和下一步。
- 关键约束不会因为上下文变长而消失。
- 每条关键事实能追溯到哪个节点、哪个 step 产生。

### 2. 生成和维护 `MEMORY.md` 运行摘要

优先级：最高。

#### 目标

为每个 run 生成一个人类可读、模型可注入的运行摘要文件：

```text
runs/{run_id}/MEMORY.md
```

这个文件不是长期经验库，而是当前任务的“状态骨架”。它应该由 `ContextLedger` 渲染而来。

#### 推荐格式

```markdown
# Run Memory

## Original Goal

## Hard Constraints

## Current Plan

## Completed

## Pending

## Verified Facts

## Unverified Assumptions

## Key Files And Resources

## Recent Failures

## Budget

## Next Action
```

#### 更新策略

- 每个 superstep 结束更新一次。
- 每次失败更新一次。
- 每次 checkpoint 更新一次。
- 如果节点输出很长，只写摘要，不写完整原文。

#### 与现有记忆系统的关系

`MEMORY.md` 应同时写入两处：

- 文件系统：便于人工查看和恢复。
- `HybridTieredMemoryStore` 的 TASK scope：便于后续语义检索。

#### 代码落点

- 新增 `ContextLedgerRenderer`。
- 在 `HybridTieredMemoryStore.append()` 或 `HookManager.on_node_end()` 后调用。
- 在 `HookManager._inject_memory_context()` 里优先注入 `MEMORY.md` 的精简内容。

#### 验收标准

- 长任务中断后，用户打开 `runs/{run_id}/MEMORY.md` 能读懂现场。
- resume 时可以把 `MEMORY.md` 注入 prompt 头部，恢复任务语义连续性。
- `MEMORY.md` 不包含明文 API key、password、token。

### 3. 做 Context Budget：上下文预算控制与预算暂停

优先级：最高。

#### 目标

防止上下文无限增长。每次构造节点输入前，系统都应知道当前 prompt 大约包含多少 token，距离上限还有多少空间，是否需要压缩、裁剪或暂停。

#### 预算字段

```python
@dataclass
class ContextBudget:
    max_context_tokens: int
    reserved_output_tokens: int
    max_memory_tokens: int
    max_tool_summary_tokens: int
    used_context_tokens: int = 0
    compression_count: int = 0
    paused: bool = False
    pause_reason: str = ""
```

#### 预算策略

按优先级保留上下文：

1. 原始任务目标。
2. 硬约束和安全边界。
3. 当前步骤指令。
4. 已验证关键事实。
5. 最近失败和恢复建议。
6. 最近工具摘要。
7. 长期记忆检索结果。
8. 未验证假设。
9. 原始历史消息。

如果超预算：

- 先压缩工具结果。
- 再压缩历史步骤。
- 再减少长期记忆 top_k。
- 再丢弃低可信、未验证、低相关内容。
- 仍超限则进入 `BUDGET_PAUSED`。

#### 代码落点

- `engine/modules/context/budget.py`
- `HookManager._inject_memory_context()`
- `HookManager.on_step_start()`
- `CompiledGraph.ainvoke()` 支持 `RunStatus.BUDGET_PAUSED`

#### 验收标准

- 给定 `max_context_tokens=2000`，系统注入内容不会超过预算。
- 超预算时不会静默截断，而是记录压缩过程。
- 无法压缩时进入 `BUDGET_PAUSED`，用户追加预算后可恢复。

### 4. 动态系统提示词重注入：防止指令稀释

优先级：很高。

#### 目标

解决原文档中的“指令稀释与注意力漂移”。随着轮次增加，原始任务约束会被推到上下文中间，模型更容易忽略。应当在每次节点执行前，把关键指令重新拼接到 prompt 的高优先级位置。

#### 注入内容

每次节点执行前，构造 `ContextInjection`：

```text
1. Original Goal
2. Non-negotiable Constraints
3. Current Node Role
4. Current Step Objective
5. Verified Facts
6. Things Not To Assume
7. Expected Output Contract
```

#### 关键原则

- 不是把全部历史塞进去。
- 只注入当前节点需要的信息。
- 原始目标和硬约束必须始终位于注入文本前部。
- 对多 agent 图，子 agent 只拿到父 agent 授权范围内的上下文。

#### 代码落点

- `engine/modules/context/injector.py`
- `NodeContext.metadata` 增加：
  - `role`
  - `objective`
  - `output_contract`
  - `context_policy`
- `HookManager.on_node_start()` 生成 `ctx.state["__context_injection__"]`。
- Agent 节点适配器在调用模型前读取该字段。

#### 验收标准

- 执行第 30 步时，模型输入头部仍能看到原始目标和硬约束。
- 子 agent 不会拿到无关或越权上下文。
- 不同节点拿到的上下文不同，避免全局大段注入。

### 5. 工具结果压缩与结构化摘要

优先级：很高。

#### 目标

工具调用结果是上下文膨胀的主要来源。浏览器页面、搜索结果、日志、测试输出、长文档内容不能原样持续进入上下文，必须压缩成结构化摘要。

#### 摘要分层

对每次工具结果保留三层：

1. `raw_ref`：原始内容存文件或冷归档，只保存引用。
2. `summary`：短摘要，供 prompt 注入。
3. `facts`：可验证事实列表，进入 ContextLedger。

示例：

```python
@dataclass
class ToolSummary:
    tool_name: str
    raw_ref: str
    short_summary: str
    extracted_facts: list[ContextFact]
    errors: list[str]
    token_count_raw: int
    token_count_summary: int
```

#### 代码落点

- `engine/modules/context/compressor.py`
- 和 `HybridTieredMemoryStore` 的 `long_text_threshold`、`raw_ref` 机制对齐。
- 浏览器工具、搜索工具、执行器输出先接入。

#### 验收标准

- 长网页不会原样进入下一轮 prompt。
- 原始内容仍能通过 `raw_ref` 找回。
- 摘要中抽取的事实有来源标记和可信度。

### 6. 上下文漂移检测 Drift Detector

优先级：高。

#### 目标

识别 Agent 是否开始偏离任务。原文档提到的表现包括：工具调用频次剧增、输出越来越长但任务指标停滞、重复操作、死循环。

#### 检测信号

第一版用规则和向量相似度即可：

- 连续 N 步 `current_objective` 与 `original_goal` 相似度下降。
- 连续 N 次调用同一个工具，参数高度相似。
- 节点输出相似度过高。
- `completed_steps` 长时间不增长。
- Evaluator 分数不升反降。
- step 数接近上限。

#### 动作

根据严重程度：

- 轻度：重注入原始目标和硬约束。
- 中度：触发总结压缩并重建计划。
- 重度：进入 `BUDGET_PAUSED` 或 `DRIFT_PAUSED`。
- 极重：改道到 evaluator / planner / repair 节点。

#### 代码落点

- `engine/modules/context/drift.py`
- `HookManager.on_step_start()`
- `HookManager.on_node_end()`
- `FlowController.decide()` 可读取 drift 结果决定跳过、延迟或改道。

#### 验收标准

- 构造一个重复调用同一工具的循环图，系统能识别重复。
- 构造一个目标逐步偏移的输出序列，系统能触发重规划。
- drift 事件写入 run trace。

### 7. 上下文污染隔离：防止级联失效

优先级：高。

#### 目标

解决原文档中的 Cascade Nightmare：A 的低质量输出被 B 当作事实，继续传播给 C。

#### 核心机制

所有上下文事实必须有状态：

```text
unverified -> verified -> trusted
unverified -> rejected
```

未经验证的内容不能直接进入全局事实区，只能作为假设注入，并明确提醒模型“不要当作事实”。

#### 多 Agent 父节点负责制

当前项目已有 `add_sub_agent(parent, ...)`，可以把父子关系用于上下文隔离：

- 子 agent 的输出默认回到父 agent。
- 父 agent 或 evaluator 验证后，才能提升为 `verified fact`。
- 子 agent 失败时，由父 agent 决定重试、改道或丢弃。

#### 代码落点

- `ContextFact.verified`
- `ContextFact.confidence`
- `ContextFact.source_agent`
- `Orchestrator` 中保留 parent/child 元数据。
- `HookManager.on_node_end()` 不直接把所有 update 写入 confirmed context。

#### 验收标准

- 子 agent 输出错误时，不会自动污染后续 agent 的 verified facts。
- 后续节点 prompt 中会区分“已验证事实”和“待验证假设”。
- 父 agent 可以拦截或修正子 agent 输出。

### 8. Post-Execution Validation：上下文进入账本前先验证

优先级：高。

#### 目标

原文档强调静默置信度失效：API 正常返回 200，但业务结果错了。上下文管理层必须在“写入账本”前做验证。

#### 验证点

- 节点输出是否符合 output contract。
- 工具结果是否包含错误信息。
- 文件/数据库真实状态是否与 Agent 声称一致。
- 生成内容是否满足原始任务约束。
- 是否引入了与 verified facts 冲突的新事实。

#### 代码落点

- 与 `engine/modules/evaluation` 联动。
- `HookManager.on_node_end()` 流程调整为：
  1. 收到 update。
  2. Evaluator 验证。
  3. 通过后写入 verified facts。
  4. 未通过则写入 rejected / failure summary。
  5. 根据 recovery 策略决定下一步。

#### 验收标准

- 节点声称“文件已创建”，但文件不存在时，不能写入 verified facts。
- JSON 格式错误时不会被后续节点当作有效输入。
- evaluator 结果能影响 recovery。

### 9. Context Checkpoint：上下文和图状态一起保存

优先级：高。

#### 目标

checkpoint 不应只保存 `GraphState`，还要保存上下文账本、MEMORY.md、预算和注入策略。否则恢复后图能继续跑，但语义现场不完整。

#### 保存内容

```text
checkpoint.json
ledger.json
MEMORY.md
trace_tail.jsonl
budget.json
tool_refs_manifest.json
```

#### 代码落点

- `engine/modules/checkpoint/store.py`
- `engine/modules/context/ledger.py`
- `CompiledGraph.ainvoke(resume_from=...)`

#### 验收标准

- 从 checkpoint 恢复后，`__context_injection__` 与中断前一致或等价。
- budget 继续累计，不会恢复后重置。
- 已验证事实不会丢失。

### 10. Harness Evolution Loop 的上下文版本

优先级：中。

#### 目标

原文档最后提到 Harness Evolution Loop。对于上下文管理来说，演化对象不是模型参数，而是：

- 压缩策略。
- 注入模板。
- 预算阈值。
- drift 检测阈值。
- evaluator 规则。
- MEMORY.md 结构。

#### 简化流程

```text
Worker Agent 执行任务
-> 生成 trace + ledger + MEMORY.md
-> Evaluator 判断上下文是否退化/漂移/污染
-> Evolution Agent 修改 context policy
-> 下一轮回归评测
```

#### 产物

```text
configs/context_policy.yaml
runs/context_eval/{timestamp}/report.md
```

`context_policy.yaml` 示例：

```yaml
max_context_tokens: 12000
max_memory_tokens: 2500
memory_top_k: 5
inject_original_goal_every_step: true
drift_similarity_threshold: 0.45
repeat_tool_call_limit: 3
unverified_fact_policy: hypothesis_only
```

#### 验收标准

- 同一批长任务，在不同 context policy 下能比较成功率、token、漂移次数。
- Evolution Agent 只能生成 policy patch，不能直接改核心代码。
- 新 policy 必须通过回归评测才接受。

### 上下文专项的推荐实施顺序

建议按下面顺序做，避免一次性铺太大：

1. `ContextLedger` 数据结构和 JSON 落盘。
2. `MEMORY.md` 渲染。
3. `ContextBudget` 和 `BUDGET_PAUSED`。
4. `ContextInjector`，每步重注入原始目标和硬约束。
5. 工具结果压缩和 `raw_ref`。
6. `Post-Execution Validation` 写入账本前验证。
7. `DriftDetector` 重复/漂移检测。
8. 多 Agent verified/unverified 事实隔离。
9. Context checkpoint/resume。
10. Context policy 回归评测和演化。

### 第一版最小可用实现

如果只做一个最小闭环，建议先实现 4 个文件：

```text
engine/modules/context/_types.py
engine/modules/context/ledger.py
engine/modules/context/injector.py
engine/modules/context/budget.py
```

并在 `HookManager` 中接入三个点：

```text
on_step_start: 检查预算、加载 ledger、生成 step 级上下文
on_node_start: 注入 original_goal / constraints / verified facts
on_node_end: 摘要 update，更新 ledger 和 MEMORY.md
```

第一版不需要 LLM 压缩器，先用规则摘要即可：

- 长文本截断到固定字符数。
- dict/list 转 JSON 摘要。
- tool result 保存 raw_ref。
- verified facts 先由规则或 output contract 决定。

这样可以最快验证该方向是否有效。

## 对当前项目论文/汇报价值的提升

完成上述路线后，项目叙事可以从：

> 基于 AgentScope 的类 LangGraph 编排框架，并带端边云学习路由。

升级为：

> 面向长周期 Agent 的状态化、高弹性、自演化 Harness：通过 checkpoint/resume、语义 evaluator、端边云联合调度、事务安全 tool boundary 和 SkillRepo 技能演化闭环，实现多 Agent 长任务在不稳定工具环境中的持续运行与过程性能力增长。

这比单独做 BGE-M3 路由器更完整，也更贴合文档中“高弹性、状态化、自演化”的系统级主题。
