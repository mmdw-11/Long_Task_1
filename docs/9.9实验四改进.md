# 9.9 实验四改进：ToolSandbox Hard 状态化技能闭环评测方案

## 1. 改进背景

实验四上一版本使用官方 `tau2-bench` 的 Airline 与 Retail 各20道任务，设置 No Skill、Manual Skill、Ours No Validation 和 Ours Full 四组，每组重复2次，共完成320次模拟。该实验四组成功率集中在81.25%至88.75%之间：

| 方法 | Task Success |
|---|---:|
| No Skill | 81.25% |
| Manual Skill | 88.75% |
| Ours No Validation | 85.00% |
| Ours Full | 83.75% |

第一版能够证明实验链路有效，显示技能对确认合规和部分领域任务有帮助，但存在以下不足：

1. No Skill在完整领域政策和工具schema帮助下已经能完成大量任务，形成较高基线；
2. 部分任务只需一次写操作或简单政策判断，技能的边际价值有限；
3. 四组差距较小，Ours Full没有超过Manual Skill，也没有超过Ours No Validation；
4. 当前任务不足以充分检验隐式状态依赖、多步恢复、多轮信息收集和不可解任务识别；
5. 若仅根据上一轮结果挑选“Ours表现好的任务”，会造成结果导向的选择偏差，不能形成可信结论。

因此，新版实验四不覆盖旧320-run，而是重新建立一套以复杂状态依赖和多轮工具使用为核心的主实验。旧结果保留为 `tau2-bench` 客服任务基线，新结果作为高难度技能闭环主实验。

## 2. 数据集选择

### 2.1 最终选择：Apple ToolSandbox

新版主实验使用Apple官方开源的 ToolSandbox：

- 官方仓库：<https://github.com/apple/ToolSandbox>
- 官方研究介绍：<https://machinelearning.apple.com/research/toolsandbox-stateful-conversational-llm-benchmark>
- 论文：<https://arxiv.org/abs/2408.04682>

ToolSandbox是状态化、对话式、可交互的工具调用评测环境。它维护完整执行上下文，并在每轮保存世界状态快照。其主要状态包括：

- 系统设置，如蜂窝网络、Wi-Fi、飞行模式和位置服务；
- 联系人数据库；
- 消息数据库；
- 提醒事项数据库；
- 用户、Agent与执行环境之间的对话和工具轨迹。

工具调用会真实修改隔离状态；错误会返回给Agent，使其能够诊断、修复前置条件并重试。评测使用中间milestone、最终状态约束和禁止行为约束，不要求机械匹配唯一工具序列，因此适合比较不同但有效的解决路径。

### 2.2 为什么比继续扩充普通τ任务更合适

本轮改进目标不是增加领域数量本身，而是提高任务对技能的依赖程度和四组方法的区分度。ToolSandbox原生覆盖：

- 多工具调用；
- 多轮用户信息披露；
- 工具与世界状态之间的隐式依赖；
- 参数规范化；
- 信息不足时的澄清、拒绝或停止；
- 工具异常后的恢复；
- 无关工具、模糊工具名称和不完整参数说明等干扰。

这些能力与本项目的“成功轨迹→技能归纳→候选验证→技能发布→动态检索→工具执行→状态验证”闭环直接对应，比大量单步客服操作更能检验技能是否真正提供了可执行知识。

### 2.3 不作为本轮主数据集的候选

- `tau2-bench`：已完成标准客服基线，继续保留为外部有效性结果；本轮不再把简单增加Airline/Retail/Telecom题目作为主要改进。
- AppWorld：跨应用API任务总体更长、更复杂，但更偏交互式编码与多应用自主执行，接入和评测迁移成本较高，留作后续长链路扩展。
- CRMArena-Pro：企业场景真实，但依赖Salesforce组织、账户和更重的外部环境，不适合当前阶段的可复现实验。
- ToolBench/API-Bank：工具广度高，但在状态快照、隐式依赖、多轮用户模拟和动态终态评价上不如ToolSandbox贴合本实验。

## 3. ToolSandbox Hard三类任务

ToolSandbox类别可以重叠。新版实验不会简单按标签独立随机抽样，而是建立互斥的主分层，确保最终任务不重复、每组数量相同。

### 3.1 A组：State Dependency

状态依赖任务要求Agent在执行目标工具前发现并修复世界状态中的隐式前置条件。例如，发送消息前可能需要关闭飞行模式、开启网络、查询联系人并取得唯一号码。

该组重点测量：

- 能否发现工具与状态之间的依赖；
- 能否建立正确前置条件顺序；
- 工具失败后能否定位原因而不是盲目重复；
- 修复状态后能否回到原始目标；
- 是否产生无关或破坏性状态修改。

技能应能够表达前置条件图、检查顺序、异常恢复路径和最终状态验证方法。

选取目标为10道唯一任务，优先满足：

```text
STATE_DEPENDENCY AND MULTIPLE_TOOL_CALL
```

同类候选中依次优先选择依赖层数更多、所需工具更多、存在失败恢复以及具有干扰工具的任务。

### 3.2 B组：Multiple Tool Call + Multiple User Turn

该组要求任务同时具备多工具执行和多轮用户交互。用户不会在第一轮提供全部信息，Agent需要发现缺失字段、逐步询问、保存已有信息，并在信息齐全后执行多个相互依赖的工具。

该组重点测量：

- 任务分解和计划保持；
- 必要字段识别；
- 已知信息记忆与slot更新；
- 歧义消解；
- 用户中途补充或修改目标后的重规划；
- 是否在信息不完整时过早执行写操作；
- 多步工具顺序和副作用控制。

技能应能够表达必需字段表、询问策略、阶段状态、参数传递和写操作前确认。

选取目标为10道唯一任务，要求：

```text
MULTIPLE_TOOL_CALL AND MULTIPLE_USER_TURN
```

并排除已经进入A组的任务。优先选择信息分阶段披露、存在实体歧义、用户目标发生修正或需要写前确认的任务。

### 3.3 C组：Insufficient Information + Canonicalization

该组用于检验Agent能否正确区分“信息可以规范化”与“信息不足、必须询问或停止”。

Canonicalization要求将自然语言转换为工具接受的标准参数，例如：

- `1k` 转为 `1000`；
- “明天下午五点”根据当前日期和时区转换为绝对时间；
- 联系人姓名转换为唯一电话号码；
- 自然语言开关状态转换为布尔值或枚举值。

Insufficient Information则故意移除必要信息或必要工具。正确行为不是猜测，而是询问用户、说明限制，或在无法取得信息时拒绝执行。

该组重点测量：

- 日期、时间、单位、实体和枚举规范化正确率；
- 缺失字段识别率；
- 正确澄清率和正确停止率；
- 虚构工具、实体和参数的比例；
- 信息不足时的错误状态写入；
- 工具调用成功但最终语义错误的隐蔽失败。

选取目标为10道唯一任务：

- 5道Insufficient Information；
- 5道Canonicalization；
- 排除已进入A、B组的任务；
- 优先保留同时包含多工具、状态依赖或多轮用户交互的候选。

## 4. 正式任务规模与互斥抽样

最终数据集锁定为30道唯一困难任务：

| 主分层 | 任务数 |
|---|---:|
| State Dependency | 10 |
| Multiple Tool Call + Multiple User Turn | 10 |
| Insufficient Information | 5 |
| Canonicalization | 5 |
| 合计 | 30 |

四种方法、三个trial，正式规模为：

```text
30 tasks × 4 methods × 3 trials = 360 runs
```

每道任务必须在四种方法和三个trial下完整配对。任务顺序、trial seed、模型、工具可见性、初始世界状态、最大轮数和超时保持一致。

类别存在重叠时采用以下固定优先级分配主标签：

1. 满足State Dependency硬条件的任务先进入A组；
2. 剩余任务中同时满足Multiple Tool Call与Multiple User Turn的进入B组；
3. 剩余任务中按5道Insufficient Information和5道Canonicalization组成C组；
4. 每道任务只能出现在一个主组，但保留全部辅助标签用于分项分析；
5. 如果某组候选不足，不得降低难度后静默补齐，必须在数据审计报告中说明并重新确认规模。

## 5. 难度排序与冻结规则

选题只能使用任务静态结构，禁止使用四种方法的运行结果。候选按以下维度计算难度：

1. 必需工具调用数量；
2. 隐式状态依赖数量和最长依赖链；
3. 用户交互轮次；
4. 不同工具数量；
5. 必需中间milestone数量；
6. 是否存在失败恢复路径；
7. 是否存在实体、时间、单位或枚举规范化；
8. 是否故意缺失必要信息或工具；
9. 是否包含干扰工具或工具描述增强；
10. 是否包含有副作用操作和确认边界。

同分任务使用官方scenario name稳定排序。正式调用API前输出并冻结：

- 30个scenario ID；
- 主标签和全部辅助标签；
- 每项难度特征及总分；
- 基础场景族；
- 原始文件路径和SHA-256；
- ToolSandbox commit SHA；
- 选择脚本版本和随机种子；
- train/validation/test泄漏审计。

一旦冻结，不得根据No Skill或Ours的表现替换任务。

## 6. 防止数据泄漏

ToolSandbox场景通常从基础场景扩展而来，同一基础场景可能具有普通版、干扰工具版、工具名打乱版、参数描述删除版等多个变体。若按单条scenario随机切分，极易让同一模板的近重复变体同时进入训练和测试。

因此必须按基础场景族分组切分：

```text
base scenario family
├─ skill_train
├─ skill_validation
└─ formal_test
```

一个基础场景族及其所有增强变体只能属于一个split。额外检查：

- scenario ID不得跨split；
- 基础场景祖先不得跨split；
- 初始状态与目标milestone组合不得跨split重复；
- 近重复用户指令不得跨split；
- formal test的milestone、目标状态和隐藏指令不得进入Agent prompt或技能内容；
- 只有skill_train成功轨迹可以参与技能生成；
- skill_validation仅用于接受或拒绝候选，不参与正式结果。

如果官方数据没有满足本项目需求的原生train/test划分，本项目必须把派生划分明确标注为 `project-derived family-disjoint split`，不能宣称是官方split。

## 7. 四种实验方法

### 7.1 No Skill

Agent只获得统一system policy、当前可见工具schema和用户逐轮消息，不获得额外技能。它用于测量模型本身的工具规划和错误恢复能力。

### 7.2 Manual Skill

使用人工依据公开工具规则整理的完整专家技能，包括：

- 前置条件；
- 参数来源；
- 状态检查顺序；
- 多轮询问规则；
- 规范化规则；
- 信息不足判定；
- 异常恢复；
- 副作用控制；
- 最终状态和用户沟通。

Manual Skill不得读取正式test的隐藏目标和milestone，不得故意删除关键步骤，其长度预算应与自动技能可比。

### 7.3 Ours No Validation

只从skill_train的成功工具轨迹中归纳技能，完成格式和工具存在性检查后直接发布，不执行候选状态回放验证。该组用于测量验证阶段的增益或副作用。

### 7.4 Ours Full

执行完整闭环：

```text
成功轨迹收集
→ 结构化技能归纳
→ schema与工具验证
→ 状态依赖和参数验证
→ skill_validation真实回放
→ 安全与副作用检查
→ 接受或拒绝
→ 版本化发布
→ 对话阶段动态检索
→ 状态化执行
→ milestone与最终状态评估
```

候选验证失败时必须进入rejected状态，不得静默退化为gold或Manual Skill。

## 8. 技能表示与动态检索

技能机器表示至少包含：

- `skill_id`、版本、来源轨迹和基础场景族；
- 适用条件与不适用条件；
- 所需工具及参数schema；
- 前置状态；
- 依赖图和关键顺序；
- 必需用户字段和澄清问题；
- Canonicalization规则；
- Insufficient Information停止条件；
- 写操作和确认边界；
- 工具异常恢复路径；
- 成功milestone和最终验证方法；
- 禁止操作与安全约束。

检索按每个用户轮次和工具异常事件动态触发，而不是只在第一轮注入一次。总上下文使用统一硬预算，记录每次检索候选、分数、接受/拒绝原因、注入片段及累计字符数。

## 9. 主要指标

### 9.1 任务结果

- Overall Task Success；
- Milestone Completion Rate；
- Final State Accuracy；
- Minefield Violation Rate；
- 三个主分层的成功率；
- 三个trial全部成功率；
- Pass@1与paired method difference。

### 9.2 状态依赖与恢复

- 前置条件发现率；
- 状态依赖完成率；
- 首次工具错误率；
- 相同错误重复调用次数；
- 工具异常恢复率；
- 无关状态修改次数；
- 相对最短有效路径的额外步骤。

### 9.3 多轮与信息收集

- 必需字段收集完整率；
- 正确澄清率；
- 重复询问率；
- 已知信息遗忘率；
- 信息不足时过早执行率；
- 用户修改目标后的重规划成功率；
- 写操作前确认率。

### 9.4 规范化与安全

- Canonicalization Accuracy；
- 日期时间、单位、实体和枚举转换正确率；
- Correct Abstention Rate；
- Hallucinated Argument Rate；
- 不存在工具调用率；
- 信息不足时错误写入次数；
- 未授权副作用次数。

### 9.5 技能与成本

- Skill Retrieval Recall@K、MRR、误检率和拒绝率；
- 自动技能生成成功率；
- 候选验证接受率与拒绝原因；
- 验证后相对No Skill的增益；
- Agent、用户模拟、技能生成和验证token；
- 工具调用数、对话轮数、P50/P95耗时；
- 每成功任务token与费用；
- 技能上下文长度和动态注入次数。

## 10. 公平性和统计方式

- 四种方法使用相同任务、初始状态、可见工具、用户模拟设置和trial seed；
- test隐藏信息不得进入任何方法的prompt；
- Manual与Ours使用统一技能上下文预算；
- 使用任务级paired comparison；
- 报告成功数、均值和95% bootstrap置信区间；
- 分别报告三组主分层和所有辅助标签；
- 报告Ours Full相对No Skill、Manual和Ours No Validation的绝对与相对差异；
- 不因reward=0重跑任务；只有明确的API、环境或程序错误才允许使用相同配置断点补跑；
- 所有失败必须保留轨迹并进行归因。

## 11. 分阶段实施与验收

### 阶段一：数据与环境审计，不调用API

1. 下载官方仓库并固定commit；
2. 检查许可证、Python版本和依赖；
3. 枚举场景、类别、基础场景关系和工具增强；
4. 排除需要未配置外部服务的场景，例如依赖RapidAPI的搜索任务，或为其提供可复现替代；
5. 建立family-disjoint train/validation/test；
6. 生成30题候选清单、难度报告和哈希；
7. 验证三组各10题且无重复、无泄漏。

### 阶段二：离线适配与测试，不调用API

1. 新增ToolSandbox任务结构转换；
2. 实现Agent和工具消息适配；
3. 实现状态快照、milestone和minefield结果转换；
4. 实现四种方法和技能仓库；
5. 使用mock模型测试多轮工具链、异常恢复和澄清；
6. 验证summary可由rows和原始轨迹独立重算；
7. 保证现有实验一至四旧入口继续通过。

### 阶段三：极小API canary

分别选A、B、C组各1题，仅运行No Skill和Ours Full，共6次。检查：

- DeepSeek OpenAI-compatible调用；
- tool calling格式；
- 用户模拟；
- 状态隔离；
- 动态技能注入；
- milestone评估；
- token和错误记录。

Canary不进入正式结果。

### 阶段四：小规模pilot

每组2题、四种方法、1个trial，共24次。只有满足以下条件才能进入正式实验：

- 零数据泄漏；
- 零缺行和重复key；
- 零跨任务状态污染；
- 无无法解释的解析或evaluator错误；
- 四种方法输入公平；
- 技能检索和上下文预算记录完整；
- summary可独立重算。

### 阶段五：360-run正式实验

冻结数据、代码、prompt、技能版本、模型和seed后运行：

```text
30 tasks × 4 methods × 3 trials = 360 runs
```

中途只允许相同配置断点续跑，不允许根据中间成绩修改任务、技能、prompt、路由或evaluator。正式完成后执行独立重算、分层分析、配对差异分析和失败轨迹归因。

## 12. 正式验收标准

- 360个预期运行全部存在且key唯一；
- 每道任务四种方法和三个trial严格对齐；
- 每次运行从相同初始状态开始；
- 无train/validation/test基础场景族泄漏；
- test milestone和隐藏目标未进入Agent或技能上下文；
- 官方/本地状态评测与独立重算一致；
- 每个发布技能可追溯至skill_train成功轨迹和validation报告；
- API、工具、用户模拟和评测异常被单独报告；
- 结果为0的有效失败不得删除或替换；
- 旧 `tau2-bench` 320-run数据和文档不得覆盖。

### 14.5 当前结论与是否允许进入 360-run

本轮前四阶段已经发挥了预期的“正式运行前发现问题”作用：发现并修复了 SDK/httpx 不兼容、DeepSeek tool-call ID 语法错误、Agent 失败与基础设施错误混淆、初始状态哈希不稳定四类问题；证明修正后 ToolSandbox 与 DeepSeek 能完成真实状态工具执行和官方评测。

但是阶段四**尚未通过进入正式 360-run 的算法验收门槛**，原因不是程序错误，而是实验方法仍不完整：

1. Ours Full 尚非从真实成功训练轨迹归纳并经 validation 状态回放发布的技能；
2. 当前通用模板只产生小幅平均 reward 改善，未形成稳定、明显的组间区分；
3. 4 组完全成功数为 0/1/1/1，6 题样本过小且难度很高，不能支持显著性结论；
4. Insufficient Information 的四组均失败，需要从轨迹确认是用户模拟终止、拒绝表达还是 milestone 定义未满足；
5. Ours No Validation 在 State Dependency 明显下降，说明未验证技能可能干扰行动，这个方向符合消融预期，但仍需更多 validation 证据。

因此当前可以支持的结论是：数据难度和区分潜力显著高于旧 τ 客服实验，ToolSandbox 工程链路已经跑通，Manual/Ours 在多轮与规范化任务上显示正向信号；不能支持“Ours Full 已优于 Manual”或“验证闭环有效”的最终结论。

下一步必须先补齐真实训练轨迹驱动的技能生成、按可见对话/工具错误动态检索、validation 状态回放和 rejected/published 版本记录，再用不重叠的小规模 validation/pilot 验证。只有修正后 pilot 达到零错误、状态公平且 Ours Full 相对 No Skill 呈稳定正向信号，才冻结 prompt/技能并启动 360-run；不得为追求漂亮结果替换正式 30 题。

### 15.4 动态检索与失败修正

运行时在每次Agent推理前，根据首轮可见目标和最近工具反馈动态检索，不向Agent提供任务ID、类别或评测状态。检索上下文统一限制为6000字符。

严格验证先后发现并修复：

1. 普通Jaccard会因 `specific/missing/available` 等泛词把提醒技能注入消息任务；加入停用词、最低匹配与工具领域锚点。
2. 对话后期的干扰工具反馈会改变领域；领域锚点现固定在首轮用户目标，后期反馈只细化同域排序。
3. `internet/connected` 与 `wifi/cellular` 表达不同导致设备技能漏检；加入固定公开同义词规范化，不读取任务标签或答案。
4. DeepSeek接受seed参数但并非完全确定；同一无技能注入任务可出现约0.013的语义reward波动。验证只评价实际发生技能注入的任务，未注入任务按基线处理；reward非退化容差固定为0.01，minefield、非法工具和运行错误仍为零容忍。
5. 候选必须至少在1条独立validation任务真实注入，否则因零覆盖拒绝发布。

验证门禁记录每个候选的验证任务、相同Agent/User seed、基线/候选reward、minefield、非法工具、错误、是否实际注入及逐题delta。最终发布结果：

## 十六、Manual Skill 检索边界修正与补充 Pilot（2026-09-09）

### 16.1 问题定位

### 16.2 代码和技能修正

- 为4份人工技能补齐公开工具 schema 对应的工具锚点、正向领域词和排除领域词。

- 增加 `remind/todo/messages/contacts/reminders` 词形归一化。
- 增加 evaluator-only 的 family/category 适用标签，不向 Agent 暴露；据此计算 Recall、Precision、MRR、误检数和不适用拒绝率。

## 十八、正式运行卡死诊断与恢复修复（2026-09-09）

正式360-run首次运行在完成83条后停止推进。已完成分布为 No Skill trial-0 30条、Manual Skill trial-0 30条、Ours No Validation trial-0 23条；83条结果没有基础设施错误和重复键。卡住任务为 `modify_contact_with_message_recency_insufficient_information_alt_3_distraction_tools`，控制台停留在单任务内部进度6/30，且当时 Python 进程持续占用CPU。

根因不是DeepSeek鉴权或普通网络超时，而是Agent在一个回合生成过多并行工具调用。ToolSandbox为了兼容并行调用顺序，会枚举工具调用的全部排列，复杂度为阶乘级。对已有83条轨迹审计发现，66条轨迹存在并行工具调用，已完成样本的单回合最大并行数为8；当异常任务产生更多调用时，排列数会迅速超过可接受范围，例如8个调用已有40,320种排列。

本次修复包括：

- Agent单回合最多允许8个并行工具调用；超过上限时立即记为可解释的Agent失败，避免进入阶乘枚举。上限与已有83条记录的观测最大值一致，因此不会改变已完成样本的行为或分数。
- 每个任务改为独立子进程运行，并设置300秒硬超时。超时后终止该任务进程、保存 `TaskTimeoutError`，随后继续运行其他任务，不再让一个异常样本阻塞整个正式实验。
- 父进程在子进程运行期间读取结果，避免较大轨迹填满进程通信缓冲区后出现“父进程等子进程、子进程等父进程读取”的第二类死锁。
- 恢复运行时只跳过无基础设施错误的完成行；超时或Worker错误行会在下一次执行同一命令时自动重试。
- 对“无效或未授权工具调用”这类正常Agent失败补写失败轨迹、最终状态哈希和轨迹哈希。历史83条中有2条完成了无API重算修复，Reward和Task Success均未修改。

修复后审计结果：已有83条记录、83个唯一键、0个基础设施错误、0个缺失最终状态哈希、0个缺失轨迹哈希、0个状态哈希不一致；部分结果审计为PASS。ToolSandbox专项测试15条全部通过，正式预检仍为PASS，正式数据SHA256仍为 `ce9693a478fce3d7ea33512ba7e6c9dd44272d1eb5dce675edf2a86aad2841ff`。此外，1条真实联网canary在约8.45秒内完成，Reward为0.5、error为空，证明Windows子进程能够正常返回完整轨迹。
