# Agent 自我进化与过程性技能提取：方案评估与落地计划

> 本文只做方案评估与实施设计，不包含代码修改。评估依据为参考文档、当前仓库实际实现，以及 SkillClaw 官方仓库截至 2026-08-04 可见的设计说明。

## 一、结论先行

当前项目最适合的不是完整照搬 SkillOS、SkillOpt 或 MAE，而是采用一套轻量混合方案：

**以 SkillClaw 的“执行链路与演化链路解耦”为总体架构，以 SkillOpt 的“小步编辑、留出验证、拒绝缓存、版本回滚”为质量控制方法，以当前项目已有的 Hook、Context Ledger、FailureTrace、Evaluator、Checkpoint 和 HybridTieredMemoryStore 作为数据与执行基础。**

第一阶段只建设“单机、离线、候选技能需审批”的闭环：运行轨迹采集 → 可提炼任务筛选 → 候选技能生成 → 回放验证 → 人工审批 → 发布到 SkillRepo → 下一次任务按需检索加载。暂不训练 Curator，不做在线 RL，不做多智能体自对弈，也不允许运行中的 Agent 直接覆盖已发布技能。

这样选择的原因是：

- 当前项目是 Python 3.10+ 的 AgentScope 扩展框架，核心是类 LangGraph 图编排、FastAPI、可插拔 Hook 与多 Agent 运行治理，不是一个拥有大规模流式任务和奖励基础设施的训练平台。
- 项目已经具备可靠的过程数据基础，但尚缺“技能生命周期、候选版本、评测集、发布治理”四个核心面；先补这四个面，比引入 RL 更直接。
- 当前 `.env.example` 同时配置 DeepSeek 兼容 API、Ollama 设备模型和边端模型，Markdown 技能有利于跨模型复用；但不同模型对同一技能的遵循度不同，因此必须做分模型验证，不能把“文本可迁移”理解成“效果天然等价”。
- 24 小时运行首先要求安全、可审计和可恢复。自动归纳可以开放，自动发布应后置。

## 二、参考文档的设计观点解释与适用性判断

### 2.1 工具与技能的分层：可直接复用

参考文档把 Tool 定义为单一、无状态的底层能力，把 Skill 定义为包含步骤、最佳实践、异常处理和结果核验的程序性规程。这个分层适合当前项目。

在本项目中：

- `examples/*/tools.py`、模型 API、浏览器、文件或日历接口属于 Tool。
- “如何规划旅行并做预算复核”“如何在边云模型之间安全降级”“如何处理邮件并核验动作结果”才属于 Skill。
- 图节点或子图是执行结构，不天然等于 Skill。只有当一套节点协作方式被抽象为可复用的前置条件、步骤、失败分支和验收规则时，才应进入技能库。

建议技能采用目录包，而不是只有一个任意 Markdown 文件：

```text
skills/
  <skill_id>/
    SKILL.md                 # Agent 可读的主规程
    manifest.json            # 机器可读元数据、版本和适用范围
    evals/                   # 回放样例与断言
    references/              # 可选领域资料，不放密钥
    scripts/                 # 可选确定性辅助脚本，必须单独审计
```

`SKILL.md` 至少应包含：用途、适用/不适用条件、输入契约、执行步骤、工具依赖、失败分类、重试/回滚、输出契约、核验清单和已知限制。技能不应复制工具实现，也不应保存一次任务的用户隐私或绝对路径。

### 2.2 文本空间外部状态：可直接复用，但要加机器可读元数据

把 Markdown 当作冻结模型之外的“可训练状态”，符合当前项目的跨 DeepSeek/Ollama/其他 OpenAI 兼容模型部署方式。它具备可读审计、Git 版本管理和低成本回滚的优势。

但仅靠 Markdown 不足以支撑稳定运行。系统还需要 `manifest.json` 保存以下内容：

- `skill_id`、语义版本、状态（draft/candidate/validated/published/retired）。
- 任务类型、标签、工具依赖、前置条件和互斥条件。
- 来源轨迹 ID，只存脱敏后的引用和哈希。
- 支持/验证过的模型、Harness 版本与依赖版本范围。
- 训练集、验证集、回归集版本。
- 质量、成功率、Token、轮次、延迟、安全告警等指标。
- 父版本、变更摘要、审批人、发布时间和回滚目标。

因此，“文本可读层 + 元数据控制层”应同时存在。

### 2.3 SkillOpt：核心控制思想适合，完整训练形态不必照搬

可复用的部分：

- 用成功/失败轨迹做差分反思，而不是只总结成功经验。
- 将技能修改限制为 Add/Delete/Replace 原子编辑。
- 设置 Edit Budget，抑制一次性大改造成的语义漂移。
- 使用隔离的留出验证集，只有优于基线且不破坏安全红线才接纳。
- 保留 Rejected-Edit Buffer，避免反复提出已经证明无效的修改。
- 定期做慢速整理，合并重复规则、淘汰过时规则。

不宜照搬或需要修正的部分：

- 当前仓库没有成熟的固定 benchmark、批量 rollout 调度器和独立 Frontier Optimizer；一开始模拟完整“文本反向传播”会使工程复杂度高于收益。
- “部署额外耗时完全为零”只在技能被固化进已有提示且不增加模型调用时近似成立。技能文本仍会占上下文 Token；如果按需检索、排序或压缩，也会产生本地或模型侧开销。
- 新版本不能只要求总分更高。还必须设置安全、正确性和关键任务成功率的不可退化约束，防止用更低 Token 换取错误答案。

因此，本项目应采用 **SkillOpt-lite**：离线小批量反思、有限编辑、确定性断言优先、留出验证、人工审批和可回滚发布，不在第一版追求多 Epoch 自动寻优。

### 2.4 SkillOS：架构思想部分复用，RL Curator 暂不适合

可复用的部分：

- Executor 与 Curator 分离。在线执行体只读取已发布技能，离线演化体读取脱敏轨迹并生成候选版本。
- SkillRepo 持久化、检索加载、去重、依赖管理和技能淘汰。
- 评价不只看成功率，也看 Token、执行轮次、延迟和技能命中后的净收益。
- 流式任务可以持续积累证据，但更新不必实时发布。

暂不适合的部分：

- 强化学习 Curator 需要稳定奖励、足够多的任务量、探索隔离和训练运维能力；当前项目没有这些前提。
- 复合奖励容易出现“奖励投机”：为了减少 Token 或轮次而跳过核验步骤。
- 依赖任务组要求业务任务之间存在可靠的依赖标注。当前示例业务较分散，强行分组会制造伪因果。
- 在线自动剪枝可能删除低频但关键的故障恢复规则，不适合尚未建立覆盖率指标的阶段。

第一版可把 Curator 实现成“规则筛选 + LLM 生成候选 + Evaluator/回放验证 + 人工审批”的确定性工作流，积累足够数据后再评估 contextual bandit 或 RL。

### 2.5 MAE：仅适合作为以后生成挑战样例的辅助，不进入主链路

Proposer/Solver/Judge 自对弈适合缺少真实标注、且结果可以被可靠 Judge 评价的开放推理任务。当前项目强调工具执行、文件状态、权限边界和长期运行，很多错误必须依靠真实环境断言，而不是另一个 LLM 的主观评分。

主要风险包括高模型调用成本、Judge 偏差、合成任务偏离真实业务、三方共享同类盲点，以及自对弈内容污染正式技能库。因此 MAE 不应负责生产技能发布。未来只能在沙箱中用于补充边界案例，且生成样例必须经过规则过滤和人工抽检后才能进入候选评测集。

### 2.6 SkillClaw：总体架构值得借鉴，不建议第一阶段直接嵌入代理

[SkillClaw 官方仓库](https://github.com/AMAP-ML/SkillClaw)目前公开的关键设计是：本地 Client Proxy 截获会话并管理本地技能；可选 Evolve Server 从共享存储读取会话，使用 workflow 或 agent 引擎演化技能；两端通过 local/OSS/S3 等共享存储解耦，并支持候选技能经后台验证后发布。

可以复用：

- 会话采集与技能演化解耦。
- 本地先行、后续再扩展到团队共享。
- candidate → validation job → publish 的分阶段发布。
- 技能去重、版本历史、状态面板、同步与恢复诊断。
- 统一 `SKILL.md` 形式，保留跨 Harness 的可能性。

不建议第一阶段直接采用其本地 API Proxy，原因是当前项目已经能在 `CompiledGraph` 和 `HookManager` 内拿到更完整的节点、工具、状态、失败和 Evaluator 数据。额外代理会引入会话边界识别、流式响应兼容、密钥转发和故障点，还会丢失一部分图语义。更合适的方式是借鉴其 Client/Evolve 分离思路，在项目 Hook 层原生导出标准轨迹；未来若要接入 Codex、Claude Code 等外部 Harness，再增加代理适配器。

## 三、当前项目可复用基础与缺口

### 3.1 已有基础

| 已有能力 | 当前落点 | 在技能演化中的用途 |
| --- | --- | --- |
| 图执行生命周期 | `engine/graph.py`、`engine/hooks.py` | 采集 step/node/tool 过程事件，控制技能注入时机 |
| 失败轨迹 | `engine/failure.py` | 提取失败模式、重试条件与回滚策略 |
| 上下文账本及 `MEMORY.md` | `engine/modules/context/ledger.py`、`renderer.py` | 提供目标、约束、已验证事实、摘要和原文引用 |
| 原文归档与恢复 | `context/compressor.py`、`raw_ref` 接口 | 回放时找回必要证据，避免只根据摘要误归因 |
| 漂移检测 | `context/drift.py` | 排除死循环或目标漂移造成的低质量轨迹 |
| 节点后验评价 | `engine/modules/evaluation.py` | 建立规则断言、暂停/改道和发布硬闸门 |
| 父子 Agent 校验 | `RuleEvaluator` 的外部父级授权 | 防止子 Agent 自证输出有效 |
| 图与上下文 checkpoint | `engine/checkpoint.py`、`context/checkpoint.py` | 回放、候选对比和失败后恢复 |
| 四级混合记忆 | `engine/modules/memory/` | 保存技能索引、历史证据和跨 run 检索信息 |
| 安全审计/脱敏 | `engine/modules/security/` | 轨迹入库前去除密钥和个人信息 |
| 路由与边云调度 | `routing.py`、`scheduling/` | 记录分模型效果，并控制演化任务只在非实时资源运行 |

### 3.2 仍缺少的关键能力

- 没有独立 SkillRepo、技能状态机、语义版本和依赖模型。
- 现有 ledger 偏运行恢复，不是完整训练轨迹；缺少 prompt/skill 版本、工具参数与结果状态、耗时、Token、模型、环境指纹和 evaluator 证据的统一事件协议。
- `RuleEvaluator` 目前主要做字段/文件/父级授权检查，尚不能覆盖业务正确性与跨模型回归。
- 没有训练/验证/回归数据隔离及防泄漏规则。
- 没有候选技能生成器、原子编辑表示、Edit Budget 与拒绝缓存。
- 没有技能检索的相关性阈值、冲突消解、注入预算和效果归因。
- 没有自动发布权限边界、签名/审批记录、快速回滚与技能熔断。

## 四、最佳方案的实现设计与先后顺序

### 阶段 0：定义边界和基线（先做，约 2～3 个工作日）

目标是先证明“改进”可被测量。

1. 选 2 个代表性场景做试点：建议 `travel_planner`（多 Agent、工具与核验链完整）和 `edge_cloud_scheduler`（异构模型与成本指标明显）。不要一开始覆盖全部示例。
2. 为每个场景准备基线任务集，并按任务族或来源隔离为 train/validation/regression。相近改写必须放在同一分组，避免语义泄漏。
3. 固定当前 prompt、模型、依赖、图版本和随机参数，记录无技能基线：任务成功率、关键断言通过率、Token、模型调用轮次、P50/P95 延迟、重试数、人工介入数和安全事件数。
4. 定义硬门槛：任何安全断言、权限断言、输出关键字段不得退化；验证提升要超过预设最小效应，而不是一次偶然高分。

交付物：指标字典、试点任务集、数据分割清单、基线报告和发布准入规则。

### 阶段 1：建立可审计轨迹协议（第一个实现里程碑）

在现有 Hook 生命周期上定义追加写的 `TraceEvent`，建议每个 run 输出：

```text
runs/{run_id}/
  trace.jsonl
  ledger.json
  MEMORY.md
  artifacts/
  evaluation.json
  environment.json
```

每条事件至少包含：`event_id/run_id/task_family/node/step/timestamp/model/harness_version/skill_ids+versions/input_ref/output_ref/tool_name/tool_args_hash/status/latency/token_usage/evaluation/failure/environment_fingerprint`。大文本继续使用 `raw_ref`，事件中不复制正文。

设计要求：

- 轨迹在进入演化区前必须经过现有 security redaction；密钥、Cookie、个人信息、业务敏感正文默认禁止进入共享区。
- 记录“使用了哪些技能版本”，否则无法做效果归因。
- 成功标签优先来自确定性断言、真实工具状态和父级验证；LLM Judge 只作为补充信号。
- 轨迹写入失败不得阻塞在线业务，采用缓冲、降级和告警。
- Context Ledger 继续服务运行恢复；TraceStore 服务技能演化，二者通过 `run_id` 和引用关联，不合并成一个臃肿对象。

验收：任一失败 run 可以从 trace 定位失败节点、输入技能版本、工具结果、Evaluator 证据和环境版本；脱敏扫描无高危泄漏。

### 阶段 2：建设只读发布的 SkillRepo 与按需加载

先实现技能“人工创建/发布、Executor 只读加载”，暂不做自动生成。

SkillRepo 建议分区：

```text
skill_repo/
  drafts/
  candidates/
  published/
  retired/
  rejected_edits.jsonl
  index.json
```

加载流程：

```text
任务与节点元数据
  → 硬过滤（工具/权限/模型/版本/适用条件）
  → BGE-M3 或关键词召回
  → 相关性阈值、冲突与依赖检查
  → Token 预算裁剪
  → 注入最多 K 个已发布技能
  → 记录命中及版本用于归因
```

Skill 不应全量塞入 system prompt。建议把“安全和全局硬约束”固定注入，把领域技能放在节点上下文中按需加载。BGE-M3 可复用，但必须保留关键词/规则降级路径，避免本地大模型不可用时中断执行。

验收：无技能命中时行为与现状一致；错误领域技能不被注入；技能总 Token 不超过预算；冲突技能触发拒绝或明确优先级；可以一键禁用某版本。

### 阶段 3：实现离线 Skill Miner 与候选生成

定时任务只消费已结束、已脱敏且证据充分的轨迹。处理步骤为：

1. **筛选**：排除用户取消、环境不可用、目标漂移、Evaluator 证据不足和敏感任务。
2. **聚类**：按 task family、工具链、失败签名和 embedding 聚类；单次偶发经验不能直接升级为通用技能。
3. **差分反思**：在同一任务族中比较成功与失败、低成本与高成本轨迹，识别真正影响结果的步骤。
4. **决策**：输出 `CREATE/ADD/DELETE/REPLACE/MERGE/RETIRE/NOOP`，每个修改必须带证据引用、适用条件、预期收益和潜在副作用。
5. **受限生成**：生成 candidate，不修改 published；单轮 Edit Budget 初始建议限制在正文 10% 或 300 字以内，结构性新技能例外但必须全量评审。
6. **静态检查**：校验 schema、链接、工具名、权限、危险命令、秘密信息、重复技能和循环依赖。

候选生成器应使用较强模型；Executor 仍可使用小模型。所有提示词、模型参数和输入轨迹集合都要版本化，保证候选可重现。

验收：候选的每条新增规则能回溯到至少两条独立证据或一条高可信确定性故障；无证据的“常识补写”被标记并拒绝自动发布。

### 阶段 4：建立 SkillOpt-lite 验证与选择闸门

对同一任务分别运行基线版本和候选版本，优先从 checkpoint 或可重建环境回放。选择规则建议采用硬门槛加综合分：

```text
硬门槛：安全断言全通过
      ∧ 关键业务断言不退化
      ∧ validation 成功率达到最低样本数和提升阈值
      ∧ regression 无显著退化

综合分：0.60 × 任务质量
      + 0.15 × 关键断言通过率
      + 0.10 × Token 改善
      + 0.05 × 轮次改善
      + 0.05 × 延迟改善
      + 0.05 × 稳定性
```

权重可按业务调整，但质量和安全必须优先，成本指标不能抵消错误。涉及写文件、发邮件、日历或外部 API 的回放必须使用沙箱、mock 或只读账户，禁止对生产环境重复产生副作用。

拒绝的编辑写入 `rejected_edits.jsonl`，包含候选哈希、失败用例、退化指标和原因；后续生成时做相似编辑拦截。通过机器验证的候选仍进入人工审批，审批可查看 diff、证据、指标和风险。

验收：训练集提高但验证集退化的候选会被拒绝；重复的失败编辑不会反复出现；任一结果可通过相同环境指纹复跑。

### 阶段 5：灰度发布、监控、熔断与回滚

发布状态流转：

```text
draft → candidate → validated → canary → published → retired
                    ↘ rejected
```

先对少量任务或单一模型启用 canary，并保留 5%～10% 无技能对照流量。监控技能命中率、采纳后成功率、错误技能率、Token 净变化、P95 延迟、回退率、安全告警和不同模型的分层效果。

触发以下任一条件应自动熔断到上一发布版本：关键断言失败、安全事件、连续窗口成功率低于基线、延迟/Token 超预算、技能解析失败或依赖不可用。回滚只切换索引指针，不在线改写 Markdown。

验收：可在一个发布周期内定位到具体技能版本；熔断后 Executor 立即恢复旧版本或无技能模式；历史任务仍能复现当时使用的版本。

### 阶段 6：稳定后再扩展团队共享与半自动发布

满足至少数周稳定运行、评测覆盖充分和误发布率可接受后，再借鉴 SkillClaw 扩展：

- 将演化服务独立部署，执行侧只通过对象存储/数据库交换脱敏轨迹与签名技能包。
- 建立团队 namespace、RBAC、审核人与发布人分离、签名校验和租户隔离。
- 使用空闲客户端或独立 worker 做二次验证，但验证环境必须可证明且不可读取其他租户数据。
- 只有在积累足够的技能调用与反事实数据后，才评估 bandit/RL Curator；先做 shadow mode，不直接控制生产发布。
- MAE 仅用于生成挑战用例，并始终隔离于正式技能来源。

## 五、关键实现细节

### 5.1 技能归因

一个任务可能加载多个技能，不能把成败平均归给所有技能。第一版采用保守归因：记录检索候选、最终注入、实际遵循证据和调用阶段；通过 A/B 或逐个消融确认收益。没有反事实证据时只记“相关”，不记“有效”。

### 5.2 更新触发条件

不按每次失败立即改技能。建议同时满足：同类问题达到最小样本数、跨不同任务出现、Evaluator 结论一致、不是环境瞬态故障。依赖库升级引起的漂移应先更新环境兼容矩阵，不能误总结成通用操作技巧。

### 5.3 技能合并与淘汰

合并要比较适用条件和失败分支，不能只按文本相似度。低频技能不等于无价值；淘汰应基于长期无命中、被新版本完全覆盖、依赖失效或持续负收益，并保留 retired 版本以便审计和回滚。

### 5.4 多模型验证

至少按云端强模型、设备小模型、边端模型分别统计。长而复杂的技能可能提升强模型却压垮 0.5B/3B 模型；必要时允许同一 `skill_id` 存在经验证的模型 profile，但共享核心安全约束和输出契约。

### 5.5 在线性能预算

演化链路必须异步，不能增加在线模型调用。在线只允许本地索引查询、读取已发布技能和上下文拼装。设置检索超时、最大技能数、最大 Token、缓存与无技能降级，确保技能系统故障不拖垮主图。

## 六、改造注意事项与风险

| 风险 | 具体表现 | 控制措施 |
| --- | --- | --- |
| 轨迹隐私与密钥泄漏 | prompt、工具参数、raw_ref 带 API Key 或用户数据 | 入库前脱敏；共享区默认只传摘要/哈希；最小权限；保留期与删除机制 |
| 轨迹投毒 | 用户或工具输出诱导 Curator 写入恶意规则 | 数据来源分级；不把原始文本当指令；静态安全扫描；双人审批关键技能 |
| 错误自强化 | 错误输出被 Judge 判为成功并沉淀 | 确定性断言优先；父级验证；多条独立证据；留出集与人工抽检 |
| 评测泄漏/过拟合 | 候选模型见过验证答案，指标虚高 | 数据分组隔离；验证集只对评测器开放；定期轮换隐藏回归集 |
| 奖励投机 | 为省 Token 跳过核验或提前结束 | 质量/安全硬门槛；成本只作次级指标；失败代价单独统计 |
| 技能冲突 | 多技能给出相反步骤或工具顺序 | 适用条件硬过滤；优先级和互斥声明；冲突即降级或请求上层决策 |
| 技能膨胀 | 重复、过细、过期技能拖慢检索 | 去重、覆盖关系、命中/净收益统计、定期人工整理与 retired 状态 |
| 环境漂移 | 库/API/模型升级后旧技能失效 | environment fingerprint；兼容范围；定期回归；依赖变化触发重新验证 |
| 跨模型迁移失真 | 同一 Markdown 在小模型上不遵循 | 分模型验证和指标；模型 profile；小模型使用更短、更确定的规程 |
| 回放副作用 | 重发邮件、重复写文件或调用生产 API | mock/沙箱/只读账户；幂等键；外部动作审批；禁止生产回放 |
| 检索误命中 | 无关技能污染 prompt | 高阈值、硬标签过滤、top-k 限制、可观测命中、无技能降级 |
| 在线性能退化 | 检索和技能文本增加延迟/Token | 异步演化、本地缓存、Token 预算、超时、P95 门槛和熔断 |
| 并发版本不一致 | 长任务中途切换技能导致行为突变 | run 开始时固定 skill snapshot；新版本只影响新 run；版本引用持久化 |
| 权限越界 | Curator 或子 Agent 直接发布/覆盖技能 | Executor 只读；候选区与发布区权限隔离；发布签名；外部父级/人工授权 |

## 七、建议验收里程碑

1. **M1：可观测**——两类试点任务拥有完整、脱敏、可回放轨迹，且不影响在线执行。
2. **M2：可使用**——人工技能能够按需检索、预算注入、版本固定和一键禁用，无命中时等价降级。
3. **M3：可演化**——系统可从重复成功/失败轨迹生成有证据的原子候选编辑，但不能自动覆盖发布技能。
4. **M4：可证明**——候选必须通过隔离验证、隐藏回归、安全门槛和人工审批；拒绝原因可复用。
5. **M5：可运营**——具备灰度、对照、效果归因、熔断、回滚、审计和跨模型分层指标。
6. **M6：可扩展**——在前五项稳定后，再拆分 Evolve Service、接共享存储和团队技能同步。

## 八、最终取舍

- **直接采用**：工具/技能分层、Markdown 程序性记忆、Executor/Curator 分工、轨迹差分反思、Edit Budget、留出验证、拒绝缓存、版本与回滚、复合运行指标。
- **改造后采用**：SkillClaw 的采集/演化解耦与候选验证机制，改为优先使用本项目原生 Hook 采集；SkillOpt 改为离线 lite 版；SkillOS 的复合奖励改为可解释的评测计分，不训练 RL。
- **暂不采用**：在线 RL Curator、自动剪枝、无审批自动发布、MAE 生产自对弈、全量技能常驻 prompt、直接把现有 MemoryStore 当 SkillRepo。
- **最佳落地路线**：先建立可靠数据和人工可控闭环，再逐步提高自动化率。对于当前项目，这是成本、风险、可验证性和未来扩展性之间最平衡的方案。
