要把当前工程变成真正可使用的产品，核心不是继续堆 Agent 模块，而是把已有能力串成一条稳定、可配置、可观察、可恢复、可迭代的业务闭环。

暂不考虑需要服务器训练的 BGE-M3 微调，建议按下面顺序推进：

```text
明确产品边界
→ 打通真实模型调用
→ 工作流持久化与版本化
→ 任务运行中心
→ 前端编排与运行页面
→ 工具管理
→ 上下文、记忆和恢复闭环
→ 轨迹与评测体系
→ 技能后台演化
→ 灰度发布与回滚
→ 权限、安全和审计
→ 测试、部署、监控
→ 受控动态 Agent
```

其中前六项决定产品能不能正常用，后面的项目决定产品能不能长期稳定运行和自我进化。

# 一、先确定产品形态和第一批业务场景

优先级：P0  
建议周期：3～5 个工作日

当前项目底层能力很多，但产品边界还比较宽：

- 图编排
- 多 Agent
- 上下文管理
- 长期记忆
- 边云调度
- 技能演化
- 邮件、旅行、日历等示例

如果同时把所有方向做成正式产品，验收标准会非常模糊。

## 1.1 建议的产品定位

建议第一阶段定义为：

> 一个支持可视化配置、执行、监控和持续优化的多 Agent 工作流平台。

核心用户是：

- Agent 应用开发人员
- 企业内部流程配置人员
- Agent 运维和审核人员

第一阶段暂时不要把“完全自主创建无限层级 Agent”作为核心卖点。

## 1.2 第一批业务场景

建议选择两个正式试点：

### 场景 A：旅行规划

用于验证：

- 多 Agent 扇出、扇入
- 搜索工具
- 多步骤协同
- 预算约束
- 最终结果审核
- 技能复用

### 场景 B：邮件或日历处理

用于验证：

- 外部工具调用
- 权限控制
- 人工确认
- 有副作用操作
- 失败恢复
- 审计记录

旅行规划偏“只读推理”，邮件和日历偏“有副作用执行”，两者可以覆盖产品最重要的能力。

## 1.3 需要输出的产品定义

- 目标用户
- 核心使用场景
- 非目标范围
- 用户角色
- 核心业务流程
- MVP 功能范围
- 产品成功指标

## 1.4 MVP 成功指标

建议先定义：

- 工作流创建成功率
- 任务成功完成率
- 任务平均执行时间
- 节点失败恢复率
- 人工介入率
- 工作流发布后执行成功率
- 技能命中率
- 技能使用后的成功率变化
- 单任务 Token 和成本
- 严重安全事件数量

## 验收标准

- 明确第一版做什么、不做什么。
- 每个功能能对应到真实用户场景。
- 每个场景拥有可重复执行的验收任务集。

# 二、打通真实 Agent 与模型调用

优先级：P0，最高  
建议周期：1～2 周

这是当前工程最重要的产品缺口。

当前 `Orchestrator` 默认把 `AgentSpec` 转成 Echo Node，只回显输入。要成为产品，用户在界面创建 Agent 后，系统必须能根据配置创建并运行真实 Agent。

## 2.1 建立统一 AgentFactory

建议新增：

```text
engine/agents/
  __init__.py
  factory.py
  registry.py
  _types.py
  validation.py
```

职责：

```text
AgentSpec
    ↓
检查模型、工具、权限和 Prompt
    ↓
构造真实 AgentScope Agent
    ↓
通过 adapters.py 包装成 Node
```

建议接口：

```python
class AgentFactory:
    def create_node(
        self,
        spec: AgentSpec,
        runtime_context: AgentRuntimeContext,
    ) -> Node:
        ...
```

## 2.2 AgentSpec 需要补充的配置

至少增加：

```text
provider
model
temperature
max_output_tokens
timeout
system_prompt
tool_ids
input_contract
output_contract
retry_policy
resource_policy
context_policy
skill_policy
```

不能继续把全部配置塞进没有约束的 `config: Dict[str, Any]`。需要结构化模型和参数校验。

## 2.3 模型供应商管理

建立统一模型配置：

```text
DeepSeek/OpenAI 兼容云端模型
Ollama 本地模型
边端 HTTP 模型
```

模型配置需要区分：

- `model_id`：产品内部 ID
- `provider`
- `model_name`
- `base_url`
- `credential_ref`
- `context_window`
- `max_output_tokens`
- `supports_tools`
- `enabled`
- `timeout`
- `cost_profile`

API Key 不能保存在工作流 JSON 或前端请求里，只保存凭据引用。

## 2.4 完善真实输入注入

真实 Agent 输入按固定顺序构造：

```text
系统身份和安全规则
→ 原始任务目标
→ 当前节点职责
→ 当前步骤目标
→ 已验证事实
→ 已发布技能
→ 相关长期记忆
→ 用户当前输入
→ 输出契约
```

需要避免：

- 同一内容重复注入。
- Skill、Memory 和 Context 顺序混乱。
- 上下文超过模型窗口。
- 子 Agent 获得不应该看到的数据。

## 2.5 统一模型返回格式

每个真实 Agent 至少返回：

```json
{
  "status": "success",
  "output": {},
  "messages": [],
  "usage": {
    "input_tokens": 0,
    "output_tokens": 0
  },
  "model": "",
  "latency_ms": 0
}
```

业务输出应该符合节点定义的 `output_contract`。

## 验收标准

- 创建 Agent 后能够真实调用指定模型。
- `sys_prompt`、模型参数和工具配置真实生效。
- 模型超时、限流和异常有统一错误。
- 技能、记忆和上下文能进入真实模型输入。
- 默认 Echo 模式只用于测试，不用于生产运行。

### 工具

每次任务启动时固定版本快照。

## 验收标准

- 草稿修改不会影响已发布工作流。
- 历史任务能查到当时使用的全部版本。
- 数据库迁移可以重复执行。

# 四、完善工作流编排生命周期

优先级：P0  
建议周期：1～2 周

当前可以创建 Agent、连接边、设置入口，但仍缺少产品级工作流管理。

## 4.1 工作流状态

```text
draft
testing
published
archived
```

用户不能直接修改已发布版本，应当：

```text
克隆已发布版本
→ 修改草稿
→ 测试
→ 发布新版本
```

## 4.2 区分两种关系

必须明确区分：

### 执行关系

```text
A 执行完以后执行 B
```

由图边表示。

### 管理关系

```text
A 是 B 的父 Agent，负责验证 B 的输出
```

由 `parent_id` 表示。

不能继续让用户误以为“父子关系自动等于执行顺序”。

## 4.3 图结构校验

发布前必须检查：

- 是否存在入口。
- 是否存在不可达节点。
- 是否存在没有终止条件的循环。
- 条件边是否覆盖必要分支。
- 子 Agent是否形成父级循环。
- 节点输入是否能由前序节点提供。
- 节点工具是否存在。
- 模型是否启用。
- 输出契约是否满足后继输入。
- 是否有未经确认的高风险外部动作。

## 4.4 工作流试运行

草稿发布前提供“测试运行”：

- 使用测试输入。
- 禁止生产副作用。
- 展示每个节点的输入、输出和状态。
- 展示模型、工具、Token 和延迟。
- 展示 Evaluator 结果。

## 验收标准

- 工作流可以创建、保存、测试、发布、复制和归档。
- 非法图无法发布。
- 每次任务绑定一个不可变的工作流版本。
- 父子管理关系与执行边互不混淆。

# 五、建设任务运行中心

优先级：P0  
建议周期：2 周

真正的产品不能只提供一个同步 `/api/run`，需要完整任务生命周期。

## 5.1 Run 状态机

```text
created
→ queued
→ running
→ completed

running
→ paused
→ running

running
→ validation_failed
→ repairing
→ running

running
→ failed/cancelled
```

## 5.2 Run API

建议新增：

```text
POST /api/runs
GET  /api/runs
GET  /api/runs/{run_id}
GET  /api/runs/{run_id}/events
POST /api/runs/{run_id}/pause
POST /api/runs/{run_id}/resume
POST /api/runs/{run_id}/cancel
POST /api/runs/{run_id}/retry
GET  /api/runs/{run_id}/artifacts
```

## 5.3 异步执行

用户提交任务后不应一直占用普通 HTTP 请求。

建议流程：

```text
POST /api/runs
    ↓
创建 run
    ↓
放入任务队列
    ↓
后台 worker 执行
    ↓
通过 SSE/WebSocket 推送事件
```

没有服务器时可以先实现进程内队列，但接口结构应当支持未来切换：

- Redis Queue
- Celery
- Dramatiq
- 独立 worker

## 5.4 实时事件

前端应收到：

```text
run_started
step_started
node_started
tool_started
tool_completed
node_completed
node_failed
validation_failed
run_paused
run_completed
```

## 5.5 暂停、恢复和取消

复用现有：

- `GraphCheckpointStore`
- `ContextCheckpointStore`
- Context Ledger
- `resume_from`

补齐：

- 用户暂停标记。
- 节点边界安全暂停。
- 取消信号。
- checkpoint 与数据库 run 状态一致性。
- 恢复时固定原工作流和技能版本。

## 验收标准

- 提交任务后立即获得 `run_id`。
- 可以实时看到执行进度。
- 页面刷新后任务仍然存在。
- 进程重启后可以从 checkpoint 恢复。
- 任务可以取消、暂停和重试。
- 运行中的版本不会被新发布内容影响。

# 七、建立正式工具管理体系

优先级：P0/P1  
建议周期：1～2 周

当前示例中的工具散落在各 `examples/*/tools.py` 中，还不是统一产品能力。

## 7.1 Tool Registry

建议建立：

```text
engine/tools/
  registry.py
  base.py
  schema.py
  permissions.py
  runner.py
```

每个工具注册：

```text
tool_id
name
description
input_schema
output_schema
risk_level
timeout
idempotent
requires_confirmation
credential_type
enabled
```

## 7.2 工具风险分类

### 只读低风险

- 搜索
- 查询天气
- 读取日历
- 读取文件

### 中风险

- 创建本地文件
- 修改草稿
- 产生费用的 API

### 高风险

- 删除文件
- 发送邮件
- 修改日历
- 修改生产数据
- 执行系统命令

## 7.3 人工确认

高风险操作流程：

```text
Agent 生成工具调用提案
→ Run 进入 awaiting_approval
→ 前端展示参数和影响
→ 用户确认
→ 执行工具
```

## 7.4 幂等与补偿

外部写操作需要：

- 幂等键。
- 执行前检查。
- 执行后验证。
- 可用时提供撤销。
- 重试时防止重复副作用。

## 验收标准

- Agent 只能调用已授权工具。
- 工具参数经过 schema 校验。
- 高风险工具未经批准不能执行。
- 超时和异常有统一结果格式。
- 重试不会重复发送邮件或创建事件。

# 八、完成上下文和长期记忆的产品化

优先级：P1  
建议周期：1～2 周

当前上下文模块已经较完整，下一步重点是配置、存储和产品接入。

## 8.1 ContextPolicy 产品化

工作流或 Agent 可配置：

```text
最大上下文 Token
预留输出 Token
最大记忆 Token
最大工具摘要 Token
漂移阈值
重复工具限制
无进展限制
超预算动作
```

## 8.2 MEMORY.md 的定位

继续保留：

```text
runs/{run_id}/MEMORY.md
```

但产品页面应将它展示为“运行摘要”，不要称为长期技能。

## 8.3 长期记忆治理

需要增加：

- 记忆来源。
- 可信度。
- 是否已验证。
- 过期时间。
- 可见范围。
- 删除能力。
- 用户纠错。
- 数据保留策略。

## 8.4 记忆污染控制

只有以下信息可以进入高可信长期记忆：

- 确定性工具结果。
- Evaluator 已验证结果。
- 父级确认结果。
- 人工确认结果。

模型自己的陈述默认是未验证信息。

## 验收标准

- 长任务不会因上下文增长而静默截断。
- 暂停后能够根据 ledger 恢复。
- 用户可以查看和删除自己的长期记忆。
- 未验证输出不会自动提升为可信事实。

# 十、建立正式评测体系

优先级：P1  
建议周期：2～3 周

没有评测体系，工作流、Prompt、模型和技能都无法安全升级。

## 10.1 评测集分层

```text
development
validation
hidden regression
safety
```

相似问题必须按任务族分组，不能随机拆分导致泄漏。

## 10.2 Evaluator 分层

优先级建议：

```text
确定性断言
→ 工具状态核验
→ schema 校验
→ 业务规则
→ LLM Judge
→ 人工抽检
```

不能让 LLM Judge 成为唯一依据。

# 十一、实现技能后台演化闭环

优先级：P1  
建议周期：3～4 周

现有代码已经具备：

- Skill 数据结构
- 文件型 SkillRepo
- 已发布技能检索
- 执行轨迹
- 候选生成基础
- 验证入口
- 发布、退休、回滚

但还缺少后台自动调度和生产级验证。

## 11.1 后台演化调度器

建议新增独立服务或 worker：

```text
evolution_worker/
  scheduler.py
  selector.py
  clusterer.py
  optimizer.py
  validator.py
  publisher.py
```

工作流程：

```text

→ 筛选有效轨迹
→ 按任务族和失败模式聚类
→ 判断 CREATE/UPDATE/MERGE/NOOP
→ 生成候选
→ 静态检查
→ 自动验证
→ 进入待审批或自动灰度
```

## 11.2 轨迹筛选

排除：

- 用户取消。
- 环境或网络临时故障。
- 敏感数据未正确脱敏。
- 严重上下文漂移。
- 无 Evaluator 证据。
- 测试或调试任务。
- 重复轨迹。
- 被人工标记为无效的任务。

## 11.3 候选生成器升级

当前规则型生成只能作为基础版本。生产候选生成应支持调用强模型，并强制输出：

```text

修改位置
修改前
修改后
来源轨迹
原因
预期收益
潜在风险
适用条件
不适用条件
```

允许的操作：

```text
CREATE
ADD
DELETE
REPLACE
MERGE
RETIRE
NOOP
```

## 11.4 自动验证

后台自动完成：

- Markdown/manifest schema 校验。
- 敏感信息扫描。
- 危险操作扫描。
- 工具存在性检查。
- 依赖检查。
- 训练任务回放。
- 隔离验证集。
- 隐藏回归集。
- 跨模型验证。
- Token 和延迟比较。

## 11.5 发布策略

第一阶段：

```text
自动生成
→ 自动验证
→ 人工批准
→ 发布
```

不需要完整 Skill 工作台，只需“待审批”入口。

## 验收标准

- 无需开发人员写 Python 即可生成候选。
- 候选有完整来源证据。
- 不合格候选自动进入 rejected。
- 未审批候选不能进入 published。
- 技能演化故障不影响在线任务。

# 十三、实现技能灰度、熔断和自动回滚

优先级：P1/P2  
建议周期：2 周

技能不能验证通过后直接覆盖全部生产任务。

## 13.1 灰度策略

建议：

```text
5% → 20% → 50% → 100%
```

每一阶段观察：

- 最低样本数
- 成功率
- 关键断言
- 安全事件
- Token
- 延迟
- 人工介入率

## 13.2 技能快照

任务开始时固定：

```text
skill_id
skill_version
skill_content_hash
```

任务中途不能切换技能。

## 13.3 熔断条件

- 安全断言失败。
- 关键业务断言失败。
- 连续窗口成功率低于旧版本。
- P95 延迟超限。
- Token 明显恶化。
- 技能文件损坏。
- 依赖工具不可用。

## 13.4 回滚

不删除新版本，只把发布索引原子切回旧版本。

## 验收标准

- 错误技能只影响小范围灰度任务。
- 熔断后新任务立即回到旧版本。
- 回滚过程不修改历史任务数据。
- 可以查明哪个指标触发了回滚。

# 十五、完善异常处理与降级

- 非关键扩展故障不会拖垮主任务。
- 关键安全组件故障时执行安全暂停。

# 十八、最后再实现受控动态 Agent

优先级：P2  
建议在前述闭环稳定后实施

这才对应“父 Agent理解任务并现场创建子 Agent”。

建议不要允许直接修改正式工作流，而是生成当前 run 专属的临时执行计划：

```text
用户任务
→ Planner 生成结构化任务 DAG
→ Dynamic Plan Validator 校验
→ 选择已有 Agent 模板
→ 实例化临时节点
→ 加入当前 run 临时子图
→ 执行
→ 任务结束后销毁
```

## 必须限制

- 最大临时 Agent 数量。
- 最大嵌套层数。
- 最大总步骤数。
- 最大 Token 和费用。
- 允许的模型列表。
- 允许的工具列表。
- 禁止临时 Agent发布技能。
- 禁止修改正式编排。
- 子 Agent结果必须验证。
- 动态图必须写入 trace 和 checkpoint。

## 验收标准

- Planner 不能创建无限 Agent。
- 动态节点只能选择已批准模板和工具。
- 动态计划不合法时回退到静态工作流。
- 可以完整复现某次任务的动态图。

# 二十、当前最应该立即开始的工作

排除 BGE-M3 微调后，近期优先级应严格按照以下顺序：

1. 明确 MVP 场景和成功指标。
2. 实现真实 `AgentFactory`，替换生产路径中的 Echo Node。
3. 建立数据库和 Repository 层。
4. 实现 Agent、工作流和版本持久化。
5. 建立 Run 状态机和异步执行。
6. 开发最小前端：Agent、编排、运行、详情。
7. 统一工具注册、权限和人工确认。
8. 补全评测体系和任务验收集。
9. 将现有技能模块接入后台调度。
10. 增加最小技能审批入口。
11. 增加灰度、熔断和自动回滚。
12. 最后实现受控动态 Agent。

最需要避免的是同时开发“动态 Agent、技能自动发布、边云学习和复杂前端”。应先确保这一条最基本链路稳定：

```text

→ 保存运行记录

```

这条链路完成后，项目才是“能用的产品”；再补上：

```text
轨迹
→ 候选技能
→ 自动验证
→ 审批
→ 灰度
→ 回滚
```

项目才真正形成长期自我进化的完整闭环。
