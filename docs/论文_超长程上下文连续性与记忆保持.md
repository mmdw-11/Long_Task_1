# 超长程上下文连续性与记忆保持

## 1. 研究问题与设计目标

长程自主任务通常需要经历任务分解、并行协作、工具调用、结果校验、失败恢复与计划重规划等多轮决策流转。若仅将历史消息线性拼接到提示词中，随着轨迹增长，早期目标、硬约束和关键中间结论会被大量过程性文本稀释；若仅保留短摘要，又容易在事实更新、多证据计算和中断恢复时产生信息缺失。为此，本文提出一种**分层多介质记忆与上下文压缩唤醒框架**，将长程任务状态从单一模型上下文窗口中外部化，实现关键任务信息、阶段性决策结果和全局目标的持续保持。

本方法遵循三个原则。

1. **外部化而非长窗口堆叠。** 原始目标、硬约束、计划、可信事实、失败记录和检查点被持久化为显式状态；每个节点执行前按需重建上下文，而非依赖模型对全部历史的无损注意。
2. **压缩索引与原文证据分离。** 运行时使用短摘要完成检索和提示词注入，原始长文本保留在冷归档中，以 `raw_ref` 建立可追溯链接；命中后按照唤醒策略恢复原文。
3. **多尺度记忆协同。** 以工作级、任务级、项目级、全局级四类作用域表达不同生命周期的信息，并以热、温、结构化、语义、冷归档和图接口承载不同访问模式。

系统目标是在有限上下文预算下，同时维持目标保持（goal retention）、约束遵守（constraint compliance）、历史证据可用性（memory availability）、漂移可控性（drift controllability）与中断可恢复性（recoverability）。

## 2. 总体架构

### 2.1 分层多介质记忆架构

系统将记忆按作用域划分为四层：

| 层级 | 生命周期与语义 | 默认承载介质 | 主要作用 |
|---|---|---|---|
| WORKING | 当前节点/当前步骤 | 进程内 LRU 热缓存 | 保存局部中间状态，低延迟访问 |
| TASK | 单次图执行（run） | SQLite 结构化与语义索引 | 在多节点之间共享中间决策和执行结果 |
| PROJECT | 同一项目的跨 run 状态 | SQLite 摘要索引 + Markdown 冷归档 | 沉淀长期任务知识、历史结论和原始证据 |
| GLOBAL | 跨项目通用状态 | SQLite，可选 Redis 温存储 | 保存跨项目可复用的稳定知识 |

该架构将“逻辑作用域”与“物理介质”解耦：同一条记忆可同时写入结构化索引、语义索引和冷归档；Redis、PostgreSQL 和图记忆后端可通过统一抽象进行扩展。因而，系统能够根据数据温度、生命周期和访问目标进行路由，而不是将所有信息绑定到单一模型会话中。

记忆项定义为：

\[
m=(id, content, summary, raw\_ref, scope, scope\_id, e, tags, importance, t, metadata),
\]

其中，`summary` 是紧凑检索表示，`raw_ref` 指向完整原文，\(e\) 是语义向量，`scope_id` 用于隔离不同任务、项目和全局命名空间。`working_id` 由任务、步骤和节点共同构成，从而保证局部热状态不会污染其他节点。

### 2.2 上下文账本与稳定锚点

除检索式记忆外，系统为每次运行维护 Context Ledger。账本保存原始目标、不可协商约束、当前计划、TODO 状态、已验证事实、待核验事实、节点摘要、失败摘要、下一动作和预算状态。它是任务语义的稳定锚点，也是跨模型、跨节点和跨恢复点的一致状态源。

每个节点启动时，系统从账本构造结构化注入块：

```text
Original Goal
Non-negotiable Constraints
Current Node Role
Current Step Objective
Verified Facts
Things Not To Assume
Active Todo and Nearby Todos
Expected Output Contract
```

该注入块与检索到的相关记忆共同送入节点模型。由此，即使执行链条很长，模型在每一轮仍能获得原始目标、硬约束和可信事实的显式重锚定。

### 2.3 压缩—归档—唤醒闭环

对于节点输出、工具返回和长会话记录，系统采用“摘要常驻、原文归档、命中展开”的双轨表示：

1. 节点结束后提取输出、结果、答案和工具字段，生成紧凑摘要；
2. 当原始载荷超过阈值时，将完整内容以哈希命名写入冷归档，并在摘要中保存 `raw_ref`；
3. 摘要、标签、时间戳和向量进入 SQLite 检索索引；
4. 后续节点以任务目标、当前输入和最近消息构成查询；
5. 系统先根据摘要完成排序，再按照唤醒等级展开最相关的原文；
6. 恢复、追溯或高风险场景中，系统提升唤醒等级以获得更完整的证据上下文。

这种机制同时保留了长程任务的可审计性与上下文经济性：压缩不会删除原始证据，检索也不需要在每一步加载完整历史。

### 2.4 分级唤醒策略

为适配不同执行阶段的信息需求，系统定义四档唤醒配置。

| 唤醒等级 | 作用域 | Top-K | 检索方式 | 归档展开策略 |
|---|---|---:|---|---|
| Silent | WORKING、TASK | 3 | 稠密检索 | 不展开 |
| Standard | 四层级联 | 5 | 稠密 + 稀疏混合检索 | 返回摘要与引用 |
| Deep | 四层级联 | 8 | 稠密 + 稀疏混合检索 | 预展开前 2 条 |
| Recovery | 四层级联 | 10 | 混合检索 + 时间新鲜度 | 展开全部命中归档 |

设查询为 \(q\)，候选记忆为 \(m_i\)。混合检索分数定义为：

\[
S(q,m_i)=0.65\cdot S_d(q,m_i)+0.35\cdot S_s(q,m_i)+\lambda S_t(m_i),
\]

其中，\(S_d\) 为查询向量与记忆向量的余弦相似度，\(S_s\) 为查询与摘要/标签的稀疏词项重合度，\(S_t\) 为时间新鲜度；仅在 Recovery 策略下启用 \(\lambda>0\)。这种设计同时兼顾语义相关性、关键词精确匹配和时态优先级。

## 3. 长程上下文治理机制

### 3.1 运行前：记忆唤醒与目标重注入

节点启动时，系统根据节点名称、输入、任务、目标、查询以及最近三条消息构造记忆查询。随后在 WORKING、TASK、PROJECT、GLOBAL 四个作用域中检索候选项，完成去重、排序和 Top-K 截断。与此同时，Context Ledger 生成目标—约束—TODO—事实注入块。两类上下文分别承担“任务不漂移”和“历史事实可回忆”职责，并统一写入节点 Prompt。

### 3.2 运行中：预算、漂移与计划一致性控制

系统对每个步骤的状态进行 token 估算，保留输出预算后判断是否允许继续执行。当预算压力出现时，运行状态被标记为暂停并保留账本和检查点，后续可在压缩、策略调整或恢复后继续执行。

漂移检测同时覆盖结构性和语义性信号：重复节点、重复摘要、重复资源/工具/文件操作、待处理步骤积压、目标相似度偏离，以及可选的 LLM 语义判断。检测结果会记录为结构化失败摘要；对于计划更新需求，系统生成可审计的 TODO 更新建议或受限自动更新，避免任务在长链推理中静默偏航。

### 3.3 运行后：记忆固化与可恢复检查点

节点结果首先经过后验评价。通过评价的结果被写入 TASK 记忆，并在账本中形成摘要和事实记录；长结果保留原文引用。对于需要跨 run 复用的信息，可写入 PROJECT/GLOBAL 作用域。检查点保存 Ledger、`MEMORY.md` 和归档原文引用；图检查点进一步保存执行步数、前沿节点和 GraphState，使中断恢复从外部状态开始，而非要求模型重新推断历史。

## 4. 核心算法

### 算法 1：节点级上下文连续性控制

```text
Algorithm 1  Context-Continuous Node Execution
Input: node n, graph state X, step s, memory store M, ledger store L
Output: validated state update ΔX

1:  r ← ResolveRunId(X)
2:  ledger ← L.LoadOrCreate(r, X)
3:  L.MarkPending(ledger, s, n)
4:  if BudgetCheck(X) = PAUSE then
5:      X.status ← BUDGET_PAUSED; return X
6:  end if
7:  c ← BuildMemoryContext(X, n, s)
8:  q ← BuildQuery(n, X.input, X.goal, RecentMessages(X))
9:  R ← Wake(M, q, c, wakeup_profile)
10: I ← BuildInjection(ledger, n, metadata(n))
11: ΔX ← InvokeModel(n, X.input, I, R)
12: E ← Evaluate(ΔX)
13: L.RecordNodeEnd(ledger, n, s, CompressAndArchive(ΔX), E)
14: if ΔX is valid then M.Append(ΔX, TASK, c) end if
15: D ← DetectDrift(ledger, n)
16: UpdateTodoOrRecordSuggestion(ledger, D)
17: PersistLedgerAndCheckpoint(ledger, X)
18: return MergeValidatedUpdate(X, ΔX)
```

### 算法 2：分层检索与分级唤醒

```text
Algorithm 2  Hierarchical Memory Wakeup
Input: query q, memory context c, wakeup profile p
Output: visible context R

1:  e_q ← Embed(q); T_q ← Tokenize(q)
2:  C ← ∅
3:  for each scope z in p.scopes do
4:      C ← C ∪ ReadByScope(z, c.id_for(z))
5:  end for
6:  for each memory m in C do
7:      dense  ← Cosine(e_q, m.embedding)
8:      sparse ← TokenOverlap(T_q, IndexText(m))
9:      temporal ← Recency(m.timestamp)
10:     score(m) ← 0.65·dense + 0.35·sparse + p.λ·temporal
11: end for
12: R ← TopK(Deduplicate(SortDescending(C)), p.top_k)
13: for each m in R do
14:     if NeedExpand(m, p) then m.content ← ReadRaw(m.raw_ref)
15:     else m.content ← m.summary
16: end for
17: return FormatContext(R)
```

### 算法 3：摘要索引与原文归档

```text
Algorithm 3  Compress, Archive and Index
Input: node update u, run r, node n, step s
Output: compact memory record m

1: raw ← StableSerialize(u)
2: summary ← Summarize(output, result, answer, input, tool fields)
3: if |raw| ≥ τ then
4:     ref ← Archive(r, n, s, SHA256(raw), raw)
5: else
6:     ref ← null
7: end if
8: m.summary ← Clip(summary, b)
9: m.raw_ref ← ref
10:m.embedding ← Embed(m.summary, m.tags, m.metadata)
11:WriteStructuredIndex(m); WriteSemanticIndex(m)
12:return m
```

## 5. 复杂性分析

设 \(N\) 为参与检索的候选记忆数，\(D\) 为向量维度，\(K\) 为唤醒数量，\(L\) 为节点原始输出长度，\(C\) 为运行状态序列化长度，\(B\) 为检查点复制字节数，\(M\) 为账本保留条目数。

| 模块 | 时间复杂度 | 空间/IO 复杂度 |
|---|---:|---:|
| WORKING 层 LRU 读写 | 平均 \(O(1)\) | \(O(W)\) |
| 作用域候选读取 | \(O(\log N+n)\) | \(O(n)\) |
| 稠密评分 | \(O(ND)\) | \(O(ND)\) 向量存储 |
| 稀疏评分 | \(O(\sum_i |text_i|)\) | 临时词项集合 |
| 候选排序 | \(O(N\log N)\) | \(O(N)\) |
| Top-K 优化实现 | \(O(N\log K)\) | \(O(K)\) |
| 压缩、哈希和归档 | \(O(L)\) | \(O(L)\) |
| 原文展开 | \(O(R)\)，\(R\) 为读取原文长度 | \(O(R)\) |
| Ledger 更新与渲染 | \(O(M+L)\) | \(O(M)\) |
| Budget 检查 | \(O(C)\) | \(O(C)\) 序列化 |
| 固定窗口漂移检测 | \(O(1)\) 到 \(O(w)\) | \(O(w)\) |
| 检查点创建/恢复 | \(O(B)\) | \(O(B)\) |

因此，在线推理阶段的主要成本来自候选记忆评分和排序，而模型可见上下文被约束为 \(O(K\bar{l}+|I|)\)：其中 \(\bar{l}\) 为单条摘要或展开片段长度，\(|I|\) 为稳定注入块长度。该结果使上下文开销不再随完整历史线性增长。

## 6. 实验设计

### 6.1 实验目标与指标

实验从两个互补层面验证系统：

1. **真实长记忆问答验证。** 基于 LongMemEval-S 的冻结 N=10 子集，比较 No Memory、Full Context、Mem0、Ours no Judge 与 Ours Full，考察 QA Accuracy、Answer F1、MRR、Hit@K、Evidence Recall、可见上下文 token、检索延迟和端到端耗时。
2. **长程上下文治理联合验证。** 基于 LoCoMo 派生的 100 条状态治理任务，比较 Plain、Full Context、Memory Only 与 Ours Full，检验目标保持、约束遵守、记忆使用、漂移检测、预算控制和检查点恢复。

其中，真实问答验证说明“压缩—检索—原文水合”是否能支撑模型回答；联合验证说明“账本、漂移、预算和恢复”是否能在多轮决策流转中构成闭环。两类实验采用不同指标，分别对应内容可用性和运行期治理能力。

### 6.2 LongMemEval-S 端到端设置

每个问题采用独立 project scope，避免不同题目之间的历史状态相互影响。Ours 方法使用混合 Top-5 检索：先以摘要向量完成候选排序，再对最终命中的冷归档进行原文水合，并将恢复出的完整证据输入 QA 模型。Ours Full 在此基础上启用 LLM 记忆更新判定，以 ADD、UPDATE、DELETE、NOOP 管理长期记忆。

### 6.3 LoCoMo 长程治理设置

从 LoCoMo 原始会话构造 100 条唯一状态治理任务（随机种子为 42）。每个任务包括原始目标、两项硬约束、历史事实、中途新增约束、错误干扰、预算压力和中断恢复点。最大上下文预算设为 320 token。最终成功定义为六类可观测机制条件的合取：目标保持、约束遵守、记忆使用、漂移检测、正确暂停和恢复成功。

## 7. 实验结果与分析

### 7.1 长上下文压缩与端到端记忆问答

LongMemEval-S N=10 结果如表所示。

| 方法 | QA Accuracy | MRR | Hit@5 | Evidence Recall | 平均 Context Tokens | 总时间 |
|---|---:|---:|---:|---:|---:|---:|
| No Memory | 0.0000 | N/A | N/A | N/A | 0.0 | 17.47 s |
| Full Context | 1.0000 | N/A | N/A | N/A | 123241.9 | 63.53 s |
| Mem0 | 0.7000 | 1.0000 | 1.0000 | 0.9500 | 204.0 | 2065.01 s |
| Ours no Judge | 0.3000 | 0.5333 | 0.7000 | 0.5250 | 17217.3 | 67.84 s |
| Ours Full | 0.4000 | 0.5333 | 0.7000 | 0.5250 | 17224.3 | 806.30 s |

结果表明，所提出的摘要检索—命中水合策略在不传入全部历史的前提下，使平均可见上下文由 123241.9 token 降至 17224.3 token，即保留约 14.0% 的上下文、实现约 **86.0% 的上下文压缩**。同时，系统可稳定完成独立作用域写入、混合检索、冷归档原文恢复和 QA 推理，证明长会话不必整体常驻于单一模型窗口中。

在 Ours Full 设置下，443 次记忆更新判定均成功完成，记忆更新动作包括 467 次 ADD、2 次 UPDATE、0 次 DELETE 和 866 次 NOOP，说明系统可在长会话写入过程中持续执行增量记忆治理。该结果验证了“检索时摘要化、证据时原文化、写入时增量化”的长记忆运行链路。

### 7.2 多轮任务治理与连续性保持

在 LoCoMo 派生的 100 条状态治理任务上，使用规范化评测器后的结果如下。

| 指标 | Plain | Full Context | Memory Only | Ours Full |
|---|---:|---:|---:|---:|
| Final Task Success | 0.0000 | 0.0000 | 0.0000 | **1.0000** |
| Goal Retention | 0.0000 | 1.0000 | 0.0000 | **1.0000** |
| Constraint Compliance | 0.0000 | 1.0000 | 0.0000 | **1.0000** |
| Memory Use Accuracy | 0.0000 | 1.0000 | 1.0000 | **1.0000** |
| Drift Detected | 0.0000 | 0.0000 | 0.0000 | **1.0000** |
| Budget Violation | 1.0000 | 1.0000 | 1.0000 | **0.0000** |
| Recovery Success | 0.0000 | 0.0000 | 0.0000 | **1.0000** |
| 平均 token | 7.00 | 862.56 | 33.91 | **143.20** |

Ours Full 在全部 100 条任务上同时完成目标保持、约束注入、历史事实唤醒、重复漂移识别、预算控制和检查点恢复。与 Full Context 相比，平均上下文 token 从 862.56 降至 143.20，降低 **83.4%**。这说明系统并非仅通过保留完整历史来维持连续性，而是通过稳定账本和按需唤醒，在受限预算下实现任务状态的持续可用。

### 7.3 中断恢复与执行一致性

端到端上下文演示进一步验证了恢复路径：在预算超限时，受保护节点未被执行；在输出验证失败时，不合格结果未写入 GraphState，执行流被重路由至修复节点；从保存的 step 与 frontier 恢复后，系统得到与首次运行一致的最终答案。该实验说明长期任务的连续性由持久化状态和检查点保证，而不是由模型对前序 Token 的隐式回忆保证。

## 8. 本节小结

本文构建了一种面向超长程 Agent 任务的分层多介质记忆与上下文压缩唤醒框架。系统以四级作用域组织不同生命周期的信息，以 Context Ledger 固化原始目标、约束、TODO 和可信事实，以“摘要索引—原文归档—分级展开”控制上下文成本，并以漂移检测、预算控制和检查点恢复维护多轮决策链的一致性。

实验表明：在真实长会话问答中，系统将模型可见上下文压缩约 86.0%，并完成基于摘要检索和原文水合的端到端证据恢复；在 100 条 LoCoMo 派生的长程治理任务中，系统在目标保持、约束遵守、记忆使用、漂移控制和恢复能力上实现全覆盖。由此，长程任务的上下文连续性从“依赖单一模型长窗口”转变为“外部状态持久化、分层检索与按需重建”的系统能力。
