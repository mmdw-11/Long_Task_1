# 超长程上下文连续性与记忆保持：面向复杂任务的外部状态、证据唤醒与可恢复执行

## 1. 问题定义与本章结论

### 1.1 从“更长 Prompt”到“可治理状态”

超长程任务并非只是模型需要记住更多对话。一次持续数十步的执行需要连续保持：最初目标、不可违反的约束、已验证与待核验事实、计划进度、工具结果、资源预算，以及中断后的恢复位置。若将历史按时间顺序全部拼入 Prompt，会产生三类失效：过程日志淹没早期目标；短摘要丢失数值、时间更新和多证据关系；中断后只能让模型猜测历史，无法审计恢复是否正确。

本文将**上下文连续性**定义为：在有限输入预算下，系统能够在每个节点重建与当前决策相关、来源可追溯的任务状态，并在异常后恢复目标、约束、计划和证据的一致版本。为此，本文不依赖“无限上下文”，而是将状态外部化为账本、记忆、原文归档和检查点，并以预算、漂移和恢复机制约束整个运行过程。

设第 $s$ 步的节点可见上下文为 $C_s$，有效输入预算为 $B_{in}$，则系统希望构造：

\[
C_s=\operatorname{Assemble}(L_s,I_s,E_s),\qquad \operatorname{Tok}(C_s)\le B_{in},
\]

其中，$L_s$ 是稳定的 Context Ledger，$I_s$ 是当前节点输入，$E_s$ 是按需唤醒的历史证据。这里的核心是让“任务骨架”始终可见，让“历史细节”仅在需要时出现。

> 【图片占位：图 1 超长程任务的上下文失效与解决路径。左侧为全量历史拼接导致窗口膨胀、目标稀释和中断失忆；右侧为 Ledger、Memory、Archive、Budget/Drift/Checkpoint 形成的闭环。】

### 1.2 设计目标

| 目标 | 设计机制 | 节点层面的可观察结果 |
|---|---|---|
| 目标不漂移 | 原始目标、硬约束和当前 TODO 稳定注入 | 每一轮均可重锚定任务意图 |
| 历史可用不过载 | 分层记忆、摘要索引、原文按需展开 | 上下文随相关证据增长，而非随全部历史增长 |
| 事实可追溯 | `summary` 与 `raw_ref` 双轨保存 | 摘要可回到原始会话、工具输出或归档 |
| 预算可治理 | BudgetController 和有效输入上限 | 超限时显式暂停并留下原因 |
| 中断可恢复 | Context/Graph Checkpoint | 恢复外部状态而非让模型猜进度 |

本章不把“答案字符串在历史中出现”直接视为 QA 正确率，也不把确定性构造场景的治理通过率写成真实 LLM Agent 的端到端成功率。第 5、6 节将严格区分这些证据。

### 1.3 当前证据的结论边界

当前工程已经实现账本、预算控制、漂移检测、上下文压缩归档、四层记忆作用域、分级唤醒和检查点，并通过 Hook 生命周期接入图执行。现有结果支持以下结论：

1. 在冻结 LongMemEval N=10 子集上，Ours Full 的平均可见上下文为 17,224.3 tokens，较 Full Context 的 123,241.9 tokens 降低约 86.0%；但 QA Accuracy 为 0.40，低于 Full Context 的 1.00 和 Mem0 的 0.70。这证明压缩链路可工作，也暴露了多证据召回不足。
2. 在 LoCoMo complex v6 的 100 条共同扰动任务中，Ours Full 能正确处理构造的重复漂移、预算暂停和检查点恢复；其平均可见/注入上下文为 247.65 tokens，Full Context 为 20,166.42 tokens。该结果是机制评测，不是 LLM QA 主实验。
3. BGE-M3 两阶段检索在 24 条直接事实诊断集上跑通，Ours Full QA Acc 为 0.250，Full Context 为 0.167；但该诊断集已限制答案证据进入词法候选窗口，不能作为通用长记忆性能主表。

因此，当前最可靠的贡献是**上下文治理和可恢复运行时设计**；最需要继续补强的是通用长历史上的候选召回、关系证据覆盖和统一 LLM QA 评测。

## 2. 系统状态模型与总体架构

### 2.1 四类外部状态

系统不让单一摘要承担所有职责，而是将状态拆分为四类。

| 状态对象 | 回答的问题 | 核心内容 | 生命周期 |
|---|---|---|---|
| Context Ledger | 现在要做什么、做到哪里 | 原始目标、约束、计划、TODO、事实、失败、预算、下一动作 | 单次 run |
| Memory Store | 哪些历史与当前问题相关 | 带作用域、标签、时间和重要度的记忆项及索引 | 节点至跨项目 |
| Cold Archive | 原始证据在哪里 | 会话片段、节点输出、工具返回等完整载荷 | 可长期保留 |
| Checkpoint | 中断后从何处继续 | 账本快照、归档引用、前沿节点、图状态 | 单次 run，可持久化 |

例如，预算约束应稳定保存在 Ledger；上周工具得到的原始表格应作为可检索、可回溯的 Archive 证据；“第 8 步完成、第 9 步待重试”则属于 Ledger 与 Checkpoint 共同维护的恢复状态。只有将它们分开，系统才能明确哪些内容不可丢、哪些内容可压缩、哪些内容应在恢复时展开。

### 2.2 Context Ledger：稳定任务锚点

`ContextLedger` 是 run 级上下文骨架，保存 `original_goal`、`hard_constraints`、`current_plan`、已完成/待完成步骤、`todo_items` 与修订事件、`key_facts`、`open_questions`、工具和失败摘要、预算以及 `next_action`。节点开始时，这些字段会渲染为固定结构：

```text
[Stable Task Anchor]
Original Goal / Hard Constraints
Current Node Role and Step Objective
Completed and Pending Todos
Verified Facts / Things Not To Assume
Expected Output Contract / Budget / Next Action
```

账本的职责是保证“模型即使没有命中任何历史记忆，仍不会忘记任务是什么”。检索层只补充当前决策所需的历史细节，不能取代账本。

### 2.3 四层作用域与多介质记忆

记忆从窄到宽划分为 WORKING、TASK、PROJECT、GLOBAL 四层；检索时可从当前局部状态逐级扩展，避免项目或任务之间相互污染。

| 作用域 | 典型内容 | 隔离理由 |
|---|---|---|
| WORKING | 当前节点草稿、局部中间量 | 仅对本节点有效 |
| TASK | 当前 run 的中间结论、执行反馈 | 不应被其他 run 默认继承 |
| PROJECT | 同项目跨 run 的历史结论、资料 | 防止跨项目串扰 |
| GLOBAL | 低风险、通用稳定知识 | 必须谨慎写入 |

作用域与物理介质是正交的：HOT 提供进程内低延迟读取，WARM 提供可选 TTL 缓存，STRUCTURED 保存结构化元数据，SEMANTIC 支持向量检索，COLD 保存 Markdown/JSONL 审计归档，GRAPH 为关系记忆扩展预留接口。单条记忆可抽象为：

\[
m=(id,content,summary,raw\_ref,scope,scope\_id,tags,importance,time,metadata).
\]

`summary` 服务检索和轻量注入，`raw_ref` 指向完整证据；实际实现支持 DENSE、SPARSE、HYBRID 和 HYBRID_TEMPORAL 检索。

> 【图片占位：图 2 任务状态与分层记忆。中心画 Context Ledger；外圈依次为 WORKING、TASK、PROJECT、GLOBAL；每一层映射到 HOT/WARM/STRUCTURED/SEMANTIC/COLD。用箭头显示 `summary` 与 `raw_ref` 的双轨关系。】

### 2.4 摘要—归档—唤醒的双轨证据链

长载荷不应反复完整输入，也不能只留无来源摘要。系统采用以下闭环：

1. 节点结束后提取结果摘要、关键事实、标签和失败原因；
2. 超过阈值的原始输出写入冷归档，摘要保存 `raw_ref`；
3. 摘要、时间、作用域和向量进入检索索引；
4. 后续节点根据目标、角色、输入和近期状态检索摘要候选；
5. 仅在命中、风险或恢复需要时展开原文，并受预算限制。

这意味着压缩并非删除：系统以短文本完成大部分定位，以原文保证可核验性。审计者可以沿 `raw_ref` 回到会话或工具原始输出，检查摘要是否遗漏了更新事实或关键数字。

### 2.5 分级唤醒

| 等级 | 适用场景 | 作用域 | Top-K | 检索与归档策略 |
|---|---|---|---:|---|
| Silent | 低风险局部步骤 | WORKING、TASK | 3 | 稠密检索；不展开 |
| Standard | 常规节点 | 四层级联 | 5 | 混合检索；按需展开 |
| Deep | 多证据复核 | 四层级联 | 8 | 混合检索；预展开前 2 条 |
| Recovery | 中断恢复、追溯 | 四层级联 | 10 | 时态混合检索；展开全部命中归档 |

Recovery Profile 在当前实现中使用 0.15 的时间权重。这里的级联不是把所有层无差别拼接，而是先搜索最窄的相关范围，再逐级扩展；风险更高、需要核验或恢复时才提高唤醒深度。

## 3. 上下文连续性运行机制

### 3.1 节点前：稳定锚点与当前证据分别构造

HookManager 在 `on_step_start` 更新账本中的步骤和前沿节点；在实际调用节点前，分别执行账本注入、记忆唤醒和预算检查。第 (s) 步上下文可表示为：

\[
C_s=A(L_s)\oplus I_s\oplus R(q_s,M)\oplus O_s,
\]

其中 (A(L_s)) 为稳定任务锚点，(R(q_s,M)) 为检索证据，(O_s) 为节点角色和输出约束。该顺序保证检索失败时仍能保持目标和约束；检索命中时，原始证据又不会覆盖任务骨架。

> 【图片占位：图 3 节点上下文装配泳道图。Graph State 分别产生 Ledger Anchor 和 Query；Query 经 Cascade Retrieval/Archive Expansion，与当前输入一起进入 Budget Gate，最后注入节点 Prompt。】

### 3.2 显式预算闸门

`ContextBudgetController` 在调用前估算状态 token，预留输出预算后计算有效输入上限：

\[
B_{in}=B_{max}-B_{out}.
\]

若已用上下文超出 $B_{in}$，控制器返回 `allowed=False`，将运行状态标为 `budget_paused`，并写入已用 token、限制值和暂停原因；此时应压缩、降低唤醒深度、等待人工决策或从检查点恢复，而不是静默截断。当前估算是与模型无关的保守近似，正式报告还应同时给出模型侧实际 token，不能将该近似当作精确计费。

### 3.3 漂移检测与受限计划更新

`DriftDetector` 不只检测图环，还检测语义重复、重复资源/工具/文件操作、TODO 长期不前移和目标语义偏离；必要时可加入 LLM Judge。检测结果作为带证据的失败摘要进入 Ledger，使后续节点知道“为何不能继续重复”，而不是只收到一句无来源告警。

| 信号 | 典型现象 | 响应 |
|---|---|---|
| 节点或动作重复 | 同一操作连续重试 | 暂停、重规划或切换节点 |
| 语义摘要重复 | 多轮没有新增进展 | 标记停滞 |
| 资源重复 | 反复读同一文件、调用同一工具 | 形成结构性循环证据 |
| 待办积压 | TODO 反复重开或不前移 | 检查计划一致性 |
| 目标偏离 | 当前状态远离原始目标 | 重新注入目标并校正 |

### 3.4 节点后：事实固化与检查点

节点结束后，系统抽取输出、工具结果、关键事实和失败原因；长结果写入 Archive，摘要写入 TASK 记忆，账本同步记录事实、TODO 事件与下一动作。记忆更新接口支持 `ADD`、`UPDATE`、`DELETE`、`NOOP`，可用于知识更新判断；但该 Judge 的稳定收益尚未证实，不能因接口存在就声称解决事实演化。

Context Checkpoint 保存 Ledger、`MEMORY.md`、归档引用和元数据；Graph Checkpoint 保存执行步数、前沿节点和图状态。恢复流程是“恢复外部状态 → Recovery 唤醒证据 → 重新预算检查 → 从前沿节点继续”，而不是把旧 Prompt 重发并让模型猜测。

> 【图片占位：图 4 执行与恢复状态机。至少包含 RUNNING、BUDGET_PAUSED、NODE_ERROR、CHECKPOINTED、RECOVERING、RESUMED；恢复路径必须同时恢复 Ledger、GraphState 和 `raw_ref`。】

## 4. 核心算法

```text
Algorithm 1  Context-Continuous Node Execution
Input : node n, state X, memory M, ledger store L, budget controller B
Output: node update ΔX or recoverable paused state

1  r ← ResolveRunId(X); ledger ← L.LoadOrCreate(r, X)
2  ledger ← UpdateStepState(ledger, current_step, frontier)
3  q ← BuildQuery(n, X, ledger.original_goal, ledger.active_todo_id)
4  profile ← SelectWakeupProfile(n, ledger, X)
5  evidence ← M.CascadeWake(q, profile, scope_context(X))
6  C ← Assemble(RenderStableAnchor(ledger), CurrentInput(X),
                evidence.context_text, OutputContract(n))
7  d ← B.Check(C)
8  if d.allowed = false then
9      Save(ledger, d); SaveContextCheckpoint(ledger, X)
10     return MarkPaused(X, d.pause_reason)
11 end if
12 Inject(C, X); return Invoke(n, X)
```

算法的关键是稳定锚点和检索证据分开生成，且在最终装配后再过预算闸门。若把目标也交给检索，目标可能因相似度不足而消失；若只保留账本，节点又缺少数值、时间和原始会话细节。

```text
Algorithm 2  Cascade Wakeup with Archive Expansion
1  按作用域从窄到宽召回候选；按 content/raw_ref 去重并排序
2  选择 profile.top_k 条候选
3  对每一候选：若 profile 要求且原文仍符合预算，则展开 raw_ref；否则注入摘要和引用
4  返回有序证据集合
```

后续改造已将实验路径升级为“词法 Top-20 高召回候选 → BGE-M3 稠密重排 → 预算内 Top-5 片段选择”。它比早期“Top-5 会话后整段水合”更接近证据级选择，但其标准 LongMemEval 完整正式结果尚未重新运行。

设索引候选数为 (K_c)，最终证据数为 (K)，单条展开长度为 (R)，则重排约为 (O(K_c)) 至 (O(K_c\log K_c))，归档展开约为 (O(KR))。系统不消除检索和重排成本，而是用“小而稳定的账本 + 有上限的相关证据”替代每一步全历史线性输入。

## 5. 实验设计与指标边界

上下文系统存在两条不同因果链：检索质量影响“证据是否足以回答问题”；Ledger/Drift/Budget/Checkpoint 影响“任务在异常下是否持续受控”。不能用一个成功率混淆两者。

| 实验 | 数据 | 目的 | 结果性质 |
|---|---|---|---|
| LongMemEval 冻结子集 | 10 题 | QA、来源检索与上下文成本 | LLM QA 子集；样本小，不做显著性结论 |
| LoCoMo complex v6 | 100 题、10 计划阶段、3 次停滞 | 预算、漂移、恢复机制 | 确定性机制评测，非真实 QA |
| BGE-M3 直接事实诊断 | 24 条候选筛选样本 | 验证新版证据选择链路 | 诊断集，非主表 |

主要指标包括：QA Accuracy（统一 QA 求解器的语义正确率）、MRR/Hit@K（检索排序质量）、Evidence Recall（gold evidence 覆盖）、Context Tokens（实际注入长度）、Budget Violation（真实超出有效预算且未控制）、Drift Detected、Recovery Success，以及严格联合代理：

\[
\text{Strict Proxy}=qa\_correct\land drift\_rate\le0.2\land constraint\_compliance\ge0.8\land budget\_violation\_rate\le0.2\land recovered.
\]

该联合代理不能直接命名为真实任务成功率。实验应保证所有方法面对相同历史、当前提示和扰动，分开报告建库成本与在线时延；“答案文本命中”只表示可见性代理，不能代替真实 QA。

LoCoMo complex v6 使用 `locomo_state_100_complex_v6.jsonl`，SHA-256 为 `96D7A7468BDE905986B7C1679F031964089AAEB9EAAF55D1DE981C74AEC6D33A`，100 条唯一任务均记录 10 个计划步骤、13 个场景事件与 3 个后置停滞。LongMemEval N=10 的冻结文件为 `longmemeval_final_10.jsonl`，SHA-256 为 `29086611cf7012c667ab184d1015e32b3d7c6e855c38b553017d02dee8aa3990`。早期 v3 使用预选答案事实和不对称扰动，不应与 v5/v6 结果混作同一性能曲线。

## 6. 结果、解释与限制

### 6.1 LongMemEval N=10：压缩有效，召回仍限制 QA

| 方法 | QA Acc | Answer F1 | MRR | Hit@5 | Evidence Recall | 平均 Context Tokens | 总时间 |
|---|---:|---:|---:|---:|---:|---:|---:|
| No Memory | 0.0000 | 0.0000 | N/A | N/A | N/A | 0.0 | 17.47 s |
| Full Context | **1.0000** | 0.416279 | N/A | N/A | N/A | 123,241.9 | 63.53 s |
| Mem0 `infer=True` | 0.7000 | **0.498802** | **1.0000** | **1.0000** | **0.9500** | **204.0** | 2,065.01 s |
| Ours no Judge | 0.3000 | 0.154579 | 0.533333 | 0.7000 | 0.5250 | 17,217.3 | **67.84 s** |
| Ours Full | 0.4000 | 0.264103 | 0.533333 | 0.7000 | 0.5250 | 17,224.3 | 806.30 s |

Full Context 是该小样本上的准确率上界，但平均上下文超过 123k tokens。Ours 将上下文压至其约 14.0%，但 Evidence Recall 仅为 0.525；多证据计算、时间更新和跨会话关系题即使 Hit@5=1，也可能漏掉必要证据。Ours Full 比 no Judge 多答对 1 题，但 MRR、Hit@K 和 Evidence Recall 完全相同，443 次 Judge 调用仅产生 2 次 UPDATE，总时间由 67.84 s 升至 806.30 s。N=10 不足以将 0.10 差异归因于 Judge，只能说观察到单题增益且代价显著。

### 6.2 LoCoMo complex v6：共同扰动下的治理闭环

有效输入预算为 14,336 tokens（16,384 窗口减 2,048 输出预留）。四种方法面对相同完整历史、当前提示和扰动事件。

| 指标 | Plain | Full Context | Memory Only | Ours Full |
|---|---:|---:|---:|---:|
| Basic Task Readiness | 0.0000 | 0.0200 | 0.1500 | 0.1500 |

### 6.4 综合解释

目前可较强支持的是：Ledger 将任务骨架显式外部化；摘要与 `raw_ref` 同时提供高效检索和可追溯原文；Budget、Drift 和 Checkpoint 在共同扰动下形成可检查的治理闭环。尚不能支持的是：系统已在真实 QA 上超过 Full Context/Mem0；更新 Judge 有稳定收益；确定性机制代理等同于真实 Agent 成功率；24 条诊断集可推广到所有长历史任务。

## 7. 局限性与下一步验证

| 优先级 | 后续工作 | 所需证据 |

| P1 | 分层统计单跳、关系、多跳、时间更新问题 | 明确检索短板而非只给平均值 |

每次正式运行都应保存数据 SHA-256、模型版本、Prompt、随机性设置、配置、`summary.json`、`rows.jsonl` 与 trajectory；不保存隐藏思维链，但应保存可审计的输入摘要、动作、观察、预算决定、Top-K 证据和裁判结果。

## 8. 本章小结

本文以 Context Ledger 为稳定锚点，以分层多介质记忆为历史索引，以摘要—原文双轨为证据链，并以预算—漂移—检查点构成运行治理闭环。该设计的关键不在于无限扩大窗口，而在于让每个节点在受控预算内获得可解释的任务骨架和按需唤醒的历史证据，并在中断后从持久化状态恢复。

现有结果证明该框架能显著降低可见上下文，并在共同构造的长过程扰动中正确处理漂移、预算和恢复；LongMemEval N=10 同时说明当前检索仍受多证据和时间更新问题限制。后续应以统一真实 QA 评测和更严格证据覆盖分析验证“小上下文”是否真正保持答案质量。
