# 实验五 v2：结构化低熵通信、冗余抑制与信息保真

## 1. 为什么重做

v1 的 EAC 从 2 降到 1，但它只说明第二条消息被门控拦截，不能说明传输内容更短或更有效。更严重的是，NR 非重复消息也被 `low_contribution` 剪掉。根因包括统一的占位 goal/subtask、无 evidence、通信 Capsule 被写回 StateDelta 后嵌套，以及把“低贡献”直接等同于“可删除”。

v2 的目标是同时验证四件事：

1. 完全重复的消息能否被抑制；
2. 非重复 claim 能否完整送达；
3. 长文本是否真的被压缩，且核心 claim 未丢失；
4. 相比全文共享历史，实际传输 token 代理值是否降低。

本实验仍是**受控通信机制实验**：五个节点均调用同一真实 LLM，但 source/verifier 的通信 payload 在 LLM 调用后被固定为冻结文本，隔离模型随机改写。它证明门控与传输机制，不证明 LLM 自发产生错误的概率。

## 2. 后端优化

| v1 问题 | v2 改动 | 预期效果 |
|---|---|---|
| `capsule` 被纳入 StateDelta | `diff_state()` 排除 `capsule` 与 `messages` | 防止通信包嵌套、降低虚假预算压力 |
| 新 claim 因低证据/低相关性被删除 | `preserve_novel_claims=true`、`novelty_threshold=0.70` | 低冗余且有 claim 的消息保留，并标为 `novel_claim_protected` |
| 不同任务共用占位语义 | 每条样本写入 topic 对应的 goal/subtask | 让通信字段具有任务语义 |
| 只用 EAC 表示低熵 | 记录输入项数、token proxy、压缩事件、claim recall、误剪枝 | 区分少消息、少 token 与保真 |

门控顺序为：过期消息剪枝 → 关键约束/冲突保护 → 高冗余剪枝 → 低冗余新 claim 保护 → 其余消息才按 contribution score 判定。也就是说，低证据的**独立 claim**会被送达并标记，而不是静默丢失。

## 3. 数据集与对照

数据集文件：`examples/experiments/sample_data/communication_error_cascade_100_v2.jsonl`，生成后共 100 条：

| 子集 | 数量 | A/B relay 的关系 | 主要验收 |
|---|---:|---|---|
| HS | 60 | 完全相同的错误 claim | 第二条应被冗余剪枝 |
| PS | 20 | 同一候选事实的不同表达 | 观察边界，不作为误剪枝主结论 |
| NR | 10 | 两条不同 claim、不同标识 | 两条都必须送达 |
| LG | 10 | 完全重复但附带超长描述字段 | 发生压缩，claim 必须保留 |

三组方法均调用同一真实模型、使用同一图和同一 payload：

| 方法 | 通信方式 | 作用 |
|---|---|---|
| `baseline_full_history` | 全量 `messages` 注入后继 prompt | 历史共享基线 |
| `structured_no_gate` | Capsule 定向投递，不做剪枝 | 分离“结构化/定向”本身的影响 |
| `structured_gate` | Capsule 定向投递 + 冗余门控 + 新 claim 保护 + 256-token 压缩预算 | v2 完整方法 |

正式全量为 100 × 3 = 300 次 run。v2 使用独立输出目录 `runs/experiments/communication_error_cascade_v2/`，不会覆盖 v1 的 200 次结果。

## 4. 指标与判定

| 指标 | 定义 | 成功判据 |
|---|---|---|
| Aggregator input items | 到达 aggregator 的 relay 项数 | HS 中完整方法低于两个基线 |
| Error copy count | 到达 aggregator 的原始错误 claim 副本数 | HS 中完整方法为 1 |
| HS REPR | HS 第二条是否因 `redundant` 被剪枝 | ≥ 90% |
| NR novel claim recall | NR 两个不同标识是否均抵达 aggregator | 100%，最低可接受 90% |
| NR FPR | NR 中缺失任一独立 claim 的比例 | ≤ 10% |
| Transport token proxy | 基线为 relay 文本 token 估计；结构化组为已投递 Capsule token 估计 | 完整方法低于基线，同时不降低 NR recall |
| LG compression events | 到达 aggregator 前发生的压缩事件数 | > 0，且 claim marker 保留 |
| Writer ECR | writer 是否仍收到首条错误 | 仅描述，不作为“纠错成功”指标 |

EAC 在 v2 中拆成 `aggregator_input_items` 与 `error_copy_count`：前者衡量扇入负载，后者衡量同一错误被重复放大的程度。它们都不是 Shannon 熵；token proxy 与压缩事件才用于证明传输负载是否下降。

## 6. 后续真实运行步骤

### 第一步：分层 smoke

```powershell
D:\Python\python.exe examples/experiments/run_communication_error_cascade.py --bootstrap-from-env --subsets HS PS NR LG --per-subset 1
```

预期：共 4 case × 3 方法 = 12 run。每条输出 `status: valid`，且 `real_llm_nodes` 恰含 5 个节点。重点检查：

- HS 的 `structured_gate`：`redundant_error_pruned: 1`；
- NR 的 `structured_gate`：`novel_claim_recall: 1`、`false_prune: 0`；
- LG 的 `structured_gate`：`compression_events > 0`；
- 若出现 `invalid`，脚本非零退出，不能继续全量。

### 第二步：阅读 smoke 汇总

打开 `runs/experiments/communication_error_cascade_v2/summary.json`。只有在所有 smoke run 均 valid、NR 未误剪、LG 触发压缩时，才进入全量。

### 第三步：正式全量

```powershell
D:\Python\python.exe examples/experiments/run_communication_error_cascade.py --bootstrap-from-env
```

预期：300 次 run；每一条 case 结果写入 `cases/<method>/<case_id>.json`，并在结束后生成 `rows.jsonl`、`summary.json` 和 `manifest.json`。运行中不要使用旧 v1 的 `summary.json` 判断 v2 进度。

### 第四步：验收

全量结束后必须同时满足：

1. `invalid_runs = 0`；
2. `structured_gate.repr_high_similarity ≥ 0.90`；
3. `structured_gate.novel_claim_recall_nr ≥ 0.90`；
4. `structured_gate.fpr_nonrepeat ≤ 0.10`；
5. `structured_gate.mean_compression_events_lg > 0`；
6. token proxy 下降没有以 NR claim 缺失为代价。

若第 3 或第 4 条失败，结论必须写为“门控仍损失独立信息”，不得用 EAC 下降掩盖该问题。
