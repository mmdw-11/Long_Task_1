# 9.6 实验代码调整说明

本次调整依据两类问题：一是 8.30 结果中 Ours 在 LongMemEval N=10 上低于 Full Context 和 mem0；二是学长指出实验三 `320 tokens` 不符合正常长任务预算、技能实验 Manual 与 Ours 全部指标相同且不自然。调整目标是提高实验的公平性和可解释性，不通过删样本、改旧结果或人为抬高分数来获得“更好看”的数字。

旧结果保留在原目录，仅作为诊断记录。以下代码变更后产生的结果必须写入新输出目录，不能和 `8.30实验3结果.md` 的旧表混合。

## 一、长期记忆实验：从 Top-5 整段水合改为候选召回加证据片段选择

### 旧问题

旧 Ours 只取 Top-5 会话，并把每个命中归档的整段原文水合后交给 QA。N=10 结果显示：

- Ours Full 的 QA Acc 为 0.4，低于 Full Context 的 1.0 和 mem0 的 0.7；
- Ours 的 Evidence Recall 为 0.525，多证据、时间和知识更新问题经常漏掉必要会话；
- 五段原始会话仍导致约 17k context tokens，虽然低于无限 Full Context，但明显高于 mem0；
- Ours Full 的更新 Judge 443 次调用只产生 2 次 UPDATE，成本高但收益不稳定。

### 新实现

`engine/experiments/memory.py` 新增两级流程：

1. `candidate_k=20`：Hybrid 检索先返回最多 20 个候选会话，用于 session-level Hit@K、MRR、Evidence Recall；
2. `context_token_budget=12000`：对候选原始会话按 1800 字符切片，依据问题词重合与会话排名选择证据片段，再限制送给 QA 的上下文；
3. QA 指标与检索指标分离：QA 使用证据片段，Hit@K/MRR 仍按完整候选会话及 gold evidence session 计算；
4. 新增 `full_context_budgeted` 方法：按时间最近原则截断 Full Context 到与 Ours 相同的 token budget。它是公平预算基线；无限 Full Context 仍保留为性能上界。

每条结果 metadata 中新增：

- `candidate_sessions`：会话级候选数量；
- `evidence_selection.selected_chunks`：交给 QA 的片段数；
- `evidence_selection.selected_tokens`：片段 token；
- `context_policy`：Full Context 是否采用最近历史截断。

## 二、长期记忆与上下文治理：16k 真实预算和完整历史

### 旧问题

旧实验把最大上下文设为 320 token，Full Context 通过重复 `memory_fact + distractor` 24 次保证超限；没有 BudgetController 的方法又会被直接记为预算违规。每条任务只写入一条已经包含答案的历史事实，无法代表真实长任务中的检索。

### 新实现

`engine/experiments/long_task.py`、`engine/experiments/datasets.py` 调整为：

- 默认 `max_context_tokens=16384`，保留输出预算 `2048`，有效输入预算为 14,336；
- LoCoMo 派生任务增加 `history` 字段，保存原问题的全部历史会话；
- Memory Only/Ours Full 写入全部历史后再检索，Full Context 直接暴露真实历史；不再重复一条答案事实制造长度；
- `Budget Violation` 仅在实际可见上下文超过预算、且方法没有预算控制时为真；
- 新增 `history_tokens`、`budget_limit`，用于判断每条任务是否真的形成预算压力。

该实验仍是确定性后端机制联合评测，不是 LLM Agent 的真实端到端任务成功率。新的结果不应再出现“所有无 Budget 方法必然预算违规”的固定模式；如果真实历史没超过 16k，预算违规为 0 是正常结果。

## 三、技能闭环：训练/测试隔离和关键步骤覆盖

### 旧问题

旧实现对每个样本先用自己的 `trajectory` 创建技能，再用同一条样本的 `expected_steps` 检查覆盖率；Manual 与 Ours 使用相同步骤，因此 30 条上几乎所有指标都相同。这是自检索泄漏，不能说明可复用性或泛化能力。

### 新实现

`engine/experiments/skills.py` 与 `datasets.py` 改为：

1. 每个任务类型 10 条中，前 3 条标为 `train`，后 7 条标为 `test`；
2. Ours 只从 3 条训练轨迹归纳并发布一份技能；Manual 只提供每类一份固定人工基础技能；
3. 只对 21 条 held-out test task 检索并评测，测试样本不会创建自己的技能；
4. 新增 `critical_step_coverage`，用于检查训练轨迹中沉淀的环境特定步骤，例如邮件的“检查发送权限”、日历的“确认时区”、旅行规划的“核验预算”；
5. 新增 `automatic_skill_generation_success`、`training_source_examples`、`manual_skill_provided`，区分自动沉淀与人工提供；
6. `Task Success` 仍是 procedural-plan coverage proxy，不是 LLM 真实任务成功率。

### 重新构建和运行

```powershell
python examples/experiments/prepare_datasets.py skills `
  --output data/processed/skill_reuse_30_split_v2.jsonl `
  --count 30 --seed 42

python examples/experiments/run_skill_experiment.py `
  --dataset data/processed/skill_reuse_30_split_v2.jsonl `
  --limit 30 --method all --train-per-type 3 --fresh `
  --output-dir runs/experiments/skills_split_v2
```

新结果每种方法的测试样本数应为 21，而不是 30；metadata 应显示 `train_examples=9`、`test_examples=21`。Manual 与 Ours 即使 Task Success 都相同，也应在 Step Coverage、Critical Step Coverage、Automatic Generation 和 Training Source Examples 上呈现不同的机制含义。论文中可表述“自动技能在未见任务上达到或超过固定基础技能的步骤覆盖”，不可表述为“真实任务成功率 100%”。
