# 实验一：动态异构拓扑正式实验设计

> 本文替代 `8.29实验第3版.md` 中原“多 Agent 编排稳定性实验”在动态异构拓扑部分的证据职责。旧实验的 300 条确定性图执行结果仍保留，作为**图运行时正确性回归实验**；不得再用它证明真实 LLM、多角色协作、外部工具使用或动态拓扑能力。

> **时间受限执行口径（本次优先采用）**：本机须在 4 小时内完成时，执行第 1.4 节的 40 条机制证据集与 **200 次正式 run**；不执行本文后续的 100 条、五方法、三重复完整研究配置。该版本用于证明“实现分支真实可运行且可审计”，并提供两次独立运行的稳定性证据；不用于声称大规模基准上的普遍优越性。

## 1. 实验目标、问题与可宣称边界

### 1.1 要验证的研究问题

本实验验证的不是“图能否按既定边运行”，而是当任务需求、资源可用性和执行事件变化时，系统能否在一次真实任务运行中完成以下闭环：

1. 根据当前 TODO 的能力、工具、Skill、知识库要求，排除不可行成员；
2. 对可行成员按语义匹配、历史表现、资源覆盖、成本、时延和风险评分，仅激活 Top-K 成员；
3. 为本轮生成可审计的临时 Delegation 边；
4. 当成员提出结构化 Handoff、成员执行失败或质量门要求返工/重规划时，重新选择成员并形成 Handoff/Fallback/下一轮 Delegation 边；
5. 使用真实 LLM 推理和真实外部工具调用完成任务，而非用脚本固定返回值替代 Agent 行为；
6. 以成功率、资源匹配、重构与恢复、拓扑稀疏度、成本和轨迹审计共同评价。

### 1.2 实现对应关系

| 要求 | 当前代码机制 | 运行轨迹中的直接证据 |
|---|---|---|
| 异构角色与资源约束 | `WorkflowNodeRuntimeFactory._member_assessment`：工具/Skill/知识库硬过滤，多指标评分 | `candidate_filtered` 的 `excluded_reasons`、`score_breakdown` |
| 按任务语义形成稀疏协作关系 | `selection_top_k`、`max_parallel` 选择有限成员 | `topology_reconfigured`、`delegation_selected` |
| 运行中重构 | 主管重新评估结构化 Handoff；失败后选择未使用的替代成员；TODO 更新后再次选择 | `handoff_selected/rejected`、`fallback_selected`、下一轮 `delegation_selected` |
| 有生命周期的临时边 | Team 调用期间的 Delegation/Handoff/Fallback 事件均标记 `temporary=true`，并记录 `edge_ttl` | 每条边事件及其 run / TODO 归属 |
| 可解释性 | 候选排除原因、总分与各项分数均事件化 | 原始 `events.jsonl`、单样本 trace |

关键边界：外层 Planner—Team—Quality Gate—Aggregator 的画布连线仍是预定义的安全控制骨架；本实验的“动态拓扑”是 **Team 内每个 TODO 的活跃成员集合与临时协作边**。当前 `edge_ttl` 是一次 Team 调用的生命周期记录，不是维护全局可写邻接矩阵的独立对象。结果中应报告“临时协作边重构”，不能声称任意修改外层执行图。

### 1.3 假设

- **H1（资源正确性）**：完整方法能显著提高 Required-resource coverage，并将资源不满足的成员在执行前排除。
- **H2（事件重构）**：在能力缺口、工具失败和 TODO 返工场景中，完整方法能产生正确的 Handoff/Fallback/重新委派事件，并提高恢复后的任务成功率。
- **H3（稀疏性）**：在不降低或提升任务成功率的条件下，完整方法的平均活跃成员数和临时边密度低于固定全员协作。
- **H4（真实可执行性）**：所有纳入正式统计的样本均有真实 LLM 调用记录；需要工具的样本还必须有真实工具请求、响应、耗时和证据来源记录。

本实验**不检验** Shannon 信息熵或 Capsule 门控效果；这些属于后续“低熵通信”实验，不能把本实验的 Token/边数结果替代为通信熵结论。

### 1.4 4 小时、200 Run 机制证据集（本次实际执行方案）

只保留动态拓扑最关键的三个可运行分支，并把“重规划”降为一条附录演示，不纳入主表。

| 场景 | 正式任务数 | Ours 必须出现的事件 | 静态对照预期行为 |
|---|---:|---|---|
| S1 任务—资源匹配 | 10 | `candidate_filtered` + 正确 `delegation_selected` + 真实工具调用 | 固定成员/固定边运行，不依据当前 TODO 排除成员 |
| S2 能力缺口 Handoff | 10 | `handoff_selected`，接收成员具有所缺能力且完成真实工具调用 | 无 Handoff；原成员继续、失败或终止 |
| S3 工具/成员失败 Fallback | 10 | `team_member_failed` + `fallback_selected` + 替代成员完成真实工具调用 | 无替代；记录失败或无法完成 |
| S4 两步混合任务 | 10 | 两个 TODO 至少两次 `topology_reconfigured`，且两轮活跃成员不同 | 固定成员集合/边不随 TODO 变化 |

本次主对照只运行两种方法：

- **B1 Fixed Sparse Team**：预先固定研究员与数值核验员两个成员、两条委派边，禁用 Handoff/Fallback；它不是“故意不用工具”的弱基线，仍可调用相同真实模型与工具，但每个 TODO 都会激活固定成员集合。
- **Ours Full**：启用当前的资源硬过滤、评分、Top-K、Handoff、Fallback 与 TODO 驱动的再次选择。

正式样本数精确计算如下：

| 方法 | 覆盖任务 | 独立重复数 | 正式 run |
|---|---:|---:|---:|
| B1 Fixed Sparse Team | S1–S4，40 条 | 2 | 80 |
| Ours Full | S1–S4，40 条 | 2 | 80 |
| A1 Dynamic Selection Only | 仅 S2、S3，20 条 | 2 | 40 |
| **合计** |  |  | **200** |

两次重复使用不同的固定 seed、相同任务和相同方法配置；它们都是真实 LLM 与真实工具调用，不能重放第一次输出。temperature 固定为 0。基础设施异常允许以相同 `run_id` 派生的 retry 运行一次，但 retry 单独留档，主表只纳入首个满足“真实调用验收门槛”的有效运行；若两次均异常，标记 `skipped`，不得无痕覆盖。

在启动正式集前只执行**不计入端到端 run 数**的连接健康检查（模型最小请求、每个工具一次 ping/最小查询、日志落盘检查），而不再额外做 2 条完整 smoke 任务。若前 10 次正式 run 的中位耗时超过 144 秒，按两个并发 worker 也难保证 4 小时完成；此时应先降低单任务工具链长度或提高已验证的安全并发度，而不是删减某一方法的失败样本。

精简版主表只保留 6 个指标：`Task Success`、`Required-resource Coverage`、`Handoff/Fallback Success`、`Active Members`、`Temporary Edges`、`Trace Completeness`。每个指标同时附 `N`；S1–S4 分开列出。Token、成本、置信区间、显著性检验和 B0/A2 等额外消融均放到后续扩展，避免为不必要的统计工作消耗 4 小时预算。

## 2. 被测系统与公平对照（2.2 是后续完整研究的扩展）

### 2.1 固定的 Agent 池

每种方法使用同一组模型、系统提示基础模板、工具目录、Skill/知识库目录、任务输入、最大轮数和预算。建议建立以下 6 个异构角色；实际 agent ID、模型版本与工具版本必须写入 `manifest.json`。

| 角色 | 挂载能力 | 真实工具 | 主要用途 |
|---|---|---|---|
| `web_researcher` | 检索、证据归纳 | GitHub Public REST API | 查找可引用的公开仓库事实 |
| `data_analyst` | 数值核验、结构化处理 | Calculator / Python sandbox | 计算、表格和单位校验 |
| `source_verifier` | 来源比对、证据核验 | Browser / URL fetch | 交叉验证和引用检查 |
| `writer` | 报告整合 | 无必需外部工具 | 形成符合模板的交付物 |
| `reviewer` | 质量验收、缺口识别 | 无 | 生成可执行的修订意见 |
| `fallback_researcher` | 独立检索通道 | GitHub Public REST API | 主成员/工具失败时恢复 |

工具必须是项目工具目录中真实可调用的工具，不可用 `script` 节点以预写答案冒充工具。建议优先选用可审计且结果可存档的 HTTP/API 工具；若用浏览器检索，保存 URL、网页标题、提取文本 SHA-256、调用时间和返回状态。工具密钥、Cookie、完整敏感响应不得写入结果目录。

### 2.2 五种方法（完整研究扩展；本次仅使用 B1、A1〔S2/S3〕和 Ours）

| ID | 方法 | 控制变量与用途 |
|---|---|---|
| B0 | Fixed Full Team | 固定激活所有可用成员，按固定顺序/固定扇出协作；无资源硬过滤、无运行中重新选择。用于比较全员协作的边数、成本与错误扩散风险。 |
| B1 | Fixed Sparse Team | 每类任务预先固定一组成员和固定边；成员数与 Ours 的平均 Top-K 尽量相当；无 TODO 条件化重选、无 Handoff/Fallback。用于隔离“稀疏”与“动态”的区别。 |
| A1 | Dynamic Selection Only | 使用当前 TODO 的硬过滤、评分和 Top-K，但禁用 `allow_handoff`、`allow_substitution`；用于检验初始动态选择本身。 |
| A2 | Dynamic + Handoff | 在 A1 上启用 Handoff，禁用失败替代；用于检验能力缺口触发的重构。 |
| Ours | Dynamic Heterogeneous Topology | 启用硬过滤、评分、Top-K、Handoff、Fallback、质量反馈后下一 TODO 的重新选择。 |

所有方法使用同一 LLM provider/model、temperature、max output tokens、工具超时和重试上限。固定团队方法也必须能调用同一真实工具；禁止因不挂载正确工具而人为制造失败。对于 B0，记录实际调用的固定成员边；对于 B1，固定边应在试验前以 `baseline_graph.json` 固化，不能看过测试结果后修改。

## 3. 任务集：真实 LLM + 真实工具 + 可判定事件

### 3.1 规模与拆分

本次正式集为 **40 个任务实例**，即 S1–S4 各 10 条；方法、重复次数与 200 run 的精确构成以第 1.4 节为准。该规模下不另设会消耗完整 LLM 调用的 Pilot：只进行连接健康检查和本地验收器 dry-run。开始正式集前，40 条任务文本、gold 验收项、事件注入和 B1/A1/Ours 配置必须冻结并计算 SHA-256。

若后续时间、算力和模型预算充足，可扩展到 100 个任务、五方法、三次独立重复的完整研究配置；该扩展不能与本次 200-run 结果混表。

| 事件族 | N | 任务特征 | 必须出现的动态证据 | 主要测量 |
|---|---:|---|---|---|
| T1 资源匹配 | 20 | TODO 明确要求检索、计算、验证或写作中的一种/多种能力 | `candidate_filtered`、正确的 `delegation_selected` | 硬过滤准确率、资源覆盖、初始成功率 |
| T2 能力缺口 Handoff | 20 | 初始成员获得新证据后，剩余工作确需另一能力；由 LLM 按协议提出 Handoff | `goal_checked`、`handoff_selected`、新成员工具调用 | Handoff 合法率、Handoff 后成功率 |
| T3 成员/工具故障 Fallback | 20 | 一个真实工具调用后注入可记录的可恢复故障，或使主 endpoint 返回可复现失败 | `team_member_failed`、`fallback_selected`、替代成员成功调用 | 恢复成功率、恢复时延、错误隔离率 |
| T4 质量返工与 TODO 更新 | 20 | Reviewer 发现缺项或任务新增约束，Planner 产生修订 TODO | 至少两轮 `topology_reconfigured`，两轮成员集合/分数可不同 | 重规划成功率、拓扑变化率、最终验收率 |
| T5 混合长任务 | 20 | 2–3 个顺序 TODO，含检索、计算/验证、写作；其中一个运行时事件 | 多阶段临时边轨迹与最终汇聚 | 端到端成功率、边密度、成本、轨迹完整率 |

### 3.2 任务实例格式

每条 JSONL 样本必须包含可机读验收，而不是仅由另一个 LLM 主观打分：

```json
{
  "id": "T2-007",
  "family": "handoff",
  "goal": "……",
  "todos": [{"id": "todo-1", "required_capabilities": ["web_search"], "required_tools": ["tool-id"], "acceptance": ["至少两个来源", "给出 URL"]}],
  "event_plan": {"kind": "capability_gap", "after": "first_tool_result", "required_capability": "numeric_verification"},
  "gold": {"required_roles": ["web_researcher", "data_analyst"], "required_tool_kinds": ["search", "calculator"], "required_artifact_fields": ["answer", "citations", "calculation"]},
  "public_input_hash": "..."
}
```

任务来源可采用公开网页/API、公开 GitHub 仓库、开放数据 API 或项目提供的可审计网页；每条外部证据保存 URL、访问时间、HTTP 状态、内容哈希和最小必要摘录。因网页会变化，正式实验同时保存一次合法的原始响应快照；**真实模式**使用 live tool call，**重放模式**仅用于复盘和单元回归，二者的结果不得合并统计。

### 3.3 真实调用的验收门槛

一条 run 只有同时满足以下条件，才可计入“真实 LLM + 真实工具”主表：

- 请求日志有模型 provider、model、非空 request/response ID（脱敏）、输入/输出 token 或 provider 可得的等价用量、耗时和温度；
- 对于标记为工具任务的 TODO，至少有一次成功的实际工具调用，记录 tool ID、参数摘要、开始/结束时间、状态和证据 URL/结果哈希；
- 最终产物通过该任务预定义的结构化验收器；需要事实证据的任务还通过 URL/字段/计算复核；
- 未因缺少密钥、网络、模型限流而被标记 `skipped`。`skipped` 单独报告，不能计作失败或成功。

## 4. 事件注入与实验流程

### 4.1 为什么需要受控事件注入

真实任务中 Handoff 和故障发生率不可控，若只等待模型“偶然提出交接”，不能得到可比较的样本。注入的作用是让每个方法面对同一个事件条件，不是伪造输出：LLM 仍需阅读任务、调用真实工具、产出结构化 Handoff 或完成替代任务；工具调用也先走真实 adapter，再在指定位置返回可审计故障。

注入记录必须包含 `event_id`、触发条件、触发时间、目标成员/工具、是否生效、恢复结果。禁止在最终答案中直接写入 gold answer 或指定“应选择某 agent”的泄漏提示。

### 4.2 每条 run 的固定步骤

1. 加载冻结的任务、成员画像、工具目录和方法配置，生成 `run_id`。
2. 调用 Planner 生成/载入当前 TODO；记录当前 TODO 的资源要求。
3. 运行 Team：收集 `candidate_filtered`、`topology_reconfigured`、`delegation_selected` 与每个成员的真实 LLM/工具日志。
4. 在预定义触发点执行事件注入；Handoff 类仅允许成员按现有 JSON 合同请求转交，故障类仅在真实调用后返回故障。
5. 运行质量门。若 `revise/replan`，记录新的 TODO，并再次运行 Team；最大重规划数、最大 Handoff 数、最大并发数对所有方法一致。
6. 由确定性验收器优先判定产物；只有语义无法确定的自由文本字段使用盲化 LLM Judge，并保存 Judge prompt、模型和原始判定。
7. 写出原始事件、脱敏 LLM/工具使用记录、拓扑快照、最终产物、自动评分和失败原因。任何异常均写入行级结果，禁止静默重跑覆盖。

### 4.3 防止结果失真

- 对同一任务的五种方法采用轮换顺序，避免 API 限流/网站瞬时变化只偏向一种方法。
- 每个重复使用固定但不同的 seed；固定 temperature=0，仍将重复视为独立 LLM 调用。
- 模型、提示词、工具版本、成员画像和分数权重一旦开始正式集即冻结；修复 bug 后须新建实验版本，不能覆盖旧结果。
- 对外部数据变动、429/5xx、超时和安全拒绝分别统计；不能把基础设施错误解释成拓扑失败。
- 执行者不应在人工阅读运行结果后修改事件类型或 gold；任务验收器和事件表由第二人/冻结提交复核。

## 5. 指标、计算方法与成功判据

### 5.1 主指标

| 指标 | 定义 | 证明什么 |
|---|---|---|
| End-to-end Task Success | 通过全部硬性验收的 run / 有效 run | 完整任务是否完成 |
| Required-resource Coverage | 被实际激活成员覆盖的 required capabilities/tools/skills/KB 数 ÷ 任务所需数 | 动态选择是否满足任务资源需求 |
| Ineligible Selection Rate | 被 `candidate_filtered` 判不可行却仍被执行的成员数 ÷ 被执行成员数 | 硬过滤是否真正生效，越低越好 |
| Initial Selection Precision | 初始被选成员中属于 gold required roles 的比例 | 初始语义/资源选择质量 |
| Recovery Success | T2/T3 中事件后最终成功的 run ÷ 已触发事件的 run | Handoff/Fallback 是否带来恢复 |
| Valid Handoff Rate | 满足“成员提出缺口—主管重新评估—接收者满足缺口且实际执行”的 Handoff ÷ Handoff 场景 | 不是只记录一个事件名 |
| Replan Success | T4 中重新产生 TODO 后最终通过验收的 run ÷ 触发返工的 run | 任务状态变化后的重构能力 |
| Trace Completeness | 同时具有候选、拓扑、成员、工具/LLM、质量门和最终事件的 run ÷ 有效 run | 可审计性 |

### 5.2 拓扑和效率指标

| 指标 | 定义 | 报告注意事项 |
|---|---|---|
| Active Members | 每个 TODO 实际执行的 Team 成员数 | 报告均值、中位数、P95，并按事件族分层 |
| Temporary Edges | 一个 TODO 中 `delegation_selected + handoff_selected + fallback_selected` 的数量 | 边由运行事件恢复，不应把画布静态边混入 |
| Team-edge Density | `TemporaryEdges / (1 + N_eligible)`，同时报告 `TemporaryEdges / N_enabled` | 因当前实现是 Supervisor 主导星型临时子图，不使用“全局可变邻接矩阵密度”措辞 |
| Reconfiguration Count | 每个 run 的 `topology_reconfigured` 数量及成员集合变化次数 | T4 应至少出现两轮；只换分数不换成员须单列 |
| Topology Adaptation Latency | 事件触发到相应 Handoff/Fallback/下一轮 Delegation 事件的毫秒数 | 用单调时钟记录，不混入人工等待 |
| LLM Input/Output Tokens | 所有成员和 Judge 的实际 token 汇总 | 若 provider 不返回 usage，标为 unavailable，不可估算为真实 token |
| Tool Success / Latency | 成功工具调用比例与端到端工具耗时 | 只统计真实模式 |
| Cost / Run | provider/token 单价和工具费用可得时计算 | 单价、币种、计价日期必须写入 manifest |

### 5.3 统计与报告

- 以**任务实例**为配对单位；同一个任务、同一个重复下比较五种方法。
- 二值成功率/恢复率使用配对 McNemar 检验或 cluster bootstrap 95% CI；连续指标（边数、Token、时延）报告中位数、IQR、配对 bootstrap CI。多重比较采用 Holm 校正。
- 主结论至少同时报告绝对差、95% CI、有效样本数和 `skipped` 数；不只报告 p 值。
- T1–T5 分层表与总体表必须同时给出。若总体提升只由某一事件族造成，应如实说明。
- 预注册主判据：Ours 相对 B1 在 T2–T4 的 Recovery/Replan Success 更高，且相对 B0 的 Active Members/Temporary Edges 更低；若结果未满足，报告失败分析，不修改假设或删样本。

## 7. 运行前检查、分阶段执行与停止规则

### 7.1 正式运行前健康检查通过条件

健康检查不执行完整任务，不计入 200 次正式 run。满足以下条件才能启动正式集：

- 模型最小请求、每个真实工具最小请求、事件日志写入和验收器 dry-run 均通过；
- 随机抽取每类 1 条任务在不调用模型的事件夹具预检中，能识别预期触发点；
- 工具型任务的日志 schema 包含 tool ID、状态、耗时和结果哈希；
- `candidate_filtered`、`topology_reconfigured` 和 `delegation_selected` 的字段完整率为 100%；
- T2 至少出现可验证 `handoff_selected`，T3 至少出现可验证 `fallback_selected`，T4 至少出现两次 Team 调用；
- 不存在同一方法专属的配置/密钥/工具健康问题。

若不通过，应修复实现或任务夹具并重新执行健康检查；正式集启动后不得从失败样本中挑选成功条目替换。

### 7.2 正式运行与停止规则

- 正式集先冻结任务、对照配置、成员画像、提示词版本、模型版本、价格表和代码 commit。
- API 连续故障或外部站点不可用导致某一任务在所有方法下不能完成时，标记该任务为 infrastructure-invalid，保留日志并从配对主分析剔除；不能只剔除 Ours 的失败。
- 若某个方法有效样本率低于 90%，停止宣称该方法的比较优势，先报告基础设施/实现问题。
- 任何数据集、任务验收器、模型或工具变更都必须创建新的实验版本；旧版本只读保留。

## 8. 与旧实验一的关系及论文表述模板

| 实验 | 可支持的结论 | 不可支持的结论 |
|---|---|---|
| 旧：300 条确定性工作流 | 图运行时对顺序、扇出扇入、条件、父子和循环结构的执行正确性 | 真实 Agent 成功率、外部工具可靠性、动态成员选择、运行期拓扑重构 |
| 新：本实验 | TODO 条件化成员选择、临时 Delegation/Handoff/Fallback 边、事件触发重构、真实 LLM/工具条件下的成功—稀疏度—恢复权衡 | 全局任意图重写、Shannon 熵显著降低、所有 Team 内消息均已逐边 Capsule 化 |

结果满足主判据后，可使用如下表述：

> 在固定外层工作流和相同异构成员池下，TIDE-Mesh 根据 TODO 资源要求动态筛选并激活有限成员；当出现能力缺口、成员/工具故障或质量返工时，主管重新选择接收成员形成临时 Handoff、Fallback 或下一轮 Delegation 边。真实 LLM 与外部工具运行的事件轨迹、资源覆盖、恢复成功率和临时边统计共同表明，该机制实现了任务局部的运行期异构稀疏协作重构。

即使实验结果良好，也不得写成“外层业务图在运行中可任意新增/删除边”或“低熵通信已被本实验验证”。
