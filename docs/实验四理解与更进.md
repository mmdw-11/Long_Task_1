# 一、实验四验证什么
系统能否从少量成功轨迹中提炼出可复用技能，验证并发布该技能，然后在未参与技能生成的新任务上检索和复用它。
流程：
```
成功任务轨迹
    ↓
提取执行步骤
    ↓
生成候选技能
    ↓
技能验证
    ↓
发布到技能库
    ↓
未见任务检索技能
    ↓
基础计划 + 技能计划
    ↓
检查必需步骤和关键步骤覆盖
```

## 当前实验数据
`skill_reuse_30_complex_v3.jsonl`是由`datasets.py`生成的，只有三个固定模板，每一类都生成十条【文本小幅更改：预算/时间/风险优先】

每一类用于训练的三条轨迹也差不多。

【改进点】需要换成更加权威的数据：ToolBench / API-Bank

## 题目的生成
每条任务随机加入一种偏好：预算优先/...
每条数据包含：
```
| 字段 | 含义 |
|---|---|
| `id` | 唯一任务 ID |
| `task` | 给系统的任务描述 |
| `trajectory` | 一条成功执行轨迹 |
| `expected_steps` | 评测要求覆盖的全部步骤 |
| `task_type` | email、calendar 或 travel_report |
| `source` | 数据来源标记 |
| `variant` | 预算、时间或风险优先 |
| `split` | train 或 test |
| `critical_steps` | 不能遗漏的关键步骤 |
| `workflow_depth` | 流程深度，本版固定为 8 |
```
成功轨迹：一个理想任务应该依次完成哪些步骤。

但是当前实验四同一类型的三条训练轨迹包含的步骤基本一致。

## 必需步骤与关键步骤
> 必需步骤：expected_steps 是完成任务所需的全部程序步骤，也是当前实验最主要的评分依据。
> 关键步骤：必需步骤中遗漏后可能导致任务产生明显风险的步骤。

设置关键步骤：防止覆盖了普通分支但是遗漏了关键步骤造成覆盖率高但是仍有明显风险。

## 相关指标的计算方式
1. Base Plan Coverage
共同基础计划覆盖了多少必需步骤：
命中的基础步骤数 ÷ 必需步骤总数
当前三种方法都使用相同基础计划：4 ÷ 8 = 0.5
所以全部为 50%。
2. Skill-only Coverage
只检查检索到的技能文本，不包含基础计划。

3. Step Coverage
检查“基础计划 + 技能”最终覆盖了多少必需步骤。
计算方式：
最终计划中出现的必需步骤数 ÷ 8
结果：
方法	覆盖数量	Step Coverage
No Skill	4/8	50%
Manual	6/8	75%
Ours	8/8	100%
基础计划和技能中有些步骤重复，因此不是简单相加。
4. Skill Coverage Gain
技能相对于共同基础计划增加了多少覆盖率：
skill_coverage_gain =
    step_coverage - base_plan_coverage
结果：
方法	计算	Gain
No Skill	0.50 − 0.50	0%
Manual	0.75 − 0.50	25%
Ours	1.00 − 0.50	50%


这个指标比较适合回答：
技能注入到底给基础 Agent 增加了多少程序知识？

5. Critical Step Coverage
检查两个关键步骤在最终计划中出现了多少：
命中的关键步骤数 ÷ 2
结果：
方法	Critical Step Coverage
No Skill	0%
Manual	0%
Ours	100%


6. Basic Task Readiness
当前定义是：
step_coverage >= 0.5
三种方法都至少达到 50%，所以都是 100%。
它表示：
计划至少包含一半必需流程，具备基本任务启动能力。

它不表示任务已经完整完成。
7. Task Success
当前严格定义是：
step_coverage >= 1.0
and critical_step_coverage >= 1.0
因此：
方法	Task Success
No Skill	0%
Manual	0%
Ours	100%


该指标更准确的名称应该是：
Complete Procedural Readiness
完整过程就绪代理

因为它只检查步骤是否出现在计划文本中，没有检查步骤是否真的执行成功。
8. Retrieval Hit
是否检索到了至少一个技能：
retrieval_hit = bool(matches)
结果：
- No Skill：0%
- Manual：100%
- Ours：100%
它只能说明技能可以被找到，不能说明技能内容正确，也不能说明使用技能后任务完成。
9. Automatic Skill Generation Success
只有 Ours 从训练轨迹自动生成并成功发布技能时为 1。
结果：
- No Skill：0%
- Manual：0%
- Ours：100%
Manual 是人工技能，所以即使发布成功，也不算自动生成。
10. Validation Pass Rate
技能是否通过候选验证并被发布：
- No Skill：0%
- Manual：100%
- Ours：100%
需要注意，它验证的是技能制品满足发布规则，不是验证真实工具执行结果。
11. Training Source Examples
每份技能使用了多少训练样本：
- No Skill：0
- Manual：0
- Ours：3
Manual 的来源被标记为人工提供，不依赖训练轨迹。
12. Tokens
对最终计划文本进行粗略 token 估计：
方法	平均 Tokens
No Skill	6.67
Manual	46.67
Ours	52.00


Ours 比 Manual 多约 5.33 个粗略 token，同时多覆盖 2 个步骤。
但这只是技能/计划文本 token，不包括：
- LLM 推理 token；
- 工具参数；
- 工具返回结果；
- 重试；
- 验证器调用；
- 完整 Agent 上下文。

# 2026/09/07：升级为最新版 τ 系列状态化技能闭环评测

### 1. 数据集选型与版本冻结

本轮主数据集改为官方 [sierra-research/tau2-bench](https://github.com/sierra-research/tau2-bench)，不再把旧合成数据作为正式结论来源，也不混入已过时的旧 tau-bench 任务。选择依据如下：

- [ToolBench](https://github.com/OpenBMB/ToolBench) 提供 16,464 个 API 和大规模自动生成轨迹，适合后续测试跨 API 检索广度；但真实 API 依赖、数据自动生成和复现实验稳定性不适合作为本轮状态闭环的第一主集。
- [API-Bank](https://aclanthology.org/2023.emnlp-main.187.pdf) 适合基础 API 调用、检索与对话能力，但没有 τ 系列同等完整的领域策略、隔离状态数据库、用户模拟和终态 evaluator。
- τ 官方实现直接提供 policy、tool schema、初始数据库、任务、用户模拟、参考轨迹和状态 evaluator；[官方评测说明](https://github.com/sierra-research/tau2-bench/blob/main/docs/evaluation.md) 明确以终态和必须传达的信息为核心，参考动作只是一条可行路径，而非默认要求逐步完全相同。

### 2. 新接口与数据审计

新增 `TauToolTask`，与旧 `SkillExample` 并存，不破坏旧实验四。它保存 domain/split/user scenario/policy/tool schemas/initial state ref/reference actions/reward basis/communicate info/env assertions/trajectory/read-write actions/确认边界/source commit/hash 等字段。

安全边界通过 `agent_view()` 固定：正式 Agent 看不到 test 的 `reference_actions`、`reward_basis`、`env_assertions` 或目标数据库状态。参考动作只进入运行结束后的 evaluator 和诊断指标。每个任务的初始状态引用由基础 DB 哈希与 task-specific initial state 共同计算，工具 schema 直接从固定 commit 的官方环境冻结；缺数据库、未知 schema、重复 ID、split 引用未知任务或跨 split 泄漏会立即失败。

当前冻结审计：Retail 官方工具 16 个，所选三类 split 中参考动作深度 0–13、均值 4.883；Airline 工具由官方环境冻结，参考动作深度 0–19、均值 2.840。正式 test 中检测到 Retail 2 个、Airline 6 个无写动作/拒绝型任务，能够覆盖“正确地不修改数据库”。

### 3. 技能归纳、验证与发布

自动技能不再按答案标点拆步骤。训练轨迹先按最后一个写工具（例如 cancel、return、exchange、booking）或 `read_or_refuse` 分成动作族；每个族只使用 `skill_train` 成功参考轨迹，调用模型输出严格 JSON，再渲染 Markdown。JSON 包含：适用/不适用条件、身份验证、读步骤、写步骤、参数依赖、逐写操作显式确认、分支、拒绝、人工转接、错误恢复、终态检查、必须告知信息和训练来源 ID。

结构门会拒绝 JSON 解析失败、字段缺失、官方不存在的工具、把只读工具放到写步骤、写步骤缺少依赖或确认、以及任何 test ID 来源。`ours_no_validation` 通过结构门后发布；`ours_full` 必须再在 skill_validation 的真实 τ 环境中与配对 No Skill 比较。候选 reward 不得下降，单任务不得回退，工具错误、策略违规和未授权写入不得增加；失败会写 validation report 并保持 rejected，runner 不能加载 rejected 技能。

本次门禁 smoke 的真实例子：Retail 候选与 No Skill 都为 reward 0，但候选先用错误退款方式调用写工具，tool error 比基线多 1，因此被正确拒绝；Airline smoke 两者均为 0、没有额外工具错误或未确认写入，按“不得下降/不得增加风险”的当前规则通过。后者只验证门禁代码有效，1 条验证样本且 reward 均为 0 不足以证明技能质量，正式发布前仍必须用完整 validation split 重跑。

### 4. 四组公平对照与状态执行

四组固定为 `no_skill`、`manual_skill`、`ours_no_validation`、`ours_full`。四组共享任务 ID、trial seed、官方 policy、tool schema、用户输入、初始 DB、模型、步数/错误/超时限制。Manual 来自官方政策与工具定义，包含完整身份验证、读写区分、确认、拒绝、恢复和转接规则，不再故意删关键步骤。自动技能只检索 `published` 且 domain 匹配的制品；相邻领域技能可以作为干扰候选，但 domain guard 禁止跨域注入。

Agent 只在用户模拟器给出第一条自然语言消息后检索技能，不用完整隐藏 user scenario 检索。技能以“可复用建议、官方 policy 优先、示例不得当作用户事实”的系统消息注入。每个 simulation 创建全新官方 Environment；工具真实修改隔离数据库。输出逐条写入并执行 `fsync`，key 为 `domain/method/trial/task_id`，断线后不加 `--fresh` 即可继续；错误行保留，summary 的 `acceptance_ready` 只有在无缺行、无多行、无错误时才为 true。

### 5. 指标与独立重算

主要指标直接保存官方 total reward、DB reward、Communicate reward、NL assertion reward、Task Success/Pass^1、两次均成功率和分域成功率。参考动作仅用于 Partial Action Reward、读/写 Action Recall 等诊断，不参与默认成功硬门。

项目补充保存工具调用数、读写次数、工具错误、写前确认率、技能候选数、检索命中/排名、跨域误注入、终止原因、初末状态哈希、完整 trajectory、Agent/User token、耗时与费用。汇总包含 bootstrap 95% CI、P50/P95、每成功任务成本、read/write/refusal 分层和 Ours Full 相对各基线的绝对提升。`analyze_tau_results.py` 从 rows 独立重算 summary，同时检查同一 task/trial 的四方法初始 DB 哈希一致；缺失 simulation 不能被当成失败并混入成功率。

### 8. 2026/09/07 最终公平性收口与回归

四种方法新增统一的 `skill_context_budget_chars=12000` 限制。Manual Skill 与自动技能都只能在这一相同字符预算内注入，避免 Manual 因可见政策摘要更长而获得额外上下文优势，也避免自动技能无限膨胀。正式运行可通过 `--skill-context-budget-chars` 显式覆盖，但四组必须使用同一个值；该值同时写入逐任务结果与总 summary，便于审计。

官方 mock 状态回放已加强为两条不同但等价的工具路径：观测路径先执行额外合法只读调用，再执行参考写操作；期望路径只执行参考写操作。两者最终数据库哈希一致，并且初始哈希与最终哈希不同。这验证了实验实现遵循“终态正确即可”，不会错误要求工具序列与参考轨迹逐步一致。

### 9. 2026/09/08：DeepSeek 32-run 本地先导实验与最终审计

#### 9.1 本轮实际完成内容

本轮已经使用 `deepseek-v4-flash` 完成动作族技能生成、完整 validation split 验证，以及 Retail 4 条 + Airline 4 条、4 种方法、1 个 trial 的 32 次本地先导模拟。自动技能库最终包含 Retail 7 个动作族技能、Airline 5 个动作族技能；旧 GLM 宽技能已移入 `archive_pre_ds_action_family_20260907`，不参与本轮检索。

运行器新增 `--limit-per-domain`，从两个领域各稳定抽取 4 条，而不是对全局排序结果直接取前 8 条。本轮固定任务为 Airline `13/16/18/19` 和 Retail `101/102/108/17`。这样避免了 pilot 被单一领域占满。

第一次 32-run 尝试暴露了 DeepSeek OpenAI-compatible 响应会同时返回说明文字和 tool calls，而 τ 的 half-duplex 协议禁止混合消息。该无效批次已隔离到 `pilot_ds32_invalid_mixed_message_20260907`。运行时随后改为：存在结构化 tool calls 时只丢弃冗余说明前缀，保留工具调用；同时把官方 `AGENT_ERROR`、`USER_ERROR` 和 `INFRASTRUCTURE_ERROR` 明确记入 error 字段，防止协议失败被当成普通 0 分。

### 10. 2026/09/08：DeepSeek 配置纠正与公平版 32-run 收口

上一节记录的 DeepSeek “认证/余额错误”经最小只读认证请求复核后确认不是用户 Key 失效，也不是余额不足。`.env` 中 `DEEPSEEK_API_KEY` 只有一条定义、格式正常；直接访问 `https://api.deepseek.com` 成功，并返回 `deepseek-v4-flash`、`deepseek-v4-pro` 和 `deepseek-v4-flash-vision-exp`。

$env:OPENAI_API_KEY = $deepseekApiKey
$env:OPENAI_BASE_URL = 'https://api.deepseek.com'

#### 11.2 首轮检索压力测试暴露的问题

新增 `examples/experiments/stress_tau_skill_retrieval.py`，候选池同时放入 12 个已发布技能，包括同领域相邻动作族和另一领域干扰技能；额外加入否定干扰句和完全不适用请求，整个过程不调用 DeepSeek。

初始实现的 40 条诊断结果只有 Hit@1=0.625、Recall@2=0.6708、MRR=0.6958。主要问题是：

- 自动生成技能的 applicable prose 过宽，例如 book 技能描述修改已有预订，不能直接作为主要路由依据；
- `return`、`exchange`、`modify` 和 `cancel` 在多目标订单请求中高度重叠；
- 简单词袋会把 “do not want to cancel” 当成取消意图；
- 把官方最终参考动作直接当作“第一条消息应检索的技能”不合理：用户可能在后续对话改变目标，或者因政策限制从修改转为拒绝/转接；
- 原运行器只在第一条用户消息注入一份技能，无法覆盖任务中途出现的新目标和 Retail 多目标任务。

#### 11.3 检索和运行时修正

当前修正包括：

1. 以技能不可变的 `metadata.action_family` 为主路由，生成模型写出的适用说明只保留 5% 权重作为确定性 tie-breaker。
2. 使用动作族专属意图规则区分 book/cancel/flight update/baggage、return/exchange/pending-item/address/profile-address。
3. 识别明确否定和延后意图，例如 “do not want ...” 与 “return later”，避免把排除条件当成正向需求。
4. 阈值以下不注入技能；完全不相关请求应 abstain，而不是为了命中率强塞 `read_or_refuse`。
5. 严格 domain guard，另一领域技能即使词面相似也不能入选。
6. 从“一次、单技能”改为“逐用户轮次动态检索”：后续用户披露新目标时可以补充新的动作族技能；同一动作族不重复注入，总技能上下文仍受统一 12,000 字符预算约束。
7. 新增 `skill_ids`、`skill_retrieval_trace`、实际技能上下文字符数、注入率、跨域误注入率和平均工具错误等审计字段。
8. 检索评测拆分为“当前可见首轮意图”与“最终动作诊断”。前者才是 Recall@K 的主指标，后者用于发现动态检索是否需要在后续轮次补技能，不能要求第一轮预知隐藏未来。

检索规则最终以 21 条 `skill_validation` 为开发门：

|---|---:|---:|

| Recall@2 | 0.9365 | 0.9365 |
| MRR | 1.0000 | 1.0000 |

#### 13.5 本轮能够与不能够支持的结论

本轮能够支持：

1. 320 次模拟全部完整落盘且无运行错误，正式结果有效；
2. 完整人工技能在当前 Retail/Airline 集合上取得最优表现，说明结构化领域指导确实有用；
3. 自动技能两组均优于 No Skill，但 Ours Full 没有优于未验证版本，当前验证闭环的增益尚未得到证明；
4. Ours Full 在 Airline、确认合规和跨域隔离方面表现良好；
5. Retail 多目标写任务、技能上下文长度和验证准则是下一轮的主要改进对象。

本轮不能支持：

1. 不能声称 Ours Full 优于 Manual Skill；正式数据恰好显示 Manual Skill 高 5 个百分点；
2. 不能声称验证阶段提高了最终成功率；Ours Full 比 Ours No Validation 低 1.25 个百分点；
3. 不能仅凭重叠的 95% CI 声称方法差异具有统计显著性；
4. 不能把本轮结论直接外推到 Telecom、Banking、ToolBench 或其他未测试领域；
5. 不能报告精确 API 成本，因为 LiteLLM 没有该模型别名的价格映射。

#### 13.6 后续完善方向

下一阶段不应修改本批结果或选择性重跑失败样本，而应保留其作为 v1 正式基线，并在新版本中开展：

- 对13个 Ours Full 失败样本逐条做轨迹归因，区分检索错误、技能内容错误、上下文干扰、工具选择错误、用户模拟波动和 evaluator 判定；
- 优先分析 Retail 中 Ours Full 相对 No Skill/Manual 退化的配对任务，并检查 Ours Full 与 Ours No Validation 的差异任务；
- 将候选验证目标从“相对 No Skill 不下降”升级为按动作族、难度和多目标写任务分层的净增益门槛；
- 压缩技能上下文，按对话阶段注入参数约束、确认规则和恢复路径，而不是累计完整 Markdown；
- 增加独立 holdout 领域或新任务版本，避免用本轮已参与检索开发的40条任务声称未见泛化；
- 在代码与数据版本冻结后运行新的 v2 对照，不能覆盖本次320-run。
