# 实验六：端—边—云自适应调度与纯云基线对照

## 1. 实验目的与待回答问题

验证当前产品的 **AUTO 端—边—云调度** 是否能在不明显损失任务效果的前提下，减少相对“全部由云端模型完成”的外部推理成本。

本实验只比较**模型选择策略**，不比较不同 Agent 架构。因此两组必须使用相同的应用/工作流图、系统提示词、工具集、输入、输出约束、温度、最大输出 token、最大重试次数和超时配置。

主问题：

> 与固定纯云方案相比，AUTO 调度的任务成功率下降多少个百分点，外部云端成本与总运行成本分别下降多少？

辅助问题：

1. AUTO 把多少任务实际分配到端、边、云？
2. 哪类任务的质量下降主要发生在端侧或边侧？
3. AUTO 的端到端延迟、失败率和重试次数是否可接受？
4. 对敏感任务，AUTO 是否遵守“优先留在可信端/边”的安全约束？

## 2. 当前系统中采用的真实实现口径

本实验中的 AUTO 不是固定模型名，而是产品“模型连接”页中配置并通过连通性测试的模型连接：用户分别为 `device`、`edge`、`cloud` 三个 AUTO 槽位选择默认连接。运行时调度器先选择层级，再调用该层级当前绑定的模型。

- AUTO 三个槽位：端侧、边侧、云侧都必须有“启用、已配置、测试成功”的默认连接。
- 调度依据：任务复杂度、实时性、敏感度、可信工作区策略及资源可用/限流状态。
- 执行记录必须保留 `selected_tier`（调度选择）、`actual_tier`（实际成功层级）、模型连接 ID/模型 ID、每次尝试和 fallback。
- 旧的环境变量默认模型仅是未接入模型连接管理时的兼容后备，不作为本实验的模型配置来源。

实验开始前，在报告首页冻结下列内容：

| 项目 | 记录内容 |
| --- | --- |
| 代码版本 | Git commit、前端版本、后端版本 |
| 三个 AUTO 默认连接 | 连接 ID、供应商、模型 ID、端点域名（不记录密钥） |
| 纯云基线连接 | 与 AUTO 云侧相同的连接 ID 与模型 ID |
| 配置 | temperature、max_tokens、超时、max_attempts、路由器开关/版本 |
| 价格表 | 每个模型的输入/输出 token 单价、生效日期、币种 |
| 设备条件 | 端/边机器型号、GPU（如有）、测量时间窗 |

## 3. 对照组设计

### 3.1 组别

| 组别 | 名称 | 唯一变化 | 用途 |
| --- | --- | --- | --- |
| C | All-Cloud（纯云） | 强制每个任务调用固定云侧连接 | 效果和成本基线 |
| A | AUTO（端边云自适应） | 使用当前调度器与三个 AUTO 槽位 | 待验证方案 |
| H（可选） | Heuristic AUTO | 仅使用启发式 gate，不加载学习路由器 | 分析学习路由的附加价值 |

主结论只比较 A 与 C。若运行 H，H 只用于解释“学习路由器是否优于规则门控”，不可替代 C。

### 3.2 公平性控制

1. 纯云组与 AUTO 组使用**同一个云模型连接**；否则质量或价格差异不能归因于调度。
2. 同一条任务在两组各运行一次，使用相同 `case_id`、输入、提示词和工具可用状态；运行顺序按随机种子交错（例如 `C-A / A-C`），降低服务时段波动影响。
3. 如模型服务支持 seed，则固定 seed；不支持时保留原始输出并以成对样本分析，不把单次生成误写成确定性结果。
4. 禁止按结果删样本。超时、失败、人工审批、fallback 都是结果的一部分，必须在逐样本表中保留。
5. 工具调用会产生额外费用时，两组使用相同工具和同一工具数据快照；模型推理成本与工具成本分别统计。

### 3.3 敏感任务的处理

主效果—成本对照集仅含可合法发送给云端的 `public` / 已脱敏任务，保证 All-Cloud 组可执行且对照公平。

另设**安全压力子集**（建议 30–50 条，包含客户资料、内部邮件、密钥片段等），不以“全部原文上云”作为可接受基线。该子集只报告：敏感任务外送率、脱敏/审计包生成率、人工审核触发率、可信端/边保留率与任务完成情况。它用于验证安全约束，不与主成本结论混合。

## 4. 任务集与标注

### 4.1 主任务集

建议先完成 60 条预实验，用于排查日志、价格计算和评测器；正式实验使用至少 300 条公开或已脱敏任务，并分层抽样：

| 分层 | 建议样本数 | 典型任务 | AUTO 的预期行为 |
| --- | ---: | --- | --- |
| 轻量、短交互 | 100 | 问答、改写、分类、短摘要 | 端侧优先 |
| 中等复杂度 | 100 | 代码解释、结构化提取、多轮归纳 | 边侧优先或端侧 fallback |
| 高复杂度/长上下文 | 100 | 长文分析、跨文档比较、复杂推理 | 云侧优先 |

每个 `case_id` 必须保存：输入、任务类别、复杂度分层、是否允许上云、参考答案或验收规则、人工评分维度、随机顺序和数据来源。训练路由器使用过的样本不得进入正式测试集；如无独立真实 trace，需新建并冻结测试集。

### 4.2 任务成功率（本文中的“准确率”）

主指标定义为：

`Task Success Rate = 成功任务数 / 纳入评测的任务数`

任务成功以任务类型对应的验收器为准，优先级如下：

1. **可验证任务**：单元测试、JSON Schema、字段 F1/EM、检索命中、数值答案等自动验收。
2. **开放生成任务**：盲评人工评分或独立评审模型评分；评审者不能看到组别、模型、tier 和成本。每题预先定义 0–2 或 0–4 分 rubric，达到阈值才算成功。
3. 对存在争议的样本，采用两名评分者独立评分；不一致时由第三人裁决，并报告一致性（Cohen's kappa 或加权 kappa）。

同时报告平均质量分，防止“刚好超过成功阈值”掩盖质量下降。

## 5. 指标与计算方式

### 5.1 主指标（必须报告）

| 指标 | 计算 | 判读 |
| --- | --- | --- |
| 任务成功率 | `successes / evaluated_cases` | AUTO 相对纯云的效果变化 |
| 成功率差 | `TSR_AUTO - TSR_CLOUD`，单位：百分点（pp） | 负值表示 AUTO 下降 |
| 云端推理成本 | 每条任务全部云 API 输入/输出 token 按冻结价格表计价后求和 | 用户最关心的外部支出 |
| 云成本降幅 | `1 - cloud_cost_AUTO / cloud_cost_CLOUD` | 正值表示 AUTO 节省云费用 |
| 总运行成本 | 云 API 成本 + 边侧成本 + 端侧成本 + 工具成本 | 真实运行经济性 |
| 总成本降幅 | `1 - total_cost_AUTO / total_cost_CLOUD` | 避免只看云账单 |

成本按单任务先计算再汇总，不能只用“云调用次数”替代成本。对每一次模型调用记录：`input_tokens`、`output_tokens`、模型 ID、单价版本、调用次数、失败/重试标记。

```text
model_cost = input_tokens / 1,000,000 × input_price
           + output_tokens / 1,000,000 × output_price
case_cost  = Σ model_cost + Σ tool_cost + edge_cost + device_cost
```

端/边成本建议双口径报告：

- **外部现金成本**：本地或自有边缘机的边际 API 支出可为 0，但必须明确其不含设备折旧。
- **全量运行成本**：`平均功耗(kW) × 推理时长(h) × 电价 + 设备折旧分摊`；无法可靠测量时标注“未计入”，不可写成 0。

### 5.2 次级诊断与安全指标

| 指标 | 用途 |
| --- | --- |
| tier 占比（selected / actual） | 确认调度实际发挥作用，而不是全部走云 |
| p50 / p95 端到端时延 | 检查成本节省是否以不可接受的响应变慢换取 |
| 失败率、重试次数、fallback 率 | 识别端/边稳定性问题 |
| 按分层的成功率差与成本降幅 | 找到轻量、中等、高复杂度任务的边界 |
| 敏感任务误送云率 | 安全压力子集中的关键 guardrail，应为 0 |
| 人工审核触发率、脱敏率 | 验证可信工作区与审计流程 |

## 6. 统计分析与判定规则

每个 `case_id` 是一对结果（Cloud、AUTO）。正式结果应报告 95% 置信区间：

- 成功率差：对成对任务结果做 paired bootstrap（至少 10,000 次重采样）；二元成功结果可同时报告 McNemar 检验。
- 平均质量分、单任务成本、时延：paired bootstrap CI；成本分布偏斜时同时给出中位数和 p95。
- 不只报告总体均值；必须按三类复杂度分层展示。

预注册推荐判定门槛：

1. **质量门槛**：AUTO 相对纯云的成功率差下限不低于 `-3 pp`（非劣界值）。该值为建议值，正式实验前可按业务容忍度调整，但不得见到结果后再修改。
2. **成本门槛**：AUTO 云端推理成本降幅大于 0，且 95% CI 下限大于 0，才可宣称“稳定降低云端成本”。
3. **安全门槛**：安全压力子集的原始敏感内容误送云率必须为 0；否则即使成本下降也不能宣称方案可安全部署。

建议把“质量不显著下降且成本显著下降”作为成功结论；若质量下降超过非劣界值，则报告成本—质量 trade-off，不把节省成本表述为优化成功。

## 7. 运行步骤

1. 在前端模型连接页创建并测试端、边、云连接；记录 AUTO 三槽位和纯云连接的快照。
2. 冻结测试集、评分 rubric、价格表、随机种子和实验配置，生成 `manifest.json`。
3. 先跑 60 条预实验，核对 token、tier、成本、原始输出和评分记录是否完整；修复记录问题后重新冻结配置。
4. 按随机交错顺序运行正式主任务集。Cloud 组强制固定云连接；AUTO 组选择 `model=auto`。
5. 单独运行安全压力子集，并确认原始敏感内容没有被发送到云端日志或请求体。
6. 对输出做盲评/自动验收；合并逐样本记录，计算主指标、分层指标和 95% CI。
7. 人工复查所有“Cloud 成功但 AUTO 失败”和“AUTO 成功但 Cloud 失败”的样本，归类为模型能力、路由错误、资源不可用、工具差异或评测误差。

## 10. 结论边界

本实验只支持以下范围内的结论：在已冻结的任务集、模型连接、价格表、硬件和运行时段中，AUTO 相对该固定纯云模型的质量—成本折中。它不能自动推广为所有模型、所有端/边硬件、所有任务或所有价格周期的结论。

在正式运行前，不得使用“准确率提升”描述该实验预期；纯云通常是质量上界候选，实验重点是验证 AUTO 的**质量损失是否处于预设容忍范围内**，以及成本节省是否真实、可重复且不违反安全约束。
