**六、E1：先诊断证据链，避免“找到了答案词却答不对”**

目的：区分候选召回失败、排序失败、预算裁剪丢证据、摘要失真和模型推理失败。

先在 Dev-Pilot 做故障定位，再在 Test-Core 上冻结评测。每题保持相同问答模型、同一评分器和同一输入上限：

| 条件 | 提供给问答模型的内容 | 作用 |
|---|---|---|
| No Memory | 当前问题 | 观察无历史下界，不预设必定为 0 |
| Recent Full Context | 同预算内的最近完整历史 | 正常窗口预算基线 |
| Retrieved Evidence | 当前检索和原文策略产生的实际片段 | 测系统真实证据能力 |
| Oracle Evidence | gold 来源中足以回答的原文片段，明确标为诊断条件 | 定位阅读/推理或参考答案问题，不参与主系统排名 |

记录三个阶段：候选 Recall@C、排序后 Recall@K、装配后 Visible Evidence Recall。分别保存源对话/轮次 ID 和实际可见文本范围，不能以“来源会话被命中”推断其中的关键数值仍被保留。

证据充分性只让裁判评价“实际送入模型的片段”。在语义充分之外，增加 exact-value/time/entity 检查和引用支持检查。不得在 Actor 输入中添加 gold evidence 标记、参考答案或特殊的正确性标签。

若 Oracle 也失败，优先检查参考答案、缺少上下文、时间计算或模型能力；若 Oracle 成功但 Retrieved 失败，优先修召回、排序、切片和裁剪。禁止通过删除当前方法答错的问题来提高主表。

为避免增加成本，固定检索配置下的向量和候选可缓存。最终进入模型的片段、QA 请求和原始输出必须逐方法保留。

**方法设置**

| 方法 | 历史供给与状态维护 | 作用 |
|---|---|---|
| Recent Full Context | 在共同预算内保留最近历史，不启用结构化 Ledger | 全历史预算基线 |
| Memory Only | 同一 BGE/词法候选与 Top-K，常规短期历史，无 Ledger 和专用恢复编排 | 与现有论文衔接 |
| RAG＋Rolling Summary | 同一检索器，加固定大小、逐步更新的目标/约束/进度摘要及常规持久化 | 强基线，检验结构化账本相比普通摘要的价值 |
| Anchor Full | Ledger、原文引用、配置化唤醒、治理和匹配检查点 | 本文系统 |
| Plain | 无历史检索的常规短期上下文 | 只在 Pilot 或附表作为下界，不占主要预算 |

四组主方法使用同一个真实 Actor、同样的工具、节点角色、初始任务、预算和事件文件。不能给基线缺失的初始目标或故意剥夺合理持久化能力。

RAG＋Rolling Summary 需将摘要和其可用的执行记录持久化；不能通过完全不保存基线执行状态来制造必败恢复。另做“相同图检查点、不同上下文状态”条件，隔离 Ledger 的贡献。

主窗口固定为 16,384，预留输出 2,048；剩余输入上限包含 system、历史、记忆、工具定义及当前输入。需要保存每个请求的实际 max_output_tokens。所有方法在共同入口都有模型请求准入检查，不能实际提交明显超限请求。各方法自己决定内容取舍，超限而未能完成治理则记录为超限需求/暂停，而非统一截断后伪装成方法本身成功。

Memory Only、Summary＋RAG、Anchor Full 在主对照中固定相同检索器参数；共享可复用索引时，建库成本单列，不能只让某一方法承担首次冷启动。名称 Anchor Full 专指上下文治理；不要与记忆实验中“开启更新 Judge”的 Ours Full 混为一个实验变量。

**八、E3：五项组件消融**

在相同任务、事件、模型、预算和检索配置上，依次只关闭一项。Full 结果可复用主实验中严格匹配的样本及重复编号，避免重复计费。

| 消融 | 只改变什么 | 主要看什么 |
|---|---|---|
| w/o Ledger | 去掉结构化账本注入，保留相同历史检索和其他条件 | 目标、动态约束、活动 TODO、最终产物 |
| Summary Only | 保留摘要及候选排序，关闭原文展开 | 精确数值/时间错误、引用支持、QA |
| w/o Drift Control | 保留记录，关闭主动漂移纠偏 | 漂移率与误报率；干净子任务是否被误拦 |
| w/o Budget Governance | 保留公共硬准入检查，关闭系统专用压缩/降级 | 治理前超限需求、暂停率、完成率及信息损失 |
| w/o Checkpoint Recovery | 关闭专用快照恢复，保留该方法本来允许的持久状态 | 可恢复故障中的恢复率、丢失进度、重复操作 |

不能因为所有已发送请求都通过公共准入检查，就把 Budget Violation=0 宣称为某个方法独有优势。必须同时报告为达到预算付出的暂停、裁剪、证据损失及质量变化。

漂移消融中加入没有扰动的合法子任务和明确授权的目标修订，报告 false-positive rate。仅在已标记 drift 事件上运行规则并拒绝它，不能证明检测器能识别未知漂移。

**九、E4：真正的长程与恢复实验**

**执行长度**

固定模型窗口和初始证据规模，运行 20、50、100 步；另用短六轮结果作参考。每个长度中穿插不同子任务，拉长目标/约束与再次使用它之间的距离，而不只是增大日志字符串。

主要比较 Anchor Full 与 RAG＋Rolling Summary。观察成功率、约束满足、遗忘后的恢复、实际 token 总量和 P95 输入长度。关键事实在早/中/晚位置均出现，并平衡复查次数，避免把长度效应与某一位置绑定。

**恢复条件**

| 条件 | 故障 | 判定 |
|---|---|---|
| R0 | 无故障 | 正常能力和恢复开销基线 |
| R1 | 进程退出，持久状态完整 | 新进程恢复位置及任务信息 |
| R2 | 易失历史丢失，持久索引可用 | 从匹配快照及持久记忆恢复 |
| R3 | 原文归档部分缺失，摘要/其他证据仍在 | 能否说明缺失并正确降级，避免伪造来源 |
| R4 | 图与账本版本不匹配或快照损坏 | 检出不一致，选择可验证旧版本或安全暂停 |
| R5 | 工具已生效、结果未记入检查点时中断 | 恢复后核对效果，避免重复副作用 |

实际采用独立子进程和沙箱文件/数据库工具。中断发生在调用前、工具完成后但快照提交前等不同位置。不能只删除 Python Runtime 对象来代替进程级恢复。

检查点清单记录 run_id、task_id、step/frontier、Ledger revision、图定义及 schema 哈希、持久记忆快照/版本、归档清单与校验值。外部记忆保持不变的实验也应显式声明这个前提。

R1/R2 作为可恢复故障的 Recovery Success 分母。R3/R4 若证据已不可恢复，应另报“正确识别并停止/降级”，不能强行要求继续成功；也不能将安全停止混入恢复成功率。R5 报重复副作用次数和结果核对率。出现无法确定工具是否完成的情形，应记录歧义，不宣称 exactly-once。

**十、E5：低成本敏感性分析**

先做单因素分析，不做所有参数的笛卡尔积：

- Top-K：1、3、5、8、10；候选数固定，比较证据完整率与 QA/成本。参数只在开发集选择，主测试保留预先定义的分析点。
- 唤醒配置：Silent、Standard、Deep、Recovery；它们同时改变范围、K、检索和展开，整体差异只能解释为配置效果，不能单独归因某一变量。
- 展开策略：在固定 K 和固定候选下比较 none/on-demand/top-2，验证数值和关系信息是否保留；按需展开必须有真实接口和读取日志。
- 输入窗口：8k、16k、32k，只有模型实际支持相应窗口时才运行；并绘制质量—总输入 token 曲线。
- 作用域隔离：向其他 task/project 写入主题相近且答案冲突的记录；检查是否越界，归档展开是否仍遵循所属记忆上下文。

检索、作用域和原文读取的功能性分析可以大量离线完成。只对少数开发样本做模型问答扫描，不把每个组合都扩大到 100 条。

**十一、指标与统计口径**

| 指标 | 定义/注意点 |
|---|---|
| QA Accuracy、Answer F1 | 最终回答质量，单独报告，不与治理机制成功混为同一个百分比；题型评分采用已冻结规则 |
| Goal Retention | 行动和实际产物是否服务于当前合法目标；仅在输出里重复原目标不算成功 |
| Constraint Compliance | 对引入后适用的约束逐项检查，优先用结构化产物/工具日志验证；另报最终硬约束违例任务比例 |
| Drift Precision/Recall、FPR | 有标注的冲突与合法子任务对比，分别报告漏检和误拦；仅有 drifted turns 不够 |
| Candidate/Top-K/Visible Recall | 三个阶段分别计算，依据 gold IDs 与实际文本范围，不以答案字符串出现代替 |
| Evidence Sufficiency | 对实际模型可见片段是否足以推导答案进行判断；裁判错误单列 |
| Memory Use Joint Accuracy | 证据充分且回答正确的任务数/N，保留与旧稿衔接口径 |
| QA Given Sufficient Evidence | 在证据充分样本中的 QA 正确率；与上一项不同，分母为充分证据样本数 |
| Recovery Success | 可恢复故障后，进度、合法目标、约束及执行前沿一致，并完成后续指定动作 |
| Side-effect Duplication | 实际重复生效次数，来自沙箱工具执行日志 |
| Budget Overflow Demand | 治理前完整请求的超限需求比例；与实际发送后违规分开 |
| Completion / Pause / Infrastructure Failure | 必须并列，避免因暂停或丢弃错误请求制造低违规、低成本 |
| Tokens / Latency / Cost | 每步与每任务的总量、P50/P95；写入、检索、Actor、Judge、恢复分别记录 |
| Task Success | 预先定义最终产物正确、必需约束满足且无禁止副作用；另报各组成项，不能用合取结果掩盖原因 |

同一任务、事件和重复编号采用配对比较。报告差值和 95% 区间；LoCoMo 按源对话聚类重采样，并明确只有 10 个源对话，区间稳定性有限。样本只有 50—100 时，小幅差异可能没有足够把握，不要求为了显著性而更换样本。

至少随机抽查 20 条轨迹及关键争议案例，由不知道方法名的评阅者核对行动、证据、约束和判分；随机样本用于估计裁判一致性，定向失败案例用于解释问题，两者不要混为总体误差率。

主实验先完整跑一个冻结重复，再在预算允许时做第二、第三次独立运行；报每次结果及配对均值，不挑最好的一次。Provider 不支持固定随机 seed 时，明确称“独立重复运行”。当前 CLI 的 --seed 不能被当成已控制 LLM 随机性。

**十二、实施规模与调用预算**

| 工作 | 最低交付规模 | 建议扩展 |
|---|---|---|
| Pilot | 10 题×5 方法×6 步 | 只用于链路、错误率和测时 |
| 主对照 | 50 题×4 方法×20 步 | 100 题；再增加独立重复 |
| 组件消融 | 20 题×5 个关闭条件×20 步 | 50 题；复用匹配的 Full 结果 |
| 长度压力 | 10 题×2 方法×50/100 步 | 20 题，并补多种故障位置 |
| 外部 QA | 30 条 LongMemEval | 50 条分层样本；不替代运行时实验 |

在“每步恰好一次 Actor 调用”的简化假设下，前四项最低约 9,300 次 Actor 调用：300＋4,000＋2,000＋3,000。它不包含证据/答案/轨迹裁判、重试和工具循环，不能据此直接给出金额。资源紧张时先交付主对照与关键消融，再完成长度压力，不一开始将所有实验重复三次。

Pilot 记录每种方法的实际输入/输出、端到端耗时和并发下错误率。使用实际供应商计费规则估算：

总成本 = Actor 成本＋各类 Judge 成本＋写入/更新模型成本＋重试成本；
总时间按实测吞吐、检索和建库瓶颈估算，不能简单把单条耗时除以并发数。

先复用索引和已完成判分，避免重复抽取整段历史。只有在知识更新诊断中确有收益时，才把高成本更新 Judge 纳入大规模主实验；旧 N=10 已显示它可能增加大量耗时而收益不稳定。

**十五、建议推进顺序与验收**

| 阶段 | 工作 | 进入下一阶段的条件 |
|---|---|---|
| 第 1 阶段 | 找回结果，整理当前证据，修类别和拒答数据 | 每个历史表可标明“原始结果已核对/仅文档记录”；新版冻结清单完整 |
| 第 2 阶段 | 完成 P0 和真实图实验驱动 | 预算、暂停恢复、计划子任务异常、完整目标、实际可见证据的边界检查通过 |
| 第 3 阶段 | 10 条 Pilot | 无静默回退；请求与裁判可追踪；恢复确为新进程；完成成本估算 |
| 第 4 阶段 | 冻结配置后跑主对照 | 方法/任务/事件可配对；所有失败有记录；不能边看测试结果边调参数 |
| 第 5 阶段 | 消融与长程恢复压力 | 消融单变量成立；长度、故障类型和有效任务数明确 |
| 第 6 阶段 | 外部数据、人工抽查、统计和成稿 | 表中数字可从 rows 重算，结论不超过实际协议和样本范围 |

工程与接口已具备且 Pilot 吞吐足够时，可按约 7 个工作日安排：前 2 天修正/驱动，第 3 天 Pilot，第 4—5 天主对照和消融，第 6 天长程/恢复，第 7 天分析。它是排期参考，实际模型运行时长以 Pilot 为准。

验收标准是实现和证据有效，不是“必须达到某个漂亮准确率”。如果 Full 相比强摘要基线只在恢复上获益，论文就突出可恢复性；若收益不足以抵消成本，应报告适用条件和失败原因。
