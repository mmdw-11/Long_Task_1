# 技能闭环实验报告

## 一、实验目的

本实验用于验证项目中的技能演化闭环是否能够跑通，并确认系统是否具备把成功运行经验沉淀为可复用技能的能力。

实验关注的核心链路是：

```text
第一次运行任务
-> 记录运行轨迹
-> 从成功 run 中生成候选技能
-> 验证候选技能
-> 审批发布技能
-> 后续同类任务检索技能
-> 运行时注入可复用技能
-> 记录技能检索与注入轨迹
```

这个实验对应 `docs/8.10做实验的计划.md` 中的第四阶段：技能演化模块实验。它主要证明当前项目不只是一次性执行 Agent 任务，而是具备“运行经验 -> 技能资产 -> 后续复用”的轻量 SkillOS 闭环能力。

## 五、实验三：产品 API 生命周期闭环

### 运行命令

### 覆盖流程

该测试覆盖了后端产品 API 的完整技能生命周期：

1. 创建 Agent。
2. 设置图入口。
3. 第一次运行任务。
4. 从 run 中生成候选技能。
5. validate 验证候选技能。
6. publish 审批发布技能。
7. search 检索已发布技能。
8. 第二次运行同类任务。
9. 验证运行时消息中注入了“可复用技能”。
10. 查询 skill trace，确认记录了 `skill_retrieved` 事件。

### 结果解释

这个测试说明技能闭环不仅在离线实验函数中可用，也已经通过 REST API 暴露为产品化链路。

换句话说，当前系统已经支持：

```text
用户运行任务
-> 系统记录 run
-> 用户从 run 生成候选技能
-> 系统验证技能
-> 管理者审批发布
-> 后续任务自动检索技能
-> Agent 输入中注入可复用技能
-> 系统记录技能检索轨迹
```

这正是实验计划中“后端产品闭环”的关键组成部分。

## 六、第二层实验：技能复用效果对比

第一层实验主要证明技能生命周期链路可用。为了进一步验证“有技能以后是否真的产生可观测变化”，补充了第二层效果实验。

### 实验设计

实验任务族选择“日历会议安排”。

实验采用同一批 10 条日历任务，分两轮运行：

```text
Round 1：无已发布技能，运行 10 条任务
-> 使用一条成功 run 生成候选技能
-> validate 验证
-> publish 发布
-> Round 2：带已发布技能，重新运行同一批 10 条任务
-> 对比技能命中、技能注入和技能指导覆盖率
```

新增实验脚本：

```text
examples\experiments\run_skill_loop_effect_experiment.py
```

运行命令：

```powershell
python examples\experiments\run_skill_loop_effect_experiment.py `
  --output-dir runs\experiments\skills\effect_calendar `
  --fresh
```

实验产物：

```text
runs\experiments\skills\effect_calendar\summary.json
runs\experiments\skills\effect_calendar\rows.jsonl
runs\experiments\skills\effect_calendar\report.md
```

### 实验结果

关键汇总如下：

| Round | 样本数 | 成功率 | 技能命中率 | 技能注入率 | 任务词覆盖率 | 技能指导覆盖率 |
|---|---:|---:|---:|---:|---:|---:|
| Round 1 无技能 | 10 | 1.0000 | 0.0000 | 0.0000 | 1.0000 | 0.2000 |
| Round 2 有技能 | 10 | 1.0000 | 1.0000 | 1.0000 | 1.0000 | 0.6200 |

效果变化：

```text
技能命中率提升：1.0000
技能注入率提升：1.0000
任务词覆盖率变化：0.0000
技能指导覆盖率提升：0.4200
```

本轮生成并发布的技能状态为：

```text
skill_status = published
validation_passed = true
search_match_count = 1
```

### 指标解释

| 指标 | 含义 |
|---|---|
| 技能命中率 | SkillRetriever 是否检索到了非空技能内容 |
| 技能注入率 | Agent 最终输入/输出中是否出现“可复用技能”上下文 |
| 任务词覆盖率 | 输出是否覆盖当前任务本身包含的关键词 |
| 技能指导覆盖率 | 输出中是否覆盖技能沉淀出的关键指导词，例如“读取参与人日历”“检查时间冲突”“创建提醒”“确认清单” |

### 第二层实验结论

第二层实验说明，技能发布后对后续同类任务产生了可观测影响：

1. 技能命中率从 `0.0` 提升到 `1.0`。
2. 技能注入率从 `0.0` 提升到 `1.0`。
3. 技能指导覆盖率从 `0.20` 提升到 `0.62`。
4. 同一批任务在 Round 2 中全部检索并注入了已发布技能。

由于本地实验使用的是 `LocalEchoExecutor` fallback，任务成功率和任务词覆盖率本身较容易达到 `1.0`，因此不能把这次结果解释为真实 LLM 任务质量的大幅提升。更准确的结论是：

```text
在受控本地环境中，发布后的技能能够稳定命中、注入，并显著增加输出中与已沉淀技能步骤相关的指导信息。
```

这已经比第一层“流程可用”更进一步，证明技能复用对后续任务上下文产生了实际影响。

## 七、阶段性结论

当前项目已经具备以下能力：

1. 可以从成功运行轨迹生成候选技能。
2. 可以对候选技能进行验证。
3. 技能发布需要审批信息，避免未验证技能直接进入运行链路。
4. 发布后的技能可以被检索。
5. 后续同类任务运行时可以注入可复用技能。
6. 技能检索和注入过程可以通过 trace 追踪。
7. 离线实验 runner 和产品 API 生命周期测试均可复现该闭环。

因此，可以认为项目已经具备“轻量 SkillOS”的核心闭环能力。

## 九、技能来源

本项目技能是在运行过程中从成功run中得到的

过程是：

```text
Agent 完成一次任务
-> 系统记录 run 的输入、输出、节点轨迹和技能轨迹
-> 从成功 run 中提取可复用经验
-> 生成 candidate skill
-> validate
-> publish
-> 后续相似任务 retrieve + inject
```

因此，技能更像是系统从历史成功执行中总结出的“可复用操作说明”
