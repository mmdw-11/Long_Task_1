# 挑战杯 XH-202631：赛题—项目差距、可复用技术与实施方案

> 审查日期：2026-08-29。本文区分“赛题要求”“当前代码已实现”“可作为论文创新”“后续计划”；不把文档中的说明文字或项目自评当作实现证据。

## 1. 赛题真正要求什么

赛题不是做一个可视化 Agent 工作流，而是构建能在开放、非确定环境里持续运行的**群体智能自治引擎**。可交付系统必须无人工干预地应对需求变更、异常和节点失效，完成从高层意图到交付物的全链路；材料还要给出核心算法伪代码与复杂度分析。

核心硬要求有四项：

1. 超长程上下文连续性：分布式记忆、压缩—唤醒，目标、关键事实和中间决策不漂移。
2. 动态异构拓扑与低熵通信：异构角色；通信图不能是预设静态全连接；按任务语义生成稀疏路由，以信息瓶颈或结构化协议抑制冗余和噪声。
3. 端—边—云自适应调度：根据实时性、数据敏感度与资源状态决定推理位置/模型切分，实际利用云端处理难任务。
4. 可演示的自治闭环：感知—规划—执行—反馈，展示中间轨迹，并在至少两个高完成度跨领域长程任务中量化成功率、鲁棒性、token 与时间。

评分上，完整闭环及数千步稳定性 15 分，组织/协作机制 15 分，跨领域场景 10 分，架构通信降噪 10 分，核心算法/底层突破 10 分，成功率、资源效率、扩展性各 5 分。因此“能拖拽画图、能跑一个链式 Demo”仅是产品基础，不能替代核心算法。

### 已有实验的可信边界

- `verification_20260828/workflow` 的 300/300 是确定性图结构单测式数据，说明图引擎正确，不证明真实 Agent 能完成复杂任务。
- `long_task/ours_full` 的 10/10 是每例 3 步的合成状态保持程序；源码明确写为“deterministic backend mechanism evaluation; not LLM QA”。它不能写成“数千步长程成功率”。
- 真实 LongMemEval 已存结果只有 2 条：本项目 engine 命中 1/2，mem0 命中 2/2；样本量不能形成结论。
- `routing/learned` 仅 5 个测试样本，准确率 0.2；路由实验本身把 latency/cost 写成可配置 proxy。不能在答辩中称“学习路由优于基线”。
- 测试环境：32 个上下文账本测试通过；`requirements.txt` 已声明 `pytest-asyncio`，但当前 Anaconda 环境未安装，导致 async 测试无法执行；全量 API 测试还缺 FastAPI。必须先建立锁定环境后再报告通过率。

## 3. 建议的论文主线：TIDE-Swarm

建议将系统命名为 **TIDE-Swarm（Task-state-aware Information-bottleneck Dynamic Heterogeneous Swarm）**。原创点不是声称发明所有模块，而是提出并验证以下联合机制：

```text
事件/状态变化 → 时态任务—证据图 → 拓扑控制器 → 稀疏协作子图
                                       ↓
端/边/云资源状态 ← 约束符号验证 ← 低熵消息胶囊 ← 各异构角色执行
                                       ↓
                        可回溯记忆、轨迹、检查点、拓扑奖励
```

### 3.1 动态拓扑控制器（第一优先级）

在现有 `RoutingPolicy` 之上新增 `TopologyController`：它不只从既有候选边中挑选，而是维护可变的通信邻接矩阵 `A_t`，可创建/删除临时协作边、选择活跃 Agent、指定汇聚者并设定边 TTL。每次目标变更、失败、预算压力、证据冲突或资源状态突变时触发重构。

对候选边 `(i,j)` 的效用建议定义为：

`U_t(i,j) = α·任务贡献 + β·新证据价值 + γ·不确定性降低 − λ·token − μ·时延 − ν·风险`。

第一版用可解释的 LinUCB/Thompson contextual bandit 学 `U_t`，特征来自角色能力、子任务依赖、记忆相关度、历史成功/失败、资源指标与消息新颖度。第二版可将 G-Designer 的“任务虚拟节点 + 图编码—解码”作为离线 teacher/对照，但不要直接把其实现当原创。每次决策产出 `{active_agents, edges, ttl, reason, expected_gain}`，写入轨迹供反事实评估。

复杂度可写为候选边打分 `O(|E_candidate|·d)`，每轮选择预算 `B` 条边用堆为 `O(|E_candidate| log B)`；若只在受影响子图上重构，则不随全局 Agent 数线性爆炸。

### 3.2 低熵、可验证的消息胶囊（第二优先级）

新增 `MessageCapsule`（Pydantic/JSON Schema）：`goal_id, subtask_id, claim, evidence_refs, constraints_delta, proposed_action, uncertainty, ttl, token_budget, digest`。禁止把完整 history 直接广播；发送前依次执行：

1. **语义保真压缩**：对长文本采用 LLMLingua-2 或本地小模型摘要；代码、URL、数字、约束键列入不可丢失字段。
2. **信息瓶颈门控**：估计接收者任务相关性、新颖度与冗余度；低于阈值则丢弃/只传引用。
3. **符号校验**：硬约束、字段类型、证据引用与版本一致性不通过时，消息进入“请求澄清/反例”而非下游执行。
4. **接收者选择**：只向 `A_t` 的出边投递；聚合 Agent 只发布经验证的共享结论。

同时记录 `tokens_sent`、边密度、有效消息率、重复率、Shannon token entropy、压缩后事实保真率和错误传播率。这样“低熵”是可量化定义，不是宣传语。

### 3.3 时态证据记忆 + 神经符号闭环（第三优先级）

保留现有四层存储，但把 PROJECT/GLOBAL 从平面向量条目升级为 `Fact(subject, predicate, object, valid_time, observed_time, source, confidence, provenance)`；以向量召回候选、时态图/PPR 重排、冲突检测和证据回链。将 `MemoryLLMJudge` 的 add/update/delete 从黑盒结果改为“带证据的变更提案”，由约束校验器接受。

对高风险计划，LLM 生成受限 JSON IR（任务、前置条件、资源、时限、不可违反约束），用 Z3/OR-Tools 校验可满足性、冲突、时序与预算；验证失败的反例回灌给规划 Agent。这是赛题“神经符号协同”最易落地、也最可解释的路径。

### 3.4 DAG 级端—边—云调度（第四优先级）

不要再把模型切分计划当成真实切分。把动态拓扑的活跃子图输入调度器，测量每个资源的真实 TTFT、生成速度、队列、网络 RTT、能耗/成本和成功率；用约束 HEFT + 在线 bandit 选择 placement。敏感数据先在端侧脱敏/抽取 capsule，云端只接收必要证据。模型层切分（EdgeShard 类）可作为扩展实验，不应阻塞主系统。

## 5. 实施顺序（建议 6 周）

1. **第 1 周：可复现底座。** 固定 Python/依赖锁文件，解决 `pytest-asyncio`、FastAPI 缺失；补真实 token/时延/成本采集和统一 JSONL trace。把当前合成实验改名为“机制回归测试”。
2. **第 2–3 周：MessageCapsule + TopologyController MVP。** 先实现角色能力表、临时边/TTL、规则触发重构、消息 schema、压缩/验证和可视化；对比静态 chain/star/full-connect 与 AgentPrune 式固定稀疏图。
3. **第 4 周：时态证据记忆与约束求解。** 加 Fact/Provenance 表、冲突检测、Z3/OR-Tools 校验器；将需求变更、节点宕机、错误证据作为统一 `RuntimeEvent` 注入。
4. **第 5 周：真实端云调度。** 以本地 Ollama、边缘 HTTP、云 API 做三资源真实 profile；加 HEFT/bandit，记录隐私违规、p95 延迟和成本。
5. **第 6 周：正式实验与材料。** 至少 3 随机种子；不同模型/预算；完整失败分析；导出架构图、算法伪代码、复杂度表和可回放轨迹。

## 6. 正式实验设计与可答辩指标

### 6.1 三组不可省略的对照

1. **动态拓扑与低熵通信**：Static Chain、Static Star、Full Communication、AgentPrune、TIDE-Swarm。固定角色和模型，比较任务成功率、tokens、消息数、边密度、冗余率、熵、错误传播、拓扑重构时间。
2. **长程状态保持**：Full Context、mem0、A-Mem/HippoRAG（可运行者）、当前 Hierarchical Memory、TIDE temporal-evidence memory。在 LongMemEval 全量上采用官方 answer evaluator；随后在 LongMemEval-V2 报准确率—查询延迟前沿。
3. **端边云自治闭环**：All-device、All-cloud、当前 heuristic、当前 learned router、HEFT、TIDE scheduler。报告端到端成功率、p50/p95 时延、真实 token/API 成本、敏感数据外发率、故障后恢复率。

### 6.2 两个展示场景

- **跨应用办公/终端助理**：邮件—日历—浏览器—文档任务，任务中途插入日程冲突、权限拒绝、需求优先级改变。突出端侧敏感信息处理、边云协同与状态连续性。
- **软件工程自治交付**：需求→代码检索→实现→测试→修复→报告，中途注入测试失败、依赖不可用、约束变更。突出 Planner/Code/Tester/Verifier 的动态图、符号约束验证与检查点恢复。

每个场景应具有一个可机读的任务完成判定器；不要只以 LLM 打分。展示时回放：事件注入 → 拓扑变化 → capsule 流转 → 资源迁移 → 验证/恢复 → 最终交付。

## 7. 最终定位建议

当前项目可以定位为一个良好的“可观测 Agent 图运行时与产品控制台”，但还不能定位为完成赛题的群体智能架构。论文最稳妥的主张是：

> 在长程、动态扰动任务中，提出一个由任务状态驱动的异构群体重构机制；它通过可验证低熵消息、时态证据记忆和资源约束调度，联合优化成功率、通信成本、恢复能力和数据边界。

请避免以下表述：

- “已实现自适应网络拓扑”：当前是静态图加条件边；需完成 TopologyController 后才成立。
- “已实现神经符号推理”：当前没有符号求解链。
- “可完成数千步”：当前长任务实验实际为 3 步合成流程。
- “学习路由显著优于基线”：现有 5 条测试结果不支持。

反过来，图运行时、账本/检查点、资源 executor、SSE 可观测性和前端控制台都应保留并作为实现创新的可靠载体；它们让新的研究机制能被部署、注入扰动、回放和量化，而不是停留在架构图上。
