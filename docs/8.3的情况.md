# 8.3的情况
# 一、BGE模型适配改造
之前的痛点：代码直接写死模型名称`BAAI/bge-m3`，FlagEmbedding会强制联网去HuggingFace仓库校验/下载模型，就算你硬盘里已经下好了模型也没用，一跑测试就联网卡顿、报错。
这次改造**彻底实现模型本地优先加载**，常态测试完全不碰外网、不加载大模型，速度拉满；需要验证向量功能时手动开启测试即可。

## 核心改造：新建`bge_local.py`本地模型路径解析器
这个文件做了一套**模型路径优先级查找规则**，按顺序挨个找本地模型，只有本地全都找不到，才会走外网HuggingFace拉取：
1. 最高优先级：读取系统环境变量`BGE_M3_MODEL_PATH`（你可以手动指定模型文件夹路径，灵活性最高）
2. 第二优先级：项目文件夹内部缓存 `.hf_cache/huggingface` 里的BGE-M3模型
3. 第三优先级：你之前早就下载好的存量模型路径 `D:\PythonProject\hf_cache\models\BAAI--bge-m3`
4. 兜底方案：前面全没找到，才使用原版`BAAI/bge-m3`触发外网下载

## 业务代码对接适配
把这套本地路径查找逻辑，接入两处使用BGE向量模型的核心代码：
1. `engine/modules/memory/embedding.py`：记忆模块的向量嵌入（做文本向量化、语义相似度对比，漂移检测、记忆检索要用）
2. `engine/modules/scheduling/learning.py`：任务调度学习模块向量计算
两处全部不再硬编码模型名称，统一调用`bge_local.py`获取本地模型真实路径，从根源杜绝无意义外网请求。

# 二、漂移检测
### 原始两点问题
1. 漂移只做节点名重复=死循环检测，没有「任务目标偏移、语义行为漂移」；
2. 单纯节点名计数容易绕过，真正死循环是**重复工具、重复文件修改、重复重试语义动作**。

### 修复:
1. **保留原有兜底规则**：节点重复、pending任务堆积、长期无进度（防止极端卡死兜底）；
2. **新增三层语义级漂移识**
   - 相似输出摘要重复（语义重复重试，哪怕节点不一样也能识别循环）
   - 同一个原始资源/文件raw反复引用（对应重复修改同一文件）
   - 同一个工具反复调用（对应循环调用工具死循环）
3. 新增专项测试用例`test_drift_detector_records_semantically_repeated_attempts`，验证语义循环漂移可被捕获、写入账本漂移记录。

✅ 修复成效
- 不再是单纯“节点名死循环检测器”，升级为**语义行为漂移检测器**，贴合Drift（任务行为跑偏、无效循环漂移）原本定义；
- 规避“换节点名做重复动作就检测失效”的漏洞，符合真实Agent运行的循环判定逻辑。

# 三、子Agent父校验标记污染问题：彻底封堵自校验漏洞
### 问题
子Agent自行返回`__parent_validated__`字段，子Agent可以自己给自己盖章放行，校验规则被轻易篡改、污染，父级校验形同虚设。

### 修复
1. **架构逻辑强约束**：子节点输出的`__parent_validated__`直接作废、不被校验器采信，禁止子Agent自证合法；
2. **授权主体变更**：**父编排器/父节点在全局State顶层写入授权记录**
   ```json
   "__parent_validation__": {"child节点名": {"approved": True}}
   ```
   只有上层统筹节点才有资格下发放行授权；
3. 两条新增测试用例双向校验：
   - `test_sub_agent_cannot_self_promote_with_parent_validation_flag`：验证子自己打标记无法通过校验；
   - `test_sub_agent_output_can_be_promoted_with_external_parent_validation`：验证父节点授权才可正常放行结果。

✅ 修复成效
彻底解决“子Agent伪造校验凭证绕过审核”的安全逻辑漏洞，父级后置校验的权威性完全成立，适配多层多Agent嵌套复杂场景，解决对多Agent落地稳定性的顾虑。

# 四、压缩记忆无原文读取接口：补齐双向链路闭环
### 原有问题
仅在MEMORY.md写入`raw_ref`文件路径做记录，**无封装程序接口**，只能人工打开文件读取原文，框架无法通过摘要索引自动回溯原始长文本，断点复盘、LLM细节召回无法自动化。

### 修复落地内容
1. 在压缩器`ContextCompressor`、上下文账本`ContextLedger`双层新增配套接口：
   - `read_raw_ref()`：根据引用标识读取原始全文；
   - `resolve_raw_ref()`：解析引用路径定位资源；
   - `raw_refs_for_run()`：一次性获取单次任务全部原始文件索引；
   - `read_raw_summary()`：同时读取摘要+原文；
2. 配套功能测试`test_compressed_memory_raw_ref_can_restore_original_payload`，验证索引可以无损还原超长原始文本。

✅ 修复成效
从「单向压缩存档」升级为**压缩摘要存储 ↔ 原始文本索引召回**完整双向链路，程序可自动根据记忆索引调取完整原始上下文，满足复盘、断点续跑、大模型深度推理的原始素材调取需求。
