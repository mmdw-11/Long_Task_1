结论先说：**“成为子智能体”不应该设计成一个普通逻辑节点。**它不是一次可执行步骤，而是一种父子隶属关系。正确交互就是你想到的：创建一个可扩展的“智能体团队/主管智能体”容器，再把普通智能体拖进去，使其成为候选 subagent。

最适合你项目的是“外层确定性工作流 + 内层动态智能体团队”的混合模式：

```text
开始 → 数据准备 →【动态智能体团队】→ 结果检查 → 结束
                       │
                       ├─ 搜索 Agent
                       ├─ 编码 Agent
                       ├─ 测试 Agent
                       └─ 评审 Agent
```

外层仍然保留你现在的条件、循环、批处理等普通逻辑；进入团队后，由主管根据运行状态动态拆解、选择、并发、交接和恢复。

## 一、左侧节点库怎样分类

你提出的两类可以保留，但我建议把“动态逻辑”在界面上命名为“协作控制（动态）”，用户更容易理解。

### 普通逻辑

完全保留现有内容：

- 条件判断
- 意图分类
- 防漂移检查
- 脚本
- 变量赋值
- 循环
- 批处理

这些节点的共同特点是：执行关系和出口在设计阶段基本已经确定。

### 协作控制（动态）

建议第一阶段提供以下节点：

| 动态组件 | 作用 | 画布形态 |
|---|---|---|
| 智能体团队 | 定义主管和候选 subagent 范围 | 可扩大、可折叠容器 |
| 任务规划器 | 将目标拆成带依赖关系的子任务 | 普通节点，通常固定在团队顶部 |
| 动态委派器 | 根据能力、状态、成本选择一个或多个 Agent | 团队头部内置控制器，不建议做普通大节点 |
| 结果汇聚器 | 合并多个 Agent 的返回结果 | 普通节点 |
| 结果裁决器 | 投票、评分、交叉验证或选择最佳结果 | 普通节点 |
| 目标检查器 | 判断任务是否完成、是否需要继续规划 | 普通节点，带“完成/继续”出口 |
| 故障恢复器 | 超时、失败、节点失效时重试、换人或重规划 | 团队级策略，也可显示为小型控制节点 |
| 临时智能体工厂 | 根据任务创建临时角色并在结束后销毁 | 高级节点，第二阶段实现 |

其中最核心的是“智能体团队”，其他都是团队内部的协作能力。

## 二、哪些东西不应该设计成节点

这里需要严格区分五种概念：

| 概念 | 应该如何显示 |
|---|---|
| Agent、团队 | 节点或容器 |
| 任务规划、汇聚、验证 | 可执行节点 |
| 成为 subagent | 空间包含关系 |
| 允许 handoff/通信 | 虚线约束边 |
| 本次真正发生的路由 | 运行时动画边 |
| 通信压缩、恢复、资源调度 | 右侧策略配置 |

因此不要增加一个叫“成为子智能体”的橙色逻辑节点。否则会形成不自然的结构：

```text
父 Agent → 成为子智能体 → 子 Agent
```

这会错误地表示“成为子智能体”是运行到某一步才发生的。

正确结构是：

```text
┌────────────── 研究团队 ──────────────┐
│  主管：研究主管                      │
│  策略：动态委派 · 稀疏通信 · 可恢复   │
│                                      │
│  [搜索 Agent] [分析 Agent] [评审 Agent]│
└──────────────────────────────────────┘
```

父子关系通过拖入容器产生，而不是通过节点连线产生。

## 三、团队容器的具体交互

### 1. 创建团队

用户从“智能体”分类拖入“智能体团队”。

落到画布后生成一个大容器：

```text
┌ 研究团队 ─────────────────────── ○输出
│ 主管：自动 / 指定 Agent
│ 协作模式：主管委派
│
│     将智能体拖入此处成为团队成员
└─────────────────────────────────
```

整个团队在外层工作流中仍然只有一个输入端和一个输出端，因此可以像普通节点一样接入现有流程。

### 2. 拖入 Agent

把小智能体拖到容器范围内时：

- 团队边框高亮；
- 出现“释放后加入团队”提示；
- 松开后设置 `parentId`；
- 团队自动扩大；
- Agent 卡片显示角色和能力标签；
- 不自动生成固定执行连线。

你现在的前端已经对循环、批处理实现了这类容器拖放：通过 `parentId`、`extent: 'parent'` 和自动扩容处理子节点，可直接复用这一机制。[WorkflowEditor.tsx](D:/PythonProject/long_task_1/long_task_1_Fronted/src/WorkflowEditor.tsx:55)

保存时现有代码也已经会序列化 `parent_id` 和 `children`，说明数据结构底座已经有了，只需为团队增加新的语义和运行时逻辑。[WorkflowEditor.tsx](D:/PythonProject/long_task_1/long_task_1_Fronted/src/WorkflowEditor.tsx:167)

### 3. 移出 Agent

将 Agent 拖出团队：

- 解除父子关系；
- 不删除 Agent；
- 已有运行版本不受影响；
- 如果该 Agent 是主管，必须先重新指定主管。

### 4. 展开与折叠

团队需要支持：

- 双击展开/折叠；
- 折叠后显示“1 个主管、4 个成员”；
- 展开后显示内部 Agent；
- 外层连线始终连接团队容器；
- 团队内部布局不代表实际执行顺序。

### 5. 多级团队

第二阶段可以允许：

```text
总协调团队
├─ 调研团队
│  ├─ 搜索 Agent
│  └─ 事实核验 Agent
└─ 开发团队
   ├─ 编码 Agent
   └─ 测试 Agent
```

这与 LangGraph 多层 Supervisor 的思路一致。建议先限制最大嵌套深度为 2，避免画布和递归失控。[LangGraph Supervisor](https://reference.langchain.com/python/langgraph-supervisor)

## 四、团队内部怎样动态执行

建议预置四种“协作模式”，而不是让用户手动画所有内部连线。

### 主管委派

```text
Supervisor → 选择成员 → 执行 → 返回 Supervisor
```

适合默认模式。参考 CrewAI Manager 和 LangGraph Supervisor：主管根据 Agent 的职责描述决定调用谁。[CrewAI Hierarchical Process](https://github.com/crewAIInc/crewAI/blob/main/docs/v1.15.0/en/learn/hierarchical-process.mdx)

### 动态选言

每轮从候选 Agent 中选择下一位：

```text
当前状态 → 候选集过滤 → Agent 评分 → 选择下一 Agent
```

类似 AutoGen `SelectorGroupChat`，它根据当前上下文和参与者描述选择下一位发言者。[AutoGen SelectorGroupChat](https://microsoft.github.io/autogen/dev/user-guide/agentchat-user-guide/selector-group-chat.html)

### 去中心化交接

当前 Agent 可以把任务移交给另一名 Agent：

```text
搜索 Agent ──handoff──> 分析 Agent
```

参考 AutoGen Swarm。这里的 handoff 应当显示成“允许交接”的虚线，而不是普通执行边。[AutoGen Swarm](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/swarm.html)

### 并行议会

主管同时选择多个 Agent：

```text
                 ┌→ Agent A ─┐
主管 → 并行委派 ─┼→ Agent B ─┼→ 汇聚/裁决
                 └→ Agent C ─┘
```

委派器配置：

- 最大并行数；
- 选择数量；
- 是否等待全部结果；
- 最少成功数量；
- 超时后是否提前汇聚；
- 汇聚方式：拼接、摘要、投票、裁决模型。

## 五、动态委派器怎样设计

委派器不建议作为一个需要用户反复拖入的大节点。它应固定在团队标题栏中，类似团队的“控制中枢”。

标题栏显示：

```text
研究团队
主管：Research Manager
策略：能力匹配 ▾
并发：2
预算：12k tokens
状态：设计态
```

右侧配置面板提供：

### 候选成员

- 当前团队成员；
- Agent 能力标签；
- 是否允许被选择；
- 最大并发任务数；
- 优先级；
- 是否为备用节点。

### 路由依据

第一版可以使用可解释加权评分：

```text
路由分数 =
  任务能力匹配度
+ 历史成功率
+ 当前可用性
+ 证据相关性
- 当前负载
- 预计成本
- 通信冗余
```

用户可以选择：

- 仅能力匹配；
- 规则 + 模型混合；
- 成本优先；
- 时延优先；
- 质量优先；
- 自定义权重。

后期再加入学习型拓扑。DyLAN使用推理时 Agent 选择和早停；G-Designer根据任务生成通信拓扑；AgentPrune裁剪冗余通信；GPTSwarm优化图连接。这些适合成为你的论文算法和实验基线，而不适合作为首版前端必须暴露的复杂参数。[DyLAN](https://github.com/SALT-NLP/DyLAN)、[G-Designer](https://arxiv.org/abs/2410.11782)、[AgentPrune](https://arxiv.org/abs/2410.02506)、[GPTSwarm](https://github.com/metauto-ai/GPTSwarm)

## 六、赛题要求对应的其他动态逻辑

除了 subagent，赛题真正需要的动态能力还有以下几类。

### 1. 动态拆解与重规划

任务规划器维护可修改的子任务 DAG。当出现：

- 用户需求变化；
- 新证据推翻旧结论；
- 子任务失败；
- 资源不可用；
- 验证结果不通过；

就重新规划受影响部分，而不是从头执行。

界面上，任务规划器是团队内部节点，运行时弹出“计划版本 v1 → v2”的变化记录。

### 2. 动态拓扑重构

这是比赛重点，不能只做到“主管选择一个 subagent”。

需要支持：

- 激活或停用成员；
- 创建临时通信边；
- 删除低价值边；
- 设置临时边 TTL；
- 发生故障时换路；
- 根据任务阶段切换星型、链式、并行或评议结构。

这些不需要设计成多个节点，而应作为团队的“拓扑策略”。

### 3. 故障恢复

团队外框可配置“恢复边界”：

- 原 Agent 重试；
- 替换备用 Agent；
- 更换模型或工具；
- 从检查点恢复；
- 把任务退回规划器重新拆分；
- 降级运行；
- 失败后转人工。

运行时失败节点变红，备用节点高亮，显示一条红色虚线：

```text
编码 Agent × ──替换──> 备用编码 Agent
```

### 4. 结果汇聚与冲突裁决

多个 Agent 返回结果后不能简单拼接，需要：

- 去重；
- 基于证据合并；
- 多数投票；
- 置信度加权；
- Judge Agent 裁决；
- 符号约束验证；
- 冲突无法解决时重新委派。

因此“结果汇聚器”和“结果裁决器”值得成为显式动态节点。

### 5. 动态终止

长程任务不能只依赖 Agent 输出“FINISH”。目标检查器至少提供：

- 验收条件是否满足；
- 硬约束是否通过；
- 证据是否充分；
- 最大轮数；
- token/时间/费用预算；
- 是否存在未完成子任务。

出口建议是：

```text
完成 → 团队输出
继续 → 返回规划器
需恢复 → 故障恢复器
```

### 6. 临时智能体生成

高阶功能可以允许规划器根据任务创建临时 Agent：

```text
任务需要“法律合规检查”
→ 从 Agent 模板创建临时合规 Agent
→ 加入当前团队
→ 完成任务
→ 归档或销毁
```

它不同于“把已有 Agent 拖入团队”：

- 拖入：设计阶段授权已有 Agent；
- 临时生成：运行阶段根据任务实例化 Agent。

第一版可以只允许从白名单模板生成，避免模型任意创建无约束 Agent。

### 7. 端—边—云动态调度

不要做成画布节点，否则每个 Agent 都要额外连接调度节点。把它设计成团队或 Agent 的运行策略：

```text
部署：AUTO
目标：均衡
敏感数据：仅端侧
云端预算：¥5
失败降级：云 → 边 → 端
```

运行时在 Agent 卡片角标显示“端/边/云”，迁移时产生事件动画。

## 七、画布上需要区分三种边

这是动态编排能否看懂的关键。

### 设计态

- 实线：固定执行边；
- 灰色虚线：允许通信/handoff；
- 容器包含：父子关系；
- 禁止把成员摆放顺序解释为执行顺序。

### 运行态

- 紫色动态线：本轮实际委派；
- 蓝色线：消息或证据返回；
- 红色虚线：失败替换；
- 绿色线：验证通过后的结果汇聚；
- 临时边显示倒计时或 TTL；
- 已结束边淡出，但保留在轨迹时间轴。

建议提供两个查看开关：

```text
[设计拓扑] [运行拓扑]
```

再增加一个时间轴：

```text
t0 初始团队
t1 选择搜索 Agent
t2 并行加入核验 Agent
t3 搜索 Agent 失败
t4 切换备用 Agent
t5 汇聚并完成
```

这样评委才能直观看到“拓扑确实发生了动态变化”，而不是只看到几个 Agent 在聊天。

## 九、推荐实施顺序

第一版先完成以下闭环：

1. “智能体团队”可扩展容器；
2. Agent 拖入/拖出成为成员；
3. 指定主管；
4. 动态选择单个或多个成员；
5. 汇聚成员结果；
6. 目标检查和继续执行；
7. 成员超时后自动换人；
8. 运行时动态边和选择原因可视化。

第二版再增加：

- Agent 间 handoff；
- 多层团队；
- 临时 Agent 生成；
- 稀疏拓扑优化；
- 时态证据驱动路由；
- 端边云迁移；
- 学习型路由策略。

最重要的产品定义可以概括为：

> 普通逻辑决定“固定流程怎样执行”；动态协作决定“当前应该由哪些智能体、以什么结构协作”。  
> 子智能体由容器包含关系定义，动态路由由运行时生成，二者不能混成一个普通逻辑节点。
