你的整体方向是对的。建议把当前动态逻辑重新收敛成三个节点：

```text
任务规划器
质量门控器（合并目标检查器和恢复边界）
结果汇聚器
```

其中技术异常恢复仍作为后端基础能力自动存在，不要求用户拖节点；用户拖入的“质量门控器”负责检查某一段业务结果是否正确、可信、完整，并决定通过、返工、重规划还是人工处理。

## 一、任务规划器应升级为“计划与执行控制器”

任务规划器不能再像当前版本一样：

```text
生成 task_plan
    ↓
把原始 input 继续传给后续节点
```

它应该维护一个真正可执行的 TODO 状态机。

### 规划模型输出

用户输入总目标后，规划模型输出严格的结构：

```json
{
  "goal": "完成多智能体架构调研与设计",
  "todos": [
    {
      "id": "todo-1",
      "order": 1,
      "objective": "理解赛题要求",
      "required_capabilities": ["文档分析", "需求提取"],
      "required_tools": [],
      "required_skills": [],
      "required_knowledge": ["赛题资料库"],
      "expected_output": "结构化需求清单",
      "acceptance_criteria": [
        "覆盖赛题核心指标",
        "每项要求能够追溯到原文"
      ],
      "evidence_requirements": {
        "citations_required": true,
        "minimum_sources": 1
      },
      "status": "pending",
      "max_attempts": 2
    },
    {
      "id": "todo-2",
      "order": 2,
      "objective": "调研动态多智能体路由技术",
      "required_capabilities": ["论文检索", "技术调研"],
      "depends_on": ["todo-1"],
      "expected_output": "相关技术与代码仓库对比",
      "acceptance_criteria": [
        "包含论文或官方文档来源",
        "给出可复用实现"
      ],
      "status": "pending"
    },
    {
      "id": "todo-3",
      "order": 3,
      "objective": "形成最终架构方案",
      "required_capabilities": ["系统架构", "方案综合"],
      "depends_on": ["todo-1", "todo-2"],
      "expected_output": "完整设计与测试方案",
      "status": "pending"
    }
  ]
}
```

第一版可以只支持严格顺序：

```text
todo-1 → todo-2 → todo-3
```

以后再扩展为有依赖关系的 DAG。

### 现有 TODO 机制如何接进来

你后端当前确实有 TODO 机制，但主要用于观测：

- 运行开始时生成 TODO 事件；
- 每完成一个工作流节点，就机械地推进一个 TODO；
- TODO 并没有真正决定下一步执行哪个节点；
- 没有针对 TODO 保存执行结果、证据和失败原因。

因此应改为持久化的 `PlanLedger`：

```json
{
  "goal": "...",
  "current_todo_id": "todo-2",
  "todos": [],
  "completed_results": {},
  "evidence": {},
  "replan_count": 0,
  "total_cost": 0,
  "total_latency_ms": 0
}
```

每次执行时：

```text
读取 PlanLedger
    ↓
找出第一个满足依赖的 pending TODO
    ↓
写入 current_todo
    ↓
选择执行节点
    ↓
质量检查
    ↓
更新 TODO 状态、结果和证据
    ↓
继续下一个 TODO
```

这样 TODO 才真正参与控制流程，而不是只显示在运行日志里。

## 二、每个 TODO 后面难道都走相同节点吗

你的疑惑非常关键：不能让所有 TODO 无条件走同一条固定线路。

建议提供两种执行模式。

### 模式一：统一执行池

画布为：

```text
开始
  ↓
任务规划器
  ↓ current_todo
智能体团队
  ↓
质量门控器
  ↓ pass
返回任务规划器
```

每个 TODO 的确都会进入同一个智能体团队，但不会执行同一个 Agent。

例如：

```text
todo-1：理解赛题
→ 团队选择文档分析 Agent

todo-2：检索论文
→ 团队选择资料检索 Agent

todo-3：形成架构
→ 团队选择方案设计 Agent
```

团队使用的评分输入不再是原始总任务，而是：

```text
current_todo.objective
required_capabilities
required_tools
required_skills
required_knowledge
acceptance_criteria
```

这和 AutoGen `SelectorGroupChat` 的思路接近：管理器根据当前上下文和参与者描述选择下一位执行者，而规划 Agent 可以先拆解任务，再由管理器逐项选择成员。[AutoGen SelectorGroupChat](https://microsoft.github.io/autogen/dev/user-guide/agentchat-user-guide/selector-group-chat.html)

这种模式适合大部分用户，因为画布简单：

```text
规划器 → 执行团队 → 检查器 → 规划器
```

虽然物理线路相同，但每轮的任务、Agent、工具、Skill、知识库和输出标准不同。

### 模式二：多执行通道

高级用户可以给任务规划器连接多个执行通道：

```text
                        ┌→ 文档分析团队
任务规划器 current_todo ├→ 资料检索团队
                        ├→ 编码 Agent
                        └→ 方案评审团队
```

用户不指定：

```text
todo-1 必须走文档团队
todo-2 必须走检索团队
```

而是为每条通道声明能力：

```text
文档分析团队：
文档解析、需求提取、PDF、OCR

资料检索团队：
论文搜索、网页检索、证据核验

编码 Agent：
代码实现、测试、调试
```

运行时的“任务分发器”根据 TODO 需求对执行通道评分，只激活得分最高的通道。

因此，用户只配置“有哪些可用执行通道”，规划器决定每个 TODO 实际进入哪个通道。

## 三、任务规划器的画布接口

任务规划器不应只有一个普通输入和一个普通输出。

建议设计为：

输入端口：

```text
总目标
执行反馈
重新规划请求
```

输出端口：

```text
执行当前 TODO
全部完成
无法规划
```

整体运行图：

```text
                       ┌───────────────────────┐
                       │                       │
开始 → 任务规划器 ─todo→ 智能体团队 → 质量门控器
          │            │                       │
          │            └──── revise ───────────┘
          │
          ├─ done → 结果汇聚器 → 结束
          │
          └─ failed → 人工处理
```

质量门控通过后，结果返回任务规划器：

```text
质量门控器.pass
    ↓
任务规划器.feedback
    ↓
将当前 TODO 标记 completed
    ↓
取下一个 TODO
```

如果失败：

```text
质量门控器.revise
    ↓
修正当前 TODO 的反馈
    ↓
重新选择原 Agent 或备用 Agent
```

如果发现计划本身有问题：

```text
质量门控器.replan
    ↓
任务规划器.replan
    ↓
保留已完成 TODO
    ↓
只修改未完成 TODO
```

这就是完整的“规划—执行—验证—重规划”闭环。

## 四、目标检查器和恢复边界建议合并

建议删除当前两个节点：

```text
目标检查器
恢复边界
```

改成一个：

```text
质量门控器
```

或者更完整地叫：

```text
验证与恢复门
```

但在界面中“质量门控器”更容易理解。

### 为什么可以合并

用户真正关心的不是：

```text
这是目标检查，还是故障恢复？
```

而是：

```text
刚刚执行的这一段结果可靠吗？
不可靠时下一步怎么办？
```

因此节点同时负责：

- 目标完成检查；
- 输出质量检查；
- 证据检查；
- 失败后的返工路由；
- 必要时触发重新规划。

LangGraph 官方的 Evaluator-Optimizer 模式就是生成器产生结果、评估器检查结果、不满足时携带反馈重新生成，直到达到标准。[LangGraph Evaluator-Optimizer](https://docs.langchain.com/oss/python/langgraph/workflows-agents)

AutoGen 也提供“主 Agent + Critic Agent”的反思模式，并在每次 Agent 回复后执行终止条件检查。[AutoGen Teams](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/teams.html)、[AutoGen Termination](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/termination.html)

## 五、质量门控器检查什么

质量门控不能只让模型回答“好/不好”，应采用“确定性检查 + 模型评审 + 证据核验”。

### 1. 完成度检查

检查：

```text
当前 TODO 的 objective 是否完成
expected_output 是否生成
acceptance_criteria 是否逐项满足
是否仍存在未回答问题
```

### 2. 格式与结构检查

确定性验证：

```text
JSON 是否符合 Schema
必要字段是否存在
数组数量是否满足
代码是否可解析
文档是否包含规定章节
```

这部分不需要模型。

### 3. 内容合理性检查

由评审模型判断：

```text
结论是否与问题相关
推理是否自洽
是否存在明显矛盾
方案是否具有可执行性
是否遗漏关键限制
```

### 4. 真实来源检查

这部分不能只相信模型声称“有来源”。

应检查：

```text
citation_id 是否真实存在
引用是否来自本次知识库检索或工具调用
URL 是否可访问
知识库 chunk 是否真实存在
引用片段是否支持对应结论
来源时间是否满足新鲜度要求
是否达到最少独立来源数量
```

建议把输出拆成“主张—证据”：

```json
{
  "claim": "SelectorGroupChat 使用模型动态选择下一位 Agent",
  "evidence_refs": ["web-result-12"],
  "entailment_score": 0.91,
  "source_status": "verified"
}
```

### 5. 执行轨迹检查

检查：

```text
要求使用的工具是否真的调用
工具是否成功
要求查询知识库时是否真正命中
是否使用了被禁止的资源
是否超时
是否超出成本预算
```

### 6. 风险与安全检查

根据任务类型可选：

```text
敏感信息
越权工具调用
提示词注入
不安全代码
政策违规
高风险外部操作
```

## 六、质量门控器的输出

不建议只有：

```text
complete
continue
```

应改成四个出口：

```text
pass       检查通过，当前 TODO 完成
revise     当前执行结果有问题，带反馈返工
replan     计划本身错误，返回任务规划器重新规划
escalate   无法自动修复，进入人工处理
```

结构化检查结果：

```json
{
  "decision": "revise",
  "overall_score": 0.68,
  "checks": {
    "task_completion": 0.9,
    "reasoning_quality": 0.8,
    "evidence_grounding": 0.35,
    "source_validity": 0.4,
    "schema_validity": 1.0
  },
  "issues": [
    {
      "type": "missing_evidence",
      "message": "动态路由结论没有对应论文或官方文档证据"
    }
  ],
  "revision_instruction": "补充至少两个真实来源，并建立主张与来源的对应关系",
  "retry_target": "资料检索团队"
}
```

## 七、技术故障恢复不要完全交给这个节点

虽然前端只保留一个质量门控节点，但后端仍应始终提供基础恢复：

```text
模型调用超时 → 自动重试
工具暂时失败 → 指数退避
Agent 失败 → 备用 Agent
节点进程崩溃 → 从检查点恢复
连续失败 → 熔断
超过预算 → 停止并请求人工处理
```

这些是运行时基础能力，不需要用户拖“恢复节点”。

质量门控器处理的是：

```text
技术调用虽然成功，但生成结果不正确、不完整或没有证据
```

两者应该分层：

```text
底层运行时恢复：自动、不可见
业务质量恢复：用户可放置质量门控器
```

## 八、质量门控器放在哪里

用户可以把它放在关键区域之后。

### 检查单个 TODO

```text
任务规划器 → 智能体团队 → 质量门控器 → 返回任务规划器
```

### 检查一次资料检索

```text
资料检索团队 → 质量门控器 → 方案设计团队
```

### 检查代码实现

```text
编码 Agent → 测试工具 → 质量门控器 → 发布
```

### 检查最终答案

```text
结果汇聚器 → 质量门控器 → 结束
```

质量门控器默认检查“上一个检查点到当前节点之间”的运行区域，而不是要求用户填写晦涩的输入字段名。

## 九、质量门控器的配置界面

简洁配置：

```text
节点名称
检查目标描述
评审模型
检查模板
通过阈值
失败后的处理方式
```

检查模板：

```text
通用质量
事实与来源
代码与测试
报告完整性
安全合规
自定义
```

可勾选检查项：

```text
目标完成度
内容合理性
来源真实性
引用支持度
来源时效性
格式 Schema
工具调用成功
知识库检索成功
内容冲突
安全风险
```

高级设置：

```text
最大返工次数
最大重新规划次数
最低来源数量
允许的来源域名
来源新鲜度
模型评审权重
确定性规则权重
证据支持度阈值
失败时是否更换 Agent
```

## 十、结果汇聚器的使用场景

你想到的“多个 Agent 讨论或辩论后选出最佳结果”是最重要的场景之一，但不是唯一场景。

### 1. 综合生成

适用于多个 Agent 分别负责不同部分：

```text
论文检索 Agent ─┐
代码调研 Agent ─┼→ 结果汇聚器 → 完整方案
架构设计 Agent ─┘
```

不是选一个，而是把互补内容合成一个结果。

### 2. Best-of-N 择优

多个 Agent 都解决同一个问题：

```text
方案 Agent A ─┐
方案 Agent B ─┼→ 结果汇聚器 → 选择最优方案
方案 Agent C ─┘
```

评审依据：

```text
正确性
证据质量
创新性
实现成本
风险
任务匹配度
```

### 3. 辩论裁决

```text
支持方 Agent
反对方 Agent
风险评审 Agent
        ↓
结果汇聚器
        ↓
裁决结论
```

汇聚器不仅总结，还需要：

```text
列出共识
列出冲突
判断哪一方证据更强
输出最终选择和理由
```

### 4. 冲突消解

当多个 Agent 给出相互矛盾的事实时：

```text
识别冲突主张
比较引用来源
检查来源时间
判断可信度
保留无法消解的不确定性
```

### 5. 结构化字段合并

例如：

```text
研究 Agent 输出 evidence
架构 Agent 输出 architecture
测试 Agent 输出 test_plan
```

汇聚为：

```json
{
  "evidence": {},
  "architecture": {},
  "test_plan": {}
}
```

### 6. 顺序输出

你提到的顺序输出其实很有价值，而且通常不需要模型。

适用场景包括：

- 长任务审计报告；
- 研究过程记录；
- 分阶段项目交付；
- 证据链归档；
- 批量任务结果；
- 教学过程；
- 客服工单处理轨迹。

例如：

```text
阶段 1：需求分析结果
阶段 2：论文检索结果
阶段 3：架构设计结果
阶段 4：实现结果
阶段 5：测试结果
```

这种模式不做裁决，只按：

```text
TODO 顺序
执行时间
自定义优先级
```

输出所有结果，方便审计和追溯。

## 十一、结果汇聚器建议提供的模式

| 模式 | 用途 | 是否需要模型 |
|---|---|---:|
| 综合生成 | 合并互补结果 | 是 |
| 评审择优 | Best-of-N | 是 |
| 辩论裁决 | 多方观点与最终裁决 | 是 |
| 冲突消解 | 比较矛盾事实和来源 | 是 |
| 结构化合并 | 按字段合并 | 可选 |
| 顺序输出 | 保留阶段性结果 | 否 |
| 投票共识 | 达到多数或阈值 | 可选 |

所有输入都应先统一成：

```json
{
  "source_node": "资料检索 Agent",
  "todo_id": "todo-2",
  "status": "succeeded",
  "output": "...",
  "evidence_refs": [],
  "quality_score": 0.87,
  "cost": 0.02,
  "latency_ms": 4300,
  "created_at": "..."
}
```

而不是直接把几个字符串拼起来。

## 十二、推荐的最终完整架构

```text
开始
  ↓
任务规划器
  ├─ 生成顺序 TODO
  ├─ 选择 current_todo
  └─ 保存 PlanLedger
  ↓ execute_current_todo
执行池
  ├─ 普通 Agent
  ├─ 智能体团队
  └─ 专业子团队
  ↓
[可选] 结果汇聚器
  ├─ 多 Agent 讨论
  ├─ 多方案择优
  └─ 阶段结果合并
  ↓
质量门控器
  ├─ pass → 返回任务规划器，执行下一个 TODO
  ├─ revise → 返工或更换 Agent
  ├─ replan → 任务规划器修改剩余 TODO
  └─ escalate → 人工处理
  ↓
任务规划器 done
  ↓
[可选] 全局结果汇聚器
  ↓
[可选] 最终质量门控器
  ↓
结束
```

最终左侧动态控制节点建议只保留：

```text
任务规划器
结果汇聚器
质量门控器
```

智能体团队仍属于“智能体”类别，不属于逻辑节点。

这套设计解决了你提出的核心问题：TODO 虽然按顺序执行，但每个 TODO 不必进入相同 Agent；任务规划器控制当前 TODO，执行池动态选路，质量门控器形成反馈闭环，结果汇聚器只在确实存在多结果时使用。




- 核心代码实现：  
任务规划器真正生成并维护顺序 TODO，一次只派发一步。  
TODO 包含能力、工具、Skill、知识库、交付物、验收条件、证据要求和最大尝试次数。  
智能体团队会按照当前 TODO 的能力和资源要求动态选人，缺少必需资源的成员会被硬过滤。
