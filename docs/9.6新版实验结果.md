### 预算结果分析

真实历史的 token 范围为 11,718 至 24,053，平均为 20,115；有效输入预算为 14,336。Full Context 中有 95/100 条实际可见上下文超过预算，另外 5 条未超过，因此 `Budget Violation=0.95`。这与旧实验“只要没有 BudgetController 就固定记为违规”的逻辑不同，新结果确实由每条任务的实际上下文长度决定。

Plain 和 Memory Only 的可见上下文没有超过预算，因此它们的 `Budget Violation=0`。该结果是正常的，说明新版指标不再人为要求所有无预算控制的方法失败。Ours Full 将平均可见/注入上下文控制在 245.95 tokens，并在构造的压力检查中正确暂停，因此 `Pause Correctness=1`、`Budget Violation=0`。

### 记忆结果分析

Memory Only 与 Ours Full 使用相同的完整历史写入和检索流程，因此两者的 `Memory Use Accuracy` 都为 0.15；Ours 的 Ledger、Drift、Budget 和 Checkpoint 组件没有改变当前记忆召回结果。Ours Full 的其他五项合取条件全部通过，所以其 15 条综合成功恰好对应 15 条记忆匹配成功；其余 85 条均受记忆匹配失败限制。

当前 Ours/Memory Only 使用项目记忆库的默认 `HashingEmbeddingModel`，在每题 390 至 722 个历史片段中只检索少量结果。15% 的匹配率表明，完整历史引入后，默认检索方案对 LoCoMo 问题的召回明显不足。下一步应优先检查 BGE-M3、公平的 embedding 对照、候选数量和片段索引方式，而不应将失败归因于 ContextLedger 或 Checkpoint。

Full Context 暴露全部历史，但 `Memory Use Accuracy` 只有 0.52。这不等于完整历史丢失了 48% 的答案。当前指标仍使用规范化 token 序列包含规则，LongMemEval/LoCoMo 的参考答案可能是计算结果、摘要、释义或多会话综合答案，不一定以连续文本形式原样出现在历史中。因此 Full Context 的 0.52 暴露出该指标作为“记忆使用准确率”的局限：它更接近答案文本可见性代理，不能单独视为真实检索或 QA 正确率。

### 当前可以支持的结论

1. 新版实验成功使用真实完整历史和 16k 上下文设置，不再通过重复单条事实制造超限。
2. 预算违规已由实际 token 决定；Full Context 的 95% 违规来自真实历史超过 14,336 token，而不是方法名称预设。
3. Ours Full 的目标保留、约束注入、漂移检测、预算暂停和检查点恢复机制均按确定性场景正常工作。
4. 当前主要瓶颈是长期记忆检索/评测：Ours 的 Memory Use Accuracy 为 15%，Full Context 的文本包含代理也只有 52%。
5. Ours Full 平均可见上下文远低于 Full Context，但当前实验没有真实 QA solver，不能据此宣称它在真实任务上以 245.95 tokens 达到 15% QA 准确率。

### 不能支持的结论

- 不能表述为“真实长任务成功率为 15%”。
- 不能表述为“Ours 记忆准确率严格为 15%”。
- 不能用 Full Context 的 52% 证明完整历史缺失答案。
- 不能把 Ours Full 的失败归因于治理模块；当前综合失败全部由记忆匹配代理限制。
- 不能与旧 v3 的 100% 直接比较为系统性能下降。旧 v3 每题只写入预选答案事实，新 v4 写入数百条完整历史，任务难度和数据路径已经改变。

### 后续完善方向

1. 为 Memory Only/Ours 增加明确的 BGE-M3 embedding 配置，并保留 Hashing 对照。
2. 增加 candidate-k、重排和片段级索引，定位 85 条未匹配样本是候选召回失败还是答案并非原文包含。
3. 将 `Memory Use Accuracy` 拆成 gold evidence session recall 与答案文本可见性，避免一个文本包含代理承担两种含义。
4. 在同一数据上接统一 QA solver 和语义 Judge，另报真实最终答案正确率。
5. 按实际历史是否超过预算分组报告结果，避免 5 条未形成预算压力的样本与 95 条超预算样本混合解释。

### 结果分析

新版协议已经修复旧版“每个测试样本先用自己的成功轨迹创建技能，再检索自己”的自检索泄漏。Ours 只读取每类 3 条训练轨迹，每类形成一份技能，再在 7 条未见测试任务上复用；因此当前结果能够支持“自动生成的技能可以被同类型 held-out 任务检索，并保留训练轨迹中的步骤”。

Manual 与 Ours 的代理 Task Success 仍然都是 1.0，因为当前成功判定只要求检索命中且普通步骤覆盖率至少达到 0.5；Manual 的 0.75 已超过该阈值。因此 Task Success 本身仍不能区分两者。新版的主要区分证据来自：Ours 的普通步骤覆盖从 0.75 提升到 1.0，关键步骤覆盖从 0 提升到 1.0，而平均技能上下文只从 29.67 增加到 31.67 tokens。

Ours 的三类自动技能分别保留了训练轨迹中的环境特定关键步骤，例如发送权限、时区或预算核验；固定 Manual 基础技能没有包含这些步骤。该结果说明自动轨迹归纳链路在当前可控数据上保留了额外过程信息，但不能证明这些步骤在真实工具执行中一定提高成功率。

No Skill 的 0% 是当前评测定义的必然结果：没有技能就没有检索文本和步骤覆盖。该组没有让无技能 LLM Agent 实际尝试任务，因此不能解释为普通 Agent 在 21 条真实任务上全部失败。

### 当前可以支持的结论

1. 技能训练与测试已经隔离，21 条测试任务没有使用自身轨迹生成技能。
2. Ours Skill Loop 完成了训练轨迹归纳、候选验证、发布和测试检索的完整链路。
3. 在当前三类可控 held-out 任务上，Ours 的普通步骤与关键步骤覆盖均高于固定 Manual Skill。
4. Ours 相比 Manual 只增加约 2 个平均上下文 token，当前文本注入成本差异很小。
5. 三种任务类型结果一致，没有观察到某一类任务单独失效。

### 不能支持的结论

- 不能称为真实 Agent 任务成功率 100%。
- 不能用 No Skill 的 0% 声称无技能 Agent 无法完成任务。
- 不能声称 Ours 在最终 Task Success 上优于 Manual；两者当前均为 1.0。
- 不能证明关键步骤覆盖必然转化为邮件发送、日历创建或旅行规划的真实执行收益。
- 不能证明跨任务类型或分布外泛化；训练和测试仍来自相同的三类模板数据。

### 后续完善方向

1. 接入统一 LLM solver 或可执行模拟工具，测量真正的任务完成率。
2. 将 Task Success 改为业务结果验证，或提高判定要求，避免 0.75 与 1.0 都被压成相同成功值。
3. 增加与训练模板表达差异更大的测试任务，以及未见任务类型。
4. 加入错误、缺步骤和过期技能，评估验证器的拒绝能力。
5. 报告工具调用次数、总 token、耗时、错误复发率和技能库重复率。

## 实验四评测器修正记录：共享基础计划与完整任务就绪（2026-09-06）

### 修正原因

`skills_split_v2` 虽然解决了训练/测试泄漏，但 No Skill 的执行计划被直接设置为空文本，且旧 `Task Success` 同时要求 `retrieval_hit=true`。因此 No Skill 在定义上不可能产生任何步骤覆盖或成功结果，所有指标均为 0。这并不能代表没有技能的 Agent 对邮件、日历或旅行任务毫无基础能力，只能说明旧评测器将“技能检索结果”错误地当成了“全部执行计划”。

旧成功条件为：

```python
task_success = coverage >= 0.5 and retrieval_hit
```

该条件还把技能检索能力与任务执行代理绑定在一起，不适合评估 No Skill 基线。

### 第一项修正：共享任务原生基础计划

三种方法现在都先获得同一份由任务类型决定的基础计划：

| 类型 | 无技能基础步骤 |
|---|---|
| email | 读取邮件；生成并核对回复 |
| calendar | 读取参与人日历；创建提醒 |
| travel_report | 确认行程约束；生成最终报告 |

Manual/Ours 检索到的技能只作为可选增量追加到该基础计划。评测分别记录：

- `base_plan_coverage`：无技能基础计划覆盖率；
- `skill_only_coverage`：技能文本自身覆盖率；
- `step_coverage`：基础计划与技能合并后的最终覆盖率；
- `skill_coverage_gain`：技能相对共同基础计划增加的覆盖率；
- `retrieval_hit`：技能是否命中，继续独立报告，不再决定 No Skill 是否拥有执行计划；
- `plan_policy=shared_task_native_base_plus_optional_skill`：记录三组采用相同基础计划策略。

第一次诊断重跑保存在 `runs/experiments/skills_split_v3_shared_base/`。结果显示 No Skill 的基础与最终覆盖率均为 0.5，不再所有指标为 0；Manual 为 0.75，Ours 为 1.0。但旧 `coverage>=0.5` 成功阈值使三组 `Task Success` 又全部变成 1.0，说明该阈值不足以表示完整任务成功。该轮作为评测器诊断记录保留，不作为最终主表。

### 第二项修正：拆分基础可执行性与完整任务就绪

为了避免用一个宽松阈值掩盖差异，最终评测拆为：

```python
basic_task_readiness = coverage >= 0.5
task_success = coverage >= 1.0 and critical_coverage >= 1.0
```

- `Basic Task Readiness` 表示至少覆盖一半基本流程，承认无技能方法具有任务常识；
- `Task Success` 表示确定性过程计划完整覆盖全部必需步骤和关键安全步骤；
- 两者都仍是 procedural-plan proxy，不是 LLM 或真实工具执行成功率。

新增单元测试专门验证 No Skill：必须有 0.5 基础覆盖、`Basic Task Readiness=1`、`Retrieval Hit=0`、`Skill Coverage Gain=0`，并且不能伪造技能检索。最终离线验收结果为：

```text
23 passed in 0.67s
```

测试过程中曾出现一次新增测试漏导入 `build_skill_reuse_dataset` 的失败，结果为 `22 passed, 1 failed`；补齐测试导入后通过全部 23 条。该问题只在测试代码导入层，不影响业务实现和正式结果。

## 实验三评测器修正记录：统一扰动与分层任务就绪（2026-09-06）

### 为什么继续修正

检查 history v4 后发现，虽然预算违规已经按实际 token 计算，但方法间仍有结构性不公平：只有 Ours Full 真正执行了三次重复步骤、预算控制器判断和检查点中断恢复；非 Ledger 方法则直接用干扰文本替换当前提示，导致 Plain 与 Memory Only 的 `Goal Retention`、`Constraint Compliance` 必然为 0。这些 0 部分反映的是 runner 的分支写法，而不是方法在相同输入下的实际表现。

此外，旧版 `Final Task Success` 把记忆命中、漂移检测、预算暂停和检查点恢复六项直接合取。该严格指标可以保留为治理机制联合代理，但不能单独承担基础任务能力解释，否则基线会因为没有某个专用治理组件而整体显示为 0。

### 修正内容

1. 四种方法现在接收相同的当前任务提示，包括原目标、原约束、中途新增约束、当前计划和干扰内容。非 Ledger 方法不再被 runner 人为抹掉目标与约束。
2. 四种方法都处于同一组实验扰动定义下：三次重复步骤、实际 token 预算压力和一次中断场景。专用组件是否能够检测、暂停或恢复仍按方法真实配置记录。
3. 无预算控制器的方法默认继续执行：输入未超限时 `Pause Correctness=1`；输入超限时才记为预算违规并令暂停正确性为 0。因此 Plain/Memory Only 不会因“没有控制器”自动失败预算项。
4. 新增 `Basic Task Readiness`：目标仍可见、约束仍可见、期望记忆在可见内容中命中且未发生预算违规。它表示基础输入是否足以继续任务，不要求方法必须安装所有治理组件。
5. 新增 `Disturbance Handling Score`：漂移得到阻断、预算行为正确、中断得到恢复三项结果的平均。该名称刻意不写成“组件覆盖率”；例如 Plain 在没有预算压力时自然继续是正确结果，但不能据此声称它具备预算控制器。
6. 保留 `Final Task Success` 作为严格六项合取代理，并在 row metadata 中写入 `final_success_scope`，明确它不是 LLM 端到端任务成功率。
7. 每行加入统一策略标记：`shared_prompt_shared_disturbances_layered_readiness_v5`。

- 输出使用独立目录 `runs/experiments/long_task_history_v5_layered/`，未覆盖 history v4 或更早结果。

### 结果解释

新版结果说明，v4 中 Plain/Memory Only 的目标和约束全为 0 确实不合理。统一当前提示后，四种方法的目标保留与约束可见性均为 100%。这不是给基线“加分”，而是移除了非 Ledger 分支中人为替换提示造成的失败。

Plain 没有历史记忆，因此 `Memory Use Accuracy=0`，基础任务就绪仍为 0；但其 33 tokens 的当前提示在预算内，所以预算行为结果正确。Memory Only 与 Ours 使用相同检索路径，记忆文本命中均为 15%，且输入均在预算内，所以两者 `Basic Task Readiness=15%`。这清楚地把“基础输入够不够”与“有没有治理闭环”分开了。

### 修正后的结论边界

当前可以表述：在相同当前任务提示和相同扰动定义下，四种方法都保留了目标与约束；Full Context 主要受到真实上下文预算限制，Memory Only/Ours 主要受到当前检索召回限制；Ours 的上下文治理组件完整处理了本实验构造的漂移、预算和恢复场景。

仍不能表述：Ours 的真实长任务成功率是 15%，Full Context 的真实 QA 准确率是 2% 或 52%，或者 Plain/Memory Only 的真实任务成功率为 0。当前仍是确定性后端机制实验，`Memory Use Accuracy` 仍是答案文本连续出现代理，尚未接统一 LLM solver、语义 judge 和 gold-evidence session recall。

### 后续仍需完善

1. 数据构建时保存 gold evidence session ID，在实验三中单独报告 Evidence Recall/MRR，而不是继续让答案文本包含规则代替检索评测。

4. 增加“确实形成预算压力”和“未形成预算压力”的分组统计，进一步解释 Full Context 的 95 条超限与 5 条未超限样本。

## 实验三、实验四复杂任务升级记录（2026-09-07）

### 调整原因与原则

此前实验三的任务计划只有 4 步，实际漂移场景主要由 3 次同质重复事件构成；实验四每类任务也只有 4 个期望步骤。它们足以验证模块是否接通，但不足以代表具有多阶段依赖、交叉核验和关键安全检查的复杂任务。
