先澄清一个关键点：

> 当前仓库只有后端编排接口，没有实际的前端页面代码。因此现在并不存在可以直接点击的“创建 Agent”“生成技能”“批准技能”按钮。

这些按钮是未来前端可以基于现有 REST API 做出来的交互形式。目前创建 Agent 可以通过调用 API 或写 Python 代码完成；技能生成、验证和发布目前只能通过 Python 调用完成，还没有 REST 接口和前端页面。

# 一、“前端创建 AgentSpec”具体是什么意思

`AgentSpec` 可以理解成一张“Agent 员工档案”。

它包含：

```text
Agent 名称
身份提示词 sys_prompt
使用的模型 model
职责描述 description
其他配置 config
子 Agent 列表 children
```

例如，未来前端可以有一个“创建 Agent”表单：

```text
Agent 名称：travel_planner

身份提示词：
你是一名旅行规划主管，负责理解用户需求并组织旅行计划。

模型：
deepseek-v4-flash

职责描述：
负责拆分旅行需求、汇总交通住宿信息并输出最终方案。

其他配置：
任务类型 travel
需要输出字段 plan、budget
```

点击“创建”以后，前端调用：

```http
POST /api/agents
```

请求：

```json
{
  "name": "travel_planner",
  "sys_prompt": "你是一名旅行规划主管……",
  "model": "deepseek-v4-flash",
  "description": "负责拆分旅行需求并汇总结果",
  "config": {
    "task_type": "travel",
    "required_update_keys": ["plan", "budget"]
  }
}
```

后端的 `Orchestrator.create_agent()` 会把它保存成：

```python
AgentSpec(
    id="agent-abcd1234",
    name="travel_planner",
    sys_prompt="你是一名旅行规划主管……",
    model="deepseek-v4-flash",
    description="负责拆分旅行需求并汇总结果",
    config={...},
)
```

所以你的理解基本正确：

> 未来可以有“创建 Agent”按钮，点击后填写 Agent 的名称、身份、职责、模型和配置。

但当前仓库中还没有这个前端页面，只有支持它的后端 API。

# 二、“为每个 AgentSpec 创建 Node”是什么意思

`AgentSpec` 和 `Node` 是两个不同层次的东西。

## 1. AgentSpec 是档案

它描述这个 Agent 是谁：

```text
名字是什么
使用什么模型
系统提示词是什么
职责是什么
有哪些子 Agent
```

它本身不能被图引擎直接执行。

## 2. Node 是可执行工位

`Node` 除了名字和元数据，还必须包含一个真正可以调用的函数：

```python
async def node_function(state):
    # 做具体工作
    return {"result": "..."}
```

所以 `Orchestrator.build_graph()` 需要把：

```text
AgentSpec：这个 Agent 是谁
```

转换成：

```text
Node：这个 Agent 在图中如何被调用
```

可以类比为：

```text
AgentSpec = 员工档案
Node = 员工在流水线上的工作岗位
```

员工档案不能直接生产产品。必须先给员工分配一个工位，并规定这个工位如何接收材料、如何工作、如何输出结果。

转换过程大致是：

```text
AgentSpec
├── name
├── sys_prompt
├── model
└── config
        │
        ▼
Node
├── name
├── node_type = AGENT
├── metadata
└── func(state) → update
```

## 3. 当前这里还有一个重要限制

`Orchestrator` 默认使用 `echo_node_factory()`。

默认 Node 只会回显：

```text
[travel_planner] 收到：用户输入
```

不会真正调用大模型。

要让它变成真实 Agent，必须提供真实的 `node_factory`，或者通过 `adapters.py` 的 `agent_node()` 包装 AgentScope Agent。

因此未来完整流程不能只是“填写 AgentSpec”，还必须解决：

```text
AgentSpec
    ↓
根据 model、sys_prompt 创建真实 AgentScope Agent
    ↓
通过 adapters.py 包装为 Node
```

当前 REST `/api/run` 默认没有完成这一步。这是后续需要重点补齐的缺口。

# 三、“手动/显式调用技能演化”究竟是什么意思

这里的“手动”目前不是指点击前端按钮，而是指开发人员需要主动写代码调用。

例如：

```python
candidate = evolution.create_candidate_from_runs(
    skill_id="travel-planning",
    name="旅行规划技能",
    run_ids=["run-001", "run-002"],
    version="1.0.0",
)
```

然后再调用验证：

```python
report = evolution.validate_candidate(
    "travel-planning",
    "1.0.0",
    evaluator,
)
```

验证通过后再调用发布：

```python
evolution.publish(
    "travel-planning",
    "1.0.0",
    approved_by="zhangsan",
)
```

现在没有自动定时任务，也没有这些 REST API：

```text
POST /api/skills/candidates
POST /api/skills/{id}/{version}/validate
POST /api/skills/{id}/{version}/approve
POST /api/skills/{id}/{version}/publish
```

所以前端也暂时无法提供对应按钮。

# 四、什么叫“在线流程”和“离线流程”

这里的“在线”和“离线”不是指有没有互联网。

它们指的是：这段工作是否位于用户等待结果的主请求中。

## 1. 在线流程

在线流程就是：

> 用户正在等待结果的任务执行流程。

例如用户提交：

```text
帮我制定杭州三日旅行计划，三个人，预算 6000 元。
```

从用户点击提交，到页面显示最终答案，这段流程都是在线流程。

```text
用户提交任务
    ↓
系统检索已有技能
    ↓
执行 Agent 图
    ↓
调用工具和模型
    ↓
进行结果质检
    ↓
返回最终答案
```

在线流程的要求是：

- 速度要快。
- 不能长时间阻塞。
- 不能因为技能演化失败而影响用户任务。
- 不能为了学习额外调用十几次模型。
- 只能读取已经验证和发布的技能。
- 出错时要能降级到无技能模式。

## 2. 离线流程

离线流程就是：

> 用户任务已经完成，不需要让用户等待的后台复盘工作。

例如晚上系统扫描白天完成的 100 个任务：

```text
哪些任务失败了？
哪些任务重复重试？
哪些成功任务使用了更短步骤？
有没有值得总结的新经验？
旧技能是否已经过时？
```

然后生成候选技能并执行回放验证。

用户不需要停留在任务页面等待这个过程。

离线流程可以：

- 花几分钟甚至几小时。
- 批量处理多条轨迹。
- 调用更强、更贵的模型。
- 重复运行候选评测。
- 生成人工审核报告。
- 被暂停或重试，而不影响在线任务。

## 3. 两者的关系

```text
在线流程负责“把当前任务做好”
                ↓
            产生轨迹
                ↓
离线流程负责“从过去任务中学习”
                ↓
        生成并发布新技能
                ↓
下一个在线任务读取新技能
```

通俗地说：

```text
在线 = 白天接订单、干活
离线 = 晚上复盘、编写操作手册
```

# 六、后续完整落地计划

## 第一阶段：补齐“真实 Agent 执行链路”

这是最高优先级。否则前端虽然能创建 AgentSpec，默认节点仍然只会回显。

### 需要实现

1. 新增统一的 `AgentFactory`。

输入：

```text
AgentSpec
模型配置
工具配置
执行资源
```

输出：

```text
真实 AgentScope Agent 或可执行 Node
```

2. `Orchestrator.build_graph()` 默认根据 AgentSpec 创建真实 Agent Node。

3. 从 `sys_prompt`、`model` 和 `config` 创建 Agent。

4. 将技能、记忆、上下文注入真实模型输入。

5. 支持工具白名单。

6. 支持模型不可用时的明确错误或降级。

7. REST `/api/run` 不再默认使用 Echo Node。

### 验收标准

- 前端创建一个 Agent 后，提交任务能获得真实模型回答。
- `sys_prompt` 确实影响回答。
- `model` 字段确实决定模型。
- 技能和 Context Ledger 确实进入模型输入。
- Echo Node 只保留为测试模式。

---

## 第二阶段：完善 Agent 编排管理

### 需要实现

1. 编排版本：

```text
draft
published
archived
```

2. 图结构持久化，而不是只保存在进程内存。

3. 编排校验：

- 无入口
- 不可达节点
- 无终止循环
- 重名 Agent
- 条件边目标不存在
- 子 Agent循环依赖
- 工具不存在
- 模型配置不存在

4. 区分两种关系：

```text
执行边：A 执行完成后到 B
管理关系：A 是 B 的父 Agent
```

当前 `add_sub_agent(auto_connect=True)` 默认把两者混合，未来前端应明确展示。

5. 保存节点坐标，支持前端流程图恢复。

### 验收标准

- 重启服务后编排仍然存在。
- 草稿修改不影响已发布版本。
- 每个 run 固定使用一个编排版本。
- 管理关系与执行关系可以分别配置。

## 第六阶段：实现自动离线演化任务

### 需要实现

1. 后台调度器定期扫描已完成轨迹。

2. 轨迹筛选：

- 排除用户取消任务。
- 排除环境故障。
- 排除漂移严重任务。
- 排除敏感任务。
- 排除证据不足任务。

3. 按任务类型、工具链和失败模式聚类。

5. 输出结构化编辑：

### 调度方式

```text
在线 API 服务
    ↓

    ↓
```

### 验收标准

- 新轨迹达到阈值后自动生成候选。
- 单次偶发失败不会生成技能。
- 自动生成失败不影响在线服务。
- 候选规则都能追溯到来源轨迹。

## 第九阶段：灰度、监控和自动回滚

### 需要实现

1. 技能发布先进入 canary。

2. 部分新任务使用候选技能，其余继续使用旧版本。

3. 对比：

```text
新技能组
旧技能组
无技能对照组
```

4. 设置熔断条件：

- 关键断言失败
- 安全事件
- 成功率持续低于基线
- Token 超预算
- P95 延迟超限
- 技能解析失败

5. 自动把 `index.json` 切回旧版本。

### 验收标准

- 一个错误技能不会影响全部任务。
- 回滚不需要修改 Markdown。
- 运行中的任务继续使用启动时固定的技能版本。
- 新任务立即使用回滚后的版本。

## 第十阶段：再考虑动态创建 Agent

你最开始描述的“父 Agent根据 Prompt 创建子 Agent”，应该放在整个系统稳定之后。

合理流程应是：

```text
用户任务
    ↓
Planner Agent 生成结构化任务计划
    ↓
判断现有节点是否足够
    ├── 足够：使用已有工作流
    └── 不足：生成临时子图提案
               ↓
          权限和资源检查
               ↓
          工具白名单检查
               ↓
          图结构校验
               ↓
          在当前 run 的临时沙箱中执行
```

不能让 LLM直接调用无限制的 `create_agent()`。

必须限制：

- 最大动态 Agent 数。
- 最大递归深度。
- 允许的模型。
- 允许的工具。
- Token 和费用预算。
- 禁止修改正式编排。
- 临时 Agent 默认不能发布为永久 Agent。
- 子 Agent输出必须由父级或 Evaluator 验证。
- 同一个 run 中动态图结构必须写入 checkpoint。

建议先实现“动态子图提案”，而不是“任意创建 Agent”。

# 七、推荐实施顺序

最合理的顺序是：

```text
1. 真实 AgentFactory
2. 编排持久化与版本
3. Run 管理与实时事件
4. 完整轨迹
5. 技能管理 API
6. 后台自动生成候选
7. 标准化验证系统
8. 前端技能治理
9. 灰度发布与自动回滚
10. 受控动态创建 Agent
```

不要先做动态创建 Agent。因为如果真实执行、运行记录、验证和回滚还没有完整，动态创建只会扩大不可控范围。

最终完整闭环应当是：

```text
前端设计并发布 Agent 工作流
    ↓
用户选择工作流并输入任务
    ↓
真实 Agent 图在线执行
    ↓
保存上下文、失败、工具和技能轨迹
    ↓
后台离线聚类和生成候选技能
    ↓
自动验证候选
    ↓
人工在前端审核批准
    ↓
灰度发布
    ↓
在线监控
    ├── 表现良好 → 正式发布
    └── 表现退化 → 自动回滚
    ↓
新任务检索并使用新技能
    ↓
继续产生新轨迹，进入下一轮演化
```

这才是完整、合理、可审计、可回滚的 Agent 自我进化闭环。
