# TIDE-Swarm：面向超长程复杂任务的任务状态驱动动态异构群体智能架构与深度协同推理引擎

> **内部论文初稿说明（截至 2026-08-31）**：本文按照题目要求的目标完成版组织架构与方法叙述，并将已经产生的确定性实验结果补入实验章节。当前代码和平台已经提供图执行、上下文治理、四级记忆、MessageCapsule/CommunicationManager、时态证据记忆、PlanIR/符号验证器、技能生命周期、恢复、调度、可视化和 REST 服务等工程底座；运行期真正改变邻接关系的动态拓扑、统一 RuntimeEvent 注入和真实端—边—云大样本评测仍需继续增强。确定性机制结果不能表述为真实 LLM 端到端成功率。

## 摘要

面向软件工程、跨应用办公和终端操控等真实任务，人工智能系统正在从单轮响应转向由多个异构智能体持续协同完成的超长程复杂任务。然而，现有多智能体系统往往将协作关系固化为静态流水线，依赖全量历史或简单摘要维持上下文，并将任务执行、资源选择和故障处理分散在彼此独立的模块中。当任务发生需求变更、证据冲突、工具失败或节点失效时，系统容易出现通信冗余、状态漂移、错误级联和恢复中断等问题。

针对上述问题，本文设计并实现 TIDE-Swarm（Task-state-aware Information-bottleneck Dynamic Heterogeneous Swarm），一种面向超长程复杂任务的动态异构群体智能架构与深度协同推理引擎。系统以可观测的状态图运行时为执行骨架，在每个运行事件上联合维护任务状态、证据记忆、协作拓扑和资源状态。首先，任务状态驱动的拓扑控制器根据子任务依赖、角色能力、证据价值、不确定性、资源约束和历史反馈动态生成稀疏协作子图，并为临时通信边设置生命周期；其次，结构化 MessageCapsule 将主张、证据、约束变化、建议动作、不确定性和预算封装为可验证消息，通过相关性、新颖度和冗余度门控抑制无效传播；再次，时态证据记忆与上下文治理机制结合分层记忆、上下文账本、预算控制、漂移检测、按需唤醒和检查点，保持长程任务中的目标、约束、中间决策和证据链；最后，神经符号验证器、故障轨迹和端—边—云调度器共同构成可解释的计划校验和自治恢复闭环。

系统在 AgentScope 之上扩展类 LangGraph 的 StateGraph/CompiledGraph 执行模型，支持异步超步、并行扇出/扇入、条件路由、循环、流式事件、可插拔 Hook 和 REST/可视化控制台。本文进一步给出动态图路由、低熵通信、记忆唤醒和资源调度的核心算法及复杂度分析，并设计包含编排稳定性、长程记忆、上下文治理、技能闭环、动态通信和故障恢复的分层实验。该架构的目标不是把静态多 Agent 流水线包装成“群体智能”，而是使协作结构、消息内容、记忆范围、执行位置和恢复路径都能随任务状态变化而变化。

**关键词**：超长程任务；动态异构拓扑；低熵通信；时态证据记忆；神经符号推理；端—边—云调度；多智能体运行时

## 1 绪论

### 1.1 研究背景与问题提出

大语言模型通过工具调用、环境感知和多步规划获得了从文本生成走向任务执行的能力。一个 Agent 可以调用浏览器、文件系统、代码解释器、日历或外部服务，并根据环境反馈继续决策。随着任务复杂度增加，系统通常进一步引入具有不同角色和工具权限的多个 Agent，将规划、检索、执行、验证和汇总等职责分配给不同节点，以获得并行处理、专业分工和相互校验能力。

但从实验性多 Agent 到真实世界的自主协作系统，困难并不只在于增加 Agent 数量。对于软件工程交付、跨应用办公和终端协同等任务，系统需要连续经历需求理解、任务分解、资源选择、工具执行、结果验证和异常修复，任务状态可能跨越数百次逻辑流转。系统必须同时回答四个问题：当前真正要完成的目标是什么；哪些历史事实和中间决策仍然有效；当前应该让哪些 Agent 互相通信；下一步应在哪一种资源位置上执行。

现有方案在这四个问题上存在结构性不足。第一，单体 Agent 依赖不断增长的上下文，容易产生注意力稀释和旧状态污染；简单截断会丢失关键决策，简单摘要又可能抹去约束和证据。第二，多 Agent 之间通常采用静态链、星型或全连接通信，任务变化时仍沿用原有连接，导致无效消息和错误传播。第三，路由、记忆、恢复和调度常常是互不感知的独立插件，无法围绕同一份运行时状态形成闭环。第四，许多系统把节点异常视为程序错误，只能终止或依赖人工重启，不能根据失败轨迹自动改变拓扑、重规划和恢复。

荣耀终端股份有限公司发布的 XH-202631 题目进一步提出了明确要求：系统必须具备超长程上下文连续性、动态异构拓扑与低熵通信、端—边—云资源自适应调度，并在无人工干预下完成异常、需求变更和节点失效条件下的长程闭环交付。由此，项目的核心不应只是“能编排 Agent”，而应是“能在任务状态变化时自主重组协作过程”。

### 1.2 国内外研究现状

#### 1.2.1 大语言模型 Agent 与多智能体协作

ReAct、Toolformer 等工作说明了语言模型可以把推理和行动结合起来，通过外部工具扩大单体模型的执行边界。AutoGen、LangGraph、AgentScope、MetaGPT、ChatDev 和相关软件工程 Agent 工作进一步表明，角色划分、任务分解、消息交互和结果汇聚能够提升复杂任务的可组织性。

然而，多数框架首先解决的是应用开发便利性，而非长程运行时治理。它们通常提供节点、消息、工具和编排抽象，却不必然提供跨节点的长期状态账本、动态通信图、消息级信息瓶颈、统一故障事件和资源位置选择。静态图适合表达已知流程，却难以表达由新证据、预算压力、需求变化或节点故障触发的临时协作关系。

#### 1.2.2 长上下文管理与记忆

滑动窗口、固定摘要和全量上下文是最常见的上下文处理方式。滑动窗口成本低但会丢弃早期信息，全量上下文保留信息却带来 Token、时延和注意力竞争，固定摘要在不同查询下难以保持合适粒度。RAG 和向量记忆能扩大可访问历史，但若只对独立片段做相似度检索，便难以恢复跨时段的因果链、约束变更和决策依赖。

Zep 等时间感知知识图谱方法、EverMemOS 等类脑记忆方法以及 A-Mem、HippoRAG 等工作说明，记忆应当具备结构、时间和关系。但在多 Agent 任务中，仅按实体组织记忆不一定能保留消息级依赖；若缺少任务账本、预算和漂移检测，检索到的记忆也可能与当前目标不一致。

#### 1.2.3 动态拓扑、通信降噪与协同推理

一些工作通过一次性 Agent 裁剪、角色评分或演化式编排减少协作规模，但许多方法在任务开始时决定网络，不能针对运行中事件持续改变连接。通信内容也往往是自由文本，接收者难以区分事实、建议、约束、证据和不确定判断。当所有 Agent 都收到完整历史时，系统不仅消耗更多 Token，还会放大局部错误。

因此，动态群体智能需要同时在“连谁”和“传什么”两个层面降噪：拓扑控制器选择必要的协作边，结构化消息协议决定每条边上发送的最小充分信息，并通过约束校验拒绝会造成错误扩散的消息。

#### 1.2.4 神经符号推理与异构资源调度

LLM 擅长从自然语言目标生成计划，但对硬约束、时序、资源冲突和预算可满足性的保证不足。Logic-LM 等工作采用“自然语言—中间表示—求解器—反例修订”的路径，为可验证规划提供了方向。与此同时，端—边—云环境中的任务放置不能只依据模型偏好，还应综合实时性、数据敏感度、网络状态、算力和成本。

现有研究往往分别讨论神经符号规划或边云调度，尚未充分处理它们与动态 Agent 拓扑、消息预算和故障恢复之间的联动。对于一个长程任务，计划是否合法、消息是否可信、哪个节点执行以及失败后如何迁移，本质上是同一运行时决策链上的不同环节。

### 1.3 研究目标

本文目标是构建一个能够承载超长程复杂任务的群体智能自治引擎，使系统从高层自然语言意图出发，经过任务分解、角色选择、动态通信、记忆唤醒、资源调度、工具执行、结果验证和故障恢复，最终生成可交付结果。具体目标如下：

1. 建立具备异步超步、并行扇出/扇入、条件路由、循环、流式事件和检查点的图运行时；
2. 设计任务状态驱动的动态异构拓扑控制器，支持临时边、边生命周期和事件触发重构；
3. 设计可验证低熵 MessageCapsule，降低消息冗余、错误传播和跨节点传输成本；
4. 构建分层、时态、可追溯的证据记忆与上下文治理机制，保持目标、约束和中间决策；
5. 将自然语言规划接入符号验证器，利用约束反例驱动计划修订；
6. 根据任务和资源状态完成端—边—云自适应调度，并在节点故障和需求变化下自主恢复；
7. 通过统一 REST 服务和可视化控制台降低编排门槛，展示任务轨迹、拓扑变化、消息流、资源位置和恢复原因。

### 1.4 主要贡献

本文的主要贡献可以归纳为以下四点。

（1）提出以任务状态为中心的动态协作闭环。系统不把路由、记忆、调度和恢复视为彼此孤立的功能，而是将它们挂接到统一的运行时 Hook 和事件流上，使目标变化、证据冲突、预算压力、资源变化和节点失败都能触发可解释的重规划。

（2）提出拓扑选择与消息选择联合优化的低熵协同机制。拓扑控制器决定哪些 Agent 形成临时协作子图，MessageCapsule 决定每条边上只传递哪些结构化信息，并记录消息价值、冗余、Token 和不确定性。

（3）提出时态证据记忆与上下文治理组合。分层记忆保存不同生命周期的信息，ContextLedger 保存运行期目标和约束，DriftDetector、BudgetController、ContextCompressor 和 CheckpointStore 共同保证上下文不会无界膨胀或无声漂移。

（4）构建可观测、可插拔、可扩展的 Agent 运行时工程底座。项目在 AgentScope 之上提供类 LangGraph StateGraph/CompiledGraph，模块通过 HookManager 注入，前端通过 REST API 管理 Agent、工作流、运行、技能、记忆和模型连接，为算法研究提供可部署、可回放、可评测的载体。

## 2 相关理论与技术

### 2.1 状态图与超步执行

TIDE-Swarm 使用有向状态图表示任务执行过程。图由节点集合 (V)、静态边集合 (E_s)、条件边集合 (E_c) 和运行状态 (S_t) 构成。节点可以是普通同步/异步函数、AgentScope Agent 或子图；状态字段通过 reducer 归并，既支持覆盖式更新，也支持消息、失败轨迹和事件的追加式更新。

执行采用 Pregel 风格超步。第 (t) 个超步中，前沿 (F_t) 的节点读取同一份状态快照并并发执行；所有节点返回的增量按 reducer 合并，再依据静态边、条件边和 Hook 决定下一前沿 (F_{t+1})。该模型天然支持顺序、扇出、扇入、条件分支和循环，并以递归步数上限防止非终止执行。

与一次性调用相比，超步执行的价值在于：每一步都可以插入记忆唤醒、流控、资源申请、计划验证、故障记录、拓扑重构、检查点和 SSE 事件。图不再只是离线流程图，而是可被运行时策略观察和控制的状态机。

### 2.2 长程任务状态

长程任务状态不仅包含模型输出，还包括：

- 全局目标与子目标；
- 硬约束和用户偏好；
- 已完成和待完成的子任务；
- 证据及其来源、时间和可信度；
- 当前拓扑、资源分配和预算；
- 节点输出、失败轨迹和恢复计划；
- 已发布技能及其适用范围。

若这些字段只存在于自然语言历史中，系统便无法稳定判断状态是否发生变化。TIDE-Swarm 将它们作为结构化运行时状态和可追溯事件处理，并通过 `GraphCheckpoint` 保存图状态、前沿、步数和元数据，使长程任务能够暂停、恢复和审计。

### 2.3 信息瓶颈与消息熵

对于发送者 (i) 和接收者 (j)，消息选择的目标不是最大化发送内容，而是在保证任务收益的前提下最小化传输信息。设消息 (m) 对接收者当前子任务的相关性为 (R(m,j))，新颖度为 (N(m,j))，冗余度为 (D(m,j))，消息成本为 (C(m))，不确定性和风险为 (U(m))，则可以定义消息效用：

\[
Q(m,j)=\alpha R(m,j)+\beta N(m,j)-\gamma D(m,j)-\lambda C(m)-\mu U(m).
\]

只有超过门控阈值且通过结构校验的消息才发送。系统进一步记录边密度、发送 Token、有效消息率、重复率、错误传播率和 Token 分布熵。由此，“低熵通信”被转化为可实验验证的工程指标。

### 2.4 时态证据记忆

普通向量记忆通常把文本当作无时间、无来源的独立条目。TIDE-Swarm 将高价值事实表示为：

\[
f=(subject,predicate,object,valid\_time,observed\_time,source,confidence,provenance).
\]

`valid_time` 表示事实在任务世界中的有效时间，`observed_time` 表示系统观察到它的时间，`source` 和 `provenance` 用于回链证据，`confidence` 用于排序和冲突检测。检索阶段先由稠密/稀疏检索召回种子，再按时间、任务关系和证据冲突进行重排和扩展。

### 2.5 神经符号协同推理

语言模型负责把自然语言意图转换为受限 PlanIR，PlanIR 至少包含任务、前置条件、资源、时间和不可违反约束。符号验证器对 PlanIR 执行类型检查、约束满足、时序一致性、资源冲突和预算检查。若验证失败，验证器输出结构化反例，供规划 Agent 修订，而不是让错误计划直接进入执行图。

### 2.6 端—边—云异构计算

终端通常具有低网络时延和较高隐私性，边缘节点提供较好的响应速度和局部算力，云端拥有更强的模型和弹性资源。任务放置可表示为：

\[
P^*=\arg\min_{p\in\{device,edge,cloud\}}
\left(w_l L_p+w_c C_p+w_e E_p+w_r R_p\right),
\]

其中 (L_p) 为时延，(C_p) 为 Token/API 或资源成本，(E_p) 为能耗，(R_p) 为隐私与运行风险。硬约束包括数据敏感等级、可用算力、网络连通性、截止时间和模型能力要求。

## 3 TIDE-Swarm 总体架构

### 3.1 设计原则

系统遵循五项原则：

1. **状态优先**：所有路由、记忆、调度和恢复决策都必须能引用当前任务状态和运行事件。
2. **拓扑可变**：静态图用于表达基础能力关系，运行期协作子图可以按事件建立、删除和过期。
3. **消息最小充分**：默认传输结构化主张、证据、约束和动作，而不是广播完整历史。
4. **验证后执行**：高风险计划、约束变化和跨资源迁移必须经过确定性校验或显式降级。
5. **全程可观测**：中间状态、拓扑理由、消息摘要、资源位置、失败轨迹和恢复动作都可以回放。

### 3.2 分层架构

TIDE-Swarm 由五个层次组成。

**（1）交互与控制台层。** React + TypeScript 的 AgentForge Console 提供 Agent 编排、工作流版本、运行中心、技能治理、工具目录、模型连接和系统管理。用户可以通过画布连接 Agent、查看运行事件、取消或重试任务，并导出图结构和系统快照。

**（2）服务与编排层。** FastAPI REST 服务提供 Agent、工作流、运行、记忆库、技能、工具和模型连接管理接口。Orchestrator 将前端可编辑结构转换为 StateGraph，支持创建 Agent、父子层级、静态连接、条件连接、入口设置、序列化和编译。

**（3）图运行时层。** StateGraph/CompiledGraph 负责节点、边、共享状态、reducer、超步、并发扇出/扇入、条件路由、循环、事件流和递归上限。HookManager 将扩展模块桥接到节点开始、节点结束、节点错误、资源申请、后继解析和检查点等生命周期。

**（4）自治策略层。** 动态拓扑控制器、MessageCapsule、记忆与上下文治理、神经符号验证、流控、恢复和端—边—云调度在该层协同工作。

**（5）执行与持久化层。** AgentScope Agent、工具执行器、MCP 连接、本地/边缘/云端模型、SQLite/JSONL 记忆、运行轨迹、技能仓库和检查点共同构成可执行基础设施。

> 【图片占位：图 3-1 TIDE-Swarm 总体架构图。建议采用五层结构，从上到下画出 AgentForge 控制台、FastAPI/Orchestrator、StateGraph/HookManager、自治策略模块、Agent/工具/记忆/模型资源，并用箭头标出状态、事件和轨迹的回流路径。】

### 3.3 Agent 角色与组织结构

系统将 Agent 描述为带有名称、系统提示词、模型、能力描述、配置和父子关系的 `AgentSpec`。典型任务可以包含：

- Planner：理解目标、拆解子任务并生成 PlanIR；
- Researcher：检索外部信息并返回带来源证据；
- Executor：调用工具或完成具体操作；
- Analyst：进行领域分析和结果比较；
- Verifier：校验事实、约束和产出物；
- Coordinator：汇聚子任务并根据状态推进流程；
- Recovery Agent：分析失败轨迹并提出重试、跳转、降级或中止策略。

这些角色不是固定的全连接群体。任务开始时只激活必要角色；事件发生后，TopologyController 可以引入新的验证者、替换故障节点、临时增加证据检索 Agent 或关闭已经完成的协作边。

### 3.4 运行闭环与数据流

一次任务执行包含以下数据流：

```text
自然语言意图
  ↓
任务状态与 PlanIR
  ↓
符号约束验证 ──失败→ 反例回灌与计划修订
  ↓
TopologyController 选择活跃 Agent 与协作边
  ↓
MessageCapsule 生成、压缩、校验与定向投递
  ↓
端/边/云调度 → Agent/工具执行 → 结果与证据
  ↓
ContextLedger、分层记忆、SkillTrace、FailureTrace、Checkpoint
  ↓
目标/约束/证据/资源状态更新
  └──────────────→ 下一超步的拓扑重构与推理
```

每个超步都会触发上下文预算检查、记忆唤醒、技能注入和漂移检测。节点结束后，执行结果、消息、证据和工具轨迹进入账本；若发现需求变化、证据冲突、预算压力或节点错误，则产生 `RuntimeEvent`，交由拓扑、恢复、调度和验证模块共同处理。

## 4 核心设计与实现

### 4.1 类 LangGraph 的 Agent 图运行时

#### 4.1.1 StateGraph 与 CompiledGraph

`StateGraph` 提供节点和边的构建接口。节点可以通过 `add_node` 注册函数，也可以通过 `add_node_object` 注册带类型和元数据的 Node。`add_edge` 支持静态边，`add_conditional_edges` 支持根据状态返回目标节点或目标列表，`add_loop` 提供布尔条件循环，`START` 和 `END` 作为入口和终止哨兵。

`compile()` 完成入口、节点和条件目标校验并生成 `CompiledGraph`。`ainvoke()` 返回最终状态，`astream()` 逐节点输出 `node_start`、`node_end` 和 `final` 事件。前端运行中心可以据此实时显示当前节点、状态变化和异常，而不是等待任务结束后才看到黑盒结果。

#### 4.1.2 共享状态与归并器

GraphState 为每个字段绑定 reducer。普通字段采用覆盖式归并，消息、失败记录、恢复轨迹、通信统计和技能轨迹采用 append reducer。这样并行节点可以各自返回增量，运行时在超步末统一合并，避免节点之间直接修改共享对象导致竞态。

状态中保留以下运行时键：目标和待办、PlanIR、计划验证结果、已完成子任务、上下文账本、记忆注入、技能注入、通信状态、失败轨迹、恢复轨迹、侧作用日志、资源降级和运行状态。结构化键使不同模块可以通过 Hook 共享上下文，又不会把所有内部实现耦合到节点代码中。

#### 4.1.3 HookManager 扩展机制

`ExecutionHook` 定义 `on_step_start`、`on_node_start`、`acquire_resource`、`on_node_end`、`on_node_error`、`resolve_successors`、`before_node_invoke` 和 `checkpoint_metadata` 等扩展点。未注册模块时使用 NoOp 实现，不改变基础图引擎行为；注册模块后，HookManager 负责把记忆、上下文、通信、验证、恢复、调度、技能和安全控制接入执行生命周期。

这种设计使研究策略可以替换而不必重写图执行器。例如，TopologyController 可以通过 `resolve_successors` 改变下一前沿，ContextLedger 可以在 `on_step_start` 更新目标和预算，Scheduler 可以在 `acquire_resource` 决定执行位置，RecoveryPolicy 可以在 `on_node_error` 返回修复目标。

### 4.2 任务状态驱动的动态拓扑控制

#### 4.2.1 状态与触发事件

TopologyController 维护运行时邻接矩阵 (A_t)、活跃 Agent 集合 (V_t) 和临时边集合 (E_t^{temp})。静态图中的候选边只表示潜在能力关系，实际执行边由控制器在每个重构点确定。重构触发事件包括：

- 新目标或硬约束进入；
- 子任务完成或失败；
- 证据冲突或不确定性升高；
- 上下文预算接近阈值；
- Agent、工具或模型不可用；
- 资源时延、成本或隐私状态突变；
- 新技能命中或当前技能被验证为不适用。

#### 4.2.2 边效用函数

对候选边 (e=(i,j))，控制器计算：

\[
U_t(e)=\alpha G_t(e)+\beta E_t(e)+\gamma H_t(e)-\lambda T_t(e)-\mu L_t(e)-\nu R_t(e),
\]

其中 (G_t) 是任务贡献，(E_t) 是新证据价值，(H_t) 是不确定性降低量，(T_t) 是 Token 成本，(L_t) 是时延，(R_t) 是隐私、权限和错误传播风险。初始版本可使用可解释规则或 LinUCB/Thompson Sampling 学习边效用，特征来自角色能力、子任务依赖、记忆相关度、历史成败、消息新颖度和资源指标。

控制器输出：

```json
{
  "active_agents": ["planner", "researcher", "verifier"],
  "edges": [{"source": "planner", "target": "researcher", "ttl": 3}],
  "aggregator": "verifier",
  "reason": "新证据冲突，需要增加独立校验",
  "expected_gain": 0.38
}
```

输出同时写入运行轨迹，用于事后分析拓扑选择是否真的带来成功率、成本或恢复能力收益。

#### 4.2.3 动态拓扑算法

```text
Algorithm 1 任务状态驱动的拓扑重构
Input: state S_t, candidate edges E_c, edge budget B
Output: active agents V_t, active edges E_t

1: events ← detect_events(S_t)
2: if events is empty and topology_is_valid(S_t) then
3:     return previous_topology(S_t)
4: candidates ← filter_by_capability_dependency(E_c, S_t)
5: for each e in candidates do
6:     feature ← build_feature(e, S_t, events)
7:     score[e] ← utility(feature) - risk_penalty(feature)
8: end for
9: E_t ← top_B_edges(score, constraints=S_t.hard_constraints)
10: V_t ← endpoints(E_t) ∪ mandatory_agents(S_t)
11: E_t ← remove_expired_edges(E_t, current_step=S_t.step)
12: record_topology_decision(V_t, E_t, events, score)
13: return V_t, E_t
```

若候选边数为 (|E_c|)，特征维度为 (d)，逐边打分复杂度为 (O(|E_c|d))；采用大小为 (B) 的堆选择边时为 (O(|E_c|\log B))。若只在受事件影响的局部子图上重构，复杂度可由全图规模降为 (O(|E_{affected}|d))。

### 4.3 可验证低熵 MessageCapsule

#### 4.3.1 消息结构

自由文本消息难以判断哪些内容是事实、建议还是约束。TIDE-Swarm 使用结构化 `MessageCapsule`：

```json
{
  "goal_id": "g-001",
  "subtask_id": "s-07",
  "sender": "researcher",
  "receiver": ["verifier"],
  "claim": "候选方案满足预算约束",
  "evidence_refs": ["fact-128", "tool-run-22"],
  "constraints_delta": {"budget_remaining": 1800},
  "next_action": "verify_budget",
  "uncertainty": 0.22,
  "ttl": 2,
  "token_budget": 160,
  "digest": "sha256:..."
}
```

字段分为主张、证据、约束、动作和控制信息五类。代码、URL、数字、时间和硬约束属于不可丢失字段；长文本只能在保留事实引用的前提下压缩为摘要。

#### 4.3.2 发送前门控

发送者先根据接收者的当前子任务计算相关性、新颖度和冗余度，再执行语义压缩、字段校验、证据引用检查和版本一致性检查。对于低相关或高重复消息，系统只发送引用或直接丢弃；对于证据缺失、约束类型错误或摘要改变事实的消息，系统发送澄清请求或反例，而不把消息交给下游执行。

```text
Algorithm 2 MessageCapsule 门控
Input: raw message m, receiver j, state S_t
Output: capsule c or DROP/CLARIFY

1: c ← extract_structured_fields(m)
2: c ← compress_long_fields(c, preserve=immutable_fields)
3: if not schema_valid(c) then return CLARIFY
4: if not evidence_refs_resolvable(c.evidence_refs, S_t) then return CLARIFY
5: relevance ← estimate_relevance(c, task_of(j, S_t))
6: novelty ← estimate_novelty(c, received_history(j, S_t))
7: redundancy ← estimate_redundancy(c, received_history(j, S_t))
8: utility ← α·relevance + β·novelty - γ·redundancy
9: if utility < threshold(j, S_t) then return DROP
10: if violates_hard_constraints(c, S_t) then return CLARIFY
11: c.digest ← hash(canonical_json(c))
12: record_message_metrics(c, utility, token_count(c))
13: return c
```

若消息字段数为 (k)，证据引用数为 (r)，接收历史中用于去重的摘要数为 (h)，单条消息门控复杂度为 (O(k+r+h))。通过只保留接收者相关历史摘要，避免随全局消息总量线性增长。

#### 4.3.3 通信指标

系统在每个运行中记录：平均发送 Token、消息总数、有效消息率、重复消息率、边密度、消息到达率、错误传播率、消息压缩比、字段保真率和 Shannon Token Entropy。动态拓扑实验将与 Full Communication、Static Chain、Static Star 和一次性 AgentPrune 式稀疏图比较，以验证“动态”和“低熵”是否带来独立收益。

### 4.4 时态证据记忆与上下文治理

#### 4.4.1 四级记忆与证据存储

项目的记忆模块提供 WORKING、TASK、PROJECT 和 GLOBAL 四级层级。WORKING 保存当前超步和局部节点上下文；TASK 保存单次任务的重要中间结果；PROJECT 保存跨运行的项目事实、规则和经验；GLOBAL 保存可复用的领域知识。记忆项可以写入 SQLite，并追加 JSONL 审计记录；冷数据可以归档为 Markdown 原文。

现有 `TemporalEvidenceMemoryStore` 已在四级记忆之上提供 Fact、TemporalEvidence、事实版本、证据关联和冲突状态。高价值事实保存 `valid_from`、`valid_to`、`observed_at`、来源、置信度、`task_id`、`agent_id` 和 `trace_id`；向量或关键词检索只负责召回候选，最终由时间一致性、任务相关性、来源和冲突检测决定是否注入。后续工作重点是扩大图关联和真实长程样本覆盖，而不是另起一套记忆存储。

#### 4.4.2 ContextLedger

ContextLedger 是运行期上下文账本，记录原始目标、硬约束、当前计划、已完成事项、待办事项、已验证事实、未验证假设、关键文件、最近失败和预算。与自然语言历史不同，账本字段可以被 DriftDetector 和 BudgetController 直接读取。

每个超步开始时，系统检查当前状态是否仍与账本一致；节点结束时，系统将新的结果、证据、失败和待办变化写入账本。对于有歧义的更新，系统生成待确认建议，不把低置信模型输出静默写入长期记忆。

#### 4.4.3 记忆检索与唤醒

记忆唤醒先根据当前节点、目标、子任务和历史失败生成查询，再从工作级、任务级、项目级和全局级依次检索。默认注入 Top-K 条与当前节点最相关的记忆；发生高风险事件、证据冲突或恢复时，提高唤醒级别并扩展到关联事实和来源。

```text
Algorithm 3 分层时态证据唤醒
Input: query q, node n, wakeup level l
Output: context pack C

1: seeds ← retrieve_dense_sparse(q, scopes=WORKING..GLOBAL, top_k)
2: seeds ← rerank_by_task_time_confidence(seeds, q, n)
3: C ← seeds
4: if l ≥ 1 then C ← expand_dependencies(C, max_hops=1)
5: if l ≥ 2 then C ← expand_sources_and_conflicts(C, max_hops=2)
6: C ← remove_stale_or_contradictory_items(C, current_state)
7: C ← compress_noncritical_items(C, preserve=goals_constraints_evidence)
8: record_wakeup_trace(q, seeds, C, l)
9: return C
```

若每层检索候选数为 (k_l)，扩展跳数为 (h)，候选依赖平均分支数为 (b)，则唤醒复杂度近似为 (O(\sum_l k_l + k_0 b^h))。通过限制 Top-K、跳数和预算，避免记忆图扩展失控。

#### 4.4.4 预算、压缩、漂移与检查点

BudgetController 为每个运行维护输入 Token、输出 Token、节点调用次数、时延和资源成本预算；达到软阈值时压缩或降低唤醒级别，达到硬阈值时暂停并记录原因。ContextCompressor 对非关键历史进行结构化摘要，对目标、约束、数字、代码、URL、证据引用和决策结果保留完整内容。

DriftDetector 比较当前输出与原始目标、硬约束和已确认事实，识别目标漂移、约束丢失、事实冲突、重复循环和异常长输出。GraphCheckpointStore 在超步前或关键节点后保存运行 ID、步数、当前前沿、状态快照和模块元数据，使暂停和故障恢复能够回到明确的状态边界。

> 【图片占位：图 4-2 时态证据记忆与上下文治理流水线。应展示四级记忆、Fact/TemporalEvidence、混合检索、冲突/版本处理、账本、预算、漂移检测、压缩、唤醒和 checkpoint 的先后关系。】

### 4.5 神经符号规划、验证与自治恢复

#### 4.5.1 PlanIR 与验证器

项目已定义 `PlanIR`、`SubtaskIR`、`ConstraintIR`、`ValidationResult` 和 `Counterexample` 等结构。Planner 先生成受限 PlanIR，例如：

```json
{
  "goal": "完成软件版本发布",
  "subtasks": [
    {"id": "test", "depends_on": ["build"], "resource": "edge"},
    {"id": "release", "depends_on": ["test"], "resource": "cloud"}
  ],
  "constraints": [
    {"type": "deadline", "value": "2026-09-15T18:00:00"},
    {"type": "budget", "value": 5000},
    {"type": "approval_required", "scope": "production"}
  ]
}
```

现有 `SymbolicPlanValidator` 已执行字段类型、依赖无环、资源可用性、时间窗口、预算和权限检查；在安装 Z3 时可进一步进行带 unsat-core 的约束求解，没有 Z3 时仍执行确定性规则校验。验证失败时返回冲突字段、涉及任务和结构化反例，Planner 根据反例生成修订版本，直到通过或进入显式降级。

#### 4.5.2 失败轨迹与恢复策略

FailureRecord 记录节点、异常类型、错误消息、步数、失败种类、严重级别和尝试次数，FailureTrace 作为共享状态写入 `__failures__`。RecoveryPolicy 根据失败轨迹、侧作用日志和当前资源状态选择：

- 重试同一节点；
- 切换到备用 Agent 或备用资源；
- 跳转到补偿或验证节点；
- 回滚到最近检查点；
- 暂停并等待外部条件；
- 在无法保证正确性时安全中止。

恢复不是简单重复调用。若失败节点已经产生外部副作用，系统先检查侧作用日志和幂等标记；若存在风险，则生成补偿计划或请求澄清。恢复动作、理由和最终结果写入轨迹，供下一次拓扑选择和技能演化使用。

#### 4.5.3 动态事件注入

统一 `RuntimeEvent` 表示需求变更、节点失效、工具拒绝、证据冲突、预算压力和资源状态变化。事件注入器在节点边界生成可复现实验事件，并交由同一套 Hook 链处理。这样实验中的故障不是外部脚本强行修改最终答案，而是完整经过感知、重规划、拓扑调整、恢复和验证路径。

> 【图片占位：图 4-3 神经符号验证与故障恢复闭环。应画出 PlanIR、SymbolicPlanValidator、unsat core/counterexample、PlanRepairer、FailureTrace、RecoveryPolicy、checkpoint 和 fallback/takeover/migrate/degrade 分支。】

### 4.6 端—边—云资源自适应调度

Scheduler 为每个 Agent 和子任务维护资源画像，包括实时性、数据敏感等级、模型需求、估计 Token、网络 RTT、队列长度、失败率、成本和可用性。调度策略遵循以下规则：

1. 高敏感数据优先在端或边缘完成脱敏、抽取和结构化封装；
2. 低时延、轻量、可离线任务优先端侧执行；
3. 需要更大模型或复杂推理的任务可迁移到云端，但只传输必要的 MessageCapsule 和证据引用；
4. 节点资源不足、网络恶化或失败率升高时，重新计算放置；
5. 任何迁移都必须保留任务 ID、检查点、上下文摘要和权限边界。

系统支持启发式、分类器、HEFT 和在线 bandit 等策略。当前工程中的 AdaptiveResourceScheduler 已提供 device/edge/cloud 选择、任务画像、资源状态、可信工作区策略、脱敏和 executor 接口，并记录 SchedulingTrace；目标完成版进一步使用真实 TTFT、生成速度、队列、网络和成本数据进行调度评估，避免把描述性模型切分步骤当作真实模型切分。

### 4.7 技能生命周期与自演化闭环

技能模块以运行轨迹为输入，从成功执行中提取可复用步骤，生成候选 Markdown 技能，经过验证、审批、发布、灰度和回滚后进入检索库。SkillTrace 记录技能命中、注入、执行步骤、覆盖率、失败和版本。技能检索在当前任务、Agent 能力和历史成功轨迹之间进行匹配；不适用技能不得自动覆盖当前硬约束。

技能自演化强调治理而不是无条件自我修改：候选技能必须经过格式验证、行为检查和人工或策略审批；发布版本具有范围、版本和回滚边界；运行中只读入与当前任务相关的技能上下文。

### 4.8 REST 服务与可视化控制台

后端 FastAPI 提供 Agent、图、运行、事件、工作流版本、记忆库、技能、工具、模型连接、审计和系统指标接口。运行中心支持后台执行、事件轮询、SSE 流式查看、取消、重试和技能轨迹；工作流中心支持保存、加载、版本历史和回滚；技能治理页面支持候选、验证、发布、拒绝、退役、灰度和版本回滚。

可视化不仅是产品包装，也是研究验证工具。画布展示候选静态图和当前活跃拓扑，运行控制台展示每个超步的节点开始/结束、消息摘要、记忆唤醒、资源位置、验证结论、失败和恢复理由，使评审者能够观察系统是否真正进行了动态协作。

平台侧新增的工程能力还包括应用草稿与发布快照、模型连接测试与 AUTO 默认层级校验、工具风险分级和人工审批、应用级主记忆库/只读参考库、自动记忆写入的去重与敏感信息拦截、Skill 导入去重与 ZIP 路径安全校验、API Key 哈希保存以及 `X-Actor`/管理员密钥审计。需要注意，第三方工具、真实模型和知识库的最终可用性仍取决于外部服务配置；没有明确 executor/model 证据时，运行成功不能等同于真实模型成功。

## 5 实验评估

### 5.1 实验目标与原则

实验围绕题目评分标准，分别回答以下问题：

1. 图运行时能否稳定支持顺序、分支、循环、父子 Agent 和扇出/扇入？
2. 时态证据记忆能否在长历史中提升检索和回答质量，并降低 Token？
3. 记忆与上下文账本、漂移、预算、检查点联合后，能否保持目标和约束？
4. 动态拓扑和 MessageCapsule 能否降低通信成本与错误传播？
5. 技能候选能否从成功轨迹中生成并在后续任务中复用？
6. 端—边—云调度和故障恢复能否提升长程任务的完成率和资源效率？

所有正式实验应固定 Python 和依赖版本，记录模型、温度、提示词、随机种子、硬件、网络、数据版本和完整 JSONL 轨迹。合成机制测试用于验证运行时正确性，不应被描述为真实 LLM 任务成功率。

当前实验 runner 已通过编译检查和 `tests/test_experiments.py` 的离线验收，修正长期记忆测试对 `avg_context_tokens` 的比较后为 `12 passed`。该结果说明实验代码和统计接口可用，不等于各项正式实验已经完成。

### 5.8 两个长程产业场景

#### 场景一：跨应用办公与终端助理

用户提出包含邮件、日历、浏览器和文档的复合请求。Planner 分解任务，Researcher 检索信息，Calendar Agent 处理时间冲突，Document Agent 生成报告，Verifier 检查权限和事实。任务中途注入日程冲突、权限拒绝和优先级变化，系统应通过账本更新、拓扑重构、端侧脱敏和检查点恢复继续完成交付。

#### 场景二：软件工程自治交付

系统接收需求后依次进行代码检索、方案规划、实现、测试、修复和交付报告生成。任务中途注入测试失败、依赖不可用和需求约束变化，TopologyController 增加验证或修复 Agent，PlanIR 验证器检查依赖和发布约束，Scheduler 根据数据和模型需求迁移执行位置。

两类场景均需采用可机读的完成判定器，记录事件注入、拓扑变化、MessageCapsule、资源迁移、验证/恢复和最终产物，不能只依赖主观演示效果或单次 LLM 评分。

## 6 讨论、边界与风险

### 6.1 与静态 Agent 编排的区别

静态图仍然有价值：它表达候选能力、基本依赖和安全边界，便于可视化编辑和编译校验。但在 TIDE-Swarm 中，静态图不是运行时最终拓扑。最终活跃 Agent 和通信边由状态和事件决定，临时边具有 TTL，故障、证据冲突和预算压力可以触发重构。

### 6.2 与全量上下文的区别

TIDE-Swarm 不把“上下文越多”当成“记忆越完整”。它保存结构化目标、约束、证据和决策，将非关键历史压缩为可回链摘要，并在需要时扩展关联记忆。这样可以同时报告信息保真度、检索效果、目标保持和 Token 成本，而不只报告模型的最终文字质量。

### 6.3 论文主张边界

正式提交时，以下表述必须以代码、日志和实验结果为依据：

- 图编排、上下文账本、检查点、技能治理和 REST/前端能力可以作为工程基础陈述；
- 动态拓扑必须有运行中新增/删除边、活跃 Agent 变化和事件理由的轨迹；
- 低熵通信必须有 MessageCapsule、门控逻辑和通信指标；
- 神经符号推理必须有 PlanIR、验证器输出和反例修订；
- 端—边—云调度必须有真实资源画像，不能把描述性模型切分当作实际切分；
- 数千步稳定性、显著优于基线、泛化能力等结论必须由充分样本、多随机种子和可复现实验支持。

### 6.4 局限性与后续工作

第一，运行时目前仍以预先编排的静态图为主要入口，动态拓扑的在线策略尚未形成大样本结果，边效用模型需要在任务成功、Token、时延和风险之间进行校准。第二，LongMemEval 端到端 QA 尚未开始，当前 100 条 v3 联合实验是确定性状态机制评测，不能替代生成式 QA。第三，时态证据记忆的冲突解决依赖来源质量和时间语义，仍需在官方长程基准和真实任务上验证。第四，神经符号验证目前更适合任务、资源、时间和预算等受限约束，不宜宣称能够验证开放域常识或通用价值判断。第五，端—边—云实验受到本地模型、网络和 API 可用性的影响，必须报告降级情况。第六，技能自演化需要严格版本、审批和回滚机制，当前本地 Echo executor 下的技能效果不能等同于真实模型能力。

## 7 结论

本文面向超长程复杂任务，提出并设计了 TIDE-Swarm 任务状态驱动动态异构群体智能架构。系统以 StateGraph/CompiledGraph 图运行时为骨架，以 HookManager 为模块桥接，以任务状态和运行事件为统一控制信号，将动态拓扑、低熵通信、时态证据记忆、上下文治理、神经符号验证、端—边—云调度、故障恢复和技能演化连接为一个可观测闭环。

与把多 Agent 固定连接起来的传统流水线不同，TIDE-Swarm 将“谁参与协作”“向谁发送什么”“哪些历史需要唤醒”“在哪个资源位置执行”和“失败后如何恢复”都变成可以随状态变化重新计算的运行时决策。MessageCapsule 使通信内容从自由文本转向带证据和约束的最小充分表示；ContextLedger、分层记忆、漂移检测、预算控制和检查点为长程连续性提供可追踪边界；PlanIR 与符号验证器把自然语言计划转换为可检查的执行约束；REST 服务和 AgentForge Console 则使协作图、运行事件和恢复过程能够被部署、观察和回放。

截至当前版本，300 条确定性工作流全部通过，100 条 LoCoMo 派生状态治理任务中 Ours Full 达到 1.0 的条件合取成功率且平均 143.20 token，技能闭环 30 条任务全部通过，二轮技能指导覆盖率由 0.20 提升到 0.62。这些结果证明工程链路和上下文治理机制已经可以运行，但不能替代真实 LLM 端到端结论。LongMemEval QA、动态拓扑通信和端—边—云真实资源实验仍是后续主要工作。

后续工作将围绕三条主线展开：其一，完成 TopologyController 和 MessageCapsule 的真实在线实验，建立成功率—通信成本—恢复能力的联合评价；其二，启动 LongMemEval/LoCoMo 端到端 QA 和更大规模跨应用任务，验证时态证据记忆与上下文治理；其三，建立真实端、边、云资源画像和多随机种子故障实验，证明系统不仅能够在架构层面描述自治，而且能够在非确定性环境中稳定完成可判定的长程交付。

## 附录 A 核心复杂度汇总

| 模块 | 主要操作 | 复杂度（典型实现） |
|---|---|---|
| StateGraph 超步 | 当前前沿并发执行 | `O(|F_t|)` 个并发节点调用，归并为 `O(|U_t|)` |
| 条件路由 | 路由函数和目标解析 | `O(1)` 至 `O(|targets|)` |
| 动态拓扑 | 候选边打分与预算选择 | `O(|E_c|d+|E_c| log B)` |
| MessageCapsule 门控 | 字段校验、证据检查、去重 | `O(k+r+h)` |
| 分层记忆唤醒 | 多层召回与关系扩展 | `O(sum_l k_l+k_0b^h)` |
| PlanIR 验证 | 字段、依赖、约束和资源检查 | 规则校验近似 `O(n+m)`，求解器复杂度随约束类型变化 |
| 端—边—云调度 | 资源候选评分 | `O(|P|d)`，其中 `|P|` 为候选资源数 |
| 故障恢复 | 失败轨迹匹配与路径选择 | `O(|policies|+|trace|)` |
