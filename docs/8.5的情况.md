# 8.5 的情况

## 一、这次改造解决什么问题

8.4 已经把“任务目标语义漂移”从 embedding 相似度改成了真实 LLM 判断，但判断依据仍然主要是：

- 顶层目标
- 顶层计划 `current_plan`
- 当前动作内容

但还不够像真正的 coding agent.真实长任务执行时，Agent 应该围绕一组待办步骤推进，而不是只拿当前动作和总目标比较。比如 Codex、OpenCode 这类 vibe coding agent，都会维护类似 todo list / plan 的执行状态：当前做哪一步、哪些已完成、哪些待处理、计划是否需要调整。

所以 8.5 的核心是：

> 把漂移检测从“是否像总目标”升级为“是否服务于当前待办，或者是否在合理修改待办”。

## 二、当前已经实现的能力

### 1. 结构化 Todo 已接入 ContextLedger

`ContextLedger` 现在除了原来的 `current_plan`，还新增了：

- `todo_items`
- `active_todo_id`
- `todo_revision`
- `todo_events`

每个 todo item 包含：

- `id`
- `content`
- `status`
- `source`
- `created_at`
- `updated_at`
- `evidence`
- `revision`

状态支持：

- `pending`
- `in_progress`
- `completed`
- `blocked`
- `cancelled`

旧接口仍然兼容：如果输入里只有 `current_plan`，系统会自动把它转换成 `todo_items`，并把第一个 todo 标记为 `in_progress`。

### 2. 新增 TodoManager

新增 `engine/modules/context/todo.py`，里面有 `TodoManager`。

支持的操作：

- `set_todos()`
- `update_todo_status()`
- `insert_todo()`
- `replace_todo()`
- `cancel_todo()`
- `select_active_todo()`

所有 todo 修改都会：

- 更新 `todo_revision`
- 写入 `todo_events`
- 同步 `current_plan`
- 保证同一时间只有一个 `in_progress`

这样可以避免模型在执行过程中静默改计划。

### 3. Context Injection 已加入 Todo 上下文

节点执行前注入的上下文现在会包含：

- 当前 active todo
- 相邻 todo
- 已完成 todo
- todo policy

todo policy 会提醒 Agent：

> 优先服务于 active todo。如果发现计划不完整或过期，可以建议修改待办，而不是直接偏离任务。

### 4. 语义漂移 LLM Judge 改成三态判断

原来 LLM 只返回：

```json
{"is_task_drift": true/false, "reason": "..."}
```

现在支持三态：

```json
{
  "decision": "on_track | todo_update_needed | drifted",
  "is_task_drift": true,
  "reason": "...",
  "todo_updates": []
}
```

含义：

- `on_track`：当前动作服务于 active todo、相邻 todo 或整体待办主线。
- `todo_update_needed`：当前动作是在合理维护计划，例如补充缺失步骤、修正过期步骤、切换下一步。
- `drifted`：当前动作既不服务于待办，也不是合理修改待办，是无关工作。

### 5. 默认只建议，不自动改计划

新增配置：

```yaml
todo_update_mode: suggest
```

当前默认是 `suggest`。

也就是说，如果 LLM 判断需要修改待办，它不会直接自动改 todo list，而是写入：

- `__context_drift__.metadata.task_drift_judge_result`
- `ledger.open_questions`

如果后续要让模型自动改计划，可以改成：

```yaml
todo_update_mode: auto
```

auto 模式下只允许受限操作：

- insert
- replace
- cancel
- complete
- select

所有操作仍然通过 `TodoManager` 写审计。

## 三、当前配置情况

`configs/context_policy.yaml` 当前是：

```yaml
repeat_node_limit: 3
pending_step_limit: 10
no_progress_step_limit: 0
repeated_summary_limit: 3
repeated_resource_limit: 3
repeated_tool_limit: 0
repeated_file_operation_limit: 3
semantic_drift_mode: llm
semantic_drift_cache_enabled: true
todo_update_mode: suggest
```

所以当前运行模式是：

- 结构性循环漂移：规则判断
- 任务目标语义漂移：真实 LLM 判断
- todo 修改：默认只建议，不自动改

## 五、当前整体状态

现在漂移检测链路已经变成：

```text
current_plan
  -> 自动转换成 todo_items
  -> 选择 active_todo
  -> 注入 active todo / nearby todos
  -> 当前动作执行
  -> DriftDetector 调用 LLM judge
  -> LLM 判断 on_track / todo_update_needed / drifted
  -> suggest 模式写建议，auto 模式受限改 todo
  -> 结果写入 __context_drift__ 和 ledger
```

这版比 8.4 更适合长任务，因为它不是孤立判断“当前内容像不像总目标”，而是结合待办进度判断 Agent 是否仍在沿着计划推进。

## 六、父 Agent 判断 validated 字段修正

### 原问题

之前子 Agent 可以在自己的输出里返回：

```json
{"__parent_validated__": true}
```

8.3 已经把这个字段从校验依据里废弃，父级校验器不会采信它；但是如果父级已经通过 `__parent_validation__` 放行，子 Agent 输出里的 `__parent_validated__` 仍然可能跟随正常 update 合并进最终 state。这样虽然不能绕过校验，但字段会残留在全局状态里，容易让后续逻辑或读文档的人误以为它仍然是有效凭证。

### 本次修改

1. 在图执行层统一清洗节点输出：节点成功返回后、执行后置校验和 state 合并之前，会删除 update 里的 `__parent_validated__`。
2. 真正的父级授权字段只保留全局 state 顶层的 `__parent_validation__`：

```json
{
  "__parent_validation__": {
    "child": {"approved": true}
  }
}
```

3. `__parent_validated__` 现在彻底变成废弃字段：
   - 不参与父级校验判断；
   - 不会放行子 Agent；
   - 即使父级已经通过其他方式授权，也不会再进入最终 state。

### 当前正确语义

父 Agent / 编排器才是授权主体。子 Agent 只能返回业务结果，不能在自己的 update 中携带自证式授权标记。

判断链路现在是：

```text
子 Agent 返回 update
  -> 图执行层删除 __parent_validated__
  -> RuleEvaluator 检查 state.__parent_validation__
  -> 未授权：验证失败，子输出不合并
  -> 已授权：业务字段合并，但 __parent_validated__ 仍不保留
```
